# Lecture 02 · Level 09 — 클래스와 객체지향

> 클래스는 붕어빵틀(설계도), 객체는 그 틀로 찍어낸 붕어빵(실체)입니다. 데이터(속성)와 절차(메서드)를 한 몸으로 묶고, 상속으로 "거의 같지만 조금 다른" 규칙을 깔끔하게 관리합니다.
**난이도** ⭐⭐⭐ / **선행** level08 / **예상 시간** 60분

## 1. 왜 배우나 — 비즈니스 관점

직원 급여 계산 프로그램을 만든다고 합시다. 직원마다 이름·기본급·근속연수(데이터)가 있고,
급여 계산·연차 산정(절차)이 있습니다. 지금까지 배운 방식이라면 데이터는 딕셔너리에,
절차는 함수에 따로 둡니다. 직원이 다섯 종류(정규직, 매니저, 계약직...)로 늘고 규칙이
조금씩 다르면, "이 딕셔너리에는 어느 함수를 써야 하지?"라는 짝 맞추기 실수가 시작됩니다.

클래스(class)는 데이터와 절차를 한 단위로 묶어 "직원이라는 개념" 자체를 코드로 만듭니다.
그리고 상속(inheritance)은 "매니저는 직원의 모든 규칙을 따르되, 급여에 직책수당만
추가"처럼 **공통 규칙은 한 곳에, 차이만 따로** 적게 해 줍니다. 여러분이 매일 쓰는
pandas 의 DataFrame, 나중에 배울 torch 의 모델이 전부 클래스이므로, 이 개념은
AI 커리큘럼 전체의 문법적 기반이기도 합니다.

## 2. 비유로 이해하기

**붕어빵틀 비유.** 붕어빵 장사를 시작하려면 먼저 틀을 만듭니다. 틀 자체는 먹을 수
없습니다. 틀에 반죽과 팥을 넣고 찍어야 비로소 먹을 수 있는 붕어빵이 나옵니다.

- **클래스 = 붕어빵틀**: "직원이란 이름·기본급·근속연수를 가지며, 급여를 계산할 수 있다"는 설계도.
- **객체(object)/인스턴스(instance) = 붕어빵**: 그 틀로 찍어낸 실체. `Employee("김주임", ...)`
  할 때마다 한 마리씩 나옵니다.
- **속성(attribute) = 각 붕어빵의 속재료**: 같은 틀에서 나와도 팥붕어빵과 슈크림붕어빵이
  다르듯, 객체마다 자기만의 이름·기본급을 가집니다.
- **메서드(method) = 붕어빵이 할 수 있는 동작**: 틀에 새겨진 절차. 모든 붕어빵이 같은
  절차를 갖되, **자기 속재료로** 동작합니다.

**상속은 개량 틀 만들기**입니다. 기존 붕어빵틀을 녹여 없애지 않고, 그 틀을 본떠
"꼬리에 치즈 추가" 틀을 만드는 것. 기본 틀이 개선되면 개량 틀도 자동으로 혜택을 봅니다.

## 3. 핵심 개념

### 3.1 클래스 정의와 __init__

```python
class Employee:
    def __init__(self, name, base_salary):   # 생성자: 붕어빵 찍는 순간 실행
        self.name = name                      # 속성: 이 객체의 속재료
        self.base_salary = base_salary

    def monthly_pay(self):                    # 메서드: 이 객체가 하는 동작
        return self.base_salary

emp = Employee("김주임", 3000000)             # 객체 생성 (틀에서 한 마리)
emp.monthly_pay()                             # 메서드 호출
```

- `__init__` 은 객체가 만들어지는 순간 자동 실행되는 초기화 절차(생성자)입니다.
- `self` 는 "지금 이 동작을 수행 중인 붕어빵 자신"입니다. 메서드 첫 인자에 항상 쓰고,
  호출할 때는 파이썬이 자동으로 채워 줍니다. `emp.monthly_pay()` 는 사실
  `Employee.monthly_pay(emp)` 의 줄임입니다.
- 관례: 클래스 이름은 대문자 시작(`Employee`), 객체·함수는 소문자(`emp`).

### 3.2 상속 — 공통은 부모에, 차이만 자식에

```python
class Manager(Employee):                      # Employee 를 물려받는다
    def __init__(self, name, base_salary, team_size):
        super().__init__(name, base_salary)   # 부모의 초기화를 먼저 수행
        self.team_size = team_size            # 매니저만의 속성 추가

    def monthly_pay(self):                    # 오버라이딩: 같은 이름, 다른 내용
        return super().monthly_pay() + 500000 + self.team_size * 30000
```

- `class Manager(Employee)` — 괄호 안이 부모 클래스입니다. 매니저는 직원의
  모든 속성·메서드를 자동으로 가집니다.
- `super()` 는 부모를 가리킵니다. "부모의 절차를 먼저 수행하고 내 것을 추가"가 기본형입니다.
- 같은 이름의 메서드를 다시 정의하면 자식 것이 우선합니다 — 재정의(overriding).

### 3.3 다형성 — 같은 지시, 각자의 방식

직원과 매니저가 섞인 리스트를 돌며 `person.monthly_pay()` 를 호출하면,
각 객체가 **자기 클래스의 방식대로** 계산합니다. 호출하는 쪽은 상대가 직원인지
매니저인지 물을 필요가 없습니다. 이것이 다형성(polymorphism)입니다.
"전 직원에게 '이번 달 급여 계산해 주세요'라고 공지하면, 각자 자기 규정대로
계산해 제출한다" — if/elif 로 직급을 일일이 분기하는 코드보다 확장이 훨씬 쉽습니다.

### 3.4 __str__ — 객체의 자기소개

`print(emp)` 했을 때 `<Employee object at 0x...>` 대신 사람이 읽을 문장이 나오게
하려면 `__str__` 메서드를 정의합니다. 이런 밑줄 두 개짜리 특수 메서드(dunder method)는
"파이썬 문법과 내 클래스를 연결하는 접점"으로, `__init__` 도 그중 하나입니다.

### 3.5 언제 클래스를 쓰나

모든 코드를 클래스로 만들 필요는 없습니다. 기준은 이렇습니다.

- 데이터와 그 데이터를 다루는 함수가 **늘 함께 다닌다** → 클래스 후보
- 같은 구조의 실체가 **여러 개** 생긴다 (직원 100명, 상품 500개) → 클래스 후보
- "거의 같지만 조금 다른" 변종이 있다 → 상속 후보
- 한 번 계산하고 끝나는 절차 → 함수면 충분

- **[3] 상속**: Manager 는 Employee 를 물려받아 직책수당+팀원수당만 추가합니다.

- **[4] 다형성 급여 대장**: 직원·매니저가 섞인 리스트를 한 반복문으로 돌려

- **[5] __str__**: 자기소개 메서드 덕분에 `print(직원)` 이 읽기 좋은 한 줄이 되는 것을
  확인합니다.

클래스 정의부의 주석이 "틀에 새기는 규칙", main 쪽 주석이 "붕어빵을 굽고 파는 현장"

## 6. 자주 하는 실수

- **self 빠뜨리기** — 메서드 정의에서 `def monthly_pay():` 로 쓰면 호출 시
  `takes 0 positional arguments but 1 was given` 에러가 납니다. 메서드 첫 인자는 항상 self.
- **클래스와 객체 혼동** — `Employee.name` 은 없습니다. 이름은 각 붕어빵(객체)에
  있으므로 `emp.name`. 틀을 먹으려 하지 마세요.
- **super().__init__ 생략** — 자식 `__init__` 에서 부모 초기화를 안 부르면 부모가
  만들어 주던 속성이 없어서 나중에 `AttributeError` 가 납니다.
- **모든 것을 클래스로** — 함수 한 개면 되는 일을 클래스로 감싸면 오히려 읽기 어렵습니다.
  3.5의 기준으로 판단하세요.
- **속성을 클래스 몸통에 공유로 두기** — `class Employee:` 바로 아래
  `members = []` 처럼 가변 값을 두면 모든 객체가 한 리스트를 공유하는 함정이 생깁니다.
  객체별 데이터는 반드시 `__init__` 에서 `self.` 로 만드세요.
