# Lecture 02 · Level 11 — 타입 힌트·테스트·코드 품질

> 타입 힌트는 함수의 입출력 규격을 명시한 계약서, 테스트는 "이 코드는 이런 경우에 이렇게 동작한다"를 자동으로 검증하는 품질검사 체크리스트입니다.
**난이도** ⭐⭐⭐⭐ / **선행** level10 / **예상 시간** 60분

## 1. 왜 배우나 — 비즈니스 관점

"내 컴퓨터에서 한 번 돌았다"와 "믿고 쓸 수 있다"는 다른 이야기입니다.
실무 코드는 다른 사람이 이어받고, 6개월 뒤의 내가 고치고, 데이터가 바뀐 뒤에도
돌아가야 합니다. 그때 필요한 것이 이번 레벨의 세 가지입니다.

- **타입 힌트(type hint)**: 함수가 무엇을 받고 무엇을 돌려주는지 규격을 코드에 명시합니다.
  주석과 달리 도구(mypy 등)가 규격 위반을 자동으로 잡아 줍니다.
- **테스트(test)**: 수정할 때마다 "기존 기능이 안 깨졌나"를 자동으로 확인합니다.
  테스트가 있으면 코드를 고치는 것이 두렵지 않게 됩니다 — 이것이 진짜 효용입니다.
- **docstring 과 컨벤션**: 코드가 스스로를 설명하게 만드는 문서화 습관입니다.

lecture02 의 졸업 시험 같은 레벨입니다. 이후 AI 실습에서 만드는 데이터 처리 함수들에
이 습관이 붙어 있는지가 "취미 코드"와 "업무 코드"를 가릅니다.

## 2. 비유로 이해하기

**계약서 비유.** 외주 업체에 일을 맡길 때는 계약서에 규격을 적습니다.
"귀사는 거래 목록(각 건은 금액 정수)을 넘기고, 당사는 요약 보고서(문자열)를 납품한다."
타입 힌트가 정확히 이것입니다.

```python
def summarize(amounts: list[int]) -> str:
```

"amounts 는 정수 리스트로 받고, 문자열을 돌려준다"는 계약이 함수 서명에 박혀 있습니다.
계약서가 없으면? 상대가 문자열 리스트를 보내와도 아무도 모르다가 납품일(실행 시점)에
사고가 납니다. 계약서가 있으면 검수 담당자(mypy)가 **일을 시작하기도 전에**
"규격 불일치"를 지적해 줍니다.

**품질검사 체크리스트 비유.** 공장에서는 제품을 출하하기 전에 체크리스트를 돌립니다.
"정상 입력 시 정상 출력? 빈 입력 시 안전 처리? 경계값(0원, 최대치)에서 오동작 없음?"
테스트 코드는 이 체크리스트를 자동화한 것입니다. 사람이 매번 눈으로 확인하는 대신,
`python3 main.py` 한 번에 전 항목이 검사됩니다. 라인을 조금이라도 바꿨으면
체크리스트를 다시 돌리는 것 — 이것이 회귀 테스트(regression test)입니다.

## 3. 핵심 개념

### 3.1 타입 힌트 문법

```python
def calc_vat(amount: int, rate: float = 0.1) -> int:
    ...

price: int = 4500
stores: list[str] = ["강남", "서초"]
stock: dict[str, int] = {"볼펜": 37}
memo: str | None = None          # 문자열이거나 None (없을 수도 있는 값)
```

`인자: 타입`, `-> 반환타입` 이 전부입니다. 컬렉션은 `list[int]` 처럼 내용물 타입까지
적고, "없을 수도 있는 값"은 `| None` 으로 표현합니다.

중요한 사실: **파이썬은 실행 시 타입 힌트를 강제하지 않습니다.** 힌트를 어겨도
프로그램은 일단 돌아갑니다. 힌트의 효력은 세 가지 경로로 나옵니다 —
(1) 읽는 사람에게 규격 전달, (2) 에디터의 자동완성·경고, (3) mypy 같은
정적 검사기(static checker)가 실행 없이 코드만 훑어 규격 위반을 보고.
mypy 는 별도 설치 도구라 이 실습에서는 개념만 다루고, main.py 에 **초미니 검사기**를
만들어 원리(서명과 실제 값의 대조)를 체험합니다.

### 3.2 assert — 한 줄짜리 자동 검사

```python
assert calc_vat(10000) == 1000, "1만 원의 부가세는 1000원이어야 함"
```

`assert 조건, 메시지` 는 조건이 참이면 조용히 통과, 거짓이면 메시지와 함께
`AssertionError` 를 냅니다. "기대값과 실제값의 대조"라는 테스트의 핵심이
이 한 줄에 들어 있습니다. 실무에서는 pytest 같은 전문 도구를 쓰지만,
그 뿌리는 전부 assert 입니다.

### 3.3 좋은 테스트의 3종 세트

같은 함수라도 세 부류의 입력을 검사해야 안심할 수 있습니다.

1. **정상 케이스**: 대표적인 입력 → 기대한 출력
2. **경계 케이스(edge case)**: 0, 빈 리스트, 최댓값, 딱 기준선인 값
3. **오류 케이스**: 잘못된 입력이 **의도한 예외를 내는지** (조용히 이상한 값을
   돌려주는 것이 최악입니다)

버그의 대부분은 2번과 3번에서 나옵니다. "빈 목록이 오면?"을 테스트로 물어보는
습관이 새벽 장애 전화를 줄입니다.

### 3.4 docstring — 함수의 사용 설명서

```python
def net_price(price: int, discount_rate: float) -> int:
    """할인 적용가를 계산한다.

    Args:
        price: 정가(원). 0 이상.
        discount_rate: 할인율. 0.0 ~ 1.0.
    Returns:
        할인 적용가(원, 정수 내림).
    Raises:
        ValueError: 할인율이 범위를 벗어나면.
    """
```

함수 첫머리의 삼중따옴표 문자열이 docstring 입니다. `help(net_price)` 로 바로
조회되고, 에디터가 자동으로 보여 주며, 타입 힌트가 못 담는 정보 — 단위, 범위,
예외 조건 — 를 담습니다. "타입 힌트 = 규격, docstring = 사용 설명서"로 역할이 나뉩니다.

### 3.5 코드 품질 체크리스트

- 이름만 읽어도 뜻이 통하는가 (level01·05의 원칙)
- 함수는 한 가지 일만 하는가, 20~30줄을 넘지 않는가
- 마법 숫자 대신 이름 붙은 상수를 쓰는가 (`0.1` 대신 `VAT_RATE`)
- 서식을 통일했는가 — 커뮤니티 표준 스타일 가이드(PEP 8)와 자동 포매터가 있습니다
- 그리고: 테스트 없이 리팩터링하지 않는가

## 4. 실습 — main.py

실행 방법:

```bash
cd lecture02_python_basics/level11_typing_testing_quality
python3 main.py
```

세금·할인 계산 함수(level05 의 소재)에 타입 힌트와 docstring 을 입히고,
자체 테스트 러너로 검증하는 종합 데모입니다.

- **[1] 계약서 읽기**: 타입 힌트가 붙은 함수들의 서명을 출력하고,
  `__annotations__` 로 파이썬이 힌트를 어떻게 기억하는지 봅니다.
- **[2] 힌트는 강제가 아니다**: 규격을 어긴 호출이 그냥 돌아가 버리는 모습을 보여 주고,
  그래서 검사기가 필요하다는 결론으로 잇습니다.
- **[3] 초미니 타입 검사기**: 함수의 힌트와 실제 인자 타입을 대조하는 20줄짜리
  `tiny_type_check` 로 [2]의 위반을 잡아냅니다 — mypy 가 하는 일의 원리 체험입니다.
- **[4] 미니 테스트 러너**: 정상·경계·오류 3종 세트 테스트 9개를 assert 로 작성하고,
  통과/실패를 집계해 `9 passed` 리포트를 출력합니다. 일부러 심어 둔 버그 1개
  (경계값 처리)를 테스트가 잡아내고, 고친 버전은 전부 통과하는 흐름을 보여 줍니다.
- **[5] docstring 활용**: `help()` 가 보여 주는 설명서를 출력합니다.

## 6. 자주 하는 실수

- **힌트를 붙였으니 안전하다고 믿기** — 파이썬은 실행 시 힌트를 강제하지 않습니다.
  검사기(mypy)를 돌리거나, 중요한 값은 코드에서 직접 검증(raise)하세요.
- **정상 케이스만 테스트** — 통과해도 안심할 수 없습니다. 경계·오류 케이스가 본론입니다.
- **테스트가 구현을 베끼는 것** — 함수 안의 계산식을 복사해 기대값을 만들면
  버그까지 복사됩니다. 기대값은 손으로, 독립적으로 구하세요.
- **docstring 과 코드의 불일치** — 코드를 고치고 설명서를 안 고치면 거짓말 문서가
  됩니다. 함수를 수정하면 docstring 도 같이 읽는 습관을.
- **assert 를 입력 검증에 사용** — assert 는 최적화 옵션(-O)에서 통째로 꺼질 수 있습니다.
  사용자 입력 검증은 raise(level07), 테스트는 assert — 용도를 구분하세요.
