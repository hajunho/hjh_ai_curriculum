# Lecture 02 · Level 07 — 예외 처리와 디버깅

> try/except 는 "문제가 생기면 이렇게 대처하라"는 비상 대응 매뉴얼이고, 에러 메시지는 컴퓨터가 보낸 정확한 사고 경위서입니다.
**난이도** ⭐⭐⭐ / **선행** level06 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

밤새 돌아야 할 정산 배치가 새벽 2시에 멈췄습니다. 원인은 1만 건 중 단 한 건 —
금액 칸에 누군가 "협의중"이라고 적어 둔 행이었습니다. 예외 처리가 없는 프로그램은
이 한 건에서 그대로 사망하고, 나머지 9,999건도 처리되지 않습니다.

실무 데이터는 반드시 깨져 있습니다. 빈 칸, 오타, 형식이 다른 날짜, 음수 수량.
예외 처리(exception handling)는 "불량 1건은 기록해 두고 건너뛰되, 전체 업무는
계속한다"는 방어 체계입니다. 그리고 디버깅(debugging)은 에러가 났을 때 감이 아니라
증거 — 에러 메시지와 중간값 출력 — 로 원인을 찾는 기술입니다. 이 두 가지가
"내 컴퓨터에서 한 번 돌던 코드"와 "실무에 투입 가능한 코드"를 가릅니다.

## 2. 비유로 이해하기

**소방 훈련 비유.** 건물에 소화기와 대피 매뉴얼이 있다고 화재가 안 나는 게 아닙니다.
불이 나도 **전체가 무너지지 않게** 하는 것이죠. try/except 가 정확히 그 역할입니다.

> try: 평소 업무를 진행한다 (불이 날 수도 있는 구역)
> except: 불이 나면 이 매뉴얼대로 대처한다 (소화기 위치)
> finally: 불이 났든 안 났든 퇴근 전 문단속은 한다 (항상 실행)

**사고 경위서 비유.** 파이썬 에러 메시지(traceback)는 겁주려고 나오는 빨간 글자가
아니라, 육하원칙으로 쓰인 사고 경위서입니다. **어느 파일, 몇 번째 줄, 어떤 코드에서,
무슨 유형의 사고가, 왜** 났는지 전부 적혀 있습니다. 읽는 요령은 하나,
**아래에서 위로**: 마지막 줄이 사고 유형과 원인(`ValueError: ...`), 바로 위가 사고 지점입니다.
경위서를 안 읽고 "코드를 이리저리 바꿔 보는" 것은 사고 현장을 안 보고
아무 벽이나 다시 칠하는 것과 같습니다.

## 3. 핵심 개념

### 3.1 자주 만나는 예외 5종

| 예외 | 뜻 | 흔한 원인 |
|---|---|---|
| `ValueError` | 값이 형식에 안 맞음 | `int("협의중")` |
| `TypeError` | 자료형이 안 맞는 연산 | `"100" + 5` |
| `KeyError` | 딕셔너리에 없는 키 | `row["금액"]` (열 이름 오타) |
| `IndexError` | 범위 밖 인덱스 | 빈 리스트의 `items[0]` |
| `ZeroDivisionError` | 0으로 나눔 | 건수가 0인데 평균 계산 |

`FileNotFoundError`(없는 파일 열기)까지 여섯 개면 초기 실무 에러의 대부분입니다.
이름 자체가 원인 설명이니, 이름만 정확히 읽어도 절반은 해결됩니다.

### 3.2 try / except / else / finally

```python
try:
    amount = int(raw_value)          # 사고 가능 구역
except ValueError:
    log_error(raw_value)             # ValueError 발생 시 대처
    amount = 0
else:
    process(amount)                  # 사고가 '없었을 때만' 실행 (선택)
finally:
    close_connection()               # 사고 여부와 무관하게 항상 실행 (선택)
```

- **예외 유형을 명시**하세요. `except:` 나 `except Exception:` 으로 전부 삼키면
  진짜 버그(오타로 인한 NameError 등)까지 숨어 버립니다.
- 여러 유형은 `except (ValueError, KeyError):` 처럼 묶거나 except 절을 여러 개 씁니다.
- `except ValueError as e:` 로 받으면 `e` 에 원인 문구가 들어 있어 로그에 남길 수 있습니다.
- finally 는 파일·연결 정리처럼 "무슨 일이 있어도 해야 하는 뒷정리"에 씁니다
  (`with` 가 내부적으로 해 주는 일이 바로 이것입니다).

### 3.3 방어 범위는 좁게, 대처는 구체적으로

try 블록에 코드 100줄을 다 넣으면 어디서 사고가 났는지 알 수 없습니다.
**사고 가능성이 있는 최소 구간**(형 변환, 파일 열기, 키 조회)만 감싸는 것이 원칙입니다.
그리고 except 에서 아무것도 안 하고 `pass` 하는 것은 화재경보기를 끄는 행위입니다.
최소한 몇 건이 왜 실패했는지 기록(로그)은 남겨야, 나중에 "합계가 왜 모자라지?"에
답할 수 있습니다.

### 3.4 raise — 스스로 경보 울리기

```python
if amount < 0:
    raise ValueError(f"금액은 음수일 수 없습니다: {amount}")
```

잘못된 값을 조용히 통과시키는 것보다 초기에 크게 알리는 편이 안전할 때,
`raise` 로 직접 예외를 발생시킵니다. "이 함수는 이런 입력을 거부한다"는 계약 선언입니다.

### 3.5 print 디버깅 — 가장 원시적이고 가장 확실한

에러는 안 나는데 결과가 이상할 때는, 의심 구간에 print 를 꽂아 중간값을 확인합니다.

```python
print(f"DEBUG: row={row!r}, amount={amount!r}")
```

요령: 변수 이름과 함께 찍기, `!r` 로 따옴표·공백까지 보이게 찍기(`"100 "` 같은
숨은 공백이 보입니다), 원인을 찾으면 디버그 print 는 지우기. 더 정교한 도구
(디버거, logging)는 나중에 배우지만, print 디버깅은 평생 씁니다.

실행 방법:


일부러 오염시킨 월간 매출 데이터 10건 — 금액에 "협의중", 빈 값, 숨은 공백,
없는 키, 0으로 나누기 유발 — 을 처리합니다.

- **[1] 예외 관찰**: 대표 예외 5종을 하나씩 일부러 일으키고, 각각을 except 로 받아
  "마지막 줄 읽는 법"을 보여 줍니다.
- **[2] 보호 없는 처리**: 예외 처리 없이 오염 데이터를 집계하면 3번째 행에서
  즉사한다는 것을 재현합니다(전체가 죽지 않도록 바깥에서 한 번 감싸 두었습니다).
- **[3] 보호된 처리**: try/except 로 불량 행은 사유와 함께 기록하고 건너뛰며
  끝까지 집계합니다. "성공 7건, 실패 3건(사유 목록)" 형태의 운영 리포트가 나옵니다.
- **[4] print 디버깅**: 에러 없이 합계만 이상해지는 사례(숨은 공백 " 1000")를
  `!r` 디버그 출력으로 잡아냅니다.
- **[5] raise**: 음수 금액을 거부하는 검증 함수로 "일찍, 크게 알리기"를 시연합니다.

[2]와 [3]의 대비 — 같은 데이터, 죽는 코드와 살아남는 코드 — 가 이 레벨의 핵심입니다.

## 6. 자주 하는 실수

- **`except:` 로 전부 삼키기** — 진짜 버그까지 숨깁니다. 예상하는 유형만 명시하세요.
- **except 에서 조용히 pass** — 실패가 존재했다는 사실 자체가 사라집니다.
  최소한 건수와 사유는 기록하세요.
- **try 범위를 통째로 감싸기** — 사고 지점을 알 수 없게 됩니다. 최소 구간만.
- **traceback 을 안 읽고 수정 시작** — 마지막 줄만 읽어도 원인의 절반이 나옵니다.
  에러 문구로 검색하는 습관도 좋습니다 (동일한 사고 경위서를 읽은 사람이 반드시 있습니다).
- **디버그 print 방치** — 원인을 찾은 뒤 지우지 않으면 운영 로그가 오염됩니다.
  `DEBUG:` 접두어를 붙여 두면 나중에 찾아 지우기 쉽습니다.
