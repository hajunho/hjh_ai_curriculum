# Lecture 09 · Level 08 — 이미지 분류 실전 파이프라인

> 검수→분할→학습→오류 분석→개선의 루프를 완주하며, 실무 단골 함정인 라벨 노이즈를 오류 분석으로 색출하는 과정을 시연합니다.
**난이도** ⭐⭐⭐⭐ / **선행** level05~07 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

실패하는 비전 프로젝트의 사후 보고서에는 놀랄 만큼 비슷한 문장이 나옵니다. "모델은 여러 개 시도했으나 데이터 품질 문제가 뒤늦게 발견되어…" 모델 코드는 몇 줄이면 바꿀 수 있지만, 잘못 붙은 라벨 수천 개는 조용히 성능 천장을 낮춥니다. 라벨링을 외주로 맡기면 오류율 몇 %는 기본으로 섞여 들어오고, 내부 라벨링도 담당자마다 기준이 달라 흔들립니다.

그래서 실무 파이프라인의 진짜 실력은 **오류 분석(error analysis)** 에 있습니다 — 성능 숫자를 보고 끝내는 것이 아니라, 모델이 틀리는(또는 괴로워하는) 사례를 체계적으로 파고들어 "다음에 무엇을 고칠지"를 데이터에서 읽어 내는 기술. 오늘은 이 기술이 라벨 노이즈를 색출하는 장면을 처음부터 끝까지 시연합니다. 도구는 새로울 것이 없습니다 — level05~07 에서 배운 부품들을 실전의 순서로 묶을 뿐입니다.

## 2. 비유로 이해하기

**오답 노트로 교재 오류 찾기**입니다.

학원에서 모의고사 성적이 이상하게 안 오릅니다. 알고 보니 **교재의 정답지 일부가 잘못 인쇄**되어 있었습니다(라벨 노이즈). 학생(모델)은 잘못된 정답지에 맞추려 애쓰느라 이상한 풀이 습관까지 생깁니다.

정답지 오류를 어떻게 찾을까요? 전체 문제를 다 재검토하는 것은 비용이 너무 큽니다. 요령은 **성실한 학생이 "아무리 해도 납득이 안 된다"고 표시한 문제부터 보는 것**입니다. 학생이 나머지 문제로 충분히 실력을 쌓았다면, 끝까지 납득 못 하는 문제는 학생 잘못이 아니라 정답지 잘못일 확률이 높습니다.

모델 학습에서 "납득 못 함"의 정확한 지표가 **샘플별 손실(per-sample loss)** 입니다. 학습이 끝난 모델로 학습 데이터를 다시 채점해 손실이 큰 순서로 정렬하면, 그 상위권에 라벨 오류가 몰려 있습니다. 사람은 그 상위권만 재검토하면 됩니다 — 600개 전수 검사 대신 60개 표적 검사.

## 3. 핵심 개념

### 3.1 파이프라인 다섯 단계

1. **데이터 검수**: 수량·크기·값 범위·클래스 균형·샘플 눈검사. 모델 코드를 열기 전에 한다.
2. **분할**: 학습/검증/테스트. 특히 **검증·테스트 라벨은 가장 믿을 만한 사람이 직접** 확인합니다. 자(측정 기준)가 굽어 있으면 어떤 실험도 무의미하니까요.
3. **베이스라인 학습**: 단순한 모델로 빠르게 기준점을 만든다.
4. **오류 분석**: 숫자가 아니라 사례를 본다. 오분류 이미지, 고손실 학습 샘플, 클래스별 패턴.
5. **개선 루프**: 분석이 가리키는 것(라벨 수정, 데이터 보강, 증강 조정…)을 하나 고치고 재실험. 반복.

### 3.2 라벨 노이즈의 두 얼굴

- **성능 천장 하락**: 정답의 8%가 거짓이면, 모델이 아무리 좋아도 그 거짓에 맞추느라 일반화가 상합니다.
- **평가 왜곡**: 노이즈가 테스트에까지 섞이면 "진짜 성능"을 영영 알 수 없게 됩니다. 그래서 평가셋 라벨 품질에 돈을 가장 먼저 씁니다.

### 3.3 고손실 재검토(loss-based review)의 원리와 한계

원리: 모델은 다수의 올바른 라벨에서 일반 규칙을 배우므로, 규칙과 심하게 어긋나는 라벨(=오류)의 손실이 커집니다. main.py 실험에서 상위 60개 재검토로 오염 48개 중 **약 98%** 가 잡힙니다(무작위 재검토의 기대치는 4.8개).

한계도 알아야 합니다: 손실 상위권에는 **라벨은 맞지만 진짜 어려운 사례**(경계에 걸린 도형, 심한 잡음)도 섞입니다. 그래서 자동 삭제가 아니라 **사람의 재검토**가 원칙입니다. 어려운 사례를 지워 버리면 모델은 쉬운 문제만 푸는 헛똑똑이가 됩니다.

### 3.4 "모델을 고칠까, 데이터를 고칠까"

성능이 부족할 때 가장 비싼 반사행동이 "더 큰 모델을 시도"입니다. 오늘 실험이 보여 주듯, 같은 모델로 데이터만 고쳐도 상당한 이득이 나옵니다. 우선순위 감각: **평가셋 품질 → 라벨 품질 → 데이터 양·다양성(증강 포함) → 모델 크기·구조**. 앞쪽이 싸고 효과가 확실합니다.

### 3.5 개선 루프는 한 번에 하나씩

라벨도 고치고 증강도 넣고 모델도 바꿔서 성능이 오르면, 무엇이 효과였는지 알 수 없습니다. 실험 관리의 철칙은 lecture06 부터 일관됩니다 — **한 루프에 변경 하나, 비교는 같은 조건, 판정은 손대지 않은 평가셋**.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

- **[1]** 데이터 검수: 수량·값 범위·클래스 균형을 점검합니다. 그리고 시나리오 발동 — 학습 라벨 600개 중 48개(8%)를 몰래 오염시킵니다. 이후 단계는 오염 사실을 모르는 척 진행합니다.
- **[2]** 분할: 학습 600(오염 포함) / 검증 150 / 테스트 150 (평가 라벨은 깨끗 — 3.2절의 원칙).
- **[3]** v1 학습: 오염된 라벨 그대로 학습. 테스트 정확도가 기대(level05 의 ~0.97)보다 낮게 나옵니다.
- **[4]** 오류 분석: 학습 데이터를 샘플별 손실로 재채점해 상위 60개를 "사람 재검토 대상"으로 뽑습니다. 그 안에 실제 오염 라벨이 몇 개 잡혔는지 정답지와 대조합니다 (전형적 결과: 48개 중 47개, 98% 검출).
- **[5]** 개선 루프: 재검토 대상의 라벨을 고쳐 v2 재학습. v1 → v2 정확도 상승을 확인하고, "처음부터 무오염이었다면"(oracle)과도 비교합니다. 고손실 사례 갤러리(빨간 제목 = 진짜 오염)와 성능 비교를 `outputs/pipeline_error_analysis.png` 로 저장합니다.

코드 핵심부는 `per_sample_loss()` — `CrossEntropyLoss(reduction="none")` 한 줄로 "모델이 샘플마다 얼마나 괴로운지"를 얻습니다. 평소 평균으로 뭉개 보던 손실을 샘플 단위로 펼치는 순간, 손실 함수가 데이터 품질 진단기로 변신합니다.

## 5. 직접 해보기

1. **(쉬움)** `NOISE_RATE` 를 0.08 → 0.20 으로 올려 보세요. v1 성능은 얼마나 무너지고, 검출률은 유지되나요? (힌트: 오염이 늘면 "다수의 올바른 라벨" 전제가 약해집니다)
2. **(보통)** 재검토 예산 `top_k` 를 오염 수의 절반(24)으로 줄여 보세요. 검출률(잡은 오염/전체 오염)과 정밀도(재검토 중 진짜 오염 비율)가 어떻게 달라지나요? 재검토 인건비와 성능의 트레이드오프입니다. (힌트: 상위권일수록 정밀도가 높습니다)
3. **(도전)** 라벨을 고치는 대신 **의심 샘플을 제거**하는 v2' 를 만들어 v2 와 비교해 보세요. 수정 대비 제거의 손해(멀쩡한 어려운 사례까지 버리는 비용)가 보이나요? (힌트: `np.setdiff1d` 로 인덱스 제외)

## 6. 자주 하는 실수

- **평가셋 오염을 방치**: 학습 라벨 청소보다 평가 라벨 청소가 먼저입니다. 자가 굽어 있으면 개선이 개선으로 안 보입니다.
- **고손실 샘플 자동 삭제**: 상위권엔 "어려운 정상 사례"도 있습니다. 자동 필터가 아니라 사람 재검토 대상 목록으로 쓰세요.
- **한 번에 여러 가지를 고치기**: 무엇이 효과였는지 알 수 없어, 다음 프로젝트에 남는 지식이 없습니다.
- **오류 분석을 1회성 이벤트로 여기기**: 배포 후에도 새 데이터가 계속 들어오고 라벨 기준은 계속 흔들립니다. 오류 분석은 파이프라인의 상설 단계입니다.
