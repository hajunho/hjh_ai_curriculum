# Lecture 07 · Level 05 — 스케일링과 파이프라인

> 단위가 제각각인 피처를 같은 자로 재도록 맞추는 스케일링, 그리고 전처리와 모델을 한 덩어리로 묶어 누설을 구조적으로 막는 sklearn Pipeline을 배웁니다.
**난이도** ⭐⭐⭐ / **선행** level04 / **예상 시간** 35분

## 1. 왜 배우나 — 비즈니스 관점

데이터 사고의 상당수는 화려한 알고리즘이 아니라 **전처리 순서 실수**에서 납니다. 대표 사례 두 가지: ① 테스트 데이터까지 포함해 평균·표준편차를 계산한 뒤 스케일링(누설), ② 학습 때 한 전처리를 배포 코드에서 깜빡함(학습-서빙 불일치). 둘 다 "검증에선 좋았는데 실전에서 이상해요"라는, 원인을 찾기 가장 어려운 유형의 장애를 만듭니다.

sklearn의 파이프라인(Pipeline)은 이 두 사고를 **코드 구조 차원에서 원천 봉쇄**하는 도구입니다. 전처리와 모델을 하나의 객체로 묶으면, fit은 학습 데이터에서만 일어나고 transform은 언제나 같은 순서로 적용됩니다. 실무에서 "모델 파일"을 주고받을 때 실제로 오가는 것이 바로 이 파이프라인 객체입니다. 검수자 입장에서도 "전처리가 파이프라인 안에 있나요?"라는 질문 하나로 프로젝트의 품질을 가늠할 수 있습니다.

## 2. 비유로 이해하기

**스케일링 = 단위 통일**입니다. 한 회의에서 A팀은 "매출 3(억 원)", B팀은 "매출 250,000,000(원)"이라고 말하면, 숫자만 보는 사람은 B팀 안건이 8천만 배 중요하다고 착각합니다. 거리 기반 모델(KNN 등)이 정확히 이 착각을 합니다. 월 요금(9,900~29,900)과 이용일수(0~30)를 같은 자로 재면, 요금의 1원 차이와 이용일수의 1일 차이를 같은 크기로 취급해 요금이 거리를 독점합니다. 표준화(standardization)는 모든 변수를 "평균 0, 표준편차 1"이라는 공용 단위로 환산하는 일입니다.

**파이프라인 = 공장의 컨베이어 벨트**입니다. 부품(데이터)이 벨트에 오르면 세척(스케일링)→조립(모델)이 항상 같은 순서로 일어납니다. 벨트가 없으면 작업자가 세척을 깜빡하거나, 출하 검사용 부품(테스트 데이터)을 세척조 물(평균·표준편차 계산)에 섞는 사고가 납니다. 벨트가 있으면 순서 실수 자체가 불가능해집니다.

## 3. 핵심 개념

### 3.1 StandardScaler — 표준화

각 컬럼에 대해 `(값 − 평균) / 표준편차`를 계산합니다. 결과는 "평균에서 표준편차 몇 개만큼 떨어졌나"라는 무단위 점수입니다. 핵심 규칙: **평균과 표준편차는 학습 데이터에서만 계산(fit)하고, 테스트에는 그 값을 그대로 적용(transform)만** 합니다. 테스트까지 섞어 평균을 내면 테스트 분포 정보가 학습에 새어 들어갑니다.

### 3.2 스케일링이 필요한 모델, 무관한 모델

- **민감**: KNN, SVM, 로지스틱/선형 회귀(규제 포함), 신경망, K-means — 거리·크기를 직접 쓰는 모델
- **둔감**: 결정트리, 랜덤포레스트, 부스팅 — "얼마보다 큰가?"로 쪼개기만 하므로 단위와 무관

트리 계열만 쓸 거라면 스케일링을 생략해도 되지만, 파이프라인에 넣어 두면 모델을 바꿔도 안전합니다.

### 3.3 Pipeline이 누설을 막는 원리

`make_pipeline(StandardScaler(), KNeighborsClassifier())`로 묶으면:

- `pipe.fit(X_train, y_train)` → 스케일러가 **학습 데이터로만** 평균·표준편차를 배우고, 변환된 데이터로 모델이 학습
- `pipe.predict(X_test)` → 학습 때 배운 평균·표준편차로 테스트를 변환한 뒤 예측

교차검증(`cross_val_score(pipe, X, y)`)에 파이프라인째 넣으면, **폴드마다** 스케일러가 그 폴드의 학습 부분만으로 다시 fit 됩니다. 스케일링을 미리 전체 데이터에 해 두고 교차검증을 돌리면 모든 폴드의 검증 데이터 정보가 스케일러에 이미 들어간 상태 — 이것이 전처리 누설의 표준 사례입니다. 스케일링 정도는 누설 효과가 작지만, 타깃 인코딩·결측 대체·피처 선택처럼 정답이나 분포를 진하게 쓰는 전처리에서는 성능이 크게 부풀 수 있습니다. 그래서 규칙은 하나로 통일합니다: **전처리는 전부 파이프라인 안으로**.

### 3.4 배포 관점의 보너스

파이프라인 객체 하나만 저장하면 전처리+모델이 함께 따라갑니다. 배포 코드에서는 `pipe.predict(새 데이터)` 한 줄이면 되고, "전처리 누락" 유형의 학습-서빙 불일치가 사라집니다.

### 3.5 파이프라인은 어디까지 자라나

오늘은 "스케일러+모델" 두 칸짜리 벨트지만, 실무 파이프라인은 결측 대체 → 인코딩(level04) → 스케일링 → 피처 선택 → 모델까지 다섯 칸 이상으로 자랍니다. sklearn의 `ColumnTransformer`를 쓰면 "숫자 컬럼은 스케일링, 문자 컬럼은 원핫"처럼 컬럼별로 다른 처리를 한 벨트에 묶을 수 있습니다. 구조는 오늘 배운 것과 동일하니, 필요할 때 이름만 찾아 쓰면 됩니다.

- [1] 피처 단위 확인: monthly_fee(수만 원대)와 usage_days_30d(0~30)의 스케일 차이를 출력합니다.

- [3] StandardScaler + KNN(파이프라인) → 같은 모델, 같은 데이터에서 AUC와 '상위 100명 중 실제 이탈자 수'가 함께 뛰는 것을 확인합니다.
- [4] 잘못된 순서 시연: 전체 데이터를 먼저 스케일링한 뒤 교차검증 vs 파이프라인을 교차검증에 넣는 올바른 방식의 점수를 비교하고, 숫자 차이보다 "구조적 안전"이 핵심임을 확인합니다.
- [5] 파이프라인 객체 하나로 새 고객 3명의 이탈 확률을 예측해 배포 관점의 편리함을 시연합니다.

코드에서 볼 핵심은 `make_pipeline(...)`이 만든 객체가 `fit / predict / cross_val_score`에서 보통 모델과 똑같이 쓰인다는 점입니다. 배우는 API는 하나인데 얻는 안전장치는 세 개(순서 보장, fit 범위 보장, 배포 일체화)입니다.

## 6. 자주 하는 실수

- **테스트 데이터에 fit_transform 호출**: 테스트에는 `transform`만. 파이프라인을 쓰면 이 실수 자체가 불가능해집니다.
- **스케일링을 교차검증 밖에서 미리 해 두기**: 폴드 밖 정보가 새어 듭니다. `cross_val_score`에는 파이프라인째 넣으세요.
- **트리 모델이라 스케일링을 아예 신경 끄기**: 지금은 맞지만, 나중에 모델을 로지스틱 회귀로 바꾸는 순간 조용히 성능이 무너집니다. 파이프라인에 넣어 두면 모델 교체가 안전합니다.
- **스케일링 후 값의 의미를 잊음**: 표준화된 계수나 값(-1.2 등)을 보고서에 원 단위처럼 쓰면 안 됩니다. 해석할 때는 원래 단위로 역환산하거나 "표준편차 단위"임을 명시하세요.
