**난이도** ⭐ / **선행** lecture06 level00~02 / **예상 시간** 25분

## 1. 왜 배우나 — 비즈니스 관점

머신러닝 프로젝트의 실패 원인 1위는 모델이 아닙니다. 업계에서 반복적으로 관찰되는 실패담의 대부분은 "애초에 무엇을 예측해야 하는지 합의가 안 됐다", "데이터가 그 질문에 답할 수 없는 상태였다", "만들어 놓고 아무도 쓰지 않았다"입니다. 즉 실패는 코딩 단계가 아니라 그 앞뒤 단계에서 일어납니다.

비전공자인 여러분이 이 지도를 알아야 하는 이유는 명확합니다. 실무에서 여러분의 역할은 모델 코드를 짜는 것이 아니라, 프로젝트가 다섯 단계 중 지금 어디에 있고 어느 관문(gate)에서 멈춰야 하는지 판단하는 것이기 때문입니다. 발주자·현업 담당자·검수자 어느 역할이든, 이 지도 하나로 회의에서 던져야 할 질문이 달라집니다.

## 2. 비유로 이해하기

데이터 프로젝트는 **식당 창업**과 놀랍도록 비슷합니다.

1. **문제정의 = 상권·메뉴 결정**: "뭐든 맛있게 만들면 되지"로 시작한 식당은 망합니다. 누구에게(타깃 고객), 무엇을(메뉴), 얼마에(성공 기준) 팔지 먼저 정해야 합니다.
2. **데이터 = 식자재 조달**: 아무리 훌륭한 셰프도 상한 재료로는 요리를 못 합니다. 재료 검수(데이터 품질 점검)를 건너뛰면 주방(모델)에서 사고가 납니다.
3. **모델 = 조리**: 전체 일의 20% 정도입니다. 창업 준비의 대부분이 요리 자체가 아니듯, 프로젝트 시간의 대부분은 앞뒤 단계에 씁니다.
4. **배포 = 개업**: 요리가 완성돼도 손님 앞에 나가는 동선(기존 업무 시스템과의 연결)이 없으면 아무도 못 먹습니다.
5. **모니터링 = 단골 관리**: 개업 첫날 맛이 영원히 유지되지 않습니다. 식자재 시세(데이터 분포)가 바뀌면 레시피를 조정해야 합니다.

"모델만 잘 만들면 된다"는 생각은 "요리만 잘하면 식당은 된다"는 생각과 같은 이유로 위험합니다.

## 3. 핵심 개념

### 3.1 다섯 단계와 각 단계의 산출물

| 단계 | 핵심 질문 | 대표 산출물 |
|---|---|---|
| ① 문제정의 | 무엇을, 왜, 성공 기준은? | 문제 명세서(예측 대상·활용 방안·목표 지표) |
| ② 데이터 | 그 질문에 답할 데이터가 있나? | 데이터 감사 리포트(행 수·결측·타깃 비율) |
| ③ 모델 | 기준선(baseline)보다 나은가? | 검증된 성능 보고서(교차검증 포함) |
| ④ 배포 | 현업이 실제로 쓸 수 있나? | 업무 프로세스 연결(예: 매주 위험고객 명단 자동 발송) |
| ⑤ 모니터링 | 성능이 유지되고 있나? | 성능 대시보드, 재훈련 기준 |

중요한 것은 각 단계 사이에 **관문**이 있다는 점입니다. 관문을 통과하지 못하면 다음 단계로 가지 말고 멈추거나 되돌아가야 합니다. 예: 데이터 감사에서 이탈 고객 표본이 50명뿐이라면, 모델 단계로 넘어가는 대신 데이터를 더 모으는 것이 정답입니다.

### 3.2 실패하는 프로젝트의 공통점

- **목표 지표가 없다**: "AI로 뭔가 해 보자"로 시작하면, 무엇이 나와도 성공인지 실패인지 판정할 수 없습니다.
- **정답 라벨이 부실하다**: "이탈"의 정의가 부서마다 다르면(해지 신청? 3개월 미접속?) 모델은 서로 다른 문제를 배웁니다.
- **기준선 없이 시작한다**: "지난달과 같다고 예측"하는 단순 규칙보다 못한 모델이 배포되는 일이 실제로 일어납니다.
- **배포 계획이 없다**: 모델이 뱉은 확률 숫자를 받아 볼 사람·시스템·업무 절차가 정해지지 않은 채 개발부터 합니다.
- **모니터링이 없다**: 코로나 같은 환경 변화로 데이터 분포가 바뀌어도(분포 이동, data drift) 아무도 눈치채지 못합니다.

### 3.3 시간 배분의 현실

교과서는 모델을 길게 다루지만, 실무 시간 배분은 대략 "문제정의·데이터 60~70%, 모델 10~20%, 배포·모니터링 20~30%"에 가깝습니다. 이 강의의 레벨 구성(부품 8개 + 실전 4개)도 그 현실을 반영한 것입니다.

## 4. 실습 — main.py

```bash
python3 main.py
```

main.py는 가상의 프로젝트 "구독 이탈 방어"를 다섯 단계 관문에 통과시키는 시뮬레이션입니다.

- [1] 문제정의: 명세서 항목(예측 대상, 활용 방안, 목표 지표)을 채웠는지 점검하고 관문 판정을 출력합니다.
- [2] 데이터: `hjh_data.churn_table()`을 실제로 불러 행 수·결측·타깃 비율을 감사하고, "소수 클래스 표본이 충분한가" 관문을 통과시킵니다.
- [3] 모델: 아직 모델을 배우기 전이므로 "다수결 기준선"의 정확도를 계산해 이후 모델이 넘어야 할 선을 확인합니다.
- [4]~[5] 배포·모니터링: 체크리스트 항목이 비어 있는 상태를 일부러 보여 주고, 관문에서 "중단" 판정이 나는 것을 관찰합니다.

출력 마지막의 요약표에서 어느 단계가 PASS이고 어느 단계가 STOP인지 확인하세요. 코드 핵심부는 `gate()` 함수입니다. 단계별 점검 항목을 리스트로 받아 하나라도 비면 통과시키지 않는, 아주 단순하지만 실무에서 가장 자주 생략되는 로직입니다.

## 6. 자주 하는 실수

- **모델부터 정하고 문제를 끼워 맞추기**: "요즘 뜨는 기법을 써 보자"는 식당 메뉴를 정하기 전에 오븐부터 사는 것과 같습니다.
- **정확도를 성공 기준으로 무조건 채택**: 이탈률 18% 데이터에서는 "아무도 이탈 안 함"이라고만 해도 정확도 82%입니다. 기준선 없는 정확도는 숫자 장식입니다.
- **일회성 분석과 운영 시스템을 혼동**: 보고서 한 번 쓰고 끝나는 분석과, 매주 돌아가야 하는 시스템은 요구사항이 전혀 다릅니다. 시작 전에 어느 쪽인지 합의하세요.
- **관문 판정을 감정으로 하기**: "여기까지 왔는데 아깝잖아"는 매몰비용의 목소리입니다. 관문은 체크리스트로, 기계적으로.
