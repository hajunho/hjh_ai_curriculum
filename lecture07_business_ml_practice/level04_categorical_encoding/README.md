# Lecture 07 · Level 04 — 범주형 변수 인코딩

> "강남점", "커피", "토요일" 같은 문자 데이터를 모델이 먹을 수 있는 숫자로 바꾸는 세 가지 방법과 각각의 함정을 실험으로 비교합니다.
**난이도** ⭐⭐⭐ / **선행** level03 / **예상 시간** 40분

## 1. 왜 배우나 — 비즈니스 관점

실무 데이터의 절반은 숫자가 아닙니다. 지점명, 상품 카테고리, 가입 경로, 직급, 지역 — 전부 **범주형(categorical)** 변수입니다. 그런데 대부분의 모델은 숫자만 입력받습니다. 문자를 숫자로 바꾸는 인코딩(encoding)은 그래서 모든 표 데이터 프로젝트의 통과 의례입니다.

문제는 바꾸는 방법이 여러 가지이고, **잘못 고르면 모델에게 거짓 정보를 주입**하게 된다는 점입니다. 지점명을 1, 2, 3으로 바꾸면 모델은 "부산점(3)은 강남점(1)의 3배"라는 있지도 않은 서열을 배웁니다. 반대로 방법을 잘 고르면 "지점"이라는 정보 하나가 매출 예측 정확도를 크게 끌어올립니다. 어떤 인코딩이 어떤 상황에 맞는지 아는 것은, 데이터팀 보고서에서 "왜 이렇게 처리했나요?"라고 물을 수 있는 검수 능력이기도 합니다.

## 2. 비유로 이해하기

설문지의 "직업란"을 전산 입력하는 세 가지 방식을 상상해 보세요.

- **원핫 인코딩(one-hot)**: 직업마다 체크박스 열을 하나씩 만듭니다. "회사원 ☑ / 자영업 ☐ / 학생 ☐". 서열 왜곡이 전혀 없지만, 직업이 500종이면 열이 500개가 됩니다.
- **순서형 인코딩(ordinal)**: 직업에 번호를 붙입니다. "회사원=1, 자영업=2, 학생=3". 열은 1개로 끝나지만, 숫자의 크기에 아무 의미가 없는데도 모델은 의미를 찾으려 듭니다. 다만 "사원<대리<과장<부장"처럼 **진짜 서열이 있는 범주**라면 오히려 정직한 방법입니다.
- **타깃 인코딩(target)**: 직업 대신 "그 직업 그룹의 과거 평균 연체율" 같은 **정답의 그룹 평균**을 적습니다. 열 1개로 정보를 압축하는 강력한 방법이지만, 정답을 재료로 쓰기 때문에 잘못 계산하면 정답이 문제지에 새어 들어가는 누설 사고가 납니다.

## 3. 핵심 개념

### 3.1 세 인코딩 요약

| 방법 | 열 개수 | 서열 왜곡 | 누설 위험 | 어울리는 경우 |
|---|---|---|---|---|
| 원핫 | 범주 수만큼 | 없음 | 없음 | 범주 수가 적을 때(수십 개 이하)의 기본값 |
| 순서형 | 1 | **있음**(무서열 범주에 쓰면) | 없음 | 진짜 순서가 있는 범주(등급, 직급), 트리 계열 모델 |
| 타깃 | 1 | 없음 | **있음** | 고카디널리티(범주 수백~수만 개) |

트리 계열 모델(결정트리, 랜덤포레스트)은 숫자를 "쪼개는 기준"으로만 쓰므로 순서형 인코딩의 왜곡에 비교적 둔감합니다. 서열 왜곡이 치명적인 것은 숫자의 크기를 그대로 믿는 선형 모델 쪽입니다.

### 3.2 타깃 인코딩의 누설과 방어

타깃 인코딩의 값은 반드시 **학습 데이터에서만** 계산해야 합니다. 테스트까지 포함해 그룹 평균을 내면, 테스트의 정답이 피처에 스며듭니다. 또 학습 데이터 안에서도 "자기 행의 정답이 자기 피처에 반영"되는 문제가 있어, 실전에서는 교차검증 방식(자기 폴드를 빼고 계산)이나 스무딩(표본이 적은 그룹은 전체 평균 쪽으로 당김)을 씁니다. main.py는 가장 기본 방어인 "학습 데이터로만 계산 + 미등장 범주는 전체 평균"을 구현합니다.

### 3.3 고카디널리티(high cardinality) 문제

고객 ID, 상품코드, 우편번호처럼 범주가 수천~수만 개면 원핫은 열 폭발(차원의 저주 + 메모리)을 일으킵니다. 이때의 선택지는 ① 타깃 인코딩, ② 빈도 인코딩(등장 횟수로 치환), ③ 상위 N개만 남기고 나머지는 "기타"로 묶기, ④ 그 컬럼 자체를 버리기(고객 ID처럼 일반화 신호가 없다면 버리는 게 정답)입니다.

### 3.4 미등장 범주 처리

배포 후 "신규 오픈 지점"처럼 학습 때 없던 범주가 들어옵니다. 원핫은 모든 열이 0, 타깃 인코딩은 전체 평균으로 대체하는 식의 **미등장(unseen) 범주 정책**을 미리 정해 두어야 운영 중 장애가 없습니다. `pd.get_dummies`를 학습/테스트에 따로 적용하면 열이 어긋나는 사고가 나므로, 실무에서는 sklearn의 `OneHotEncoder(handle_unknown="ignore")`를 파이프라인(level05)에 넣는 것이 정석입니다.

## 4. 실습 — main.py

```bash
python3 main.py
```

`sales_table` 1년치에서 지점·카테고리·요일로 매출을 예측하는 선형 회귀(Ridge)를 인코딩만 바꿔 세 번 훈련합니다.

- [1] 데이터 정제: 결측·음수 매출 행을 제거하고 범주형 3개 컬럼의 범주 수를 확인합니다.
- [2] 원핫: `OneHotEncoder`로 열이 몇 개로 늘어나는지 확인하고 성능(MAE, R²)을 잽니다.
- [3] 순서형: 범주를 번호로 치환. 열은 3개뿐이지만 성능이 무너지는 것을 관찰합니다(서열 왜곡).
- [4] 타깃: 학습 데이터의 그룹 평균 매출로 치환. 열 3개로 원핫에 근접하는 성능을 확인합니다.
- [5] 요약표: 방법별 "열 개수 vs 성능"을 나란히 놓고, 고카디널리티 상황의 선택 기준을 출력합니다.

핵심 관찰 포인트: 순서형의 R²가 원핫보다 뚜렷이 낮다는 것(선형 모델 + 무서열 범주의 궁합 문제), 그리고 타깃 인코딩이 열 3개로 그 격차를 대부분 메운다는 것입니다.

## 6. 자주 하는 실수

- **무서열 범주에 무심코 번호 붙이기**: 엑셀에서 "서울=1, 부산=2"로 코딩된 데이터를 그대로 모델에 넣는 사고가 가장 흔합니다. 선형 모델이라면 반드시 원핫으로 풀어 주세요.
- **타깃 인코딩을 전체 데이터로 계산**: 검증 성능이 갑자기 좋아졌다면 기뻐하기 전에 누설을 의심하세요. 계산은 언제나 학습 데이터만으로.
- **get_dummies를 학습/테스트에 따로 적용**: 두 쪽의 열 구성이 달라져 배포 때 터집니다. `OneHotEncoder(handle_unknown="ignore")` + 파이프라인이 정석입니다.
- **고객 ID를 타깃 인코딩해서 성능이 오른 것처럼 보임**: 고객당 행이 몇 개 없으면 그룹 평균이 사실상 정답 복사가 됩니다. ID류 컬럼은 원칙적으로 제외하세요.
