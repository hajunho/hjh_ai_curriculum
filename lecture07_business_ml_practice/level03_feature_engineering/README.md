# Lecture 07 · Level 03 — 피처 엔지니어링

> 같은 데이터, 같은 모델이라도 피처를 어떻게 빚느냐에 따라 성능이 달라집니다. 원본 피처 vs 파생 피처를 같은 모델로 겨루게 해 그 위력을 증명합니다.
**난이도** ⭐⭐⭐ / **선행** level02, lecture06 level05 / **예상 시간** 40분

## 1. 왜 배우나 — 비즈니스 관점

캐글(대회)에서든 회사에서든, 예측 성능을 가르는 것은 대개 모델의 종류가 아니라 **피처(feature, 입력 변수)의 품질**입니다. 그리고 좋은 피처를 만드는 재료는 수학이 아니라 **도메인 지식** — 그 업무를 아는 사람의 감각입니다.

"새벽에 해외에서 연달아 긁힌 카드는 수상하다"는 것은 카드사 심사역이라면 누구나 아는 상식입니다. 그런데 데이터에는 `hour=2`, `is_foreign=1`, `tx_count_1h=9`라는 낱개 숫자만 있을 뿐, "수상한 패턴"이라는 컬럼은 없습니다. 그 상식을 모델이 먹을 수 있는 숫자 컬럼으로 번역하는 일이 피처 엔지니어링이고, 이것이 비전공 실무자가 데이터 프로젝트에 기여할 수 있는 가장 큰 지점입니다. 코딩은 데이터팀이 해도, "어떤 피처를 만들어야 하는지"는 현업만 압니다.

## 2. 비유로 이해하기

모델은 **재료를 주는 대로만 먹는 편식쟁이 심사역**입니다. 신용 심사역에게 서류를 준다고 생각해 보세요.

- 원본 그대로: "월소득 400만 원", "월 대출상환액 180만 원" — 두 숫자를 각각 보면 판단이 어렵습니다.
- 파생 피처: "소득 대비 상환 비율 45%" — 나누기 한 번 했을 뿐인데 판단이 한눈에 됩니다.

사람 심사역은 머릿속에서 이 나눗셈을 자동으로 하지만, 선형 모델은 스스로 나눗셈을 만들어 내지 못합니다(덧셈과 곱하기 상수만 가능). 그래서 사람이 미리 비율·차이·묶음 컬럼을 만들어 "소화되기 좋은 형태"로 차려 줘야 합니다. 요리로 치면 피처 엔지니어링은 재료 손질입니다. 손질 안 한 통생선을 주면 아무리 좋은 요리사(모델)도 실력을 못 냅니다.

## 3. 핵심 개념

### 3.1 파생 피처의 대표 레시피

| 레시피 | 예시 | 언제 쓰나 |
|---|---|---|
| 비율(ratio) | 소득 대비 상환액, 이용일수/가입개월 | 두 수의 상대 관계가 중요할 때 |
| 차이(diff) | 이번 달 − 지난달 사용량 | 변화·추세가 신호일 때 |
| 로그 변환 | log(거래금액) | 금액처럼 한쪽으로 심하게 치우친 분포 |
| 구간화·플래그 | 새벽 시간대 여부(is_night) | "구간"이 의미를 가질 때 |
| 상호작용 | 해외 × 새벽 | 조건이 겹칠 때만 위험한 패턴 |
| 집계(aggregate) | 고객별 최근 30일 평균 결제액 | 거래 단위 데이터를 고객 단위로 요약 |

이 중 로그 변환은 특히 금액 데이터의 단골입니다. 1만 원과 2만 원의 차이(2배)와 1억과 2억의 차이(2배)를 같은 크기로 만들어 주어, 선형 모델이 "배율"의 언어로 생각할 수 있게 합니다.

### 3.2 어디서 아이디어를 얻나 — EDA와 현업 인터뷰

level02의 이변량 분석이 그대로 재료 목록입니다. "사기 거래는 새벽에 몰린다"를 봤다면 `is_night` 플래그를, "금액 분포가 심하게 치우쳤다"를 봤다면 로그 변환을 만듭니다. 여기에 현업 인터뷰("우리는 어떤 걸 보고 수상하다고 느끼나요?")를 더하면 피처 후보 목록이 완성됩니다.

### 3.3 데이터 누설(data leakage) — 피처 엔지니어링의 최대 함정

파생 피처를 만들다 보면 실수로 **미래의 정보**나 **정답의 그림자**를 피처에 섞게 됩니다.

- "환불 여부"로 이탈 예측: 환불은 이탈 **후에** 일어나는 일 — 예측 시점엔 알 수 없는 값입니다.
- 전체 데이터(테스트 포함)의 평균으로 파생 피처 계산: 테스트 정보가 학습에 새어 들어갑니다.
- "조사 결과 코드"로 사기 예측: 조사는 사기로 **판정된 뒤에** 하는 것.

판별 질문은 하나입니다. **"예측해야 하는 그 시점에, 이 값을 알 수 있는가?"** 답이 "아니오"면 성능이 아무리 좋아도 버려야 합니다. 누설 피처는 검증 성능은 환상적으로 좋고 실전에서는 무용지물인, 가장 악질적인 버그입니다.

### 3.4 성능 비교는 공정하게

파생 피처의 효과를 주장하려면 **모델·데이터 분할·평가지표를 완전히 고정**하고 피처 목록만 바꿔야 합니다. main.py가 정확히 이 통제 실험을 수행합니다.

## 4. 실습 — main.py

```bash
python3 main.py
```

`fraud_table` 5,000건으로 사기 탐지 모델을 두 번 훈련합니다. "원본"은 결제 승인 순간 바로 실려 오는 필드 3개(amount, hour, is_foreign)라고 가정합니다.

- [1] 데이터를 불러 원본 피처 3개를 확인합니다.
- [2] 도메인 지식 기반 파생 피처 3개를 만듭니다: `log_amount`(로그 변환), `is_night`(새벽 플래그), `foreign_night`(해외×새벽 상호작용).
- [3] 같은 로지스틱 회귀, 같은 분할로 "원본만" vs "원본+파생"을 훈련하고 AUC와 PR-AUC(평균 정밀도)를 비교합니다.
- [4] 파생 피처 세트의 계수를 출력해 어떤 피처가 일하는지 확인합니다.
- [5] 누설 데모: 정답을 슬쩍 섞은 가짜 피처 하나를 넣으면 성능이 비현실적으로 치솟는 것을 보여 주고, 경고를 출력합니다.

주목할 출력은 [3]의 PR-AUC 비교입니다. 모델은 한 글자도 안 바꿨는데 성능이 뛰는 것 — 그것이 피처의 위력입니다. [5]에서 "너무 좋은 성능은 버그"라는 감각도 함께 가져가세요.

## 5. 직접 해보기

1. **(쉬움)** 파생 피처 중 하나씩을 빼고 실행해 어떤 피처가 성능에 가장 크게 기여하는지 확인해 보세요. 힌트: `DERIVED` 리스트에서 하나씩 지워 보기.
2. **(중간)** 집계 피처를 참전시켜 보세요. 테이블에 있는 `tx_count_1h`(최근 1시간 결제 건수 — 거래 이력을 집계해야 얻는 값)와 비율 피처 `amount_per_tx = amount / (tx_count_1h + 1)`을 DERIVED에 추가하면 PR-AUC가 어디까지 오르나요? "집계 피처가 단골 에이스"인 이유를 체감해 보세요.
3. **(도전)** churn_table로 같은 실험을 설계해 보세요. 후보: `usage_days_30d / tenure_months`(가입 기간 대비 활동성), `support_calls_30d - plan_changes` 등. 어떤 피처가 도메인 상식과 맞는 방향의 계수를 갖는지 확인하세요.

## 6. 자주 하는 실수

- **예측 시점 검증 생략**: 피처 하나마다 "예측 시점에 알 수 있는 값인가?"를 묻지 않으면 누설은 반드시 일어납니다. 피처 목록 옆에 "생성 시점" 열을 만들어 관리하세요.
- **피처를 무한정 늘리기**: 피처가 많을수록 좋은 게 아닙니다. 표본 대비 피처가 많으면 과적합(lecture06 level09)이 옵니다. 만들고→검증하고→기여 없으면 버리기.
- **0으로 나누기**: 비율 피처의 단골 사고. 분모에 +1을 하거나(main.py 방식) 조건 처리하세요.
- **테스트 데이터를 포함해 통계 피처 계산**: "전체 평균 대비 비율" 같은 피처는 반드시 학습 데이터의 통계만으로 만들어야 합니다. level05의 파이프라인이 이 문제를 구조적으로 해결합니다.
