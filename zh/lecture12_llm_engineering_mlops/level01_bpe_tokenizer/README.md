# Lecture 12 · Level 01 — 打造分词器 — 亲手实现 BPE

> 只靠"把最常相邻出现的字符对不断合并"这一条简单规则，从零造出 LLM 的词表 (BPE)。

**难度** ⭐⭐⭐ / **先修** level00 / **预计时间** 50分钟

## 1. 为什么要学 — 业务视角

LLM 的价目表全是按"每 token 多少钱"写的。同一份文档，分词器 (tokenizer) 怎么切，token 数就能差出两三倍，这直接就是 API 账单和响应速度的差距。中文在以英文为中心的分词器里尤其吃亏: 一个汉字在 UTF-8 里占 3 个字节，词表里没收录的汉字会被拆到字节级，问同样的问题往往比英文计费更贵。要回答"为什么我们服务的 LLM 成本比预期高"，你得先知道 token 是怎么造出来的。

另外，分词器还是模型能力的隐形决定因素。后面我们会做实验: 数字怎么切，模型的计算能力就跟着变。"模型不会做加法"这个问题的病根，可能不在训练，而在切数据的那把刀 —— 这就是工程直觉。今天要实现的 BPE (Byte Pair Encoding，字节对编码) 正是 GPT 系列等绝大多数 LLM 所用方法的原型。

## 2. 打个比方

想想输入法里的自定义短语。一开始你每个字都得老老实实打全拼。后来发现"报告"这两个字一天要打几十遍，于是注册了短语"bg → 报告"。接着又把常用的词一个个加进去…… **从最高频的组合开始依次造快捷短语**，这就是 BPE 的全部。

- 起点: 每个字符各自是一个 token (0 条短语)
- 第 1 步: 找出语料中最常相邻出现的两个 token，合并成一个 (注册第一条短语)
- 重复: 合并出的块也能继续参与合并，于是"报+告" → "报告"、"把+报告" → "把报告"，越来越长的词就长出来了

短语注册得越多 (vocab 越大)，敲键次数 (token 数) 越少，但短语表越庞大，管理成本也越高。这个取舍，和真实 LLM 在 3 万~25 万之间纠结 vocab 大小的原因一模一样。

## 3. 核心概念

### 3-1. BPE 训练算法

1. 把语料里的词拆成单个字符，并在词尾加上 `</w>` 标记。(同一个"报告"，出现在词中间和词结尾要区分开。)
2. 统计所有相邻 token 对的出现频次。
3. 把最高频的对合并成一个新 token，并记下这条规则。
4. 重复第 2~3 步，直到达到想要的合并次数。

训练结束后留下的，是**一份按顺序排列的合并规则清单**。给新句子分词时，先拆成字符，再按学习时的顺序重放这些规则即可。规则顺序就是优先级 —— 同样的 vocab，顺序不同，切出来的结果也不同。

顺带一提: 我们的迷你语料贴心地在词与词之间留了空格，所以能用教科书式的"词内 BPE"。真实的中文没有空格，字符种类又上万，所以工业级实现 (GPT 系列等) 干脆下沉到**字节级 (byte-level BPE)**: 任何文本先变成 UTF-8 字节流 (一个汉字 = 3 字节)，再在字节上做完全相同的合并游戏。原理丝毫不变，起点从"字符"换成"字节"而已。

### 3-2. vocab 大小的取舍

| 合并次数 (=vocab 大小) | 优点 | 缺点 |
|---|---|---|
| 少 (vocab 小) | 嵌入表小，每个 token 都高频出现、学得充分 | 句子变长，推理成本与延迟上升 |
| 多 (vocab 大) | 句子变短 → 同样的上下文窗口装下更多内容 | 稀有 token 训练机会不足，嵌入参数暴增 |

中文服务用中文语料重训分词器后 token 数大幅下降，也能用这张表解释: 高频的中文组合被收进了 vocab。

### 3-3. 数字分离 (digit split)

BPE 放着不管，语料里高频出现的数字组合就会整块变成 token。价格数据一多，就会长出"00"、"500韩元"这样的块。问题在于**同一个数字的切法会变得忽长忽短**: 987 被切成 "9"+"87"、986 却整块保留 —— 在模型眼里这俩是形状完全不同的符号，数位概念根本没法学。所以最新的 LLM 都在预处理里强制把数字按一位 (或最多三位) 切开。切菜规则一条，改写数学成绩。

## 4. 动手练习 — main.py

```bash
cd lecture12_llm_engineering_mlops/level01_bpe_tokenizer
python3 main.py
```

`[1]` 加载 tiny_corpus (32,857 字、仅 44 种不同字符)；`[2]` 做 60 次 BPE 合并并原样打印前几步。最先被合并的是 "。+</w>"、"好+了"、"好了+。</w>" —— 句号和结果补语这类高频尾巴最先成块，之后"把计划+书 → 把计划书"这样的整词也陆续出现。实际只合并了 49 次就提前收工: 语料的用词太规整，可合并的对用完了。`[3]` 用合并 0/10/30/60 次的四个分词器切同一句话，token 数从 11 降到 4。`[4]` 是重头戏: 用金额密集的语料分别在"不分离/分离数字"两种设定下训练，再切 "98700韩元" —— 不分离的一侧切成 `['9', '8', '700韩元']` 这样忽长忽短，分离的一侧则一位一位整整齐齐。

代码的心脏是三个函数: `count_pairs()` 统计相邻对频次 (digit_split 开关负责拦下含数字的合并)，`merge_pair()` 在所有词里把该对粘合，`train_bpe()` 把这两步循环起来。与真实库的实现原理相同，只是规模更小。

## 6. 常见误区

- **以为 token = 词**: token 是频率切出来的碎片，与"词"并不对齐。估算费用时按"词数 × 1"来算，中文会错得离谱。
- **忽视合并规则的顺序**: 只存 vocab 列表、弄丢顺序，同一句话就会被切出不同结果。训练和推理必须用同一份规则文件。
- **换了分词器却不动模型**: 一换分词器，所有 token id 的含义全变，嵌入层必须重训。"把分词器换成中文专用的就行"这种提案没那么简单，原因就在这。
- **把预处理 (数字分离等) 当小事**: 如今天所见，一行预处理能改变模型能力。请务必把预处理规则写进数据管线文档。
