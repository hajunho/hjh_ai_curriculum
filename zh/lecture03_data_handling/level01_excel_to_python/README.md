# Lecture 03 · Level 01 — 从 Excel 到 Python

> 把你每天在 Excel 里做的合计、筛选、排序搬进代码，亲身体会代码是怎么越过 Excel 的三面墙 — 可复现性、规模、自动化。

**难度** ⭐ / **先修** level00 / **预计时间** 45分钟

## 1. 为什么要学 — 从业务视角出发

Excel 是了不起的工具。好学、边看边改、而且是公司的通用语。可是在实际工作中，一旦数据变大、活儿开始重复，你就会撞上三面墙。

1. **可复现性 (reproducibility)**: 有人问上个月报表里的数字是怎么算出来的，你的回答往往是"先筛选，然后复制到哪儿，再套个公式……"，全靠记忆。点击的顺序哪儿都没有记录。经手人一换，数字就再也做不出来的情况非常常见。
2. **规模 (scale)**: Excel 工作表的物理上限大约是 104 万行，而实际上从几十万行开始就明显变卡了。"文件打不开"是数据岗的日常哀号。
3. **自动化 (automation)**: 每周一打开同一个文件、做同一张透视表这件事，人做是 30 分钟外加出错可能，代码做是 3 秒而且每次都一样。

搬到 Python 并不意味着扔掉 Excel。它的意思是**把"点击的步骤"换成"读得懂的文档 (代码)"**。代码本身就是作业说明书，所以它可以被评审、可以被重跑、还可以被定时执行。

## 2. 用比喻来理解

Excel 手工活就像**凭手感炖的一锅汤**。当天确实好吃，但"放了点生抽，呃……然后又放了什么来着"，同样的味道很难再做一次。代码则是**写明了分量的菜谱**。有了菜谱:

- 谁来炖都是同一个味道。→ **可复现性**
- 一人份的菜谱可以原样搬到一百人份的大锅上。→ **规模**
- 把菜谱塞进料理机，每天早上就自动炖好。→ **自动化**

而且菜谱上写着"盐 2 勺"，那么客人抱怨太咸时，你能准确知道改哪里。这就是"代码可以被评审"的意思。Excel 文件的撤销 (Ctrl+Z) 记录在关闭文件那一刻就消失了，代码会留下来。

## 3. 核心概念

### 3-1. CSV — Excel 和 Python 相遇的那座桥

CSV (Comma-Separated Values) 是用逗号分隔值的纯文本表格。Excel 能打开，记事本能打开，Python 也能读。它没有格式、公式、图表，**只有值**。所以它几乎成了系统之间交换数据的标准。本关实战里我们会把销售表存成 CSV 再读回来。实际工作中"下载数据"按钮给你的文件，大多就是这个格式。

### 3-2. Excel 操作 ↔ Python 代码对照表

| 以前在 Excel 里做的事 | Python 里的对应写法 |
|---|---|
| `=SUM(G2:G1000)` | `sum(值的列表)` |
| 用自动筛选只看"朝阳店" | `[r for r in rows if r["store"] == "朝阳店"]` |
| 数据 → 排序 (降序) | `sorted(rows, key=..., reverse=True)` |
| SUMIF (各门店合计) | 用字典按门店累加 |
| 录制宏 | 脚本文件本身 |

这套对应关系在脑子里扎根之后，"Excel 里我会做，可代码怎么写?"这个问题就变成了"Excel 的这个动作翻译成代码是什么?"。后者好回答得多。

### 3-3. CSV 的陷阱 — 读进来全是字符串

用 `csv.DictReader` 读 CSV，所有值都会以字符串 (str) 形式进来。`"512000"` 看着像数字，其实是字符串，不能直接丢给 `sum()`。所以读完之后必须有一步用 `int()`/`float()` 转换。空格子 (`""`) 转换时会报错，所以要先滤掉。这个"类型还原"的活儿，等到 level04 你会对比出 Pandas 帮你做得有多省事。

### 3-4. "可验证的流程"这个视角

Excel 手工活的产物只留下"数字"。代码的产物是"数字 + 生成这个数字的流程"一起留下。在审计 (audit) 或交接的场合，这个差别是决定性的。本关的 main.py 也被做成会自己汇报跳过了多少条缺失行、负数行。好的数据代码总会告诉你它丢掉了什么。

## 4. 实战 — main.py

运行方法:

```bash
cd zh/lecture03_data_handling/level01_excel_to_python
python3 main.py
```

脚本的流程就是把"Excel 工作的一天"原样翻译成了代码。金额沿用韩元 (KRW) 计价。

- **[1] 存 CSV**: 把 60 天的销售表 (1,500 行) 存到 `outputs/sales.csv`。你也可以直接用 Excel 打开这个文件看看。
- **[2] 读 CSV**: 用 `csv.DictReader` 重新读进来。此时用输出确认所有值都是字符串。
- **[3] 类型还原 + 跳过污染**: 把 `revenue` 转成整数，但跳过空值和负数，并汇报跳过了多少条。
- **[4] SUM**: 全部销售额合计。跟 Excel 的 `=SUM()` 一下子搞定是一回事。
- **[5] SUMIF**: 用字典累加做出各门店合计。
- **[6] 自动筛选**: 只挑"朝阳店 & 周末"的行，和工作日比较销售额平均值。
- **[7] 排序取前 5**: 按降序输出销售额最高的 5 行。
- **[8] 可复现性宣言**: 输出"这个脚本跑 100 次都出同样数字"的原因 (固定 seed + 被记录的流程)。

输出里可以确认: 各门店合计按 朝阳 < 海淀 < 浦东 < 天河 < 南山 的顺序递增 (约 1.26 亿 → 1.92 亿韩元)，周末平均高于工作日 (48.1 万 vs 40.7 万韩元，约 1.18 倍)。埋在数据生成器里的规律被代码准确地揭了出来。这一轮里，1,500 行中跳过了 21 条缺失和 4 条负数，实际使用了 1,475 行。

## 5. 动手试试

1. **(简单)** 参考 [5]，求"各品类"的销售额合计。提示: 把累加字典的键换成 `r["category"]` 就行。
2. **(普通)** 取"后 5 名"而不是前 5 名 (排除负数)。提示: 去掉 `reverse=True`，或者取排序结果的前面部分。
3. **(挑战)** 把结果摘要 (各门店合计) 存成一个新的 CSV 文件 `outputs/summary.csv`。提示: `hjh_data.to_csv` 接收字典列表，所以要做成 `[{"store": s, "total": t} for ...]` 这种形状再传进去。

## 6. 常见错误

- **把从 CSV 读出来的值直接拿去算**: `"500" + "300"` 是 `"500300"`。读完必须先转成数字。
- **把空字符串丢给 `int()`**: 缺失在 CSV 里是存成 `""` 的，而 `int("")` 会抛 `ValueError`。转换前先做空值检查。
- **中文 CSV 在别的程序里显示成乱码**: 这是编码 (encoding) 问题。本课程统一用 UTF-8，详细的应对办法在 level04 讲。
- **用代码把原始文件覆盖掉**: 养成原始文件只读、结果一定存到别的文件 (`outputs/`) 的习惯。这和在 Excel 里忘了"另存为"、直接盖掉原件是同一类错误。
