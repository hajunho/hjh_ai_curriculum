# Lecture 07 · Level 05 — 缩放与流水线 (Pipeline)

> 学两样东西: 把单位五花八门的特征统一到同一把尺子上的缩放 (scaling)，以及把预处理和模型捆成一个整体、从结构上杜绝泄漏的 sklearn Pipeline。
**难度** ⭐⭐⭐ / **先修** level04 / **预计时间** 35分钟

## 1. 为什么要学 — 从业务视角出发

相当一部分数据事故不是出在炫酷的算法上，而是出在**预处理顺序的失误**上。两个代表案例: ① 把测试数据也算进平均·标准差再做缩放 (泄漏); ② 训练时做过的预处理，部署代码里忘了做 (训练-上线不一致)。这两种都会造成"验证时挺好，一上线就不对劲"这类最难排查的故障。

sklearn 的流水线 (Pipeline) 是**从代码结构层面根除**这两种事故的工具。把预处理和模型捆成一个对象后，fit 只会发生在训练数据上，transform 永远按同样的顺序执行。实际工作中互相传递的所谓"模型文件"，传的正是这个流水线对象。站在验收方的角度，一句"预处理放进流水线了吗?"就能掂量出项目的质量。

## 2. 用比喻来理解

**缩放 = 统一单位**。同一场会上，A 团队说"销售额 3 (亿韩元)"，B 团队说"销售额 250,000,000 (韩元)"，只看数字的人会误以为 B 团队的议题重要八千万倍。距离系模型 (KNN 等) 犯的正是这个糊涂。把月费 (9,900~29,900) 和使用天数 (0~30) 放在同一把尺上量，月费差 1 韩元和使用天数差 1 天被当成同样大小，于是月费垄断了距离。标准化 (standardization) 做的就是把所有变量折算成"均值 0、标准差 1"这个通用单位。

**流水线 = 工厂的传送带**。零件 (数据) 一上传送带，清洗 (缩放)→组装 (模型) 永远按同一顺序发生。没有传送带，工人可能忘了清洗，或者把出厂检验用的零件 (测试数据) 混进清洗池的水里 (平均·标准差的计算)。有了传送带，顺序失误从物理上就不可能发生。

## 3. 核心概念

### 3.1 StandardScaler — 标准化

对每一列计算 `(值 − 平均) / 标准差`。结果是"离平均差几个标准差"的无量纲分数。核心规则: **平均和标准差只在训练数据上计算 (fit)，对测试集只套用这套值 (transform)**。把测试集也混进来求平均，测试分布的信息就渗进了训练。

### 3.2 哪些模型需要缩放、哪些无所谓

- **敏感**: KNN、SVM、逻辑/线性回归 (含正则化)、神经网络、K-means — 直接用距离·数值大小的模型
- **迟钝**: 决策树、随机森林、提升树 — 只用"比多少大?"来切分，与单位无关

只用树系模型的话可以省掉缩放，但放进流水线里，将来换模型也安全。

### 3.3 Pipeline 防泄漏的原理

用 `make_pipeline(StandardScaler(), KNeighborsClassifier())` 捆起来之后:

- `pipe.fit(X_train, y_train)` → 缩放器**只用训练数据**学平均·标准差，模型再用变换后的数据训练
- `pipe.predict(X_test)` → 用训练时学到的平均·标准差变换测试集，然后预测

把整条流水线塞进交叉验证 (`cross_val_score(pipe, X, y)`)，缩放器会**在每一折里**只用该折的训练部分重新 fit。如果提前对全量数据做缩放再跑交叉验证，各折验证数据的信息早已进了缩放器 — 这就是预处理泄漏的标准案例。缩放本身泄漏效应不大，但换成目标编码、缺失填补、特征选择这类重度使用答案或分布的预处理，性能可能被大幅吹胀。所以规则统一成一句话: **预处理全部进流水线**。

### 3.4 部署视角的红利

只要保存一个流水线对象，预处理+模型就一起带走了。部署代码里一行 `pipe.predict(新数据)` 即可，"漏做预处理"这类训练-上线不一致从此消失。

### 3.5 流水线能长到多大

今天是"缩放器+模型"两节的传送带，实战流水线会长到五节以上: 缺失填补 → 编码 (level04) → 缩放 → 特征选择 → 模型。用 sklearn 的 `ColumnTransformer` 还能把"数字列做缩放、文字列做独热"这种按列区别对待的处理捆进同一条带子。结构和今天学的一模一样，需要时查个名字就能用。

在 `churn_table` 上用 KNN 预测流失，实验缩放和流水线的效果。

- [1] 确认特征单位: 输出 monthly_fee (几万韩元级) 和 usage_days_30d (0~30) 的尺度差距。
- [2] 不缩放直接 KNN → 月费垄断距离，挑出的风险前 100 名和随机抽取差不多。
- [3] StandardScaler + KNN (流水线) → 同一模型、同一数据，AUC 和"前 100 名中实际流失人数"一起起飞。
- [4] 错误顺序演示: 先对全量数据缩放再交叉验证 vs 把流水线整条放进交叉验证的正确姿势，比较分数，并确认重点不在数字差距而在"结构性安全"。
- [5] 用一个流水线对象预测 3 名新客户的流失概率，演示部署视角的便利。

代码里要看的核心是: `make_pipeline(...)` 造出的对象在 `fit / predict / cross_val_score` 里的用法和普通模型一模一样。学的 API 只有一个，换来的安全装置有三重 (顺序保证、fit 范围保证、部署一体化)。

## 6. 常见错误

- **对测试数据调用 fit_transform**: 测试集只能 `transform`。用了流水线，这个错误从物理上不可能发生。
- **在交叉验证之外提前做缩放**: 折外信息会渗进来。给 `cross_val_score` 要塞整条流水线。
- **因为用树模型就彻底不管缩放**: 现在没错，但哪天把模型换成逻辑回归，性能会悄无声息地塌掉。放进流水线，换模型才安全。
- **缩放后忘了数值的含义**: 标准化后的系数或数值 (-1.2 之类) 不能当原始单位写进报告。解读时要么换算回原单位，要么注明是"标准差单位"。
