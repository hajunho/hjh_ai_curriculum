# Lecture 07 · Level 04 — 类别变量编码

> 用实验比较把"朝阳店"、"咖啡"、"周六"这类文字数据变成模型能吃的数字的三种方法，以及各自的陷阱。
**难度** ⭐⭐⭐ / **先修** level03 / **预计时间** 40分钟

## 1. 为什么要学 — 从业务视角出发

实际工作中一半的数据不是数字。门店名、商品品类、注册渠道、职级、地区 — 全是**类别型 (categorical)** 变量。可绝大多数模型只接收数字输入。把文字变成数字的编码 (encoding)，因此是所有表格数据项目的必经仪式。

问题在于换法不止一种，而且**选错了会给模型注入虚假信息**。把门店名换成 1、2、3，模型就会学到"浦东店(3) 是天河店(1) 的 3 倍"这种根本不存在的排序。反过来，方法选得好，"门店"这一条信息就能把销售预测的准确度拉高一大截。知道哪种编码适合哪种场景，也是一种验收能力 — 你可以对着数据团队的报告问出"为什么这样处理?"。

## 2. 用比喻来理解

想象把问卷里的"职业栏"录入电脑的三种方式。

- **独热编码 (one-hot)**: 给每种职业开一列复选框。"公司职员 ☑ / 个体户 ☐ / 学生 ☐"。完全不会歪曲排序，但职业有 500 种时就得开 500 列。
- **顺序编码 (ordinal)**: 给职业编号。"公司职员=1, 个体户=2, 学生=3"。一列就搞定，可数字大小本无含义，模型却偏要去找含义。不过，如果是"专员<主管<经理<总监"这种**真有排序的类别**，它反而是最诚实的方法。
- **目标编码 (target)**: 不写职业，而写"该职业群体的历史平均逾期率"这种**答案的分组平均**。用一列压缩信息，非常强力; 但因为拿答案当原料，一旦算法不当，答案就会渗进考卷 — 泄漏事故。

## 3. 核心概念

### 3.1 三种编码速览

| 方法 | 列数 | 排序歪曲 | 泄漏风险 | 适用场景 |
|---|---|---|---|---|
| 独热 | 与类别数相同 | 无 | 无 | 类别数不多 (几十个以内) 时的默认选择 |
| 顺序 | 1 | **有** (用在无序类别上时) | 无 | 真有顺序的类别 (等级、职级)、树系模型 |
| 目标 | 1 | 无 | **有** | 高基数 (类别几百~几万个) |

树系模型 (决策树、随机森林) 只把数字当"切分的门槛"用，所以对顺序编码的歪曲相对迟钝。排序歪曲真正致命的，是把数字大小当真的线性模型。

### 3.2 目标编码的泄漏与防御

目标编码的值必须**只用训练数据**计算。把测试集也算进分组平均，测试集的答案就渗进了特征。即使只在训练集内部，也存在"自己那一行的答案反映进自己的特征"的问题，所以实战中会用交叉验证式计算 (排除自己所在的折) 或平滑 (样本少的组向全局平均收缩)。main.py 实现的是最基本的防御: "只用训练数据计算 + 未见过的类别用全局平均"。

### 3.3 高基数 (high cardinality) 问题

客户 ID、商品编码、邮政编码这类有几千到几万个类别的列，独热会引发列爆炸 (维度灾难 + 内存)。这时的选项是: ① 目标编码，② 频次编码 (换成出现次数)，③ 只留前 N 个、其余归并为"其他"，④ 干脆丢掉这一列 (像客户 ID 这种没有泛化信号的，丢掉才是正解)。

### 3.4 未见类别的处理

上线之后，会出现训练时没见过的类别，比如"新开门店"。独热是所有列全为 0，目标编码是用全局平均代替 — **未见 (unseen) 类别策略**必须提前定好，运营中才不会宕机。把 `pd.get_dummies` 分别套在训练/测试上会导致两边列对不上的事故，所以实战的标准做法是把 sklearn 的 `OneHotEncoder(handle_unknown="ignore")` 放进流水线 (level05)。

## 4. 实战 — main.py

```bash
python3 main.py
```

在一年的 `sales_table` 上，用门店·品类·星期预测销售额的线性回归 (Ridge)，只换编码方式训练三次。

- [1] 数据清洗: 删掉缺失·负数销售额的行，确认 3 个类别列各有多少类别。
- [2] 独热: 用 `OneHotEncoder` 看列膨胀到多少个，测性能 (MAE、R²)。
- [3] 顺序: 把类别换成编号。列只有 3 个，但性能崩塌 — 观察排序歪曲的代价。
- [4] 目标: 换成训练数据的分组平均销售额。确认 3 列就能逼近独热的性能。
- [5] 汇总表: 把各方法的"列数 vs 性能"摆在一起，输出高基数场景的选择准则。

核心观察点: 顺序编码的 R² 明显低于独热 (线性模型 + 无序类别的八字不合)，而目标编码用 3 列就填平了大部分差距。

## 5. 动手试试

1. **(简单)** 在 [3] 里换一换给类别编号的顺序 (例: 把 `categories` 顺序倒过来)。性能又变了 — 这就是顺序编码的结果受"编号顺序"这种偶然因素摆布的证据。
2. **(普通)** 把 Ridge 换成 `DecisionTreeRegressor(max_depth=8)` 再比一次三种编码。确认在树模型下顺序编码的性能下滑小得多，并用 3.1 解释原因。
3. **(挑战)** 亲手实现"频次编码" (把每个类别换成它在训练数据中的出现次数)，作为第四位选手参战。提示: `value_counts()` 配 `map`，两行搞定。

## 6. 常见错误

- **随手给无序类别编号**: 最常见的事故是把 Excel 里已经编成"北京=1, 上海=2"的数据直接喂给模型。用线性模型的话，务必展开成独热。
- **用全量数据计算目标编码**: 验证性能突然变好，先别高兴，先怀疑泄漏。计算永远只用训练数据。
- **get_dummies 分别套在训练/测试上**: 两边列构成不一致，部署时爆炸。`OneHotEncoder(handle_unknown="ignore")` + 流水线才是正解。
- **对客户 ID 做目标编码后性能"提升"**: 每个客户没几行数据时，分组平均实际上就是答案的复印件。ID 类的列原则上剔除。
