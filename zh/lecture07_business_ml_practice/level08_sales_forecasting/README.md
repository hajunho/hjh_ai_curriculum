# Lecture 07 · Level 08 — 实战 1: 销售需求预测

> 用咖啡连锁店一年的销售额，搭一条预测"下一周每日销售额"的完整流水线。主角是星期·季节·移动平均特征，以及基于时间的划分。
**难度** ⭐⭐⭐⭐ / **先修** level03、level06 / **预计时间** 50分钟

## 1. 为什么要学 — 从业务视角出发

"下周销售额大概多少?"是所有行业的共同问题。答案不同，进货量、排班表、现金流计划就都不同。预测偏差 10%，马上就变成库存报废或缺货、人员过剩或排长队——全是成本。

需求预测不是分类，而是**回归 (regression)**；而且数据里有**时间轴**，这让它和前面所有问题的性质都不一样。有时间轴，两件事就会变。第一，特征的主力变成"星期·季节·近期趋势"这类时间衍生特征。第二，验证规则变了——必须用过去训练、用未来考试 (level06 [4] 见过的那个陷阱)。这一关就是具备这两点的**第一个从头跑到尾的实战项目**。

## 2. 用比喻来理解

把一位老练的咖啡店店长的脑子搬出来看看。他定下周进货量的时候，大致是这样想的。

1. "最近一天平均卖多少?" → **移动平均** (近期趋势)
2. "下周六应该和平常周六卖得差不多" → **星期效应**
3. "夏天要来了，饮品会涨" → **季节效应**
4. "昨天突然卖得很多，明天会不会有余温?" → **前一日销售额 (lag)**

机器学习的需求预测，就是把这四种直觉各做成一个数字列喂给模型。模型不是靠魔法看见未来，而是**把店长的直觉翻译成特征，再一致地、大批量地、每天自动地**套用——这才是本质。所以这一关的代码大部分不花在模型上，而花在造特征上。

## 3. 核心概念

### 3.1 时间序列特征三大主力

- **日历特征**: 星期 (独热或周末标记)、月份、是否节假日。装的是反复出现的规律。
- **滞后 (lag) 特征**: `lag_1` (前一日)、`lag_7` (一周前的同一天)。装的是"最近怎么样"。
- **移动平均 (rolling mean)**: 近 7 天均值、28 天均值。装的是滤掉噪声后的趋势。

注意: lag 和移动平均必须**只用预测时点之前的值**，也就是先 `shift(1)` 再计算。预测今天销售额时用了包含今天销售额的移动平均，就是抄答案的泄漏。

### 3.2 把季节性变成数字 — sin/cos 变换

直接把"一年中的第几天 (1~365)"塞进去，12 月 31 日 (365) 和 1 月 1 日 (1) 看起来就是天南地北。换成 `sin(2π·day/365)`、`cos(2π·day/365)` 两列，年末和年初就自然成了邻居，变成一本圆形日历。星期也能这么做，但只有 7 种，所以独热更常见。

### 3.3 基于时间的划分与基准线

- **划分**: 最后几周当测试集 (= 复现即将到来的那一周的处境)，之前的当训练集。禁止随机划分。评估区间太短 (例如 7 天) 名次就会被手气左右，所以实务里要用横跨好几周的回测来评估。
- **基准线 (baseline)**: 模型必须跨过的最低线。需求预测的惯例基准线是 ① "和昨天一样" (naive)、② "和上周同一天一样" (seasonal naive)。连这种简单规则都赢不了的模型，没有上线的理由。实务报告里也一定要用相对基准线的改善率说话。

### 3.4 评估指标 — MAE 与 MAPE

- **MAE** (平均绝对误差): "平均每天偏 N 韩元"。单位是韩元，很直观。
- **MAPE** (平均绝对百分比误差): "平均偏 N%"。比较规模不同的门店时很好用，但实际值接近 0 时会爆炸，要小心。

## 4. 实战 — main.py

```bash
python3 main.py
```

- [1] 把 `sales_table` 一年的数据清洗 (去掉缺失和负数)，再汇总成每日总销售额。
- [2] 特征生成: 星期独热、周末标记、季节 sin/cos、lag_7 (上周同一天)、7 天/28 天移动平均 (全部以 7 天前为基准 — 只用预测时点能知道的值)。
- [3] 基于时间的划分: 把最后 4 周 (28 天) 封存为评估区间。只用 7 天的话运气成分太多，所以按"每周更新一次预测"的运营方式做 4 周回测。
- [4] 在 4 周回测上，把两种基准线 (和昨天一样 / 和上周同一天一样) 与 RandomForest 回归的 MAE·MAPE 摆在一起比。
- [5] 逐日输出'下一周' (最后 7 天) 的预测 vs 实际，并把近 8 周走势和预测区间画成 PNG 存到 `outputs/`。
- [6] 用特征重要性确认"模型是看着什么做预测的"。

观察要点: 基准线 (尤其是 seasonal naive) 比想象中强，以及模型的改善量来自哪里 (星期+趋势的结合)。看看 PNG 里预测线有没有跟上实际的星期节奏。

## 5. 动手试试

1. **(简单)** 换一换评估区间 (`BACKTEST_DAYS = 7`、`56`)。7 天评估里基准线有时会赢 — 请再确认一次 level06 的教训: 评估区间越短，名次越被手气左右。
2. **(普通)** 把 lag_14 (两周前的同一天) 和 lag_28 加进特征。MAE 有改善吗? 特征重要性的排名怎么变?
3. **(挑战)** 不用总销售额，改成"只取饮品品类"的每日销售额跑同一条流水线。季节 sin/cos 的重要性会明显上升 —— 看看这是否和"夏天是饮品旺季"这个领域知识吻合。

## 6. 常见错误

- **用随机划分做验证**: 时间序列第一禁忌。分数看着漂亮，实战一塌糊涂。划分永远按时间顺序。
- **移动平均里含了今天**: `rolling(7).mean()` 不加 `shift(1)`，今天的值就进了今天的特征。安静的泄漏里的老熟客。
- **不给基准线就汇报"MAE 50 万韩元"**: 这数字是好是坏没人知道。要像"相对'和昨天一样'改善 23%"那样用相对改善来汇报。
- **一口气预测很远的未来**: lag 特征是给提前一天用的。想预测 7 天后，就得明确设计: 要么把预测值再当输入的递归方式，要么只用 7 天前 lag 的直接方式 (main.py 是只用 lag_7·移动平均等"7 天前为止的信息"的直接方式)。
- **忽略节假日和促销**: 真实数据里最大的误差都出在特殊日。把特殊日日历做成特征，实务精度的一半就到手了。
