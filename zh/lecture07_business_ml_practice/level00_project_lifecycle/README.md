# Lecture 07 · Level 00 — 数据项目的完整流程

> 把"问题定义→数据→模型→部署→监控"这张五阶段地图装进脑子，并提前学习"失败项目的共同点"。
**难度** ⭐ / **先修** lecture06 level00~02 / **预计时间** 25分钟

## 1. 为什么要学 — 从业务视角出发

机器学习项目失败的头号原因不是模型。业界反复上演的失败故事，绝大多数是"一开始就没就'到底要预测什么'达成一致"、"数据根本回答不了那个问题"、"做出来了却没人用"。也就是说，失败发生在写代码之前和之后的阶段，而不是写代码的阶段。

作为非科班出身的你，需要这张地图的理由非常明确: 在实际工作中，你的角色不是写模型代码，而是判断项目当前处在五个阶段中的哪一个、应该在哪道关口 (gate) 停下来。无论你是发包方、业务负责人还是验收人，有了这张地图，你在会议上该问的问题都会不一样。

## 2. 用比喻来理解

数据项目和**开餐馆**惊人地相似。

1. **问题定义 = 选商圈、定菜单**: 抱着"只要做得好吃就行"开张的餐馆会倒闭。得先定好卖给谁 (目标客群)、卖什么 (菜单)、卖到什么程度算成功 (成功标准)。
2. **数据 = 采购食材**: 再厉害的大厨也没法用变质的食材做菜。跳过食材验收 (数据质量检查)，后厨 (模型) 一定出事故。
3. **模型 = 烹饪**: 只占全部工作的 20% 左右。就像开店筹备的大头并不是做菜本身一样，项目的大部分时间花在前后两头。
4. **部署 = 开业**: 菜做好了，如果没有端到客人面前的动线 (和现有业务系统的衔接)，谁也吃不到。
5. **监控 = 维护回头客**: 开业第一天的味道不会永远保持。食材行情 (数据分布) 变了，菜谱就得跟着调整。

"只要模型做得好就行"这个想法之所以危险，和"只要菜做得好餐馆就能成"是同一个道理。

## 3. 核心概念

### 3.1 五个阶段与各阶段的产出物

| 阶段 | 核心问题 | 代表性产出物 |
|---|---|---|
| ① 问题定义 | 预测什么、为什么、成功标准是? | 问题说明书 (预测对象·使用方式·目标指标) |
| ② 数据 | 有能回答这个问题的数据吗? | 数据审计报告 (行数·缺失·目标比例) |
| ③ 模型 | 比基准线 (baseline) 好吗? | 经过验证的性能报告 (含交叉验证) |
| ④ 部署 | 业务方真的能用吗? | 与业务流程的衔接 (例: 每周自动发送高风险客户名单) |
| ⑤ 监控 | 性能还保持着吗? | 性能看板、重训标准 |

关键在于，每两个阶段之间都有一道**关口**。过不了关口，就不要进入下一阶段，而应该停下或退回。例如: 数据审计发现流失客户样本只有 50 人，那正确答案是去多收集数据，而不是硬闯模型阶段。

### 3.2 失败项目的共同点

- **没有目标指标**: 以"用 AI 搞点什么吧"开局，做出什么都无法判定是成功还是失败。
- **标签质量差**: 如果"流失"的定义各部门不统一 (提交退订申请? 3 个月未登录?)，模型学到的就是彼此不同的问题。
- **没有基准线就开工**: "预测下个月和上个月一样"这种简单规则都打不过的模型被部署上线 — 这种事真的会发生。
- **没有部署计划**: 谁来接收模型吐出的概率数字、进哪个系统、走什么业务流程都没定，就先开发了。
- **没有监控**: 遇到疫情这类环境变化、数据分布发生偏移 (data drift) 时，没有任何人察觉。

### 3.3 时间分配的现实

教科书用大量篇幅讲模型，但实际工作中的时间分配大致是"问题定义·数据 60~70%，模型 10~20%，部署·监控 20~30%"。这门课的关卡编排 (8 个零件 + 4 个实战) 也正是照这个现实设计的。

## 4. 实战 — main.py

```bash
python3 main.py
```

main.py 是一场模拟: 让虚构项目"订阅流失防御"依次通过五道阶段关口。

- [1] 问题定义: 检查说明书条目 (预测对象、使用方式、目标指标) 是否填齐，并输出关口判定。
- [2] 数据: 实际调用 `hjh_data.churn_table()`，审计行数、缺失、目标比例，并通过"少数类样本是否足够"这道关口。
- [3] 模型: 还没学建模，所以先计算"多数票基准线"的准确率，确认之后的模型必须跨过的那条线。
- [4]~[5] 部署·监控: 故意留下几项空白的检查清单，观察关口给出"STOP"判定的样子。

在输出末尾的汇总表里，确认哪个阶段是 PASS、哪个阶段是 STOP。代码的核心是 `gate()` 函数: 接收各阶段的检查项列表，只要有一项为空就不放行 — 逻辑极其简单，却是实际工作中最常被省略的一步。

## 5. 动手试试

1. **(简单)** 把 [4] 部署阶段检查清单里空着的项 (`""`) 填上真实的计划语句，重新运行，确认判定变成 PASS。
2. **(普通)** 把 `min_minority` 调高到 500，数据关口会变成 STOP。这时实干者应该权衡哪些选项 (延长收集周期、放宽定义、暂缓项目)? 参考 README 3.1 写下来。
3. **(挑战)** 从你的公司 (或想象中的公司) 挑一个问题，亲手写出 [1] 问题定义的字典。关键在于"目标指标"能不能写成数字。提示: "降低流失率" (×) → "6 个月内把月流失率从 18% 降到 15%" (✓)。

## 6. 常见错误

- **先定模型再往上套问题**: "试试最近很火的那个技术"就像还没定菜单先买烤箱。
- **无脑把准确率当成功标准**: 在流失率 18% 的数据上，光喊"没人会流失"准确率就有 82%。没有基准线的准确率只是数字装饰。
- **把一次性分析和运营系统混为一谈**: 写完一份报告就结束的分析，和每周都要跑的系统，需求完全不同。开工前先谈妥是哪一种。
- **凭感情做关口判定**: "都做到这儿了，放弃多可惜" — 这是沉没成本在说话。关口要靠检查清单，机械地判。
