# Lecture 07 · Level 03 — 特征工程

> 数据相同、模型相同，特征怎么捏，性能就怎么变。我们让"原始特征 vs 衍生特征"用同一个模型同台竞技，证明它的威力。
**难度** ⭐⭐⭐ / **先修** level02、lecture06 level05 / **预计时间** 40分钟

## 1. 为什么要学 — 从业务视角出发

无论在 Kaggle (竞赛) 还是在公司里，决定预测性能的通常不是模型的种类，而是**特征 (feature, 输入变量) 的质量**。而打造好特征的原材料不是数学，是**领域知识** — 懂那摊业务的人的直觉。

"凌晨在境外被连续刷的卡很可疑" — 这是信用卡审核员人人皆知的常识。可数据里只有 `hour=2`、`is_foreign=1`、`tx_count_1h=9` 这些零散数字，并没有一列叫"可疑模式"。把这条常识翻译成模型咽得下去的数字列，就是特征工程; 这也是非科班业务人员对数据项目能做出的最大贡献。代码可以让数据团队写，但"该造哪些特征"只有业务方知道。

## 2. 用比喻来理解

模型是个**只吃你端上来的东西的挑食审核员**。想象给信贷审核员递材料:

- 原始数据: "月收入 400 万韩元"、"月还贷额 180 万韩元" — 两个数字分开看，很难下判断。
- 衍生特征: "还贷占收入比 45%" — 不过做了一次除法，判断一眼就出来了。

人类审核员会在脑子里自动做这个除法，但线性模型自己造不出除法 (它只会加法和乘常数)。所以得由人提前做好比率、差值、分箱这些列，把菜"料理成好消化的形状"端上桌。用做菜打比方，特征工程就是食材预处理。扔给厨师一条没收拾的整鱼，再好的厨师 (模型) 也施展不开。

## 3. 核心概念

### 3.1 衍生特征的代表性配方

| 配方 | 例子 | 什么时候用 |
|---|---|---|
| 比率 (ratio) | 还贷额/收入、使用天数/入网月数 | 两个数的相对关系重要时 |
| 差值 (diff) | 本月 − 上月使用量 | 变化·趋势是信号时 |
| 对数变换 | log(交易金额) | 金额这类严重偏斜的分布 |
| 分箱·标志位 | 是否凌晨时段 (is_night) | "区间"本身有含义时 |
| 交互项 | 境外 × 凌晨 | 条件叠加才危险的模式 |
| 聚合 (aggregate) | 每客户最近 30 天平均支付额 | 把交易级数据汇总到客户级 |

其中对数变换是金额数据的常客。它把 1 万韩元和 2 万韩元的差距 (2 倍) 与 1 亿和 2 亿的差距 (2 倍) 变成同样的刻度，让线性模型能够用"倍率"的语言思考。

### 3.2 灵感从哪来 — EDA 与业务访谈

level02 的双变量分析就是现成的原料清单。看到"欺诈交易扎堆在凌晨"，就造 `is_night` 标志位; 看到"金额分布严重偏斜"，就上对数变换。再加上业务访谈 ("你们平时看到什么会觉得可疑?")，特征候选清单就齐了。

### 3.3 数据泄漏 (data leakage) — 特征工程的头号陷阱

造衍生特征的时候，一不小心就会把**未来的信息**或**答案的影子**混进特征里。

- 用"是否退款"预测流失: 退款发生在流失**之后** — 预测时点根本不知道这个值。
- 用全量数据 (含测试集) 的平均值计算衍生特征: 测试集信息渗进了训练。
- 用"调查结果代码"预测欺诈: 调查是被**判定为欺诈之后**才做的事。

判别问题只有一个: **"在需要做预测的那个时点，这个值知道吗?"** 答案是"不知道"，那不管性能多好都得扔。泄漏特征是最恶劣的 bug: 验证性能好得梦幻，上了实战一文不值。

### 3.4 性能比较必须公平

要主张衍生特征有效，必须**把模型、数据划分、评估指标全部钉死**，只换特征清单。main.py 做的正是这个对照实验。

## 4. 实战 — main.py

```bash
python3 main.py
```

用 `fraud_table` 的 5,000 笔交易训练两次欺诈检测模型。"原始"指支付授权瞬间就随报文送达的 3 个字段 (amount、hour、is_foreign)。

- [1] 加载数据，确认 3 个原始特征。
- [2] 基于领域知识造 3 个衍生特征: `log_amount` (对数变换)、`is_night` (凌晨标志)、`foreign_night` (境外×凌晨交互项)。
- [3] 用同一个逻辑回归、同一份划分，训练"仅原始" vs "原始+衍生"，比较 AUC 和 PR-AUC (平均精确率)。
- [4] 输出衍生特征组模型的系数，看哪些特征在干活。
- [5] 泄漏演示: 塞进一个偷偷掺了答案的假特征，性能会飙到不真实的高度，并输出警告。

重点看 [3] 的 PR-AUC 对比。模型一个字都没改，性能却跳了一截 — 这就是特征的威力。[5] 里"好得过分的性能就是 bug"这份直觉也请一并带走。

## 5. 动手试试

1. **(简单)** 每次去掉一个衍生特征再运行，看哪个特征对性能贡献最大。提示: 从 `DERIVED` 列表里逐个删。
2. **(普通)** 让聚合特征参战。把表里的 `tx_count_1h` (最近 1 小时交易笔数 — 需要聚合交易历史才能得到的值) 和比率特征 `amount_per_tx = amount / (tx_count_1h + 1)` 加进 DERIVED，PR-AUC 能冲到多少? 体会一下为什么"聚合特征是常年的王牌"。
3. **(挑战)** 用 churn_table 设计同样的实验。候选: `usage_days_30d / tenure_months` (相对入网时长的活跃度)、`support_calls_30d - plan_changes` 等。确认哪些特征的系数方向和领域常识一致。

## 6. 常见错误

- **省略预测时点检查**: 不对每个特征问一句"预测时点知道这个值吗?"，泄漏必然发生。请在特征清单旁边加一列"生成时点"来管理。
- **无限堆特征**: 特征不是越多越好。特征相对样本太多就会过拟合 (lecture06 level09)。造出来→验证→没贡献就扔。
- **除以零**: 比率特征的常见事故。给分母加 1 (main.py 的做法) 或做条件处理。
- **把测试数据算进统计特征**: "相对全体平均的比率"这类特征，必须只用训练数据的统计量来造。level05 的流水线会从结构上解决这个问题。
