# Lecture 06 · Level 02 — 把业务问题转化为 ML 问题

> 学会把"想降低流失"这个愿望，翻译成机器能解的说明书 (预测什么、以谁为单位、以什么时点为准、用什么指标衡量)。

**难度** ⭐⭐ / **先修** level01 / **预计时间** 35分钟

## 1. 为什么要学 — 从业务视角出发

机器学习项目失败最常见的原因不是模型差，而是**开工之前问题定义就没做**。"想降低流失"是很好的经营目标，但没法直接派给机器。流失到底是什么? 3 个月没登录? 点了退订按钮? 以谁为单位预测 —— 客户? 账户? 整个家庭套餐? 在什么时点预测 —— 每月 1 号? 你知道那个时点只能用当时已知的信息吗?

这项翻译工作不是写代码，所以业务人员反而可能比数据科学家做得更好。而这里一旦跑偏，后面的任何建模都是白费。这一关是整门课里唯一"不建模"的一关，但论实战价值，可能是最大的一关。

## 2. 用比喻来理解

**ML 的问题定义就像写外包委托书。** 对装修公司说"把家里弄漂亮点"，结果全凭运气。好的委托书不一样: 哪个房间 (单位)、什么时候完工 (时点)、什么风格 (对象)、预算和验收标准是什么 (指标)、装完打算怎么用 (行动)，全都写着。

机器学习模型也是一家没法沟通的外包公司。委托书 (问题说明书) 一含糊，它就会勤勤恳恳地做出个不着边际的东西。尤其可怕的是: **模型不会反问委托书里的漏洞。** 如果你漏掉了"不能把预测时点还不存在的信息当材料"这个条件，模型会偷偷用上那些信息，交付一件只有考试成绩漂亮的假名牌 (这叫泄漏, leakage)。

## 3. 核心概念

### 3-1. ML 说明书的五要素

把业务问题转成 ML 问题时必须回答的五件事。

1. **预测对象 (target)**: 到底预测什么? 要写成可度量的定义。—— "流失" → "以本月底为基准，未来 30 天内退订 (1/0)"
2. **预测单位 (unit)**: 一行 (记录) 是什么? —— 1 位客户? 1 个账户? 1 笔订单? 1 家门店的一天?
3. **预测时点 (timing)**: 什么时候按下预测按钮? 那个时点**实际能拿到的信息**才可以当材料。—— 违反时点就发生泄漏。
4. **评估指标 (metric)**: 用什么衡量预测得好不好? 这个指标和业务盈亏挂钩吗? —— 流失预测该看召回率、精确率而不是准确率 (level06)。
5. **行动 (action)**: 预测结果出来后做什么? —— "给风险最高的前 10% 客户打挽留电话"。**没有行动的预测就是摆设。** 行动定了，"前 10%"这样的模型输出形式才随之确定。

在实务中还要加上**基线 (baseline)** —— "不上模型、按现在的做法 (直觉、规则) 干，成绩是多少"。赢不了基线的模型没有上线的理由。

### 3-2. 能解的问题 vs 解不了的问题

即使按同样的格式写下来，也有 ML 能解和不能解的问题。

**能解的问题的条件**: (a) 过去反复发生过类似的事，并留有数据；(b) 输入和结果之间说得通存在规律；(c) 能拿到正确答案 (标签)；(d) 允许一定误差，行动仍然成立。

**解不了的问题的信号**: 正确答案的数据只有几十条 ("预测本公司 10 年来 M&A 的成败")；规则已经 100% 明确 (增值税计算 — level00)；就算预测出来也没有可执行的行动；过去的规律难以延续到未来 (制度刚刚大改之后)；人命或法律责任在身、误差容忍度为零。

### 3-3. 泄漏 (leakage) — 偷看未来的材料

审查说明书时最要上心的一项。例: "退订违约金账单金额"这一列几乎能完美预测流失 —— 因为只有退订的人才会被开账单。但在预测时点 (月初) 这个信息还不存在。训练数据里有、预测时点却没有的列，或者结果确定之后才被填上的列，一律要怀疑。判别问题只有一个: **"按下预测按钮的那一刻，这个值能拿到吗?"**

### 3-4. 说明书是一份反复打磨的文档

第一版说明书通常是错的。比如定义成"30 天内退订"之后才发现，扣款周期是 45 天的客户全被算成了流失 —— 这类问题都是看着数据才暴露出来的。说明书→核对数据→修改说明书的往返，才是正常流程。

## 4. 实战 — main.py

运行:

```bash
python3 main.py
```

这个程序是一台**检查清单引擎**。把 ML 说明书写成 Python 数据结构，它就自动检查: 五要素填齐了吗、有没有泄漏风险、这问题适不适合 ML，并打出分数。

- **[1]** 把"想降低流失"原封不动地写成一份烂说明书 (到处空白) 送去检查 → 收获一堆指出空白的批注。
- **[2]** 把同一个愿望补成一份好说明书再检查 → 借通过的过程掌握五要素。
- **[3]** 泄漏风险检查: 送入一份材料清单里混进"退订违约金账单金额"的说明书，看引擎能否抓出来 (检测预测时点之后才产生的列)。
- **[4]** 对 4 个候选问题 (需求预测、增值税计算、M&A 成败预测、异常交易检测) 按"能解/不能解"的标准自动分类并输出理由。

代码核心是 `MLSpec` 数据类和 `validate()` 函数。每条检查规则都与第 3 节的概念一一对应，请对照输出和代码来回读。这份清单在真实会议上照抄到白板上都行。

## 5. 动手试试

1. **(简单)** 把 [2] 好说明书里的 `action` 改成空字符串再运行。引擎批注了什么? 找找"没有行动的预测就是摆设"这条规则是怎么写成代码的。
2. **(普通)** 把你工作里的一个真实困扰写成 `MLSpec` 送进 `validate()`。五要素里哪个最难填? (经验上是 timing 和 action。)
3. **(挑战)** 给 `check_leakage()` 加一条新规则: 材料名称里含"满意度调查"且调查时点晚于预测时点就发出警告。(提示: 比较 `available_at` 字段)

## 6. 常见错误

- **把目标和预测对象混为一谈**: 目标是"降低流失" (业务)，预测对象是"30 天内是否退订" (ML)。模型只做后者。降低流失要靠预测+行动 (回访、优惠) 一起完成。
- **不假思索地把指标写成准确率**: 在流失率 15% 的数据上，硬说"全员都会留存"也有 85% 的准确率。指标选择在 level06 深入讲。
- **把泄漏列当成性能提升**: 考试成绩突然好得反常，先别高兴，先怀疑泄漏。
- **想一次写出完美说明书**: 说明书是看着数据反复改写的活文档。
