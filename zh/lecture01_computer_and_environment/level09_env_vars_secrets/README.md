# Lecture 01 · Level 09 — 安全地管理环境变量与密钥

> 理解为什么把 API 密钥、密码写进代码会出事故，并用环境变量和 .env 模式养成把秘密放在代码之外管理的习惯。

**难度** ⭐⭐⭐ / **先修** level06 / **预计时间** 40分钟

## 1. 为什么要学 — 从业务视角出发

有一类事故在现实中反复上演: 开发者把云服务的接入密钥写在代码里，push 到了 GitHub 公开仓库。互联网上有 24 小时扫荡公开仓库的收割机器人，**几分钟之内**那把钥匙就落入贼手。贼用它租下一大批高性能服务器挖虚拟货币，下个月公司就收到几十万元的账单。这不是夸张，而是业界真实反复发生的模式。

到了 AI 时代，风险更大了。一把 LLM API 密钥就能无限制地发起付费调用; 公司数据库密码一旦泄露，就会演变成客户信息外泄。所以"不把秘密写进代码"是开发安全的第一守则，也是安全审计最先检查的项目。幸好解法并不难: **秘密通过环境变量注入，代码只按名字引用** — 把这一句话练进肌肉记忆，就是这一关的全部。

## 2. 用比喻来理解

**写在代码里的密码，等于贴在大门上的保险柜密码便条**。

代码会被到处复制、被分享、被永久记录在仓库里 (level06 学过，Git 历史抹不掉)。往这样的文件里写保险柜号码，就等于把号码写在每次搬家都会跟着走的大门便条上。

**环境变量 (environment variable) 可以理解成公司的储物柜钥匙制度**。工作手册 (代码) 里只写"保险柜钥匙在各自的储物柜里"。真正的钥匙 (秘密值) 放在每位员工的储物柜 (每台电脑的环境变量) 里。手册就算外泄，钥匙也安全，而且每位员工 (开发用/生产用服务器) 可以用不同的钥匙。

环境变量就是操作系统递给每个程序的一沓"名字=值"便签。其实你已经在用了 — level03 的 PATH 正是环境变量。往里面加一条 `OPENWEATHER_API_KEY=abc123`，代码就可以用 `os.environ["OPENWEATHER_API_KEY"]` **只喊名字**把值取来。代码的任何角落都不出现真实值。

## 3. 核心概念

### 3-1. 读写环境变量

```bash
# 在 Shell 里设置 (只在这个终端窗口活着期间有效)
export MY_API_KEY="sk-demo-1234"
python3 app.py
```

```python
import os
key = os.environ.get("MY_API_KEY")        # 不存在则 None (安全读法)
key = os.environ["MY_API_KEY"]            # 不存在则报错 (必填值时用)
```

关掉终端就没了，所以常用的值可以把 export 写进 Shell 配置文件 (`~/.zshrc` 等)，按项目管理则用下面的 .env 模式。

### 3-2. .env 文件模式

在项目文件夹里建一个叫 `.env` 的文件，把秘密集中放进去。

```
# .env — 这个文件绝对不上 Git!
DB_PASSWORD=s3cret!
LLM_API_KEY=sk-demo-abcd1234
```

然后**务必把 `.env` 加进 `.gitignore`**。这两行是一套的，缺一不可。运行时读取这个文件、把内容抬进环境变量的工具 (python-dotenv 包) 已是事实标准，但文件格式很简单，这一关的实战我们自己写一个解析器来验证原理。为了同事，可以往仓库里放一份把值留空的样板 `.env.example` (`DB_PASSWORD=在这里填写`)，只共享"需要哪些名字的秘密"。

### 3-3. 防泄露的三重防线

1. **预防**: 秘密只放 .env/环境变量。代码、提交信息、聊天里都不写值本身。
2. **检测**: 提交前扫描有没有硬编码的秘密。实际工作中由提交钩子或 CI 自动检查; 这一关的实战里我们亲手做一个迷你扫描器看原理。以 `sk-` 开头的长字符串、`password = "..."` 模式等都是线索。
3. **事后处置**: 一旦泄露，**立即作废并重新签发密钥**是唯一解。就算删了提交，也要假定历史、fork、机器人的收割副本里已经留了底。

### 3-4. 输出时要打码

秘密值在日志和屏幕上也不整个打印。需要确认时，按惯例做**掩码 (masking)**，只留前后几位、像 `sk-d****1234` 这样遮住。把"值设没设"和"值是什么"分开，只展示前者。

## 4. 实战 — main.py

```bash
python3 main.py
```

依次演示三样工具。所有值都是实战用的假值，不联网。

- **[1] 读环境变量**: 设置实战用变量并用 `os.environ` 读取。顺带演示用 `.get()` 安全读取不存在的变量、查看 PATH 这类已有变量。
- **[2] 掩码输出**: 用 `mask()` 函数把秘密值遮成 `sk-d****5678`，学会"只报告设没设"的技巧。
- **[3] .env 解析器**: 亲手解析"名字=值"格式的 .env 文本、抬进环境变量的迷你实现，验证 dotenv 工具的原理。
- **[4] 硬编码扫描器**: 准备一份故意嵌着秘密的坏示例代码和一份使用环境变量的好示例代码，用正则规则 (API 密钥的长相、password= 模式等) 跑一个只对坏代码报警的扫描器。
- **[5] 守则总结**: 把三重防线打印成清单。

核心代码是 `scan_for_secrets()`。它把"秘密有着特定的**长相** (模式)"这条观察翻译成几行正则表达式 — 真实安全工具的基本原理正是如此。

## 5. 动手试试

1. **(简单)** 在终端里 `export PRACTICE_KEY="hello123"` 之后运行 `python3 main.py`，确认 [1] 步骤发现了这个变量。*(提示: 必须在 export 过的那个终端窗口里运行。)*
2. **(普通)** 往 [4] 的坏示例代码里加一行 `token = "ghp_aaaa1111bbbb2222"`，看看扫描器抓不抓得到。抓不到的话，往 `SECRET_PATTERNS` 里加一条匹配 `ghp_` 开头的模式规则。*(提示: 照着现有的 `sk-` 模式仿写即可。)*
3. **(挑战)** 修改 `mask()` 函数，让不足 8 位的短秘密一律只显示成 `****`。因为短值光靠前后几个字符就可能被猜出来。*(提示: 用 `len(value)` 分支。)*

## 6. 常见错误

- **"私有仓库所以没事"**: 仓库总有一天会公开，或者因为离职、外包而访问者变多。无论公开与否，秘密放在代码之外才是原则。
- **建了 .env 却忘了 .gitignore**: 最常见的惨案路线。创建 `.env` 和添加 `.gitignore` 务必当成一套动作。
- **泄露后只删提交**: 历史、fork、机器人早就复制走了。重新签发密钥是唯一解。
- **报错信息和日志里混出秘密**: 调试时像 `print(config)` 这样把整份配置打出来，秘密也会跟着出来。让打码成为习惯。
- **往样板文件 (.env.example) 里填真值并提交**: 样板里只能放占位文本。
