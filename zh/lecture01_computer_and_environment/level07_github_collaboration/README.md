# Lecture 01 · Level 07 — GitHub — 远程仓库与协作

> 理解远程仓库 (clone/push/pull) 和 Pull Request 协作流程，并且不用联网、把本地 bare 仓库当作"假 GitHub"来实战 push/pull。

**难度** ⭐⭐ / **先修** level06 / **预计时间** 45分钟

## 1. 为什么要学 — 从业务视角出发

level06 建的审批档案柜 (仓库) 只存在于我自己的电脑里。笔记本一坏，连历史一起报销; 团队成员也看不到我的档案柜。所以需要**远程仓库 (remote repository)** — 一只所有人都能访问的中央档案柜。而出借这只中央档案柜的全球最大服务，就是 **GitHub**。

GitHub 是开发者的协作场所兼简历，也是全世界开源项目汇聚的广场。对非开发者同样意义重大: 你能看懂公司的开发产出在哪里、如何被管理; 听懂开发团队说"PR 还在评审，上线要晚一点"是什么意思; 引入外部开源工具时，也能判断那个项目健不健康 (最近的提交、issue 响应)。学完这一关，push/pull/PR 这些词你就开始听得懂了，远程协作的全貌也就成形了。

## 2. 用比喻来理解

**远程仓库是总部中央档案馆，我的仓库是分公司档案柜**。

- **clone (克隆)**: 新任分公司经理上任时**把中央档案馆整个复制**一份带到分公司。连历史一起复制，之后分公司就能独立干活。
- **push (推送)**: 把分公司审批过的文件 (提交) **送上总部档案馆**、变成正式记录。
- **pull (拉取)**: 把其他分公司送上去的最新文件**从总部取回来**，让自己分公司的档案柜跟上最新状态。
- **Pull Request (PR)**: 一份"请把我的修改方案并入正传"的**正式签报**。修改内容由同事评审 (review)，批准后并入正传 (main) — 即 merge。签报下面有讨论留言、有修改要求来回，整个过程全部留档。

流程一句话总结: **clone 开局 → 在分支上干活 → push 上传 → PR 接受评审 → 并入 main → 同事们 pull 更新**。

一个有趣的事实: 总部档案馆 (远程仓库) 里没有供人办公的桌子。这种没有工作文件夹、只保管历史的仓库叫 **bare 仓库**，GitHub 的服务器实际上就是这种形态。今天的实战会在自己电脑里造一个 bare 仓库当"假 GitHub" — 不联网，push/pull 的原理也完全一样。

## 3. 核心概念

### 3-1. 远程协作命令五条

```bash
git clone <地址>          # 整个复制远程仓库来开局
git remote -v             # 查看我的仓库连着哪个远程 (别名 origin)
git push origin main      # 把我的提交送上远程的 main
git pull origin main      # 取回远程的新提交并合并
git fetch                 # 只取回、不合并 (先预览)
```

`origin` 是 clone 来的远程仓库自动获得的别名，读作"总部"就行。

### 3-2. GitHub 提供什么

Git 是工具 (程序)，GitHub 是出借这个工具用的中央仓库的**服务** (类似的还有 GitLab、Bitbucket 等)。GitHub 在仓库托管之上叠加了协作功能: PR 评审、issue (待办和 bug 的公告板)、wiki，以及在提交和 PR 时自动跑测试的自动化 (CI) 等。公司里通常用**私有 (private) 仓库**，开源项目则用**公开 (public) 仓库**与世界分享代码。

### 3-3. 冲突 (conflict) — 协作的成人礼

两家分公司把**同一个文件的同一个部分**改成了不同的样子并都上传时，Git 不会替你判断谁对，而是来问人。这就是冲突。文件里会用 `<<<<<<<`、`=======`、`>>>>>>>` 标记把双方内容并排摆出来，由人改成想要的那边 (或第三种折中方案) 后重新提交即可解决。样子吓人，实质只是一句礼貌的提问: "两份修改方案都给您摆好了，请定夺。" 减少冲突的诀窍是**勤 pull、小步勤 push**。

### 3-4. 协作礼仪

- 不直接往 main 分支 push，走"分支 + PR"接受评审是标准做法。
- PR 要拆小。500 行的签报没人能认真审完。
- 先 pull、后 push: 上传前先取回最新、在自己这边合一遍，能减少冲突。

## 4. 实战 — main.py

```bash
python3 main.py
```

装了 git 的话，脚本会在临时文件夹里建**一个总部 (bare 远程) 和两家分公司 (开发者 A、B) 仓库**，自动跑一遍协作场景。(没装 git 就用概念模拟代替。)

- **[1] 成立总部**: 用 `git init --bare` 建一座没有办公桌的中央档案馆。
- **[2] 开设分公司**: 开发者 A 和 B 各自用 `clone` 开设分公司。
- **[3] A 的 push**: A 创建菜单文件、提交、push 到总部。
- **[4] B 的 pull**: B 一 pull，A 的文件就出现在 B 的分公司 — 远程协作的核心时刻。
- **[5] 你来我往**: B 追加内容后 push，A 再 pull 回来，确认双方达到同一个最新状态。
- **[6] PR 流程解说**: 如果是真 GitHub，这次 push 会接上 PR、评审、merge — 用流程图输出这一过程。

关键在于**远程并没有什么特别的**。远程地址是互联网 URL 还是自己电脑上的文件夹路径，push/pull 的行为完全一样。观察代码里 `run()` 函数在各分公司文件夹里执行 git 命令的样子，亲眼确认"谁 (cwd) 和哪个远程 (origin) 交换什么"的结构。

## 5. 动手试试

1. **(简单)** 在输出的 [4] 里找找 B pull 前后，B 分公司文件夹的文件列表有什么变化。*(提示: pull 之前是空的。)*
2. **(普通)** 想一想: 如果不加"A 再 pull"这一步、A 一直只 push，会出什么问题? *(提示: 不知道 B 的提交就往上推，远程会拒收 — 所以要先 pull。)*
3. **(挑战)** 注册一个 GitHub 账号 (免费)，在网页上新建仓库、直接在网页里编辑并提交 README 文件。然后用 `git clone` 拉到自己电脑上。*(提示: 仓库页面绿色的 Code 按钮里有 clone 地址。)*

## 6. 常见错误

- **不 pull 就 push**: 远程上有别人的新提交时，push 会被拒绝。这不是报错，而是"请先取回来合并"的提示。`git pull` 之后再 push 即可。
- **把密钥 push 上去**: push 过一次的密钥会永远留在历史里。要是公开仓库，几分钟内就会被小偷机器人收割。level09 学预防方法。
- **把 clone 和下载 (zip) 混为一谈**: 下载 zip 只是无历史的文件拷贝。要协作就必须 clone，push/pull 才能用。
- **把远程和本地当成一回事**: 只 commit 忘了 push，同事那边什么都看不见。"commit=分公司审批，push=呈送总部"是两个独立步骤。
