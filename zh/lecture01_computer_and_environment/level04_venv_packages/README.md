# Lecture 01 · Level 04 — 虚拟环境与包管理

> 学会给每个项目建一间独立的 Python 工作室 (venv)，并用 pip 采购需要的工具 (包)。

**难度** ⭐⭐ / **先修** level03 / **预计时间** 40分钟

## 1. 为什么要学 — 从业务视角出发

软件行业有个流传已久的段子: "在我电脑上明明能跑啊?" — 开发者 A 的代码在开发者 B 的电脑上跑不起来。原因绝大多数是两人安装的**包 (package) 的组成或版本不同**。比如 A 用的是某个库的 2.0，B 用的是 1.5。

这个问题个人也会碰到。项目 X 需要旧版库、新项目 Y 需要新版，而全电脑只能装一个的话，两者必坏其一。解决方案就是**虚拟环境 (virtual environment)** — 给每个项目各建一个独立的 Python 安装空间。实际工作中的 Python 项目无一例外都从虚拟环境开始，本课程的仓库里也有一个叫 `.venv` 的虚拟环境。学完这一关，你将随时答得出"我现在在哪个环境里、带着哪些工具干活"。

## 2. 用比喻来理解

**包是专业工具，虚拟环境是项目专用工具箱**。

装好 Python 就自带基本工具 (标准库)，相当于锤子、螺丝刀级别的必需品。但做数据分析需要电钻 (pandas)，画图需要喷涂设备 (matplotlib) 这样的专业工具。从全球公用仓库 (PyPI, Python Package Index) 把这些工具领回来的采购员，就是 **pip**。

问题出在把所有工具都塞进**公司唯一的公用工具柜**时。装修组需要旧规格的电钻、新建组需要新规格，而柜子里只能放一种的话? 一个组换了工具，另一个组的活就停了。

所以聪明的公司会**给每个项目配一只专用工具箱**。这就是虚拟环境。在项目文件夹里建一只叫 `.venv` 的箱子，只装这个项目用的 Python 和包。箱子之间完全独立、互不干扰，项目结束后连箱子一起扔掉即可。"activate (激活)"就是开工前**把那个项目的工具箱系到腰上**的动作。

## 3. 核心概念

### 3-1. 虚拟环境生命周期四步

```bash
# 1) 创建 — 在项目文件夹里只做一次
python3 -m venv .venv

# 2) 激活 — 每次开工时
source .venv/bin/activate        # macOS/Linux
# .venv\Scripts\activate         # Windows (PowerShell)

# 3) 安装工具 — 在激活状态下
pip install requests

# 4) 退出 — 收工时
deactivate
```

激活后，提示符前面会多出 `(.venv)`。这个标记就是"现在系着哪只工具箱"的视觉信号。激活状态下，`python` 和 `pip` 都会切换成箱子里的那一套。

### 3-2. pip 必备命令

| 命令 | 做的事 |
|---|---|
| `pip install 名字` | 从公用仓库 (PyPI) 安装包 |
| `pip install 名字==2.1.0` | 指定特定版本安装 |
| `pip list` | 列出此环境已安装的包 |
| `pip uninstall 名字` | 卸载 |
| `pip freeze > requirements.txt` | 把当前工具清单记录成文件 |
| `pip install -r requirements.txt` | 按清单一次性重建 |

`requirements.txt` 就是**工具箱的物品清单**。只要把这个文件递给同事，对方就能在自己电脑上原样重现一只同样配置的箱子。它是"在我电脑上明明能跑"的第一支疫苗 (第二支是 level10 的 Docker)。

### 3-3. 怎么知道自己在哪个环境里

在 Python 代码里有个万无一失的确认方法。

- `sys.prefix` — 当前 Python 查找工具的安装空间位置
- `sys.base_prefix` — 原始 (系统) Python 的位置
- 两者**不同就是在虚拟环境里**，相同就是在直接用系统 Python。

打个比方，`sys.base_prefix` 是总部工具仓库的地址，`sys.prefix` 是现在系在腰上那只箱子的地址。地址不一样，说明你系的是专用箱子。

### 3-4. 要遵守的惯例

- 虚拟环境文件夹按惯例命名为 `.venv`，放在项目文件夹正下方。
- `.venv` 文件夹不提交到 Git (体积大、每台电脑都不一样)，提交的是 `requirements.txt`。
- 不要往系统 Python 里滥用 `pip install`。较新的操作系统甚至直接禁止 (externally-managed 报错)。养成只在虚拟环境里安装的习惯。

## 4. 实战 — main.py

```bash
python3 main.py
```

这个脚本会打印**当前运行环境的诊断书**。用仓库的 `.venv` Python 运行 (`../../.venv/bin/python main.py` 或激活后 `python main.py`) 时判定为"虚拟环境里"，用系统 `python3` 运行时判定为"系统 Python" — 请亲自对比两种结果。

- **[1] 是哪只工具箱**: 并排打印 `sys.prefix` 和 `sys.base_prefix`，比较两个值来判定是否在虚拟环境里。
- **[2] 工具箱里的东西**: 用 `importlib.metadata` 列出已安装的包和版本。这是用代码获取和 `pip list` 一样的信息。
- **[3] 检查标准库**: 确认几样不用安装就能用的基本工具 (json、csv、datetime 等) 已经在位。
- **[4] requirements.txt 预览**: 把当前环境的包清单按 `名字==版本` 格式输出，揭示 `pip freeze` 生成的物品清单的真面目。

核心代码是 `sys.prefix != sys.base_prefix` 这一行比较，以及对 `importlib.metadata.distributions()` 的遍历。Python 能用自己的代码审视自己的环境 — 这正是你不必害怕环境问题的原因。

## 5. 动手试试

1. **(简单)** 把同一个 main.py 分别用 (a) 系统 `python3` 和 (b) 仓库 `.venv` 的 Python 运行，比较 [1] 的判定和 [2] 的包数量有何不同。*(提示: 可以像 `.venv/bin/python main.py` 这样直接指定运行的 Python。)*
2. **(普通)** 在任意练习文件夹里用 `python3 -m venv test_env` 建一个新虚拟环境并激活，用 `pip list` 确认它几乎是只空箱子，然后 `deactivate` 并把文件夹整个删掉。*(提示: 箱子建了就扔、毫无负担，这才是正常的。)*
3. **(挑战)** 把 [2] 的输出从按名字排序改成按"名字长度"排序。*(提示: 改 `sorted(..., key=...)` 的 key 函数即可。)*

## 6. 常见错误

- **忘了激活就安装**: 没有 `(.venv)` 标记时 `pip install` 会装到错误的地方 (系统)。装之前先看提示符。
- **建了虚拟环境，IDE 却用着别的 Python**: 编辑器 (VS Code 等) 需要单独指定解释器 (下一关会讲)。这是"装了却 import 不了"的头号常客。
- **把 `.venv` 文件夹整个复制、移动**: 虚拟环境和创建位置绑定，挪动后容易坏。要搬的话，正规做法是用 `requirements.txt` 重新建。
- **忘了更新 requirements.txt**: 加了包就要重新 `pip freeze` 生成清单，同事的环境才能跟上。
