# Lecture 04 · Level 09 — 索引与查询性能

> 用"书末目录"这个比方理解索引为什么能让检索变快，用 EXPLAIN QUERY PLAN 读出数据库的作战方案，并在 30 万行的表上实测建索引前后的时间差。

**难度** ⭐⭐⭐⭐ / **先修** level08 / **预计时间** 50分钟

## 1. 为什么要学 — 业务视角

"这个页面怎么这么慢？"— 公司内部系统被吐槽的相当一部分原因，
就是**没有索引的检索**。数据量小的时候随便写什么查询都快，问题一直
藏着；等数据攒起来，速度就会突然慢上几十倍。懂了索引 (index) 的原理，
你就多了两件本事。第一，自己写的查询变慢时，不再只能干等，而是能诊断
原因。第二，你能和开发团队进行这种级别的对话: "这里按 customer_id
的检索好像在走全表扫描，能帮我看看索引吗？"能说出这一句话的非开发岗
少之又少，也因此格外被人看重。

## 2. 打个比方

**索引就是书末的目录 (索引页)。** 想在一本 600 页的书里找"折旧"出现
的地方，有两种办法: (1) 从第 1 页翻到最后一页 — 全表扫描 (full scan)。
(2) 翻到书末目录，看到"折旧 → 152 页、380 页"，直接翻过去 —
索引查找。目录是按拼音顺序排好的，所以只要扫几眼就能找到条目。
数据量变成 10 倍，全表扫描就慢 10 倍；而在排好序的目录里查找，
成本几乎不怎么涨。

天下没有白吃的午餐。往带目录的书里插入新内容，**目录也得跟着改**。
一张表上的索引越多，INSERT/UPDATE 就越慢，占的存储空间也越大。
所以索引的原则是"只加在常检索的列上，够用就好"。

还有一点 — 目录是**按第一个字排序**的。像"…折旧"这样从词中间去找是
找不到的。所以 `LIKE '%咖啡%'` 这类中间匹配的检索，就算有索引也会
变成全表扫描。

## 3. 核心概念

### 3-1. 建索引

```sql
CREATE INDEX idx_big_customer ON big_orders (customer_id);
```

指定 `表(列)` 之后，数据库就会为那一列的值另建一份排好序的数据结构
(B 树)，之后凡是按这一列检索的查询，数据库会**自动**用上索引。
查询语句一个字都不用改 — 变快的只是执行路径。

### 3-2. EXPLAIN QUERY PLAN — 读出数据库的作战方案

在查询前面加上 `EXPLAIN QUERY PLAN`，数据库就不执行，只把**作战方案**
给你看。

- `SCAN big_orders` — 打算把所有行翻一遍 (全表扫描)。表一大就是警报。
- `SEARCH big_orders USING INDEX idx_... (customer_id=?)` — 打算用目录
  直接找。放心。

碰到慢查询: (1) 用 EXPLAIN 确认是不是 SCAN → (2) 确认 WHERE 里用到的列
有没有索引 — 这两步就是性能诊断的基本功。

### 3-3. 主键本来就有索引

主键上自动带索引。这就是 `WHERE order_id = 5` 永远很快的原因。
真正的问题在外键，以及经常当检索条件用的普通列 (customer_id、日期、
状态……)，这些列才是索引候选。

### 3-4. 索引帮不上忙的情况

- **中间匹配 LIKE**: `LIKE '%咖啡%'` — 目录按第一个字排序，做不到。
  (`LIKE '咖啡%'` 是可以的。)
- **对列做了运算的条件**: `WHERE price * 1.1 > 1000` — 算过的值不在
  目录里。把条件改写成 `price > 1000 / 1.1` 就能用上索引。
- **结果占了表大半的条件**: 要取一半数据的话，在目录和数据之间来回
  跑可能反而比直接翻一遍慢，数据库有时会自己选择全表扫描。

### 3-5. 写入成本 — 索引的账单

每多一个索引，INSERT/UPDATE/DELETE 就要多做一份索引更新的活。
以查询为绝对主力的分析用表可以多加索引，写入频繁的订单接收表就只留
必需的 — 这是个权衡 (trade-off)。

## 4. 动手练习 — main.py

运行:

```bash
python3 main.py
```

main.py 会在练习库里造一张 30 万行的 `big_orders` 表来做实验
(生成要花几秒)。

- **[1] 搭实验台**: 生成 30 万行 (固定 seed，每次都是同一份数据)。
- **[2] 没有索引时的检索**: 把 `WHERE customer_id = ?` 重复执行 200 次，
  实测总耗时。EXPLAIN 的结果是 `SCAN` — 意思是每次都把 30 万行翻一遍。
- **[3] 建索引**: 一行 `CREATE INDEX`。创建耗时也一起量出来。
- **[4] 建索引后同样的检索**: 同一个查询再实测 200 次。EXPLAIN 变成了
  `SEARCH ... USING INDEX`，时间缩短几十到几百倍，用数字看得清清楚楚。
- **[5] 索引帮不上忙的检索**: 用 EXPLAIN 确认 `LIKE '%送%'` 这种中间
  匹配条件，就算有索引也还是 SCAN。
- **[6] 写入成本**: 把同样的 1 万行 INSERT 分别灌进无索引表和有索引表，
  量出写入速度的差别。

绝对时间会随运行环境而变，但**倍数**永远很夸张。
去看看输出里那个"快了大约 N 倍"的数字。
(在本仓库的虚拟环境里跑出来的参考值: 2.58 秒 → 0.0034 秒，约 760 倍。)

## 6. 常见误区

- **给每一列都建索引**: 写入变慢、空间也浪费。
  只有"WHERE/JOIN 里常用的列"才是候选。
- **一慢就怪服务器**: 先 EXPLAIN。一行全表扫描就是大多数问题的原因。
- **指望在小表上看到效果**: 几百行的表全表扫描也是一瞬间，看不出差别。
  数据越大，索引才越发光。
- **被函数包起来的条件**: `WHERE SUBSTR(ordered_at,1,7)='2025-06'` 用不上
  索引。改写成范围条件
  `ordered_at BETWEEN '2025-06-01' AND '2025-06-30'` 就能用上。
- **不测就争**: 别靠"感觉有点慢"这种直觉，像本关一样用反复实测的数字
  说话。
