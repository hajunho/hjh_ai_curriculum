# Lecture 04 · Level 08 — 数据修改与事务

> 学习用 INSERT·UPDATE·DELETE 修改数据，以及把多个修改捆成"要么全部成功、要么全部取消"的事务 (BEGIN/COMMIT/ROLLBACK)。用扣减库存的场景把成功和失败-回滚都演一遍。

**难度** ⭐⭐⭐ / **先修** level07 / **预计时间** 50分钟

## 1. 为什么要学 — 业务视角

从只做查询到开始**修改**数据的那一刻，责任的分量就变了。
一行 UPDATE 就可能把 20 万客户的等级全改掉。所以本关在学语法
(INSERT/UPDATE/DELETE) 的同时也学**安全装置**。
订单处理、扣减库存、积分累积这些实际业务，都是好几个修改捆成一组的。
万一中间有一个失败呢？"订单存进去了、库存却没扣"的数据，
将来会以财务审计和客户投诉的形式找上门来。事务 (transaction)
就是保证这一组修改**要么全部成功、要么全当没发生**的装置，
它是银行、电商、ERP 所有系统的心脏。

## 2. 打个比方

**银行转账**是最好的比方。从我的账户扣 5 万韩元 (修改 1)、
往对方账户加 5 万韩元 (修改 2)，这两个动作必须是一体的。
扣款成功、入账失败，5 万块就凭空蒸发了。所以银行把两个动作装进
一个信封，两个都成功才封上信封 (COMMIT)，有一个失败就整个信封作废
(ROLLBACK)。

另一个比方是**先用铅笔写、最后用钢笔誊清**。BEGIN 之后的修改都是
铅笔草稿: 在我眼里看着像是改了，但还不是账本原件。COMMIT 是用钢笔
定稿，ROLLBACK 是用橡皮擦个干净。哪怕遇上"UPDATE 忘了写 WHERE!"
这种惊魂时刻，只要还没提交，橡皮就还在。

## 3. 核心概念

### 3-1. INSERT — 添加行

```sql
INSERT INTO customers (customer_id, name, city, grade, joined_at)
VALUES (204, '张雪', '北京', 'BASIC', '2025-12-20');
```

请养成写明列清单的习惯，将来表结构变了语句也不会坏。
主键重复时数据库会像 level00 那样拒绝 — 这是安全装置在工作。

### 3-2. UPDATE — 修改行

```sql
UPDATE customers
SET    grade = 'GOLD'
WHERE  customer_id = 204;
```

**UPDATE 的命根子是 WHERE。** 没有 WHERE，所有行都会被改。
实战守则: 先用同样的 WHERE **执行一遍 SELECT** 确认会命中几行，
再执行 UPDATE。顺序是"先瞄准 → 再开枪"。

### 3-3. DELETE — 删除行

```sql
DELETE FROM customers WHERE customer_id = 204;
```

同样是 WHERE 保命。实际工作中经常干脆不删，只做个
`status='已注销'` 之类的标记 (软删除) — 需要留痕的数据，
DELETE 之前先确认公司政策。

### 3-4. 事务 — BEGIN / COMMIT / ROLLBACK

```sql
BEGIN;                       -- 打开信封 (之后都是铅笔草稿)
UPDATE inventory SET stock = stock - 2 WHERE product_id = 1;
INSERT INTO orders ...;
COMMIT;                      -- 两个都成功 → 钢笔定稿
-- 出了问题就: ROLLBACK;  → 信封作废，回到 BEGIN 之前
```

事务保证的性质叫 ACID。记住核心两条就够了:
**原子性 (Atomicity)** — 要么全部、要么全无。**一致性 (Consistency)**
— 违反规则的中间状态不会留在账本上。(剩下的隔离性、持久性，
保证的是"多人同时写也没事、断电也没事"。)

### 3-5. 先验证再提交的模式

实战事务的骨架长这样。

```
BEGIN
  修改 1, 修改 2, ...
  验证: 库存是不是负数? 余额够不够?
  没问题 → COMMIT / 发现问题 → ROLLBACK
```

之所以能"先扣了再说，扣成负数就整体取消"，就是因为提交之前都还是
铅笔草稿。这个模式在 main.py 的第 [5] 步会原样上演。

## 4. 动手练习 — main.py

运行:

```bash
python3 main.py
```

main.py 开始前会在 products 旁边造一张库存表 `inventory`。

- **[1] INSERT**: 添加新客户 — 确认添加前后的行数和新行。
- **[2] UPDATE**: 演示"瞄准 (用 SELECT 确认目标) → 开枪 (UPDATE)"的顺序。
- **[3] 重现忘写 WHERE 的 UPDATE 事故**: 在事务里故意执行没有 WHERE 的
  UPDATE，让全体客户变成 VIP 的惨剧上演 — 再用 ROLLBACK 原样恢复。
  这就是橡皮出手的瞬间。
- **[4] 扣减库存事务 (成功)**: 创建订单 + 扣库存装进一个信封，
  验证通过 → COMMIT。确认库存真的减少了。
- **[5] 扣减库存事务 (失败→回滚)**: 下单数量超过库存 →
  扣减后验证发现负库存 → ROLLBACK。确认**订单和库存都和尝试之前
  一模一样**。"没有半截子状态"是本关最关键的输出。

## 6. 常见误区

- **没有 WHERE 的 UPDATE/DELETE**: 事故榜第一名。"先瞄准 (SELECT)"守则
  加上在事务里操作的习惯，是双保险安全带。
- **忘记提交**: Python 的 sqlite3 里改完不调 commit() 就关连接，
  修改就没了。"我的 UPDATE 怎么没生效"的头号原因。
- **事务开得太久**: 信封开着的时候，别的用户的操作可能在排队等。
  信封要开得短、关得快，这是礼貌。
- **出错了也不 ROLLBACK**: 失败时回滚未必是自动的。
  请在 try/except 里显式调用 rollback()。
- **在生产库上练手**: 练习永远用副本。像这个练习库这样重跑一次就能
  重建的环境，才是练习本。
