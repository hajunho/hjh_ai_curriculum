# Lecture 04 · Level 01 — 表、行、列与主键

> 学习数据库内部的模样: 表、行、列的结构，每一行独有的编号 (主键)，以及把表和表连接起来的引用编号 (外键)。我们会直接查询练习数据库的结构 (schema) 来一一确认。

**难度** ⭐ / **先修** level00 / **预计时间** 35分钟

## 1. 为什么要学 — 业务视角

你对公司系统管理员说"把订单数据给我一份"，得到的回答往往是:
"orders 表里没有金额，得把 order_items 和 products 连起来才行。"
听不懂这句话，数据需求就会永远在来回踢皮球。数据库里的数据不是 Excel 那种
"一张大表"，而是**多张小表通过编号互相连接**的结构。
学会读这张结构图 (schema)，你就能自己判断: 哪份数据放在哪里、
要拼哪几张表才能得到想要的结果。这是比 SQL 语法更先要学的"看地图的方法"。

## 2. 打个比方

想想社区文具店老板是怎么记账的。一开始他把所有事都记在一个本子上:
"3月2日，王志明 (住北京的老主顾)，钢笔 2 支，每支 29,000 韩元……"
可当王志明搬了家，麻烦就来了: 得在整个本子里**逐条找出**所有出现王志明的行，
挨个改地址。漏掉一行，账本就自相矛盾。

聪明的老板会把账本拆开: **客户名册** (每位客户一个会员号)、
**商品目录** (每件商品一个商品号)、**订单账本** (日期加上"7 号会员
买了 9 号商品 2 件")。这样一来，地址变了只需要改客户名册里的那一行。

数据库的核心概念这就全出场了。

- 一本账本 = **表 (table)**
- 账本里的一行 = **行 (row)** — 一位客户、一笔订单
- 账本上的栏目 (姓名、地址……) = **列 (column)**
- 像会员号那样每行独有的编号 = **主键 (primary key, PK)**
- 订单账本上写的"7 号会员" = 指向另一本账本的**外键 (foreign key, FK)**

## 3. 核心概念

### 3-1. 主键 — 绝不重复的名牌

姓名当不了主键，因为会有重名。所以每张表都要给每行定一个独有的值
(客户编号、订单编号、工号……)。主键有两个条件: **不许重复，不许为空
(NULL)。** 违反这两条规则的保存请求，数据库会直接拒绝
(level00 已经亲眼见过了)。

### 3-2. 外键 — 指向另一本账本的手指

orders 表的 customer_id 列里放的不是客户姓名，而是 **customers 表的
主键值**。意思是"这笔订单的主人是客户名册第 7 行"。这样一来
(1) 修改客户信息只需改一处，(2) 还能挡住"不存在的客户下的订单"
这类幽灵数据。

### 3-3. 练习数据库的五张表

这就是整门课都要用的网店数据库 `hjh_shop.db` 的结构。

| 表 | 内容 | 主键 | 外键 |
|---|---|---|---|
| customers | 客户 200 人 (姓名·城市·等级·注册日期) | customer_id | — |
| products | 商品 10 种 (名称·品类·售价·成本) | product_id | — |
| employees | 员工 20 人 (姓名·部门·薪资·上级) | employee_id | manager_id → employees |
| orders | 订单 1,000 笔 (谁·何时·状态) | order_id | customer_id → customers, employee_id → employees |
| order_items | 订单明细 (哪件商品几件) | (order_id, product_id) | order_id → orders, product_id → products |

画成文字关系图:

```
customers ──< orders >── employees ┐
                │              └───┘ (manager_id 自引用)
                └──< order_items >── products
```

`──<` 表示一对多 (1:N) 关系。一位客户可以拥有多笔订单。

### 3-4. 为什么订单账本里没有金额 — 规范化初体验

如果在 orders 里把商品名和价格一起记上，同样的信息就要重复上千遍，
价格一变就得改上千行。**一个事实只记在一个地方** —— 这个原则叫
规范化 (normalization)。代价是查询时需要把表拼起来，
拼法 (JOIN) 会在 level06 学。"存的时候拆开，查的时候拼上"
就是关系型数据库的基本节奏。

### 3-5. order_items 的主键有两个？

order_items 的主键是 (order_id, product_id) 这个**组合**。意思是
"17 号订单里的 3 号商品"这个组合只能出现一次。这叫复合键 (composite key)。
在化解两本账本之间 (订单↔商品) 多对多关系的"桥梁表"里，你会经常见到它。

## 4. 动手练习 — main.py

运行:

```bash
python3 main.py
```

main.py 先创建 `hjh_shop.db`，然后问数据库本尊: "你长什么样？"
SQLite 有一张叫 `sqlite_master` 的特殊表，保存着所有表的建表语句，
所以用 SQL 就能查询结构。

- **[1] 表清单**: `SELECT name FROM sqlite_master WHERE type='table'`
- **[2] 各表结构**: 用 `PRAGMA table_info(表名)` 把列名、数据类型、
  是否主键打印成表。pk 列为 1 以上就是主键。
- **[3] 数行数**: 每张表跑一次 `SELECT COUNT(*)`，确认数据规模。
- **[4] 关系图**: 顺着外键连接打印一张文字关系图。
- **[5] 引用验证**: orders 里的 customer_id=7 是否真的指向 customers 的
  第 7 行？把两张表并排查出来，亲眼确认。

请特别留意输出里**标了 pk 的列**和**以 `_id` 结尾的列**。
`_id` 列大多是指向某处主键的外键。以后面对陌生数据库时，
这套要领 (表清单 → 各表的键 → 画关系图) 同样管用。

## 6. 常见误区

- **拿姓名当键**: 重名、改名、错别字面前不堪一击。
  键最好用没有含义的独有编号。
- **想把所有东西塞进一张表的习惯**: 这是 Excel 式思维。
  看到重复的信息，就该想到拆表。
- **把外键列的数字当"普通数字"读**: customer_id=7 不是数量也不是金额，
  而是**另一张表第 7 行**这个地址。它是不能求平均、不能相加的数字。
- **不看结构就直接写查询**: 面对陌生数据库，一定先确认表清单和键结构。
  本关的 [1]~[4] 就是标准顺序。
