# Lecture 11 · Level 02 — 提示词工程基础：怎么把指令书写好

> 同一个模型，指令书 (提示词) 怎么写，结果能差出天壤之别 —— 用实操把角色、情境、格式、示例这四大要素练熟。

**难度** ⭐⭐ / **先修** level01 / **预计时间** 40分钟

## 1. 为什么要学 — 业务视角

在 LLM 落地项目里，投入产出比最高的技术既不是换模型，也不是加服务器，而是**把提示词改一改**。成本是 0，质量却明显不一样。"AI 回答得莫名其妙"这类抱怨里，一半以上其实是"指令写得太含糊"。

提示词工程 (prompt engineering) 不是另一门编程语言，它是**把工作交代清楚的能力**——说白了就是一个好管理者的沟通能力。所以没写过代码的业务同事做得比开发还好，这种事经常发生。你以前把活派给团队成员的那些经验，在这里可以直接变成资产。

## 2. 打个比方

比一比两位给新人派活的组长。

**A 组长**: "这个你总结一下。"——新人当场懵了。总结成几行？谁看？什么算重点？交出来的东西全靠运气。

**B 组长**: "你就当自己是负责高管汇报的秘书 (角色)，总监很忙，30 秒内要读完 (情境)，以决议事项为主、写成 3 行要点 (格式)，参照上次那份报告的样子 (示例)。"——就算是新人第一次做，产出也稳。

LLM 是一个每次都会记忆清零、但非常能干的新员工。**每一次都得重新把 B 组长的那份指令书递给它**，质量才稳得住。提示词工程，归根结底就是"把 B 组长的指令书做成模板"。

## 3. 核心概念

### 3.1 提示词四大要素

| 要素 | 作用 | 示例说法 |
|---|---|---|
| 角色 (Role) | 设定语气与专业程度 | "你是负责高管汇报的秘书" |
| 情境 (Context) | 提供取舍标准 | "忙碌的高管要在30秒内读完" |
| 格式 (Format) | 固定输出样子 | "写成3行要点"、"输出 JSON" |
| 示例 (Example) | 用样本传达风格 | "示例: 输入→输出" |

四项不必全填。结果不满意的时候，把它当成**该补哪一项的检查清单**来用就行。

### 3.2 few-shot — 示例的威力

只给指令、不给示例叫 zero-shot；给出 1 个以上输入输出示例叫 few-shot (少样本)。示例一次解决两件事: (1) 传达那些说不清楚的风格；(2) **固定输出格式**——尤其是分类、抽取这种结果要交给下一段程序处理的活，格式一晃动整条自动化就断，所以 few-shot 基本算必需品。

### 3.3 系统提示词 vs 用户提示词

真实 API 里，指令书分成两层。系统提示词 (system prompt) 放角色、规则这类每次都一样的内容；用户消息放这一次任务的材料。拿公司作比: 系统提示词是"岗位说明书"，用户消息是"今天的工作委托"。main.py 末尾注释里的 Claude API 示例中，`system=` 参数就是它。

### 3.4 反复打磨的循环

提示词不可能一次成型。实务顺序是: 写初稿 → 用 5~10 个代表性输入测试 → 看失败案例补要素 → 再测。这份"测试输入集"，以后就长成了评估集 (level11)。

### 3.5 提示词是资产 — 模板化与版本管理

打磨好的提示词很容易散落成个人诀窍。团队层面应该: (1) 把好用的提示词做成带空位的模板共享；(2) 每次修改都记下日期和改动原因 (版本管理)；(3) 把在哪些输入上失败过的案例攒起来。"提示词从 v3 改到 v4 之后，分类准确率掉了"——要能察觉这种事，就得有记录。这套管理体系会和 level11 的评估集接上而后完整: 每次改提示词，都用同一份评估集打分，用数字确认到底是变好还是变坏。

## 4. 动手练习 — main.py

运行:

```bash
cd zh/lecture11_llm_and_rag/level02_prompt_engineering
python3 main.py
```

输出解读:

- **[1]** 四大要素小结。
- **[2] 案例 A (会议纪要总结)**: 差提示词 ("总结一下。") 只随手丢回一句 "下次会议将重新确定各门店的安全库存标准。"；填上角色+情境+格式的提示词 (评分 `3/4`) 则返回以决议事项为主的 3 行要点。每份提示词上方会一起打印 `包含要素 N/4` 的评分。
- **[3] 案例 B (客诉分类)**: 差提示词给出 "嗯，这看起来像是退款/支付方面的内容。"——人读着没问题，但程序没法处理。few-shot 提示词返回的是固定格式:

```
分类: 退款/支付
依据关键词: 退款, 支付
```

- **[4]** 各要素效果小结。

代码核心: `audit_prompt()` 是个简易检查器，用关键词判断提示词里有没有四大要素。`MockLLM.complete()` 被设计成"检测到角色/格式/示例就给结构化回答，没有就给含糊回答"，以此复现真实 LLM 上观察到的倾向。真模型不会这么机械，但"指令清楚 → 输出稳定"这个方向是一致的。

## 5. 自己动手试试

1. **(简单)** 把案例 A 好提示词里的"按要点格式"几个字删掉再运行。输出退化成什么样了？(提示: `audit_prompt` 的分数和回答结构会一起变。)
2. **(中等)** 自己给"翻译"任务写一份好提示词，丢进 `llm.complete()`。四大要素全填满，把分数刷成 `4/4`。(提示: 必须出现"示例"这两个字才会被认定为示例要素。)
3. **(挑战)** 挑一件你自己经常做的工作 (比如写周报)，做一份提示词模板。会变的部分留成 `{本周业绩}` 这样的空位，再加一段用 3 个代表性输入批量测试的代码。

## 6. 常见误区

- **一句话指令却期待复杂产出** — "好好总结一下"里的"好好"没给模型任何信息。把标准写成句子。
- **只列一堆禁止事项** — "别怎样"不如"要怎样"好使。把想要的样子用示例摆出来，是最优解。
- **不指定格式就接自动化** — 给人读的时候自由格式没关系，但程序要接收的输出必须强制格式 (能用 JSON 就用 JSON，见 level03)。
- **测一次就宣布完工** — 输入稍微一变就崩的提示词比比皆是。至少用 5 个不同的输入测一遍。

## 下一关预告

即使提示词写得好，输出也只是"大体上"守格式，不是 100%。要接到程序里，就得用 JSON 接收、校验模式 (schema)、失败了还能重试的安全装置。Level 03 就来实现这套模式。
