# Lecture 11 · Level 04 — LLM API 调用模式与密钥管理

> LLM 是网络另一头的付费 API —— 密钥安全、token 计费、重试与退避、超时，这些运维必备的调用技术，我们用一个假服务器来练。

**难度** ⭐⭐⭐ / **先修** level03 / **预计时间** 50分钟

## 1. 为什么要学 — 业务视角

把 LLM 接进业务系统的那一刻，你会同时撞上三个现实。第一，**每调一次就花一次钱**——按 token (词元) 计量的用多少付多少。第二，**它时不时会失败**——用量超限 (429)、服务器错误 (500)、响应变慢，这些都是正常运营的一部分。第三，**API 密钥一泄露，别人就拿你公司的卡在刷**——把密钥推到公开仓库、一夜之间被刷掉一大笔钱的事故反复发生。

演示和运维的分水岭就在这里。只有成功路径的代码是演示；把失败路径 (重试、超时、费用上限、密钥安全) 也补齐的代码才是运维。这一关讲的就是造成这个差距的四项基本功。

## 2. 打个比方

LLM API 就像**一家靠电话下单的外部专业翻译公司**。

- **API 密钥 = 公司卡卡号**: 电话里得报出卡号，人家才接活。把卡号写在便利贴上贴显示器 (硬编码进代码)，总有一天会被拍照传出去。请放进保险柜 (环境变量、密钥管理器)。
- **token 计费 = 按字数收费**: 原文越长 (输入 token)、译文越长 (输出 token)，费用就越高。不看报价就一直往外派活，月底账单会让你吓一跳。
- **429 错误 = "现在单子积压了"**: 对方忙的时候会说"请稍后再打"。这时候每秒打一次 (无脑重试) 只会更堵。1 分钟、2 分钟、4 分钟……把间隔逐步拉长再打，这就是指数退避 (exponential backoff)。
- **超时 = "30分钟内不回复就算了"**: 傻等下去，我们整条业务就停住了。给等待设一个上限，超了就挂断重来。

## 3. 核心概念

### 3.1 请求/响应结构

请求里放模型名和对话消息列表，响应里放生成的文本以及 **usage (token 用量)**。每次调用都把 usage 记下来，是费用管理的起点。中文大致 1~2 个字对应 1 个 token (各模型不同)。

### 3.2 错误分两类 — 该重试的和不该重试的

| 类别 | 例子 | 处理 |
|---|---|---|
| 临时性 (值得重试) | 429 超限、500 服务器错误、超时 | 退避后重试 |
| 配置问题 (重试无意义) | 401 密钥错误、400 请求格式错误 | 立刻中断，改代码/改配置 |

对 401 做退避重试，等于拿着错卡号一遍遍打电话——分清这两类很关键。

### 3.3 指数退避 + 抖动

把重试间隔按 1 秒 → 2 秒 → 4 秒 → 8 秒往上拉 (指数)，再加一点随机时间 (抖动，jitter)。没有抖动的话，同时失败的几百个客户端会在同一刻一起重试，把服务器再压垮一次。上限 (比如最多 4 次) 一定要设，超了就入队列或者通知人工。

### 3.4 密钥管理三原则

1. 不把密钥写进代码和仓库——用 `os.environ.get("ANTHROPIC_API_KEY")` 读取。
2. 不把完整密钥打到屏幕和日志里——只留前几位，其余打掩码。
3. 一旦怀疑泄露，立刻作废并重新签发——设计上要让密钥随时可以换。

### 3.5 大批量就走批处理

不需要实时响应的活 (比如通宵给 1 万份文档分类)，别一条一条调，先考虑批处理 (batch)。主流 API 都提供批量专用通道，价格通常打对折。就算不走批处理，大量调用时也应该在调用之间留间隔，从设计上就别去撞每分钟上限 (rate limit)，这比靠重试硬扛好得多。"事先限速"和"超了之后退避"是互补关系，两样都有的客户端才算运维级。

输出解读:

- **[2]** 观察请求/响应的 JSON 结构。`usage` 里的输入/输出 token 就是计费依据。
- **[3]** 用错误的密钥调用会拿到 401 —— 确认"不重试、立刻中断"这条分支。
- **[4]** 处理 5 条请求，4 种失败路径全都登场了: 第 (1) 条连着撞上 500、429、429、45 秒延迟超时，最后**超过重试上限被判失败** (入队列/通知人工)；第 (2)(4) 条 429 退避后成功；第 (3) 条 500 重试后成功；第 (5) 条一次就成功。等待时间为演示压缩到了 1/100，所以实际跑起来是瞬间结束的。
- **[5]** 报告累计 token 与费用 (虚拟单价):

```
成功调用 4 次，重试 7 次 | 输入 17tok + 输出 61tok = $0.000966 (约 1.35 韩元)
```

代码核心: `fake_llm_api()` 是用固定种子随机数复现真实 API 成功/429/500/延迟的假服务器。`RobustClient.chat()` 是本关的主角，装着"调用 → 按状态分流 (成功/永久错误/临时错误) → 退避等待 → 重试 → 超上限就放弃"这套运维模式。就像文件末尾注释里那样，真实的 Claude SDK 把重试和超时做成了选项 (`timeout=`、`max_retries=`)，但只有懂了原理，才知道这些选项该怎么设。

## 6. 常见误区

- **硬编码密钥** — 代码里出现 `api_key = "sk-..."`，推到 git 的那一刻就是事故。留在提交历史里的密钥即使删掉也能被恢复，所以必须立刻重新签发。
- **所有错误一律照同一种方式重试** — 401/400 重发多少次都还是失败。请按错误码分流。
- **没有退避就重试** — 一失败立刻重调的循环，只会让超限更严重，还白烧钱。
- **不设超时** — 默认值往往很长，一个慢响应就能把整批任务卡上好几分钟。
- **不记费用日志** — 把 usage 扔掉，月底账单就成了你的第一份费用报告。请按调用逐条记录。
