# Lecture 11 · Level 01 — LLM 办公应用全景图

> 总结、初稿、分类、抽取、翻译、代码——画一张"公司里 LLM 该用在哪"的地图，并用模拟 LLM 把其中 3 种任务自动化。

**难度** ⭐ / **先修** level00 / **预计时间** 35分钟

## 1. 为什么要学 — 业务视角

一旦领导发话"咱们公司也要引入 AI"，事情往往这样收场：折腾几个月做了个聊天机器人，然后机器人在客户面前胡说八道，项目被叫停。失败的原因不是技术，而是**选题**。因为一上来就让 LLM 干最危险的活——在客户面前陈述事实。

成功的组织反着来。先从错了也损失不大的任务做起——写初稿、做总结、做分类——积累信任和经验，等配好验证装置 (本课后半部分的 RAG 和护栏) 之后，再扩展到客户接触点。这一关提供的就是那张"从哪里开始"的地图。

## 2. 打个比方

引入 LLM 就像**招了一个口才极好的新员工**。这位新人文笔惊人、永不疲倦、工资便宜。但他对公司情况一无所知，还有个毛病：不知道的事也装懂。

想想你会按什么顺序给这位新人派活。

- **第一周**: 整理会议纪要、写邮件初稿——错了也无妨，前辈改改就行。
- **第一个月**: 把收到的咨询按部门分类——偶尔分错，重新归类即可。
- **信任建立之后**: 把资料 (文档) 塞给他，让他辅助客户应答——但要附一条规矩：没有依据的话不许说。

绝对不能派的活也很清楚：不经审核就盖公司公章发出去的事、把公司机密暴露给外部的事。LLM 应用地图说到底就是一张"给新人派活的顺序表"。

## 3. 核心概念

### 3.1 六大任务类型

| 类型 | 示例 | LLM 擅长的原因 | 风险 |
|---|---|---|---|
| 总结 | 会议纪要→3行 | 原文就在眼前 (幻觉空间小) | 低 |
| 初稿 | 邮件·通知 | 默认由人做最终修改 | 低 |
| 分类 | 客诉路由 | 选项是固定的 | 中 |
| 抽取 | 从合同里提金额·日期 | 可以格式化 (level03) | 中 |
| 翻译 | 客户邮件 | 语言模式的精华 | 中 |
| 代码 | Excel 公式·SQL | 跑一下就能验证 | 中 |

共同原理：**给了原文、有人审核、或者能机械验证的任务**越安全。反过来，"依赖模型的记忆去陈述事实"的任务 (自由问答客服) 最危险。

### 3.2 风险清单 — 引入前的六连问

main.py 的 [5] 打印的清单就是核心。尤其是第 3 问 (个人信息、机密能不能发给外部 API)，必须事先和 IT 部门、法务部门协商。很多公司正是因为这一条选择了私有化部署模型或企业级合同。

### 3.3 自动化程度的三个台阶

1. **辅助 (Copilot)**: LLM 出初稿，人来定稿——最理想的起点。
2. **半自动**: LLM 处理，人抽样质检——分类、抽取类任务。
3. **全自动**: 无人介入——只有在配齐依据引用和护栏 (level11) 之后。

### 3.4 成本感觉 — 和人工时薪比一比

做引入决策需要有个大致的成本概念。LLM API 按 token (词元，词的碎片) 计量收费，中文大约 1~2 个汉字对应 1 个 token。一封邮件初稿 (输入+输出约 2 千 token)，视模型不同只要几韩元到几十韩元 (本课程示例货币为韩元 KRW)——和人花 10 分钟 (按时薪折算要几千韩元) 相比差着数量级。不过当调用量达到每天数万次时情况就不同了，所以要养成按月计算"单次成本 × 预计调用量"的习惯。计算方法和成本追踪代码会在 level04 亲手实现。

## 4. 动手练习 — main.py

运行:

```bash
cd lecture11_llm_and_rag/level01_llm_business_map
python3 main.py
```

输出解读:

- **[1]** 把办公应用全景图打成表格。可以直接拿去开团队会。
- **[2]** 只给收件人、目的、期限三条信息，MockLLM 就能写出一封格式得体的邮件初稿。关键在于"人只负责审核和签名"这个协作结构。
- **[3]** 从 5 句话的会议纪要里挑出核心 3 行。请确认"午餐菜单"那句被剔除了——这就是总结质检的迷你体验。
- **[4]** 把 4 条客诉分类为物流配送/退款·支付/质量·故障/服务态度，并同时输出依据关键词。让模型把依据一起交出来，是抓误分类的实战诀窍。
- **[5]** 风险清单六连问。

代码核心: 这一关的 MockLLM 是 `mock_llm.py` 里的规则式实现。`complete()` 从提示词里找"分类/总结/邮件"这类指令词来路由任务。真实 LLM 内部原理不同，但**"读指令、定工作模式"**这个用户视角的行为是一样的。文件底部注释里有真实 Claude API 的调用代码，等你拿到密钥，只要替换 `llm.complete(prompt)` 那一处即可。

## 5. 自己动手试试

1. **(简单)** 往 `COMPLAINTS` 里加一条新客诉试试: "App 登录不上去了"。它被分到哪一类？(提示: 词典里没有的类型会落到"其他"——分类体系之外的输入怎么处理，正是实务设计的要点。)
2. **(中等)** 在 `mock_llm.py` 的 `_CATEGORY_LEXICON` 里加一个"账号/App"类别 (关键词: 登录、密码、App、报错)，让第 1 题的客诉被正确分类。
3. **(挑战)** 写下你们公司 (或一家虚构公司) 的 10 项业务，按 3.1 的标准 (给原文吗？有人审核吗？能机械验证吗？) 划分安全/危险。再从中挑出"这个月就能启动的 1 项"，逐条回答 [5] 的六连问。

## 6. 常见误区

- **从最难的任务 (自由问答客服机器人) 开始** — 这是失败概率最高的起点。先做初稿、总结、分类。
- **没有审核环节的自动化** — "LLM 写的邮件直接发出去"是通往事故的捷径。从辅助 (Copilot) 阶段做起。
- **只要分类结果、不要依据** — 让模型连依据关键词一起输出，人找误分类的速度能快 10 倍。
- **跳过安全审查** — 把含客户个人信息的文本发给外部 API，在大多数公司都算违规。先学会脱敏 (level11)。
