# Lecture 11 · Level 03 — 结构化输出与解析：用 JSON 接收

> 要让 LLM 的回答不是给人读、而是给程序吃 —— 实现 JSON 输出、模式校验、失败重试这一整套模式。

**难度** ⭐⭐⭐ / **先修** level02 / **预计时间** 45分钟

## 1. 为什么要学 — 业务视角

在聊天窗口里由人来读 LLM 的回答，格式散一点也没什么。可真正的业务自动化——从合同里抠出金额灌进 ERP，按客诉分类结果派工单，从简历里提取工作经历入库——LLM 的输出就成了**下一段程序的输入**。

程序理解不了"合同金额看起来差不多是1亿2千万韩元哦^^"，它要的是 `{"amount_krw": 120000000}`。LLM 自动化项目里，演示阶段一切顺利、上线之后崩掉，最常见的那个点就是这个"输出格式偶尔跑偏"；而今天学的请求-校验-重试模式，就是它的标准解法。

## 2. 打个比方

想想报销。员工把票据明细写成**自由格式的邮件**发过来，财务每次都得人工读、人工转录，遇到"午饭大概三万韩元左右"这种条目就要出事。所以公司都用**固定表单**: 日期栏、金额栏 (只填数字)、科目栏 (从选项里选一个)。

让 LLM 用 JSON 回答，就是"发给它一张表单"。而且财务收到表单照样要验算 (金额栏里出现汉字就打回)，程序也一样要校验收到的 JSON，有问题就**写明打回理由、要求重新提交**。被打回三次呢？那就人工处理。今天要实现的循环，正是这套流程。

## 3. 核心概念

### 3.1 JSON — 程序之间的通用表单

JSON (JavaScript Object Notation) 是 `{"字段": 值}` 形态的标准数据格式，和 Python 的字典几乎一模一样，`json.loads()` 一行就能变成字典。起点就是告诉 LLM: "只输出 JSON。字段有 party_a (字符串)、amount_krw (数字)……"。

### 3.2 实战中最常撞到的三类失败

1. **夹带闲聊**: "好的！我来帮您抽取: {...} 希望有帮助！"——JSON 前后带寒暄。
2. **markdown 代码围栏**: 用 ` ```json ... ``` ` 包起来返回。
3. **类型/字段错误**: 金额变成 `"1亿2千万韩元"` (字符串)，或者字段干脆缺了。

第 1、2 类用**防御式解析** (用正则只截出 JSON 部分) 解决，第 3 类用**模式校验 + 重新请求**解决。

### 3.3 请求-校验-重试循环

```
提示词(写明模式) → 回答 → 截出 JSON → 解析
  → 校验通过？ → 使用
  → 失败？ → 追加"上一次回答的问题: 金额必须是数字"后重新请求 (最多 N 次)
  → 超过 N 次？ → 转人工复核队列 (兜底)
```

关键在于重新请求的提示词里要**把失败原因原样带上**。告诉 LLM 它自己的输出哪里错了，大多数情况 1~2 次内就改对。另外别搞无限重试，要设上限；超了也绝不能悄悄扔掉，必须交给人。

### 3.4 模式校验 — 至少查这三样

- **字段是否存在**: 需要的键都在吗。
- **类型**: 数字栏里是不是数字 (`isinstance` 检查)。
- **格式/范围**: 日期是不是 `YYYY-MM-DD`，比例在不在 0~100 之间。

顺带一提，新一些的 API 带有服务端强制模式的结构化输出功能 (见文件末尾注释示例)，重试基本就不需要了；但校验这个习惯仍然必须保留——因为它保证不了值的**内容** (比如凭空编出合同里没有的金额)。

### 3.5 实务适用边界 — 能放手到哪一步

这套模式可以原样照搬的业务: 从简历抽取工作经历与学历，从票据抽取金额、日期、科目，从咨询记录抽取投诉类型与诉求，从会议纪要抽取决议、负责人与期限。共同点是"有原文，且输出格式固定"。反过来，需要推断原文里没有的值的项目 (例如"这份合同的风险等级")，那是判断题而非抽取题，没有另一套校验体系就不该自动化。实务部署时，把抽取结果连同置信标记 (是否一次校验通过、重试了几次) 一起存下来，以后挑抽检样本就容易多了。

## 4. 动手练习 — main.py

运行:

```bash
cd zh/lecture11_llm_and_rag/level03_structured_output
python3 main.py
```

输出解读:

- **[1]** 任务定义: 展示 153 字的合同原文和期望的 6 个字段 (双方、金额、期限、违约金比例)。
- **[2] 第 1 次尝试**: 模拟 LLM 给出一个实战常见的回答——闲聊 + 代码围栏 + 金额是字符串 `"1亿2千万韩元"` + 字段缺失。防御式解析能过，但校验抓到 2 条错误:

```
  [校验失败] 共 2 条:
    - 类型错误: amount_krw 必须是 int (当前值: '1亿2千万韩元')
    - 字段缺失: penalty_rate_per_day (每逾期1日的违约金比例(%))
```

- **[2] 第 2 次尝试**: 错误内容被加进提示词之后，回来的就是正确的 JSON，校验通过。
- **[3]** 用定稿数据立刻算出"每逾期1日违约金 = 120,000,000 x 0.1% = 120,000 韩元"——这就是类型有保证的数据的威力。

代码核心: `extract_json_block()` (去围栏、去闲聊)、`validate()` (把缺失、类型、日期格式一次性收集)、`extract_with_retry()` (把失败原因累积到 `feedback` 里再请求)。`MockExtractorLLM` 靠"提示词里有没有错误反馈"来复现第 1 次失败、第 2 次成功——这是把真实 LLM 的自我修正倾向做了简化。

## 5. 自己动手试试

1. **(简单)** 往 `SCHEMA` 里加一条 `"vat_included": (bool, "是否含增值税")`。第 2 次的回答里没有这个字段，会发生什么？(提示: 3 次全失败 → 人工复核兜底那条路第一次被走通。)
2. **(中等)** 给 `validate()` 加上范围校验: `amount_krw` 必须大于 0，`end_date` 必须晚于 `start_date`。(提示: `YYYY-MM-DD` 字符串的字典序比较等价于日期比较。)
3. **(挑战)** 把 `MockExtractorLLM` 第 1 次的回答改成"少了一个花括号的坏 JSON"，让 `json.JSONDecodeError` 那条分支也跑起来。对比一下解析失败和校验失败的反馈文案有什么不同。

## 6. 常见误区

- **不加 try 就调 `json.loads()`** — LLM 的输出是随时可能坏掉的外部输入。异常处理不是选项，是默认值。
- **第一次成功就省掉校验** — LLM 的水平就是 100 次里对 97 次。剩下那 3 次就是线上事故。
- **重试时原样重发同一份提示词** — 不告诉它错在哪，它就会一模一样地再错一遍。把错误信息写进提示词。
- **无限重试** — 没有上限的循环既是费用炸弹也是故障点。3 次上下 + 人工兜底是标准做法。
- **把"校验通过"当成"内容正确"** — 模式校验只看"外形"。金额跟合同是否一致，得靠抽检和评估 (level11) 来确认。
