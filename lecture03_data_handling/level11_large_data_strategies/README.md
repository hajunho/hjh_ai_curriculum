# Lecture 03 · Level 11 — 대용량 데이터 처리 전략

> 데이터가 메모리보다 커지기 시작할 때 쓰는 생존 기술 — dtype 다이어트, 청크 처리, categorical — 과 "pandas를 떠날 타이밍"을 배웁니다.

**난이도** ⭐⭐⭐⭐⭐ / **선행** level04, level07 / **예상 시간** 70분

## 1. 왜 배우나 — 비즈니스 관점

어제까지 잘 돌던 분석 스크립트가 어느 날 "MemoryError"와 함께 죽습니다. 회사가 성장해서 데이터가 10배가 됐기 때문입니다. 이때 두 갈래 길이 있습니다. 하나는 "우리도 이제 빅데이터니까 Spark 도입하자"며 몇 달짜리 프로젝트를 여는 길, 다른 하나는 30분짜리 튜닝으로 같은 노트북에서 계속 돌게 만드는 길입니다. 놀랍게도 실무에서 마주치는 "대용량" 문제의 대다수는 두 번째 길로 해결됩니다.

이 레벨에서 배우는 것은 그 30분짜리 튜닝의 정체입니다. 데이터 타입(dtype)을 다이어트해서 메모리를 절반 이하로 줄이고, 파일을 청크(chunk) 단위로 나눠 읽어 메모리보다 큰 파일을 처리하고, 반복되는 문자열을 categorical로 바꿔 압축하는 기술입니다. 그리고 마지막으로, 이 기술들로도 안 될 때 — 진짜로 DB나 Spark로 넘어가야 할 때 — 를 판별하는 기준을 정리합니다. 도구를 아는 것만큼, 도구의 한계를 아는 것이 시니어의 실력입니다.

## 2. 비유로 이해하기

**메모리는 책상, 디스크는 서고입니다.** pandas는 "서고(파일)에서 책(데이터)을 몽땅 꺼내 책상(메모리)에 펼쳐 놓고 작업하는" 도구입니다. 책상보다 책이 많아지면 세 가지 전략이 있습니다.

- **dtype 다이어트 = 문고판으로 바꾸기.** 같은 내용이라도 양장본(int64, 8바이트) 대신 문고판(int32, 4바이트)으로 꽂으면 책상 위 공간이 절반이 됩니다. 숫자의 범위가 문고판에 다 들어간다면 양장본을 고집할 이유가 없지요.
- **categorical = 줄임말 사전.** "강남점"이라는 글자를 25만 번 반복해서 적는 대신, 사전에 "1=강남점"이라고 한 번 적고 본문에는 1만 적는 방식입니다. 반복되는 문자열이 많을수록 극적으로 줄어듭니다.
- **청크 처리 = 책을 한 챕터씩 가져오기.** 전집을 통째로 책상에 올릴 수 없으면, 한 권씩 가져와 요약 메모만 남기고 반납하면 됩니다. 책상은 작아도 전집 전체를 요약할 수 있습니다. 단, "요약(집계)"처럼 부분 결과를 합칠 수 있는 작업에만 통합니다.

그리고 서고 자체를 바꾸는 방법이 파케이(Parquet) 같은 열 지향 포맷이고, 서고가 도서관 규모가 되면 사서(DB)나 분산 서고(Spark)를 부르는 것입니다.

## 3. 핵심 개념

### 3-1. 먼저 재라 — memory_usage(deep=True)

다이어트의 시작은 체중계입니다. `df.memory_usage(deep=True)`는 열별 메모리 사용량을 바이트로 알려 줍니다. `deep=True`가 중요합니다. 문자열(object) 열은 이 옵션 없이는 포인터 크기만 세어 실제보다 훨씬 작게 보고되기 때문입니다. 재 보면 거의 항상 문자열 열이 메모리 하마입니다.

### 3-2. dtype 다이어트

| 변환 | 크기 변화 | 조건 |
|---|---|---|
| int64 → int32 | 8B → 4B (½) | 값이 ±21억 이내 |
| float64 → float32 | 8B → 4B (½) | 유효숫자 7자리면 충분할 때 |
| object → category | 수십 분의 1까지 | 고유값 수 ≪ 행 수 |

주의할 점은 두 가지입니다. float32는 유효숫자가 7자리 정도라 금액 합계처럼 큰 수를 다룰 때 끝자리가 달라질 수 있고(회계 보고면 float64 유지), category는 고유값이 행 수에 육박하면(주문번호 같은 ID) 오히려 사전 유지 비용 때문에 손해입니다.

### 3-3. read_csv(chunksize=...) — 스트리밍 집계 패턴

`pd.read_csv(path, chunksize=50_000)`은 DataFrame 대신 "5만 행씩 꺼내 주는 반복자(iterator)"를 돌려줍니다. 실무 패턴은 정해져 있습니다.

```python
total = None
for chunk in pd.read_csv(path, chunksize=50_000):
    part = chunk.groupby("store")["revenue"].sum()
    total = part if total is None else total.add(part, fill_value=0)
```

핵심은 **부분 집계를 합쳐도 전체 집계와 같은 연산**(합, 개수, 최대·최소)이어야 한다는 것입니다. 평균은 "합과 개수를 따로 모아 마지막에 나누기"로 바꿔야 하고, 중앙값처럼 전체를 봐야 하는 통계는 이 패턴으로 안 됩니다.

### 3-4. 열 지향 포맷 — 파케이(Parquet) 개념

CSV는 행 단위 텍스트라 ① 숫자를 글자로 저장해 크고 ② 매번 파싱이 필요하며 ③ 열 2개만 필요해도 전체를 읽어야 합니다. 파케이는 데이터를 열 단위로, 타입 정보와 압축을 포함해 저장하는 이진 포맷입니다. 필요한 열만 골라 읽을 수 있고, dtype이 보존되며, 보통 CSV의 몇 분의 1 크기가 됩니다. pandas에서는 `df.to_parquet(...)` / `pd.read_parquet(...)` 한 줄이지만 pyarrow 같은 엔진 설치가 필요해, 이 실습에서는 개념과 코드 예시(주석)로만 다룹니다. 반복해서 읽는 데이터라면 "CSV로 받아 파케이로 저장해 두고 쓰는" 습관이 팀 전체의 시간을 아껴 줍니다.

### 3-5. 언제 pandas를 떠나는가

| 신호 | 처방 |
|---|---|
| 데이터가 메모리의 1/3 이하 | 그냥 pandas |
| 메모리에 빠듯하게 들어옴 | dtype 다이어트 + 파케이 |
| 메모리보다 크지만 집계가 목적 | chunksize 스트리밍, 또는 Polars/DuckDB |
| 여러 사람이 같은 데이터를 조회·갱신 | DB (lecture04에서 배웁니다) |
| 수억 행 이상, 여러 서버가 필요 | Spark 등 분산 처리 |

"몇 GB냐"보다 중요한 것은 **작업의 성격**입니다. 혼자 하는 일회성 분석은 놀랄 만큼 큰 데이터까지 pandas로 버틸 수 있고, 반대로 작은 데이터라도 동시 접근·갱신이 필요하면 DB가 답입니다.

## 4. 실습 — main.py

실행 방법:

```bash
cd lecture03_data_handling/level11_large_data_strategies
python3 main.py
```

출력 흐름은 다음과 같습니다.

- **[1] 체중 재기** — 8년 치 매출 73,000행을 만들어 `memory_usage(deep=True)`로 열별 메모리를 출력합니다. 문자열 열(date, weekday, store, category)이 숫자 열보다 몇 배 무거운지 확인하세요.
- **[2] dtype 다이어트** — 문자열 열을 category로, int64를 int32로, float64를 float32로 바꾼 뒤 전/후 총 메모리와 절감률(%)을 비교합니다. 값이 달라지지 않았는지 검증도 함께 합니다.
- **[3] 청크 스트리밍 집계** — 데이터를 CSV로 저장한 뒤 `chunksize=10_000`으로 나눠 읽으며 지점별 매출 합계를 누적 집계하고, 한 번에 읽어 집계한 결과와 일치함을 검증합니다. "메모리보다 큰 파일도 이 패턴이면 된다"는 것을 몸으로 익히는 단계입니다.
- **[4] 읽기 최적화 비교** — 같은 CSV를 ① 아무 옵션 없이 ② `usecols` + `dtype` 지정으로 읽어, 걸린 시간과 결과 DataFrame의 메모리를 비교합니다. 필요한 열만 읽는 것이 가장 확실한 최적화임을 확인합니다.
- **[5] 판단 기준 요약** — "언제 pandas를 떠나는가" 기준표를 출력합니다.

3. **(도전)** `chunksize`를 1,000 / 10,000 / 50,000으로 바꿔 가며 [3]의 처리 시간을 재 보세요. 너무 작은 청크가 오히려 느린 이유(청크마다 드는 고정 비용)를 설명해 보세요.

## 6. 자주 하는 실수

- **deep=True 없이 메모리를 재기** — 문자열 열의 실제 크기가 숨겨져 "메모리 충분한데 왜 죽지?"라는 미스터리가 생깁니다.
- **ID 열까지 category로 바꾸기** — 고유값이 행 수만큼 많은 열은 category가 오히려 메모리를 늘립니다. 반복이 많은 열에만 쓰세요.
- **float32로 바꾸고 회계 숫자 보고하기** — 유효숫자 7자리 한계로 큰 합계의 끝자리가 달라질 수 있습니다. 원 단위가 맞아야 하는 보고서라면 float64를 유지하거나 정수(원)로 다루세요.
- **청크 패턴으로 중앙값 구하기** — 부분 결과를 합칠 수 없는 통계는 청크 스트리밍으로 계산할 수 없습니다. 근사 알고리즘이나 DB/분산 도구가 필요합니다.
- **성급한 Spark 도입** — 수백만 행은 아직 pandas(또는 Polars/DuckDB)의 영역입니다. 분산 시스템은 그 자체가 운영 비용이라는 점을 잊지 마세요.
