# Lecture 04 · Level 06 — JOIN: 여러 테이블 연결

> 나뉘어 저장된 테이블을 키로 다시 붙이는 JOIN 을 배웁니다. INNER JOIN 과 LEFT JOIN 의 차이, 조인 키를 고르는 법, 그리고 집계를 부풀리는 팬아웃 함정까지 다룹니다.

**난이도** ⭐⭐⭐ / **선행** level05 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

level01 에서 봤듯 DB는 "한 사실은 한 곳에만" 원칙으로 테이블을 나눠
저장합니다. 그래서 실무 질문은 거의 항상 여러 테이블에 걸칩니다. "누가
(customers) 무엇을(products) 얼마나(order_items) 언제(orders) 샀나?" —
네 테이블을 붙여야 답이 나옵니다. JOIN(조인)을 못 하면 SQL 은 테이블
하나짜리 장난감에 머물고, JOIN 을 하는 순간 회사 DB 전체가 하나의 분석
대상이 됩니다. 또 하나, "주문 안 한 고객"처럼 **없는 것을 찾는 질문**
(휴면 고객, 미납 거래처)은 LEFT JOIN 없이는 아예 표현할 수 없습니다.

## 2. 비유로 이해하기

주문 장부에는 "회원번호 7, 상품번호 3"처럼 번호만 적혀 있습니다. 보고서를
만들려면 직원이 **주문 장부의 한 줄을 읽고 → 회원번호를 들고 고객 명부에서
그 번호의 행을 찾아 → 이름을 옮겨 적는** 작업을 합니다. 이 "번호 들고 다른
장부 찾아가기"가 JOIN 이고, 들고 가는 번호가 **조인 키(join key)** —
대부분 한쪽의 외래키와 다른 쪽의 기본키입니다.

INNER JOIN 과 LEFT JOIN 의 차이는 **짝 없는 행의 처리**입니다. 소개팅
명단을 생각해 보세요. 참가자 명단(고객)과 매칭 기록(주문)을 붙일 때:

- **INNER JOIN**: 매칭된 사람만 결과에 남김. 매칭 기록이 없는 참가자는
  결과에서 사라짐.
- **LEFT JOIN**: 왼쪽 명단은 **전원 유지**. 매칭 기록이 없는 사람은 기록
  칸이 NULL(빈칸)로 남음. → "매칭 안 된 사람 찾기" = 빈칸인 행 찾기.

"주문 없는 고객"을 찾으려면 고객을 왼쪽에 두고 LEFT JOIN 한 뒤 주문 칸이
NULL 인 행을 고르면 됩니다.

## 3. 핵심 개념

### 3-1. INNER JOIN 기본형

```sql
SELECT o.order_id, c.name, o.ordered_at
FROM   orders AS o
JOIN   customers AS c ON c.customer_id = o.customer_id;
```

- `AS o`, `AS c`: 테이블 별칭. 여러 테이블이 등장하면 열 이름 앞에
  `별칭.` 을 붙여 어느 테이블의 열인지 명시합니다.
- `ON`: 어떤 키로 짝을 맞출지. **외래키 = 기본키** 형태가 표준입니다.
- `JOIN` 만 쓰면 INNER JOIN 의 줄임말입니다.

### 3-2. 세 테이블 이상 연결

JOIN 은 사슬처럼 이어 붙입니다. 주문상세 → 주문 → 고객, 그리고 주문상세 →
상품. level01 의 관계도를 옆에 두고, **외래키 화살표를 따라** ON 절을 쓰면
길을 잃지 않습니다.

```sql
FROM order_items AS oi
JOIN orders    AS o ON o.order_id    = oi.order_id
JOIN customers AS c ON c.customer_id = o.customer_id
JOIN products  AS p ON p.product_id  = oi.product_id
```

### 3-3. LEFT JOIN — 왼쪽은 전원 생존

```sql
SELECT c.name, o.order_id
FROM   customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id;
```

주문이 없는 고객도 결과에 남고 order_id 칸이 NULL 이 됩니다. 여기에
`WHERE o.order_id IS NULL` 을 붙이면 "주문 없는 고객"만 남습니다 —
휴면 고객 분석의 정석 패턴입니다. (RIGHT JOIN 은 좌우만 바꾼 것이라
실무에선 대부분 LEFT 로 통일합니다.)

### 3-4. 팬아웃(fan-out) 함정 — 조인이 행을 불린다

1:N 관계를 조인하면 **1쪽의 행이 N개로 복제**됩니다. 주문 1건에 상품이
3종이면, orders 를 order_items 에 붙이는 순간 그 주문은 3행이 됩니다.
여기까지는 정상입니다. 사고는 그다음에 납니다. 불어난 결과에서
`COUNT(*)` 로 "주문 수"를 세면 1,000건이 아니라 2,000건쯤으로 **부풀려**
나옵니다. 매출 합계에 고객 테이블을 잘못 붙여도 같은 일이 벌어집니다.

방어법 두 가지:

1. 집계 대상의 **고유 키로 세기**: `COUNT(DISTINCT o.order_id)`.
2. **필요한 테이블만 조인**: 그 집계에 안 쓰는 테이블은 붙이지 않기.

조인 후 집계 결과가 "느낌보다 크게" 나오면 무조건 팬아웃부터 의심하세요.

### 3-5. ON 과 WHERE 의 역할 분담

ON 은 "짝 맞추는 규칙", WHERE 는 "붙인 결과에서 고르는 조건"입니다. INNER
JOIN 에서는 어디에 써도 결과가 같지만, LEFT JOIN 에서는 WHERE 에 오른쪽
테이블 조건을 쓰는 순간 NULL 행이 탈락해 **사실상 INNER JOIN 이 되어**
버립니다. LEFT JOIN 의 오른쪽 조건은 ON 에 쓰는 것이 안전합니다.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

- **[1] 두 테이블**: 주문+고객 — 번호 대신 이름이 보이는 첫 조인.
- **[2] 네 테이블**: "누가 무엇을 몇 개, 얼마어치 샀나" — 주문상세를
  중심으로 주문·고객·상품을 사슬 조인.
- **[3] 조인+집계**: 고객별 총구매액 톱5 — JOIN 과 GROUP BY 의 합체.
- **[4] LEFT JOIN**: 고객 전원 + 주문 수. 주문 없는 고객이 0으로 나오는
  것을 확인합니다.
- **[5] 안티 조인**: `WHERE o.order_id IS NULL` 로 "한 번도 주문하지 않은
  고객" 명단 — 휴면 고객 리포트.
- **[6] 팬아웃 시연**: 같은 "주문 수" 질문을 (a) orders 단독, (b) order_items
  조인 후 COUNT(*), (c) COUNT(DISTINCT order_id) 세 가지로 세어 (b)만
  부풀려지는 것을 숫자로 확인합니다. 이 표 하나가 이 레벨에서 가장
  값진 출력입니다.

## 6. 자주 하는 실수

- **ON 누락(카티전 곱)**: ON 없이 조인하면 모든 행×모든 행 조합이
  생깁니다. 1,000행×200행=20만 행. 결과가 폭발하면 ON 부터 확인.
- **잘못된 키 조인**: 이름처럼 중복 가능한 열로 조인하면 동명이인끼리
  뒤엉킵니다. 조인 키는 기본키↔외래키.
- **팬아웃 상태에서 SUM/COUNT**: 3-4절 참고. 집계 전에 "이 조인으로 행이
  불었나?"를 자문하세요.
- **LEFT JOIN + WHERE 오른쪽 조건**: NULL 행이 잘려 INNER 가 됩니다.
  오른쪽 테이블 조건은 ON 으로.
- **별칭 없이 같은 열 이름**: 두 테이블에 다 있는 name 을 그냥 쓰면
  모호성 에러이거나, 더 나쁘게는 엉뚱한 쪽이 선택됩니다. 조인문에서는
  모든 열에 별칭을 붙이는 습관을.
