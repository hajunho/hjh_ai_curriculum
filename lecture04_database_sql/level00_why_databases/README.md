# Lecture 04 · Level 00 — 데이터베이스가 왜 필요한가

> 엑셀 파일 돌려쓰기가 만드는 세 가지 지옥(동시 수정·정합성·권한)을 직접 시뮬레이션으로 겪어 보고, 데이터베이스가 이 문제를 어떻게 해결하는지 확인합니다.

**난이도** ⭐ / **선행** 없음 (lecture02 수준의 파이썬 읽기 능력이면 충분) / **예상 시간** 30분

## 1. 왜 배우나 — 비즈니스 관점

회사에서 이런 메일을 받아 본 적이 있을 겁니다.
"고객명단_최종.xlsx 말고 고객명단_최종_진짜최종_v3.xlsx 로 봐 주세요."
파일을 주고받는 순간부터 **어느 것이 진짜인지** 아무도 모르게 됩니다.
두 사람이 같은 파일을 동시에 고치면 한 사람의 작업이 조용히 사라지고,
같은 고객이 시트마다 다른 이름으로 적혀 매출 합계가 매번 다르게 나오고,
연봉 정보가 든 파일이 "참고하세요"라는 메일 한 통으로 전 직원에게 퍼집니다.

데이터베이스(Database, DB)는 이 문제를 풀기 위해 만들어진 도구입니다.
"엑셀보다 어려운 것"이 아니라 "엑셀 돌려쓰기의 사고를 막는 것"이라고
이해하는 순간, 왜 모든 회사 시스템 뒤에 DB가 있는지 보이기 시작합니다.

## 2. 비유로 이해하기

**엑셀 돌려쓰기 = 장부 복사해서 나눠 갖기**입니다. 경리부 장부를 복사기로
복사해 영업부, 마케팅부가 한 부씩 가져가서 각자 고친다고 상상해 보세요.
한 달 뒤 세 장부의 숫자는 전부 다릅니다. 누가 맞는지 확인하려면 세 장부를
한 줄씩 대조하는 야근이 기다립니다.

**데이터베이스 = 금고 안의 원본 장부 + 창구 직원**입니다. 장부 원본은 금고에
한 권만 있습니다. 아무도 장부를 직접 만지지 못하고, 창구 직원(DBMS,
데이터베이스 관리 시스템)에게 "3번 고객 주소를 바꿔 주세요", "이번 달 매출
보여 주세요"라고 **요청**합니다. 창구 직원은 요청을 한 줄로 세워 순서대로
처리하고(동시 수정 해결), 장부 규칙에 어긋나는 기록은 거절하고(정합성),
요청한 사람의 권한을 확인해 보여 줄 것만 보여 줍니다(권한).

이 창구 직원에게 말을 거는 표준 언어가 SQL(에스큐엘, Structured Query
Language)이고, 이번 강의 전체에서 배울 내용입니다.

## 3. 핵심 개념

### 3-1. 동시 수정 문제 (Lost Update)

김대리와 박과장이 같은 엑셀 사본을 열어 각자 다른 셀을 고친 뒤 저장하면,
**나중에 저장한 사람의 파일이 통째로 이깁니다.** 먼저 저장한 사람의 수정은
흔적도 없이 사라집니다. 이를 갱신 손실(lost update)이라고 부릅니다.
무서운 점은 **에러가 나지 않는다**는 것입니다. 아무도 모르게 데이터가 사라집니다.

DB는 수정 요청을 한 곳에서 순서대로 처리하므로, 서로 다른 행을 고치는 두
요청은 둘 다 반영되고, 같은 행을 고치는 요청은 잠금(lock)으로 순서를 보장합니다.

### 3-2. 정합성 문제 (Integrity)

엑셀은 셀에 무엇이든 들어갑니다. 수량 칸에 "세 개", 날짜 칸에 "월요일쯤",
같은 고객이 "(주)한빛"과 "한빛 주식회사"로 두 번 등록되는 것을 막을 방법이
사실상 없습니다. 집계할 때마다 다른 숫자가 나오는 이유입니다.

DB는 테이블을 만들 때 **규칙을 먼저 선언**합니다. "수량은 정수만", "고객
번호는 중복 불가", "주문의 고객 번호는 고객 명단에 실제로 있어야 함" 같은
규칙(제약조건, constraint)을 어기는 데이터는 저장 자체가 거부됩니다.

### 3-3. 권한 문제 (Access Control)

엑셀 파일은 복사되는 순간 통제를 벗어납니다. 연봉 열 하나 때문에 파일
전체를 못 보내거나, "이 열은 못 본 걸로 해 주세요"라는 비현실적 부탁을
하게 됩니다. DB는 사용자별로 "이 테이블은 조회만", "이 열은 아예 안 보임"
같은 권한을 창구에서 걸어 줍니다. 원본은 한 번도 밖으로 나가지 않습니다.

### 3-4. 그래서 언제 DB를 쓰나

| 상황 | 엑셀 | DB |
|---|---|---|
| 혼자 쓰는 일회성 계산 | ✅ 최적 | 과함 |
| 여러 명이 같은 데이터를 수정 | ❌ 사고 예정 | ✅ |
| 수십만 행 이상 | ❌ 느려짐/한계 | ✅ |
| 규칙 있는 데이터 (주문, 회원, 재고) | ❌ 오염됨 | ✅ |
| 민감 정보 포함 | ❌ 유출 위험 | ✅ 권한 관리 |

엑셀이 나쁜 도구라는 뜻이 아닙니다. **여럿이, 오래, 규칙을 지키며** 써야
하는 데이터의 원본 보관소로는 부적합하다는 뜻입니다. 실무 최강 조합은
"원본은 DB, 분석과 보고서는 SQL 로 뽑아서 엑셀/파이썬"입니다.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

이 레벨의 main.py 는 SQL 을 아직 몰라도 읽을 수 있습니다. 네 단계로
'엑셀 방식'의 사고를 파이썬 시뮬레이션으로 재현하고, 마지막에 DB 방식과
대비합니다.

- **[1] 동시 수정 사고**: 같은 '파일'(딕셔너리 목록)을 김대리와 박과장이
  복사해 각자 다른 항목을 고친 뒤 차례로 '저장'합니다. 출력에서 김대리의
  수정이 사라진 것을 직접 확인하세요. 에러 메시지는 한 줄도 없습니다.
- **[2] 정합성 오염**: 같은 고객이 표기만 다르게 두 번 입력된 명단으로
  거래처별 합계를 내면, 하나여야 할 거래처가 둘로 쪼개져 보고서가 틀립니다.
- **[3] 권한 부재**: 파일을 통째로 전달하는 순간 연봉 열까지 함께 전달되는
  상황을 보여 줍니다.
- **[4] DB 방식**: 파이썬 내장 sqlite3 로 실제 데이터베이스 `hjh_shop.db` 를
  만들고, 두 개의 연결(두 명의 사용자에 해당)이 각각 다른 행을 수정해도
  **둘 다 안전하게 반영**되는 것, 그리고 잘못된 데이터(문자 수량)가
  **저장 단계에서 거부**되는 것을 확인합니다.

출력에서 주목할 부분: [1]의 마지막 표에는 박과장의 수정만 남아 있고,
[4]의 표에는 두 사람의 수정이 모두 남아 있습니다. 같은 시나리오, 다른 결과 —
이 차이가 이 강의 전체의 출발점입니다.

## 6. 자주 하는 실수

- **"DB = 큰 엑셀"이라는 오해**: 핵심 차이는 크기가 아니라 *창구(요청 처리)*
  의 존재입니다. 규칙 검사, 순서 보장, 권한이 전부 창구에서 이뤄집니다.
- **엑셀을 무조건 버리려는 것**: 일회성 분석·보고서엔 엑셀이 여전히
  최고입니다. 원본 보관과 공동 수정만 DB에 맡기면 됩니다.
- **"우리 회사는 공유 드라이브라 괜찮다"**: 동시 편집이 되는 클라우드
  스프레드시트도 정합성 규칙과 세밀한 권한, 대용량 처리는 해결해 주지
  못합니다. 문제의 절반만 풀린 상태입니다.
- **sqlite3 설치를 검색하는 것**: SQLite 는 파이썬에 내장되어 있습니다.
  `import sqlite3` 한 줄이면 끝. 이 강의 전체에서 설치할 것은 없습니다.
