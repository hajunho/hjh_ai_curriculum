# Lecture 04 · Level 09 — 인덱스와 쿼리 성능

> 인덱스가 왜 검색을 빠르게 하는지 색인 비유로 이해하고, EXPLAIN QUERY PLAN 으로 DB의 작전을 읽고, 30만 행 테이블에서 인덱스 전후의 실측 시간을 비교합니다.

**난이도** ⭐⭐⭐⭐ / **선행** level08 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

"이 화면 왜 이렇게 느려요?"— 사내 시스템에 대한 불만의 상당수는 **인덱스
없는 검색** 때문입니다. 데이터가 적을 때는 아무 쿼리나 빨라서 문제가
숨어 있다가, 데이터가 쌓이면 갑자기 수십 배 느려집니다. 인덱스(index)의
원리를 알면 두 가지가 가능해집니다. 첫째, 내가 만든 쿼리가 느릴 때
막연히 기다리는 대신 원인을 진단할 수 있습니다. 둘째, 개발팀과 "여기
customer_id 검색이 풀스캔으로 도는 것 같은데 인덱스 확인해 주실래요?"
수준의 대화가 가능해집니다. 이 한 문장이 되는 비개발자는 정말 드물고,
그만큼 귀한 대접을 받습니다.

## 2. 비유로 이해하기

**인덱스는 책 뒤의 색인(찾아보기)입니다.** 600쪽짜리 책에서 '감가상각'이
나오는 곳을 찾는 두 가지 방법: (1) 1쪽부터 끝까지 훑기 — 풀스캔(full
scan). (2) 뒤쪽 색인에서 '감가상각 → 152, 380쪽'을 보고 바로 펴기 —
인덱스 탐색. 색인은 가나다순으로 정렬돼 있어 몇 번의 눈길만으로 원하는
항목을 찾습니다. 데이터가 10배로 늘면 풀스캔은 10배 느려지지만, 정렬된
색인에서 찾는 비용은 거의 늘지 않습니다.

공짜는 아닙니다. 색인이 있는 책에 새 내용을 끼워 넣으면 **색인도 함께
고쳐야** 합니다. 인덱스가 많은 테이블일수록 INSERT/UPDATE 가 느려지고
저장 공간도 더 씁니다. 그래서 인덱스는 "자주 검색하는 열에만, 필요한
만큼만"이 원칙입니다.

또 하나 — 색인은 **첫 글자부터 정렬**되어 있습니다. '…상각'처럼 단어
중간으로는 찾을 수 없죠. 그래서 `LIKE '%커피%'` 같은 중간 일치 검색은
인덱스가 있어도 풀스캔이 됩니다.

## 3. 핵심 개념

### 3-1. 인덱스 만들기

```sql
CREATE INDEX idx_big_customer ON big_orders (customer_id);
```

`테이블(열)` 을 지정하면 그 열의 값이 정렬된 별도 자료구조(B-트리)가
만들어지고, 이후 그 열로 검색하는 쿼리에서 DB가 **알아서** 인덱스를
사용합니다. 쿼리 문장은 한 글자도 바꿀 필요가 없습니다 — 빨라지는 것은
실행 경로뿐입니다.

### 3-2. EXPLAIN QUERY PLAN — DB의 작전 읽기

쿼리 앞에 `EXPLAIN QUERY PLAN` 을 붙이면 실행하지 않고 **작전만** 보여
줍니다.

- `SCAN big_orders` — 전 행을 훑겠다(풀스캔). 큰 테이블이면 경고 신호.
- `SEARCH big_orders USING INDEX idx_... (customer_id=?)` — 색인으로
  바로 찾겠다. 안심.

느린 쿼리를 만나면 (1) EXPLAIN 으로 SCAN 인지 확인 → (2) WHERE 에 쓰인
열에 인덱스가 있는지 확인 — 이 두 단계가 성능 진단의 기본기입니다.

### 3-3. 기본키는 이미 인덱스다

기본키에는 자동으로 인덱스가 걸립니다. `WHERE order_id = 5` 가 항상 빠른
이유입니다. 문제는 외래키나 검색 조건으로 자주 쓰는 일반 열
(customer_id, 날짜, 상태…)이며, 이런 열이 인덱스 후보입니다.

### 3-4. 인덱스가 소용없는 경우

- **중간 일치 LIKE**: `LIKE '%커피%'` — 색인은 첫 글자부터 정렬이므로 불가.
  (`LIKE '커피%'` 는 가능합니다.)
- **열을 가공한 조건**: `WHERE price * 1.1 > 1000` — 가공된 값은 색인에
  없습니다. 조건식을 `price > 1000 / 1.1` 로 바꾸면 인덱스를 탑니다.
- **결과가 테이블의 대부분인 조건**: 절반을 가져올 거면 색인을 오가는
  것보다 그냥 훑는 게 빠를 수 있어, DB가 스스로 풀스캔을 택하기도 합니다.

### 3-5. 쓰기 비용 — 인덱스의 청구서

인덱스 하나가 늘 때마다 INSERT/UPDATE/DELETE 는 인덱스 갱신 작업을
추가로 합니다. 조회가 압도적으로 많은 분석용 테이블은 인덱스를 넉넉히,
쓰기가 잦은 주문 접수 테이블은 꼭 필요한 것만 — 트레이드오프입니다.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

main.py 는 실습 DB에 30만 행짜리 `big_orders` 테이블을 만들어 실험합니다
(생성에 몇 초 걸립니다).

- **[1] 실험대 준비**: 30만 행 생성 (seed 고정으로 매번 같은 데이터).
- **[2] 인덱스 없이 검색**: `WHERE customer_id = ?` 를 200회 반복 실행해
  총 소요 시간을 실측합니다. EXPLAIN 결과는 `SCAN` — 매번 30만 행을
  훑는다는 뜻입니다.
- **[3] 인덱스 생성**: `CREATE INDEX` 한 줄. 생성 시간도 측정합니다.
- **[4] 인덱스 후 같은 검색**: 같은 쿼리 200회를 다시 실측. EXPLAIN 이
  `SEARCH ... USING INDEX` 로 바뀌고, 시간이 수십~수백 배 줄어드는 것을
  숫자로 확인합니다.
- **[5] 인덱스가 소용없는 검색**: `LIKE '%몰%'` 성 중간 일치 조건은
  인덱스가 있어도 SCAN 임을 EXPLAIN 으로 확인합니다.
- **[6] 쓰기 비용**: 같은 1만 행 INSERT 를 인덱스 없는 테이블/있는 테이블에
  각각 수행해 쓰기 속도 차이를 측정합니다.

실행 환경에 따라 절대 시간은 다르지만 **배율**은 언제나 극적입니다.
출력의 "배 빨라짐" 숫자를 확인해 보세요.

## 6. 자주 하는 실수

- **모든 열에 인덱스를 거는 것**: 쓰기가 느려지고 공간을 낭비합니다.
  "WHERE/JOIN 에 자주 쓰는 열"만 후보입니다.
- **느리다 → 서버 탓**: 먼저 EXPLAIN. 풀스캔 한 줄이 원인의 대부분입니다.
- **작은 테이블에서 효과를 기대**: 수백 행짜리 테이블은 풀스캔도
  순식간이라 차이가 안 보입니다. 인덱스는 데이터가 클수록 빛납니다.
- **함수로 감싼 조건**: `WHERE SUBSTR(ordered_at,1,7)='2025-06'` 은 인덱스
  무용. 범위 조건 `ordered_at BETWEEN '2025-06-01' AND '2025-06-30'` 으로
  다시 쓰면 인덱스를 탑니다.
- **측정 없이 논쟁**: "느린 것 같다"는 감이 아니라 이 레벨처럼 반복 실측
  숫자로 말하세요.
