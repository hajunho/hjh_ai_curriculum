# Lecture 04 · Level 01 — 테이블·행·열·기본키·외래키

> 데이터베이스 안이 어떻게 생겼는지 배웁니다. 테이블·행·열의 구조, 행마다 붙는 고유 번호(기본키), 테이블끼리 연결하는 참조 번호(외래키)를 실습 DB의 스키마를 직접 조회하며 확인합니다.

**난이도** ⭐ / **선행** level00 / **예상 시간** 35분

## 1. 왜 배우나 — 비즈니스 관점

회사 시스템 담당자에게 "주문 데이터 좀 주세요"라고 하면 이런 답이 돌아옵니다.
"orders 테이블에는 금액이 없어요. order_items 랑 products 를 붙여야 합니다."
이 말을 알아듣지 못하면 데이터 요청은 늘 핑퐁이 됩니다. DB의 데이터는 엑셀의
'한 장짜리 큰 표'가 아니라 **여러 개의 작은 표가 번호로 연결된 구조**로
저장됩니다. 이 구조도(스키마, schema)를 읽을 줄 알면, 어떤 데이터가 어디에
있고 무엇과 무엇을 붙여야 원하는 표가 나오는지 스스로 판단할 수 있습니다.
SQL 문법보다 먼저 배워야 하는, 지도 읽는 법입니다.

## 2. 비유로 이해하기

동네 문구점 사장님의 장부 정리법을 떠올려 보세요. 처음엔 공책 한 권에
"3월 2일, 김민준(서울 사는 단골), 만년필 2개, 개당 29,000원…"이라고 전부
적었습니다. 그런데 김민준 님이 이사를 가자 문제가 생깁니다. 공책 전체에서
김민준이 나오는 줄을 **모두 찾아** 주소를 고쳐야 합니다. 한 줄이라도 놓치면
장부가 서로 모순됩니다.

똑똑한 사장님은 장부를 나눕니다. **고객 명부**(고객마다 회원번호), **상품
목록**(상품마다 상품번호), **주문 장부**(날짜와 "회원번호 7번이 상품번호 9번을
2개")로요. 이제 주소가 바뀌면 고객 명부의 딱 한 줄만 고치면 됩니다.

여기서 DB의 핵심 개념이 전부 나왔습니다.

- 장부 한 권 = **테이블(table)**
- 장부의 한 줄 = **행(row)** — 고객 한 명, 주문 한 건
- 장부의 항목(이름, 주소…) = **열(column)**
- 회원번호처럼 행마다 붙는 고유 번호 = **기본키(primary key, PK)**
- 주문 장부에 적힌 "회원번호 7번" = 다른 장부를 가리키는 **외래키(foreign key, FK)**

## 3. 핵심 개념

### 3-1. 기본키 — 절대 겹치지 않는 이름표

이름은 기본키가 될 수 없습니다. 동명이인이 있으니까요. 그래서 모든 테이블은
행마다 고유한 값(고객번호, 주문번호, 사번…)을 하나 정해 둡니다. 기본키의
조건은 두 가지: **중복 불가, 비어 있음(NULL) 불가.** DB는 이 규칙을 어기는
저장을 거부합니다(level00 에서 이미 목격했습니다).

### 3-2. 외래키 — 다른 장부를 가리키는 손가락

orders 테이블의 customer_id 열에는 고객 이름이 아니라 **customers 테이블의
기본키 값**이 들어 있습니다. "이 주문의 주인은 고객 명부 7번 행"이라는
참조입니다. 이렇게 하면 (1) 고객 정보 수정은 한 곳에서 끝나고, (2) 존재하지
않는 고객의 주문 같은 유령 데이터를 막을 수 있습니다.

### 3-3. 실습 DB 다섯 테이블

이번 강의 내내 쓸 쇼핑몰 DB `hjh_shop.db` 의 구조입니다.

| 테이블 | 내용 | 기본키 | 외래키 |
|---|---|---|---|
| customers | 고객 200명 (이름·도시·등급·가입일) | customer_id | — |
| products | 상품 10종 (이름·카테고리·판매가·원가) | product_id | — |
| employees | 직원 20명 (이름·부서·급여·상사) | employee_id | manager_id → employees |
| orders | 주문 1,000건 (누가·언제·상태) | order_id | customer_id → customers, employee_id → employees |
| order_items | 주문 상세 (어떤 상품 몇 개) | (order_id, product_id) | order_id → orders, product_id → products |

텍스트 관계도로 그리면:

```
customers ──< orders >── employees ┐
                │              └───┘ (manager_id 자기참조)
                └──< order_items >── products
```

`──<` 는 일대다(1:N) 관계입니다. 고객 한 명이 주문 여러 건을 갖습니다.

### 3-4. 왜 주문 장부에 금액이 없을까 — 정규화 맛보기

orders 에 상품명과 가격을 함께 적으면 같은 정보가 천 번 반복되고, 가격이
바뀌면 천 줄을 고쳐야 합니다. **한 사실은 한 곳에만 적는다** — 이 원칙을
정규화(normalization)라고 합니다. 대신 조회할 때 테이블을 붙여야 하는데,
그 방법(JOIN)은 level06 에서 배웁니다. "저장은 나눠서, 조회는 붙여서"가
관계형 DB의 기본 리듬입니다.

### 3-5. order_items 의 기본키가 두 개?

order_items 의 기본키는 (order_id, product_id) **묶음**입니다. "17번 주문에서
3번 상품" 조합은 한 번만 나올 수 있다는 뜻이죠. 이런 것을 복합키(composite
key)라고 합니다. 두 장부 사이(주문↔상품)의 다대다 관계를 풀어 주는 다리
역할 테이블에서 자주 보게 됩니다.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

main.py 는 `hjh_shop.db` 를 만든 뒤, DB 자신에게 "너는 어떻게 생겼니?"라고
물어봅니다. SQLite 는 `sqlite_master` 라는 특별 테이블에 모든 테이블의 생성
문장을 보관하고 있어서, SQL 로 스키마를 조회할 수 있습니다.

- **[1] 테이블 목록**: `SELECT name FROM sqlite_master WHERE type='table'`
- **[2] 각 테이블 구조**: `PRAGMA table_info(테이블명)` 으로 열 이름·자료형·
  기본키 여부를 표로 출력합니다. pk 열이 1 이상이면 기본키입니다.
- **[3] 행 수 세기**: 테이블마다 `SELECT COUNT(*)` 로 데이터 규모를 확인합니다.
- **[4] 관계도**: 외래키 연결을 따라 텍스트 관계도를 출력합니다.
- **[5] 참조 확인**: orders 의 customer_id=7 이 customers 의 7번 행을 실제로
  가리키는지, 두 테이블을 나란히 조회해 눈으로 확인합니다.

출력에서 **pk 표시가 붙은 열**과 **`_id` 로 끝나는 열**을 눈여겨보세요.
`_id` 열은 대부분 어딘가의 기본키를 가리키는 외래키입니다. 처음 보는 DB를
파악할 때도 이 요령(테이블 목록 → 각 테이블의 키 → 관계도 그리기)이
그대로 통합니다.

1. **(쉬움)** main.py 의 [2]단계 출력을 보고, 다섯 테이블의 기본키를 종이에
   적어 보세요. order_items 는 왜 두 줄이 pk 인가요?
   *힌트: 3-5절 복합키 설명을 다시 읽어 보세요.*
2. **(보통)** [5]단계를 흉내 내어, orders 테이블의 employee_id 가 employees
   테이블의 어느 행을 가리키는지 확인하는 조회를 추가해 보세요.
   *힌트: 기존 코드의 customer_id 부분을 복사해 테이블명만 바꾸면 됩니다.*
3. **(도전)** 여러분 업무의 데이터(예: 거래처, 계약, 담당자)를 테이블
   2~3개로 나눈다면 어떤 테이블에 어떤 열을 두고, 기본키와 외래키는 무엇으로
   할지 표로 설계해 보세요.
   *힌트: "한 사실은 한 곳에만" — 반복해서 적게 되는 정보가 있으면 테이블을 분리할 신호입니다.*

## 6. 자주 하는 실수

- **이름을 키로 쓰는 것**: 동명이인, 개명, 오타 앞에서 무너집니다. 키는
  의미 없는 고유 번호가 가장 안전합니다.
- **모든 것을 한 테이블에 넣으려는 습관**: 엑셀식 사고입니다. 반복되는
  정보가 보이면 테이블 분리를 떠올리세요.
- **외래키 열의 숫자를 '그냥 숫자'로 읽는 것**: customer_id=7 은 수량이나
  금액이 아니라 **다른 테이블의 7번 행**이라는 주소입니다. 평균을 내거나
  더하면 안 되는 숫자입니다.
- **스키마 확인 없이 바로 쿼리부터 쓰는 것**: 처음 보는 DB에서는 반드시
  테이블 목록과 키 구조부터 확인하세요. 이 레벨의 [1]~[4]가 그 순서입니다.
