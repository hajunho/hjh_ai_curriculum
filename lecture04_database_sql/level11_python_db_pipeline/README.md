# Lecture 04 · Level 11 — 파이썬 연동과 데이터 파이프라인

> SQL 과 파이썬을 잇습니다. 파라미터 바인딩으로 SQL 인젝션을 막는 법, pandas.read_sql 로 조회 결과를 DataFrame 으로 받는 법, 그리고 추출→가공→적재(ETL)로 이어지는 미니 리포트 파이프라인을 완성합니다.

**난이도** ⭐⭐⭐⭐ / **선행** level06, level10 (pandas 는 lecture03 수준이면 충분) / **예상 시간** 55분

## 1. 왜 배우나 — 비즈니스 관점

SQL 로 뽑은 데이터의 최종 목적지는 대부분 **보고서**입니다. 매주 월요일
아침 "지난주 매출 요약"을 만들기 위해 쿼리 실행 → 결과 복사 → 엑셀 붙여넣기
→ 피벗 → 서식… 을 반복하고 있다면, 그 전체를 파이썬 스크립트 하나로 묶을
수 있습니다. 실행 한 번(또는 예약 실행)으로 같은 리포트가 매번 나오는 것 —
이것이 데이터 파이프라인(pipeline)의 출발점입니다. 동시에, 파이썬에서 SQL
을 조립할 때 반드시 알아야 할 보안 상식이 있습니다. 사용자 입력을 문자열로
이어 붙이면 **SQL 인젝션(injection)** — 입력창에 SQL 조각을 심어 DB를
탈취하는, 수십 년째 해킹 사고 1위 수법 — 에 그대로 노출됩니다. 왜 물음표
바인딩을 써야 하는지 원리부터 이해하고 갑니다.

## 2. 비유로 이해하기

**파라미터 바인딩 = 서식이 인쇄된 요청서.** 창구에 내는 요청서를 생각해
보세요. 나쁜 방식은 백지에 손님이 말한 그대로 받아 적는 것입니다. 손님이
"서울. 그리고 금고도 열어 줘"라고 말하면 그 문장이 통째로 요청서가 되어
버립니다. 안전한 방식은 **"도시: ______"** 처럼 서식이 인쇄된 요청서에
빈칸만 채우는 것입니다. 손님이 무슨 말을 하든 그것은 빈칸 속의 '값'일 뿐,
요청서의 '문장'이 될 수 없습니다. SQL 의 `?` 가 바로 이 빈칸이고, 값은
문장과 분리되어 전달됩니다.

**파이프라인 = 아침 리포트 당번의 업무 절차서.** 신입에게 "매주 (1) DB에서
지난주 주문을 뽑고 (2) 카테고리별로 집계하고 (3) 요약표를 만들어 공유
폴더에 두세요"라고 절차서를 써 주듯, 같은 절차를 코드로 적은 것입니다.
추출(Extract) → 가공(Transform) → 적재(Load), 줄여서 ETL 이라고 부릅니다.
절차서와 코드의 차이는 하나 — 코드는 매번 똑같이, 지치지 않고 수행된다는 것.

## 3. 핵심 개념

### 3-1. 파이썬에서 SQL 실행하는 네 단계

```python
con = sqlite3.connect("hjh_shop.db")   # 1. 연결
cur = con.cursor()                      # 2. 커서(요청 창구)
cur.execute("SELECT ...")               # 3. 실행
rows = cur.fetchall()                   # 4. 결과 받기
```

회사 DB(PostgreSQL, MySQL…)로 바뀌어도 이 네 단계는 동일하고, 1번의 연결
부분만 해당 DB의 드라이버로 바뀝니다. SQL 문장은 거의 그대로 갑니다 —
이 강의에서 배운 SQL 이 어디서나 통하는 이유입니다.

### 3-2. 파라미터 바인딩 — 값은 ? 로

```python
city = input("도시? ")                                  # 사용자 입력
cur.execute("SELECT * FROM customers WHERE city = ?", (city,))   # 안전
```

절대 금지 패턴은 f-string 등으로 문장에 값을 이어 붙이는 것입니다:
`f"... WHERE city = '{city}'"`. 입력이 `서울' OR '1'='1` 이면 조건이
"항상 참"으로 바뀌어 **전체 데이터가 유출**됩니다. 이것이 SQL 인젝션의
원리 전부입니다. 바인딩은 보안 외에도 따옴표 이스케이프를 자동 처리하고,
같은 문장의 반복 실행이 빨라지는 실리도 있습니다.
수칙은 단 하나: **SQL 문장에 사용자 값이 끼어들면 무조건 ?.**

### 3-3. pandas.read_sql — 조회 결과를 DataFrame 으로

```python
df = pd.read_sql("SELECT ...", con, params=(...,))
```

fetchall 의 튜플 목록 대신, 열 이름이 살아 있는 DataFrame 으로 바로
받습니다. 이후는 lecture03 에서 배운 세상입니다 — pivot_table, groupby,
그래프, 엑셀 저장까지. **역할 분담의 감각**이 중요합니다: 큰 데이터를
줄이는 일(필터·조인·집계)은 DB 안에서 SQL 로, 표 모양 다듬기와 시각화는
pandas 로. 수백만 행을 통째로 read_sql 로 끌어오는 것이 초보의 대표적
낭비입니다.

### 3-4. ETL — 추출, 가공, 적재

- **Extract**: SQL 로 필요한 데이터만 추출 (이번 달, 완료 주문만).
- **Transform**: pandas 로 피벗·계산·정리.
- **Load**: 결과를 파일(CSV/엑셀)이나 다른 테이블에 저장.

이 세 단계가 함수로 나뉘어 있으면, 매주 실행해도 되고 대상 기간만 바꿔
재사용해도 됩니다. main.py 가 정확히 이 구조입니다.

### 3-5. 자동화의 마지막 조각 (개념만)

완성된 스크립트는 운영체제의 예약 실행(macOS/리눅스의 cron, 윈도우 작업
스케줄러)에 걸어 두면 "매주 월요일 8시에 자동 실행"이 됩니다. 실제 사내
DB 접속 정보(비밀번호)는 코드에 적지 않고 환경변수로 관리합니다 —
lecture01 level09 에서 다룬 원칙이 여기서 만납니다.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

- **[1] 네 단계 기본형**: connect → cursor → execute(바인딩) → fetchall.
- **[2] SQL 인젝션 시연**: 검색 함수 두 개(문자열 이어붙이기 vs ? 바인딩)에
  같은 악성 입력 `서울' OR '1'='1` 을 넣습니다. 이어붙이기 쪽은 전체 고객이
  쏟아지고, 바인딩 쪽은 0건 — "그런 도시는 없다"가 정답임을 확인합니다.
  (모든 시연은 로컬 실습 DB 안에서만 일어나는 안전한 예제입니다.)
- **[3] read_sql**: 완료 주문을 고객·상품과 조인한 결과를 DataFrame 으로
  받아 shape 와 head 를 확인합니다.
- **[4] Transform**: pivot_table 로 "월×카테고리 매출" 표를 만들고 파생
  지표(월 합계)를 붙입니다.
- **[5] Load + 리포트**: 요약표를 `outputs/monthly_category_revenue.csv` 로
  저장하고, 경영진용 텍스트 리포트(총매출, 최고 매출 달, 카테고리 톱,
  구매액 톱3 고객)를 출력합니다 — 매주 돌릴 수 있는 완성형 미니
  파이프라인입니다.

## 6. 자주 하는 실수

- **f-string 으로 SQL 조립**: 편해 보여서 손이 가지만, 사용자 입력이 한 번
  이라도 끼는 순간 보안 사고 후보입니다. 값은 언제나 `?` + 튜플.
- **? 에 튜플 대신 값 하나**: `execute(sql, city)` 는 에러입니다. 값이
  하나여도 `(city,)` 처럼 튜플로 — 쉼표를 잊지 마세요.
- **전량 추출 후 파이썬에서 필터**: WHERE 로 DB에서 줄일 수 있는 일을
  read_sql 로 다 끌어와서 하면 메모리와 시간을 낭비합니다. "줄이는 건
  SQL, 다듬는 건 pandas".
- **연결을 닫지 않는 것**: 작업이 끝나면 `con.close()`. 스크립트가 길어질
  때 잠금 문제의 원인이 됩니다.
- **비밀번호를 코드에 하드코딩**: 실습 DB야 상관없지만, 회사 DB 접속 정보는
  환경변수나 비밀 관리 도구로. 코드 공유 = 비밀번호 공유가 되어 버립니다.
