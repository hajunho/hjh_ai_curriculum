# Lecture 04 · Level 08 — 데이터 변경과 트랜잭션

> INSERT·UPDATE·DELETE 로 데이터를 바꾸는 법과, 여러 변경을 "전부 성공 아니면 전부 취소"로 묶는 트랜잭션(BEGIN/COMMIT/ROLLBACK)을 배웁니다. 재고 차감 시나리오로 성공과 실패-롤백을 모두 시연합니다.

**난이도** ⭐⭐⭐ / **선행** level07 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

조회만 하던 사람이 데이터를 **바꾸기** 시작하는 순간, 책임의 무게가
달라집니다. UPDATE 한 줄로 고객 20만 명의 등급이 바뀔 수 있으니까요.
그래서 이 레벨은 문법(INSERT/UPDATE/DELETE)과 함께 **안전장치**를
배웁니다. 주문 처리, 재고 차감, 포인트 적립 같은 실무 작업은 여러 변경이
한 묶음입니다. 중간에 하나라도 실패하면? "주문은 저장됐는데 재고는 안
줄어든" 데이터는 회계 감사와 고객 클레임으로 돌아옵니다. 트랜잭션
(transaction)은 이 묶음을 **전부 성공 아니면 전부 없던 일**로 보장하는
장치이며, 은행·쇼핑몰·ERP 모든 시스템의 심장입니다.

## 2. 비유로 이해하기

**계좌이체**가 가장 좋은 비유입니다. 내 계좌에서 5만 원을 빼고(변경 1),
상대 계좌에 5만 원을 넣는(변경 2) 두 동작은 반드시 한 몸이어야 합니다.
빼기만 성공하고 넣기가 실패하면 5만 원이 증발합니다. 은행은 그래서 두
동작을 하나의 봉투에 넣고, 둘 다 성공했을 때만 봉투를 봉인(COMMIT)하고,
하나라도 실패하면 봉투째 파기(ROLLBACK)합니다.

또 하나의 비유는 **연필로 쓰고 나중에 볼펜으로 덮어쓰기**입니다.
BEGIN(비긴) 이후의 변경은 연필 메모입니다. 내 눈에는 바뀐 것처럼 보이지만
아직 장부 원본은 아닙니다. COMMIT(커밋)은 볼펜으로 확정하는 것, ROLLBACK
(롤백)은 지우개로 싹 지우는 것입니다. "UPDATE 에 WHERE 를 빼먹었다!"
같은 아찔한 순간에도, 커밋 전이라면 지우개가 있습니다.

## 3. 핵심 개념

### 3-1. INSERT — 행 추가

```sql
INSERT INTO customers (customer_id, name, city, grade, joined_at)
VALUES (204, '박겨울', '서울', 'BASIC', '2025-12-20');
```

열 목록을 명시하는 습관을 들이세요. 테이블 구조가 바뀌어도 문장이
깨지지 않습니다. 기본키가 중복이면 level00 에서 본 것처럼 DB가
거부합니다 — 안전장치가 작동하는 것입니다.

### 3-2. UPDATE — 행 수정

```sql
UPDATE customers
SET    grade = 'GOLD'
WHERE  customer_id = 204;
```

**UPDATE 의 생명은 WHERE 입니다.** WHERE 가 없으면 전 행이 바뀝니다.
실무 수칙: 같은 WHERE 로 **SELECT 를 먼저 실행**해 몇 행이 걸리는지
확인한 뒤 UPDATE 로 바꿉니다. "조준 → 발사" 순서입니다.

### 3-3. DELETE — 행 삭제

```sql
DELETE FROM customers WHERE customer_id = 204;
```

역시 WHERE 가 생명입니다. 실무에서는 아예 지우지 않고 `status='해지'`
같은 표시만 하는 경우(소프트 삭제)도 많습니다 — 이력이 남아야 하는
데이터라면 DELETE 전에 정책부터 확인하세요.

### 3-4. 트랜잭션 — BEGIN / COMMIT / ROLLBACK

```sql
BEGIN;                       -- 봉투 열기 (이후는 연필 메모)
UPDATE inventory SET stock = stock - 2 WHERE product_id = 1;
INSERT INTO orders ...;
COMMIT;                      -- 둘 다 성공 → 볼펜으로 확정
-- 문제가 생겼다면: ROLLBACK;  → 봉투째 파기, BEGIN 이전으로
```

트랜잭션이 보장하는 성질을 ACID 라고 부릅니다. 핵심 두 가지만 기억하면
됩니다. **원자성(Atomicity)** — 전부 아니면 전무. **일관성(Consistency)**
— 규칙을 어기는 중간 상태가 장부에 남지 않음. (나머지 격리성·지속성은
"동시에 여러 명이 써도, 정전이 나도 괜찮다"는 보장입니다.)

### 3-5. 검증 후 커밋 패턴

실무 트랜잭션의 뼈대는 다음과 같습니다.

```
BEGIN
  변경 1, 변경 2, ...
  검증: 재고가 음수인가? 잔액이 부족한가?
  문제 없음 → COMMIT / 문제 발견 → ROLLBACK
```

"일단 차감해 보고, 음수가 되면 전체 취소"가 가능한 이유는 커밋 전까지는
연필 메모이기 때문입니다. 이 패턴이 main.py 의 [5]에서 그대로 나옵니다.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

main.py 는 products 옆에 재고 테이블 `inventory` 를 만들어 놓고 시작합니다.

- **[1] INSERT**: 신규 고객 추가 — 추가 전후의 행 수와 새 행을 확인.
- **[2] UPDATE**: 조준(SELECT 로 대상 확인) → 발사(UPDATE) 순서를 시연.
- **[3] WHERE 빼먹은 UPDATE 사고 재현**: 트랜잭션 안에서 일부러 WHERE 없는
  UPDATE 를 실행해 전 고객이 VIP 가 되는 참사를 보여 주고 — ROLLBACK 으로
  원상복구합니다. 지우개가 작동하는 순간입니다.
- **[4] 재고 차감 트랜잭션(성공)**: 주문 생성 + 재고 차감을 한 봉투에 넣고
  검증 통과 → COMMIT. 재고가 실제로 줄어든 것을 확인합니다.
- **[5] 재고 차감 트랜잭션(실패→롤백)**: 재고보다 많은 수량을 주문 →
  차감 후 검증에서 음수 재고 발견 → ROLLBACK. **주문도 재고도 시도 전과
  완전히 동일**함을 확인합니다. "반만 처리된 상태"가 없다는 것이 핵심
  출력입니다.

## 6. 자주 하는 실수

- **WHERE 없는 UPDATE/DELETE**: 최다 사고 유형. "조준(SELECT) 먼저" 수칙과
  트랜잭션 안에서 작업하는 습관이 이중 안전벨트입니다.
- **커밋을 잊는 것**: 파이썬 sqlite3 에서 변경 후 commit() 없이 연결을
  닫으면 변경이 사라집니다. "내 UPDATE 가 반영이 안 돼요"의 단골 원인.
- **트랜잭션을 너무 길게 여는 것**: 봉투를 열어 둔 동안 다른 사용자의
  작업이 대기할 수 있습니다. 봉투는 짧게 열고 빨리 닫는 것이 예의입니다.
- **에러가 나도 ROLLBACK 하지 않는 것**: 실패 시 롤백은 자동이 아닐 수
  있습니다. try/except 에서 명시적으로 rollback() 을 호출하세요.
- **운영 DB에서 연습하는 것**: 연습은 언제나 사본에서. 이 실습 DB처럼
  다시 만들면 되는 환경이 연습장입니다.
