# Lecture 10 · Level 03 — トークン化と日本語の特殊性

> 文をどんな単位に切るか — 空白・文字・n-gram・形態素・サブワードの各戦略を自作して比較します。
**難易度** ⭐⭐⭐ / **前提** level01, level02 / **想定時間** 45分

## 1. なぜ学ぶのか — ビジネスの視点

すべてのテキスト分析は「文を何の単位で数えるか」という決定から始まります。
この単位をトークン (token) と呼び、切り分ける作業をトークン化 (tokenization) と呼びます。
トークン化のやり方次第で、検索品質、分類精度、キーワード統計がすべて
変わります。社内検索で「配送」と打ったのに「配送が遅い」がヒットしないなら、
十中八九トークン化の問題です。

そしてこれは LLM の請求書にも直結します。GPT 系の API はトークン数で
課金しますが、同じ内容でも日本語は英語よりトークンが多くなる傾向が
あります。なぜそうなるのかは、このレベルの最後のテーマ (サブワード) で明らかになります。

## 2. たとえ話で理解する

トークン化は **のり巻きを切る仕事** です。同じ一本ののり巻きでも、切り方次第で
使い道が変わります。

- **丸ごと** (文単位): 持ち運びには良いですが、分けて食べられません。
- **一口サイズ** (単語単位): たいていの場合はちょうど良い大きさです。
- **みじん切り** (文字単位): 誰でも食べられますが、のり巻きの味 (意味) が散ってしまいます。
- **具材ごとに解体** (形態素単位): たくあんは たくあん、にんじんは にんじん —
  一番手間はかかりますが、「このお巻きに何が入っているか」を正確に把握できます。

英語は具材の間に切れ込み (空白) があらかじめ入っているのり巻きなので、切るのが簡単です。
日本語は **切れ込みが 1 本も入っていない** のり巻きです。どこで切るかを自分で
決めるところから仕事が始まります。

## 3. 核心となる概念

### 3-1. 空白トークン化 — 英語の基本、日本語では成立しない

英語の "I love this product" は空白で切ればほぼ終わりです。
ところが日本語は分かち書きをしません。「配送が速くて助かりました」を空白で
切っても、文全体が 1 つの塊として返ってくるだけです。**日本語では空白分割は
「切らない」のと同じ** — これが英語 NLP チュートリアルをそのまま日本語に適用したときに
最初に踏む地雷です。ちなみに隣の韓国語は分かち書きをするので単語の塊 (어절) までは
取れますが、助詞がくっついたまま出てくるという別の悩みを抱えます。

### 3-2. 文字トークン化と n-gram — 単純だが意外に強い

文字単位に切れば「配/送/が/速/く/て」 — 未登録語 (新語) の問題が
消えます。どんな単語でも文字には必ず切れるからです。代わりにトークン 1 つの意味が
薄くなりすぎます。「速」1 文字では、速度なのか速達なのか分かりません。

折衷案が **文字 n-gram**: 連続する n 文字を重ねながら束ねる方式です。
「配送が速い」の 2-gram は「配送、送が、が速、速い」。意味の塊 (「配送」) が偶然
捕まりつつ未登録語にも強いので、日本語の検索エンジンが長年使ってきた実戦的な技法です
(バイグラムインデックスという名前で全文検索の世界に登場します)。代わりにトークン数が
大きく増え、「送が」のような無意味な断片も混ざります。

### 3-3. 形態素解析 — 意味の最小単位に解体する

形態素 (morpheme) は、意味を持つ最小の言葉の単位です。
「配送が速くて助かりました」を形態素に分けると:

```
配送(名詞) + が(助詞) + 速く(形容詞語幹) + て(接続助詞) + 助かり(動詞語幹) + ました(助動詞)
```

こうすると「配送が/配送は/配送を」がすべて「配送」にまとまり、「速くて/速かった/
速いです」が「速-」にまとまります。集計・検索・分類の品質が一段上がります。
実務では形態素解析器 (MeCab、Sudachi、Janome などのオープンソース) が大規模辞書と
統計モデルでこの仕事をします。本物の MeCab は「ラティス探索 + コスト最小化」という
仕組みで最適な切り方を選びますが、このレベルではその原理を体感するために、小さな語彙
辞書と助詞・語尾のリストによる **最長一致法のミニ解析器** を自作します。おもちゃですが、
「辞書 + ルール + 最も長い一致を優先」という実物の骨格は同じです。

### 3-4. サブワード (BPE) — 最新 LLM の選択

形態素解析は言語ごとに辞書と文法ルールを作る必要があります。サブワード (subword)
方式は発想を逆転させます: 言語学の知識なしで、**データの中で頻繁に隣り合う文字の
ペアを繰り返し併合** してトークンのリストを作ります。これが BPE (Byte Pair Encoding)
アルゴリズムです。

1. すべての単語を文字にバラして始めます。
2. コーパスの中で最も頻繁に隣り合う文字ペアを見つけて 1 つに併合します。(例: 「配」+「送」 → 「配送」)
3. 望みの語彙サイズになるまで 2 を繰り返します。

よく出る言葉は長い 1 トークンに、まれな言葉は短い断片の集まりで表現されます。
新語も断片としてなら必ず表現できるので、未登録語問題が消えます。
分かち書きのない日本語とはとりわけ相性が良く、GPT 系がこの方式 (をバイト単位に拡張
したもの) を使っています。ただし学習データに日本語が少ないと日本語の併合ルールが
育たず、**同じ文でもトークンが細かく割れて料金がかさむ** 現象が起きます。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

- **[1] トークン化 4 種の比較**: 同じレビュー文「配送が速くて助かりました」を
  空白/文字/2-gram/ミニ形態素解析器で切り、トークンのリストと個数を並べて出力します。
  実測: 空白分割 1 個 (文が丸ごと!)、文字分割 12 個、2-gram 11 個、ミニ形態素 6 個。
- **[2] ミニ形態素解析器の内部**: 小さな辞書 (名詞・語幹) と助詞・語尾のリストで
  連続した文字列を「最長一致」で解体する過程を見せます。辞書にない「新製品」が
  1 文字ずつバラバラになる未登録語問題も確認します。
- **[3] 語彙サイズの実験**: hjh_data のレビュー 60 件を戦略別にトークン化し、語彙集合の
  大きさと「配送系の表現が何トークンに散るか」を比較します。
  実測: 空白分割 24 種 (文全体が語彙になってしまう)、文字分割 135 種、
  2-gram 230 種、ミニ形態素 112 種。形態素方式だけが「配送」を 1 つの語彙にまとめます。
- **[4] ミニ BPE 学習**: レビューコーパスから BPE 併合ルールを 60 回学習します。
  最初の併合は「し+た→した」「ま+した→ました」のような頻出の語尾で、やがて
  「星の数」のような意味の塊が自然に生まれます。最後に、初めて見る単語
  「超高速配送」が学習済みの断片 (「配送」を含む) で表現されることを確認します。

## 5. やってみよう

1. **(かんたん)** [1] で n-gram の n を 3 に変えてみましょう。トークン数と意味の
   捕まり方はどう変わりますか?
2. **(ふつう)** ミニ形態素解析器の辞書 (`NOUNS`) にない単語を含む文を入れて
   どう処理されるかを見てから、辞書にその単語を追加して改善してみましょう。未登録語
   (OOV) 問題を身をもって確認する実験です。
3. **(チャレンジ)** [4] の BPE 併合回数を 10/30/80 に変えながら、同じ文のトークン
   数がどう変わるかを表に整理してみましょう。ヒント: 併合が多いほどトークン数は
   減りますが語彙サイズは増えます — このトレードオフが実際のトークナイザー設計の
   中心的なジレンマです。

## 6. よくある間違い

- **英語チュートリアルの `split()` を日本語にそのまま使う**: エラーは出ませんが、
  文が丸ごと 1 トークンになり、何も分析できていない状態になります。エラーが出ない分、
  かえって危険です。
- **ミニルール解析器を実戦投入**: このレベルの解析器は教育用です。実務では実績のある
  形態素解析器 (MeCab、Sudachi など) を使い、今日学んだ原理でその出力を点検できる
  ようになりましょう。
- **トークン化と前処理の順序の混同**: 特殊文字の整理 (level01) の前にトークン化すると、
  「よかった!!!」のようなトークンが生まれます。クリーニング → トークン化の順序を守りましょう。
- **語彙サイズを確認しない**: トークン化の戦略を変えたら、語彙集合の大きさと頻度上位の
  トークンを必ず目で確認しましょう。変なトークンが上位に居座っていたら、戦略が間違っています。
