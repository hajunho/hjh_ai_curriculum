# Lecture 10 · Level 00 — コンピュータが言語を扱う難しさ

> 数値はお手のもののコンピュータが、なぜ文章の前では迷子になるのか。失敗事例を実際に動かして体感します。
**難易度** ⭐ / **前提** なし (lecture02 の文字列の基礎があると良いです) / **想定時間** 25分

## 1. なぜ学ぶのか — ビジネスの視点

会社のデータの大部分は、表ではなく **文章** です。カスタマーレビュー、問い合わせ記録、メール、契約書、
議事録 — 業界では、全データの 80% 以上がこうした非構造化テキストだと言われています。
売上表なら Excel で合計を出せば済みますが、「お客様は配送に不満を持っているのか?」という質問には、
文章を読まなければ答えられません。人が全部読むには多すぎるし、コンピュータに任せようにも、
コンピュータは文章を「理解」できません。

このレベルの目標は、技術を学ぶ前に **問題の大きさを正確に知ること** です。
「検索窓に単語を入れればいいんじゃないの?」と思っていた方が、単純な文字列マッチングが
どこでどう崩れるのかを自分の目で確かめると、この後の 11 レベルで学ぶ道具たちが
なぜ必要なのか、自然と腑に落ちます。

## 2. たとえ話で理解する

コンピュータにとっての言語とは、**日本語をひと言も知らない外国人の新入社員に辞書を 1 冊だけ
持たせてカスタマーサポートをやらせる** ようなものです。

この新入社員は辞書引き (文字列マッチング) は完璧です。「返金」という文字が文書に
あるかどうかを 0.001 秒で見つけます。ところが:

- お客様が「お金を返してください」と書くと見つけられません。辞書には「返金」と「お金を返す」が
  同じ意味だというつながりがないからです。(**同義語問題**)
- 「あめをなめた」の「あめ」がお菓子の飴なのか、空から降る雨なのか、区別できません。
  同じ文字が複数の意味を持ち得るという事実そのものを知りません。(**曖昧性問題**)
- 「配送速いですね(笑) 二度と買いませんが」のように前後の文脈がひっくり返す文では、
  「速いですね」だけを見て褒め言葉に分類します。(**文脈問題**)
- 「エモい」「コスパ神」のような言葉は、そもそも辞書に載っていません。(**新語問題**)

これから学ぶ NLP (自然言語処理、Natural Language Processing) は、この新入社員に
「辞書引き」を超えて「言葉の使われ方」を統計的に教えていく過程です。

## 3. 核心となる概念

### 3-1. 曖昧性 (ambiguity) — 同じ文字、違う意味

ひらがなで書いた「あめ」は、空から降る雨でもあり、なめる飴でもあります。
「はし」は橋でもあり箸でもあり端でもあります。人間は文を見た瞬間に
自動で区別しますが、文字列マッチングにとって 2 つの「あめ」は完全に同一のバイト列です。

| 文 | 人間の解釈 | 文字列マッチングの解釈 |
|---|---|---|
| あめが激しく降る | 雨 (rain) | 「あめ」発見 (区別不能) |
| いちご味のあめ | 飴 (candy) | 「あめ」発見 (区別不能) |

意味を分ける手がかりは文字ではなく **周辺の単語 (文脈)** にあります。「降る」が来れば
雨、「なめる」「味」が来れば飴。この直観 — *単語の意味は周辺の単語が決める* — は、
level06 単語埋め込みの理論的なルーツ (分布仮説) になります。

### 3-2. 文脈と皮肉 — 部分の総和は全体ではない

「良い」という単語があるからといって、ポジティブなレビューとは限りません。

- 「品質が良い」 → ポジティブ
- 「品質が良いと聞いて買ったのに完全にがっかり」 → ネガティブ
- 「良いとは言えない」 → ネガティブ (ほんの数文字の違い)

単語をバラバラに数えるやり方 (level04 の BoW) はこの地点で限界を見せ、
順序と文脈を見るモデル (level07 RNN、level08 アテンション) がその限界を埋めます。

### 3-3. 日本語には単語の切れ目がない — 分かち書き問題

英語は単語の間が空白できれいに区切られ、形の変化も少なめです。
日本語は **分かち書きをしない言語** です。「配送が速くて驚きました」という文の
どこからどこまでが 1 つの単語なのか、文字列だけを見ても分かりません。

さらに日本語は **膠着語 (agglutinative language)** でもあります。語幹の後ろに
助詞や活用語尾が次々とくっついて、表面の形が変わり続けます。

「食べる」という 1 つの動詞が、実際の文の中ではこう現れます:
食べた、食べます、食べました、食べて、食べたら、食べれば、食べていたのですが...

コンピュータから見れば、これらはすべて **互いに異なる文字列** です。「食べる」で検索しても
「食べました」はヒットしません。しかも空白がないので、「どこまでが単語か」を決める作業
(トークン化) からして一仕事です。隣の韓国語は分かち書きこそするものの、助詞・語尾が
くっつく点は同じで、同種の悩みを抱えています。これが日本語 NLP で形態素解析 (level03) が
必須になる理由です。

### 3-4. 言語は生まれ続ける

2015 年の辞書に「エモい」も「推し活」もありませんでした。どんなルール集を作っても、
言語はそのルール集より速く変わります。だから現代の NLP はルールを人間が書く代わりに
**データからパターンを学習する** 方向 (lecture06 で学んだ機械学習の哲学) に舵を切り、
知らない単語も断片に割って扱うサブワード方式 (level03) を発明しました。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

main.py は「単純な文字列マッチングのサポートボット」を作っておいて、わざと崩す実演です。

- **[1] 同義語の失敗**: 「返金」のキーワード検索が「お金を返してください」を見逃す場面。
  6 件の実際の返金依頼のうち何件見つかるか、的中率を出力します (実測: 2/6、33%)。
- **[2] 曖昧性の失敗**: 「あめ」を含む 6 つの文を並べ、文字列マッチングはすべて同一に
  扱うのに対し、周辺の単語のヒントを見れば rain/candy が分かれることを示します (実測: 6/6 成功)。
- **[3] 感情キーワードの裏切り**: 「良い/最高/満足」キーワードでポジティブ判定するルールが、
  ネガティブな文 (「良いと聞いて買ったのにがっかり」) を誤分類する混同事例を表で出力します
  (実測: 6 件中 3 件を誤分類)。
- **[4] 分かち書き実験**: 空白区切りの完全一致検索 vs 部分包含検索。日本語には空白がないため
  完全一致は 0 件に終わり、部分包含は「再配送」「無料配送」のような別の単語まで
  釣り上げてしまう副作用を示します。

核心のコードは `keyword_match(text, keywords)` というたった 1 行の関数です。この単純な
関数がどこまで通用し、どこで崩れるのか — それがこのレベルのすべてです。最後の出力
[5] では、各失敗がこの講義のどのレベルで解決されるのか、ロードマップを印字します。

## 5. やってみよう

1. **(かんたん)** `AMBIGUOUS_SENTENCES` リストに「はし」(橋/箸) を含む文を
   2 つ追加し、ヒント単語の辞書 (`CONTEXT_HINTS`) も埋めて、区別できるか確かめてみましょう。
   ヒント: 「はしで食べた」の手がかりは「食べ」です。
2. **(ふつう)** [3] のポジティブキーワードのルールに「否定語が近くにあったら反転」ルールを
   追加してみましょう (例: 「ない」「がっかり」「のに」が同じ文にあればネガティブ)。精度が
   上がるか、それでも捕まえられない文は何か、観察してみてください。
3. **(チャレンジ)** ルールをいくら追加しても 100% にならない理由を、自分の言葉で 3 行
   書いてみましょう。ヒント: ルールを 1 つ追加するたびに、そのルールの例外がまた生まれます —
   これがルールベースアプローチの本質的な限界です。

## 6. よくある間違い

- **「検索、普通にうまくいってるけど?」** — Google や社内検索がうまく動くのは、裏で形態素解析、
  同義語辞書、埋め込みが回っているからです。純粋な文字列マッチングではありません。
- **部分文字列の包含 (`in`) を万能だと思う** — 「配送」が「再配送」「配送料」にも引っかかります。
  広く取れば関係ないものが入り込み、狭く取れば必要なものを見逃します。
- **全角・半角や大文字・小文字を忘れる** — 「AS申請」と「as 申請」と「A/S 申請」はすべて別の
  文字列です。次のレベル (前処理) で正面から扱います。
- **日本語と英語の NLP を同じ難易度だと思う** — 空白で区切ればそれなりに動く英語と違い、
  日本語は分かち書き・活用の処理を飛ばすと性能が大きく落ちます。
