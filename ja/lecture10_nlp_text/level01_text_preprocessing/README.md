# Lecture 10 · Level 01 — テキスト前処理の基礎

> 散らかったレビューテキストを分析可能な状態にするクリーニングパイプラインを、段階を追って作ります。
**難易度** ⭐⭐ / **前提** level00 / **想定時間** 35分

## 1. なぜ学ぶのか — ビジネスの視点

テキスト分析プロジェクトでは、時間の大半がモデリングではなく **掃除** に費やされます。
お客様が残すレビューには、顔文字、繰り返し文字 (「よかったですーーー」)、URL、
全角/半角の混在 (「ＡＳ」「as」「A/S」) が入り混じっています。これをそのまま数えると
「よかった」と「よかったーー」が別の単語として集計され、統計が全部狂います。

前処理は華やかではありませんが、効果は確実です。同じモデルでも前処理の品質次第で
分類精度が数パーセントポイント上下することは珍しくなく、何より **集計結果をレポートに
使える水準** にしてくれます。「今月の最多言及キーワード: ｗｗｗｗ」というレポートを
出すわけにはいきませんから。

## 2. たとえ話で理解する

前処理は **調理前の下ごしらえ** です。市場で買ってきた野菜 (元のテキスト) には
土 (特殊文字) が付いていて、大きさもバラバラ (全角/半角・大文字小文字) で、食べない
根っこや外葉 (ストップワード) が付いています。どんな料理 (分析) をするにせよ、下ごしらえは
ほぼ同じ順序で進みます: 洗う → 整える → 大きさを揃える → 使えない部分を捨てる。

大事なのは **下ごしらえは料理によって変わる** という点です。出汁用の煮干しは頭を
取りますが、炒め物用はそのまま使います。同じように、感情分析では「!!!」が貴重な
シグナル (強い感情) かもしれないので無条件に消してはいけませんし、キーワード集計では
消すのが正解です。「標準の前処理」は存在せず、「目的に合った前処理」だけがあります。

## 3. 核心となる概念

### 3-1. 正規化 (normalization) — 同じものは同じ形に揃える

表記だけが違って意味が同じものを 1 つにまとめます。

| 処理 | 例 |
|---|---|
| NFKC 正規化・小文字化 | 「ＡＳセンター」「ASセンター」 → 「asセンター」 (全角英数字→半角) |
| 空白の整理 | 「配送  が  」 → 「配送 が」 (連続空白、前後の空白、全角空白の除去) |
| 繰り返し文字の圧縮 | 「よかったですーーーー」「ｗｗｗｗｗ」 → 「よかったですーー」「ww」 |
| 特殊文字の処理 | 「★イチオシ★」 → 「イチオシ」 (ただし目的に応じて保存するかを判断) |

英語の小文字化 (lowercasing) に相当する日本語の作業が、全角/半角の統一 (NFKC) と
繰り返し文字の圧縮です。Python では `unicodedata.normalize("NFKC", text)` の
1 行で全角英数字・全角空白・半角カナをまとめて揃えられます。

### 3-2. ストップワード (stopword) 除去 — シグナルのない単語を捨てる

「そして」「本当に」「とても」のような単語はほぼすべての文に登場するため、文書を
区別する力がありません。こうした単語をストップワードと呼び、集計や検索から除外します。

注意点は 2 つ:
- ストップワードのリストは **ドメインごとに違います**。ショッピングレビューでは「商品」は
  事実上ストップワードですが、一般のニュースではそうではありません。
- 感情分析で「ない」「〜のに」のような否定表現をストップワードとして消すと、「良くない」が
  「良い」になってしまいます。何を消すかは常に目的とセットで決めます。

### 3-3. 日本語で特に気をつけること — 分かち書きがない

英語の前処理チュートリアルをそのまま真似すると、日本語では事故が起きます。
最大の落とし穴は **空白で単語が区切れない** ことです。「配送が速い」を空白で
分割しても、文全体が 1 つの塊として返ってくるだけです。しかも助詞や活用語尾が
語幹にくっつくので、「配送が/配送は/配送を」を雑に扱うと同じ概念がバラバラに数えられます。

このレベルでは、**漢字の連続・カタカナの連続・英数字の連続を「キーワード」として
切り出す簡易ルール** を使います。ひらがなの助詞・語尾はこの段階で自然にふるい落とされます。
この方法は「ひらがなの内容語 (例: よかった)」を取りこぼす限界があり (6 章参照)、
本格的な解法である形態素解析は level03 で扱います。今日は「単語の切り出しを処理しないと
集計が合わない」という感覚をつかむのが目標です。

### 3-4. パイプラインで考える

前処理は各段階の **決まった順序** です。順序が変わると結果が変わります。
たとえば特殊文字を先に消すと、URL 除去のルール (「http で始まる…」) が動かなく
なります。だから実務では各段階を小さな関数として作り、順番につなげたパイプラインを
組んで、どんなテキストも同じ順序で通します。こうすれば「第 3 段階まで処理した結果」を
途中で取り出して確認でき、デバッグも楽になります。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

- **[1] 汚れたレビューの生成**: hjh_data のレビューに記号・URL・繰り返し文字・
  全角英字/全角空白をわざと乗せて、「現実的な」散らかったレビュー 8 件を作ります (seed 固定)。
- **[2] 段階ごとのクリーニング**: サンプル 1 件がパイプラインの 5 段階 (NFKC 正規化・URL 除去 →
  特殊文字の整理 → 繰り返しの圧縮 → 空白の整理 → ストップワード除去・キーワード切り出し) を
  通過するたびに before/after を出力します。テキストがだんだんきれいになる過程が一目で分かります。
- **[3] 全件一括処理**: 8 件すべてをパイプラインに通し、原文→結果を比較します。
  たとえば「★★★ 店内の雰囲気がとても快適でした…ｗｗｗｗｗ」が
  「店内 雰囲気 快適 星 数 正直」に整います。
- **[4] 前処理前後の単語集計の比較**: 同じレビューの束から単語頻度の上位 8 個を
  前処理の前/後で取り出して比較します。前処理前は「【写真レビュー】」のようなノイズの塊や
  文全体がそのまま数えられていたのが、後には「写真 6回」「正直 4回」「残念 3回」のように
  キーワード単位に揃い、「ＴＨＡＮＫＳ。」と「thanks」も 1 つに統一されることを確認します。

コードの核心は `PIPELINE = [(段階名, 関数), ...]` というリストです。各段階は
文字列を受け取って文字列を返す純粋な関数なので、順序の入れ替えや段階の削除といった
実験がリストの修正だけでできます。

## 5. やってみよう

1. **(かんたん)** `STOPWORDS` に「写真」「レビュー」を追加して、[4] の頻度上位が
   どう変わるか確認してみましょう。
2. **(ふつう)** パイプラインの `collapse_repeats` の段階をコメントアウトして実行し、
   「ｗｗｗｗｗ」が集計をどう汚すかを確認してから、元に戻してみましょう。
3. **(チャレンジ)** 感情シグナル保存バージョンを作ってみましょう: 「!」と「(泣)」を消す
   代わりに、それぞれ `<感嘆>` `<悲しみ>` トークンに置き換える段階を追加します。
   ヒント: `re.sub(r"!+", " <感嘆> ", text)` のパターンを応用すればできます。

## 6. よくある間違い

- **とにかく全部消す**: 特殊文字や顔文字を反射的に削除すると、感情のシグナルが
  消えます。「消す/残す/置き換える」の 3 つの選択肢を常に天秤にかけましょう。
- **ストップワードのリストを別ドメインからコピー**: ニュース用のリストをレビューに使うと、
  「記者」「報道」のような場違いな単語が入っている一方、肝心の「商品」がありません。
- **簡易キーワード切り出しを過信**: 漢字・カタカナの連続だけを拾う方法は、「よかった」の
  ようなひらがなの内容語を取りこぼし、「期待以上」のように複数語がくっつくこともあります。
  簡易ルールはあくまで応急処置です (level03 参照)。
- **原本を上書き**: 前処理の結果で元の列を上書きすると、ルールを直したときに
  元に戻せません。原本は必ず別に保管しましょう。
