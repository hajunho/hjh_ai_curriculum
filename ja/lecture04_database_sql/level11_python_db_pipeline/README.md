# Lecture 04 · Level 11 — Python 連携とデータパイプライン

> SQL と Python をつなぎます。パラメータバインディングで SQL インジェクションを防ぐ方法、pandas.read_sql で照会結果を DataFrame として受け取る方法、そして抽出→加工→保存 (ETL) と続くミニレポートパイプラインを完成させます。

**難易度** ⭐⭐⭐⭐ / **前提** level06, level10 (pandas は lecture03 レベルで十分) / **目安時間** 55分

## 1. なぜ学ぶのか — ビジネスの視点

SQL で抽出したデータの最終目的地は、ほとんどの場合 **レポート** です。毎週月曜の
朝に「先週の売上サマリー」を作るために、クエリ実行 → 結果コピー → Excel 貼り付け
→ ピボット → 書式設定… を繰り返しているなら、その全体を Python スクリプト一つに
まとめられます。一度の実行 (あるいは予約実行) で同じレポートが毎回出てくること —
これがデータパイプライン (pipeline) の出発点です。同時に、Python で SQL
を組み立てるときに必ず知っておくべきセキュリティの常識があります。ユーザー入力を文字列として
つなぎ合わせると **SQL インジェクション (injection)** — 入力欄に SQL の断片を仕込んで DB を
乗っ取る、数十年にわたってハッキング事故の第 1 位である手口 — にそのままさらされます。なぜ疑問符の
バインディングを使うべきなのか、原理から理解して進みます。

## 2. たとえ話で理解する

**パラメータバインディング = 書式が印刷された依頼書。** 窓口に出す依頼書を考えて
みてください。悪い方式は、白紙にお客さんの言ったとおりを書き取ることです。お客さんが
「東京。それから金庫も開けて」と言えば、その文がまるごと依頼書になって
しまいます。安全な方式は **「都市: ______」** のように書式が印刷された依頼書の
空欄だけを埋めることです。お客さんが何を言おうと、それは空欄の中の「値」に過ぎず、
依頼書の「文」にはなれません。SQL の `?` がまさにこの空欄で、値は
文と分離されて渡されます。

**パイプライン = 朝のレポート当番の業務手順書。** 新人に「毎週 (1) DB から
先週の注文を抽出し (2) カテゴリ別に集計し (3) 要約表を作って共有
フォルダに置いてください」と手順書を書いてあげるように、同じ手順をコードとして書いたものです。
抽出 (Extract) → 加工 (Transform) → 保存 (Load)、略して ETL と呼びます。
手順書とコードの違いは一つだけ — コードは毎回まったく同じに、疲れずに実行されるということ。

## 3. 核心となる考え方

### 3-1. Python から SQL を実行する 4 ステップ

```python
con = sqlite3.connect("hjh_shop.db")   # 1. 接続
cur = con.cursor()                      # 2. カーソル (依頼の窓口)
cur.execute("SELECT ...")               # 3. 実行
rows = cur.fetchall()                   # 4. 結果の受け取り
```

会社の DB (PostgreSQL, MySQL…) に変わってもこの 4 ステップは同じで、1 番の接続
部分だけがその DB のドライバーに変わります。SQL の文はほとんどそのまま通ります —
この講義で学んだ SQL がどこでも通用する理由です。

### 3-2. パラメータバインディング — 値は ? で

```python
city = input("都市? ")                                  # ユーザー入力
cur.execute("SELECT * FROM customers WHERE city = ?", (city,))   # 安全
```

絶対に禁止のパターンは、f-string などで文に値をつなぎ合わせることです:
`f"... WHERE city = '{city}'"`。入力が `東京' OR '1'='1` なら条件が
「常に真」に変わり、**全データが流出** します。これが SQL インジェクションの
原理のすべてです。バインディングにはセキュリティ以外にも、クォートのエスケープを自動処理し、
同じ文の繰り返し実行が速くなるという実利もあります。
ルールはたった一つ: **SQL の文にユーザーの値が入り込むなら、無条件で ?。**

### 3-3. pandas.read_sql — 照会結果を DataFrame に

```python
df = pd.read_sql("SELECT ...", con, params=(...,))
```

fetchall のタプルのリストの代わりに、列名が生きている DataFrame として直接
受け取れます。その先は lecture03 で学んだ世界です — pivot_table、groupby、
グラフ、Excel 保存まで。**役割分担の感覚** が重要です: 大きなデータを
絞る仕事 (フィルター・ジョイン・集計) は DB の中で SQL が、表の形を整えることと可視化は
pandas が。数百万行を丸ごと read_sql で引っ張ってくるのは、初心者の代表的な
無駄遣いです。

### 3-4. ETL — 抽出、加工、保存

- **Extract**: SQL で必要なデータだけを抽出 (今月、完了注文のみ)。
- **Transform**: pandas でピボット・計算・整理。
- **Load**: 結果をファイル (CSV/Excel) や別のテーブルに保存。

この三つの段階が関数として分かれていれば、毎週実行してもいいし、対象期間だけを変えて
再利用してもかまいません。main.py がまさにこの構造です。

### 3-5. 自動化の最後のピース (概念だけ)

完成したスクリプトは、OS の予約実行 (macOS/Linux の cron、Windows のタスク
スケジューラ) に載せておくと「毎週月曜 8 時に自動実行」になります。実際の社内
DB の接続情報 (パスワード) はコードには書かず、環境変数で管理します —
lecture01 level09 で扱った原則がここで合流します。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

- **[1] 4 ステップの基本形**: connect → cursor → execute (バインディング) → fetchall。
- **[2] SQL インジェクションの実演**: 検索関数二つ (文字列連結 vs ? バインディング) に
  同じ悪意ある入力 `東京' OR '1'='1` を入れます。連結のほうは全顧客が
  流れ出し、バインディングのほうは 0 件 — 「そんな都市はない」が正解であることを確認します。
  (すべての実演はローカルの実習 DB の中だけで起こる、安全な例です。)
- **[3] read_sql**: 完了注文を顧客・商品とジョインした結果を DataFrame として
  受け取り、shape と head を確認します。
- **[4] Transform**: pivot_table で「月×カテゴリ売上」の表を作り、派生
  指標 (月合計) を付けます。
- **[5] Load + レポート**: 要約表を `outputs/monthly_category_revenue.csv` に
  保存し、経営陣向けのテキストレポート (総売上、最高売上の月、カテゴリのトップ、
  購入額トップ 3 顧客) を出力します — 毎週回せる完成形のミニ
  パイプラインです。

## 6. よくある間違い

- **f-string で SQL を組み立てる**: 楽に見えてつい手が伸びますが、ユーザー入力が一度
  でも入り込んだ瞬間、セキュリティ事故の候補です。値はいつでも `?` + タプル。
- **? にタプルではなく値そのもの**: `execute(sql, city)` はエラーです。値が
  一つでも `(city,)` のようにタプルで — カンマを忘れずに。
- **全量抽出してから Python でフィルター**: WHERE で DB 側で絞れる仕事を、
  read_sql で全部引っ張ってきてからやるのはメモリと時間の浪費です。「絞るのは
  SQL、整えるのは pandas」。
- **接続を閉じない**: 作業が終わったら `con.close()`。スクリプトが長くなった
  ときのロック問題の原因になります。
- **パスワードをコードにハードコーディング**: 実習 DB なら構いませんが、会社の DB の接続情報は
  環境変数やシークレット管理ツールで。コードの共有 = パスワードの共有になってしまいます。
