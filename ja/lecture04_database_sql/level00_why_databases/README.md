# Lecture 04 · Level 00 — データベースはなぜ必要なのか

> Excel ファイルの使い回しが生む三つの地獄 (同時更新・整合性・権限) をシミュレーションで体験し、データベースがこの問題をどう解決するのかを確認します。

**難易度** ⭐ / **前提** なし (lecture02 レベルの Python が読めれば十分) / **目安時間** 30分

## 1. なぜ学ぶのか — ビジネスの視点

会社でこんなメールを受け取ったことはないでしょうか。
「顧客リスト_最終.xlsx ではなく、顧客リスト_最終_本当に最終_v3.xlsx を見てください」。
ファイルを回し始めた瞬間から、**どれが本物なのか** 誰にも分からなくなります。
二人が同じファイルを同時に直すと片方の作業が音もなく消え、
同じ顧客がシートごとに違う名前で書かれて売上合計が毎回違う数字になり、
年収情報の入ったファイルが「ご参考まで」というメール一通で全社員に広がります。

データベース (Database, DB) はこの問題を解くために作られた道具です。
「Excel より難しいもの」ではなく「Excel 使い回しの事故を防ぐもの」だと
理解した瞬間、なぜ会社のあらゆるシステムの裏側に DB があるのかが見えてきます。

## 2. たとえ話で理解する

**Excel の使い回し = 帳簿をコピーして配ること** です。経理部の帳簿をコピー機で
複写して、営業部とマーケティング部が一部ずつ持ち帰り、それぞれ書き換えると
想像してください。ひと月後、三冊の帳簿の数字はすべて違っています。どれが正しいか
確かめるには、三冊を一行ずつ突き合わせる残業が待っています。

**データベース = 金庫の中の原本帳簿 + 窓口担当者** です。帳簿の原本は金庫に
一冊しかありません。誰も帳簿を直接は触れず、窓口担当者 (DBMS、データベース
管理システム) に「3番のお客様の住所を変えてください」「今月の売上を見せてください」と
**依頼** します。窓口担当者は依頼を一列に並べて順番に処理し (同時更新の解決)、
帳簿のルールに反する記録は断り (整合性)、依頼した人の権限を確認して
見せてよいものだけを見せます (権限)。

この窓口担当者に話しかける標準の言語が SQL (エスキューエル、Structured Query
Language) で、この講義全体を通して学ぶ内容です。

## 3. 核心となる考え方

### 3-1. 同時更新の問題 (Lost Update)

高橋さんと田中課長が同じ Excel のコピーを開いてそれぞれ別のセルを直して保存すると、
**後から保存した人のファイルが丸ごと勝ちます。** 先に保存した人の修正は
跡形もなく消えます。これを更新の消失 (lost update) と呼びます。
怖いのは **エラーが出ない** ことです。誰にも気づかれずデータが消えます。

DB は更新リクエストを一か所で順番に処理するため、別々の行を直す二つの
リクエストは両方反映され、同じ行を直すリクエストはロック (lock) で順序が保証されます。

### 3-2. 整合性の問題 (Integrity)

Excel のセルには何でも入ります。数量の欄に「三個」、日付の欄に「月曜あたり」、
同じ顧客が「(株)ひかり」と「ひかり株式会社」として二重登録されるのを防ぐ方法は
事実上ありません。集計するたびに違う数字が出てくる理由です。

DB はテーブルを作るときに **ルールを先に宣言** します。「数量は整数のみ」「顧客
番号は重複不可」「注文の顧客番号は顧客リストに実在しなければならない」といった
ルール (制約条件、constraint) に反するデータは、保存そのものが拒否されます。

### 3-3. 権限の問題 (Access Control)

Excel ファイルはコピーされた瞬間、コントロールの外に出ます。年俸の列一つのために
ファイル全体を送れなかったり、「この列は見なかったことにしてください」という
非現実的なお願いをするはめになります。DB はユーザーごとに「このテーブルは閲覧のみ」
「この列はそもそも見えない」という権限を窓口で設定できます。原本は一度も外に出ません。

### 3-4. では、いつ DB を使うのか

| 状況 | Excel | DB |
|---|---|---|
| 一人で使う一回きりの計算 | ✅ 最適 | 大げさ |
| 複数人が同じデータを更新する | ❌ 事故は時間の問題 | ✅ |
| 数十万行以上 | ❌ 重くなる/限界 | ✅ |
| ルールのあるデータ (注文、会員、在庫) | ❌ 汚染される | ✅ |
| 機密情報を含む | ❌ 流出リスク | ✅ 権限管理 |

Excel が悪い道具だという意味ではありません。**大人数で、長期間、ルールを守りながら**
使うデータの原本置き場としては不向きだという意味です。実務での最強の組み合わせは
「原本は DB、分析とレポートは SQL で抽出して Excel/Python」です。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

このレベルの main.py は SQL をまだ知らなくても読めます。四つのステップで
「Excel 方式」の事故を Python シミュレーションで再現し、最後に DB 方式と
対比します。

- **[1] 同時更新の事故**: 同じ「ファイル」(辞書のリスト) を高橋さんと田中課長が
  コピーしてそれぞれ別の項目を直し、順番に「保存」します。出力で高橋さんの
  修正が消えたことを直接確認してください。エラーメッセージは一行も出ません。
- **[2] 整合性の汚染**: 同じ取引先が表記ゆれで二重に入力されたリストで
  取引先別の合計を出すと、一つであるべき取引先が二つに分裂してレポートが狂います。
- **[3] 権限の不在**: ファイルを丸ごと渡した瞬間に年俸の列まで一緒に渡ってしまう
  状況を示します。
- **[4] DB 方式**: Python 内蔵の sqlite3 で本物のデータベース `hjh_shop.db` を
  作り、二つの接続 (二人のユーザーに相当) がそれぞれ別の行を更新しても
  **両方とも安全に反映** されること、そしてルールに反するデータ (重複した顧客番号) が
  **保存の段階で拒否** されることを確認します。

出力で注目すべきポイント: [1] の最後の表には田中課長の修正だけが残っており、
[4] の表には二人の修正が両方とも残っています。同じシナリオ、違う結果 —
この差がこの講義全体の出発点です。

## 6. よくある間違い

- **「DB = 大きな Excel」という誤解**: 本質的な違いはサイズではなく *窓口
  (リクエスト処理)* の存在です。ルール検査、順序の保証、権限のすべてが窓口で行われます。
- **Excel を全部捨てようとすること**: 一回きりの分析やレポートには Excel が今でも
  最強です。原本の保管と共同更新だけを DB に任せれば十分です。
- **「うちは共有ドライブだから大丈夫」**: 同時編集ができるクラウドの表計算でも、
  整合性のルールと細かい権限、大容量の処理は解決できません。問題の半分しか
  解けていない状態です。
- **sqlite3 のインストール方法を検索すること**: SQLite は Python に内蔵されています。
  `import sqlite3` の一行で終わり。この講義全体でインストールするものはありません。
