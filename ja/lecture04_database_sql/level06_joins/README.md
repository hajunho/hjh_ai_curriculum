# Lecture 04 · Level 06 — JOIN: 複数テーブルをつなぐ

> 分けて保存されたテーブルをキーでつなぎ直す JOIN を学びます。INNER JOIN と LEFT JOIN の違い、ジョインキーの選び方、そして集計を膨らませるファンアウトの落とし穴まで扱います。

**難易度** ⭐⭐⭐ / **前提** level05 / **目安時間** 50分

## 1. なぜ学ぶのか — ビジネスの視点

level01 で見たとおり、DB は「一つの事実は一か所にだけ」の原則でテーブルを分けて
保存します。そのため実務の質問は、ほぼ必ず複数のテーブルにまたがります。「誰が
(customers) 何を (products) どれだけ (order_items) いつ (orders) 買ったのか?」—
四つのテーブルをつながないと答えが出ません。JOIN (ジョイン) ができないと SQL は
テーブル一つのおもちゃにとどまり、JOIN ができた瞬間に会社の DB 全体が一つの分析
対象になります。もう一つ、「注文していない顧客」のように **ないものを探す質問**
(休眠顧客、未入金の取引先) は、LEFT JOIN なしにはそもそも表現できません。

## 2. たとえ話で理解する

注文帳簿には「会員番号 7、商品番号 3」のように番号だけが書かれています。レポートを
作るには、担当者が **注文帳簿の一行を読み → 会員番号を持って顧客名簿でその番号の
行を探し → 名前を書き写す** 作業をします。この「番号を持って別の帳簿を訪ねる」ことが
JOIN で、持っていく番号が **ジョインキー (join key)** —
ほとんどの場合、片方の外部キーともう片方の主キーです。

INNER JOIN と LEFT JOIN の違いは **相手のいない行の扱い** です。お見合いパーティーの
名簿を考えてみてください。参加者名簿 (顧客) とマッチング記録 (注文) をつなぐとき:

- **INNER JOIN**: マッチングが成立した人だけが結果に残る。マッチング記録のない参加者は
  結果から消える。
- **LEFT JOIN**: 左側の名簿は **全員残る**。マッチング記録のない人は記録の
  欄が NULL (空欄) のまま。→「マッチングしなかった人探し」= 空欄の行探し。

「注文のない顧客」を探すには、顧客を左に置いて LEFT JOIN したあと、注文の欄が
NULL の行を選べばよいのです。

## 3. 核心となる考え方

### 3-1. INNER JOIN の基本形

```sql
SELECT o.order_id, c.name, o.ordered_at
FROM   orders AS o
JOIN   customers AS c ON c.customer_id = o.customer_id;
```

- `AS o`, `AS c`: テーブルの別名。複数のテーブルが登場するときは、列名の前に
  `別名.` を付けてどのテーブルの列かを明示します。
- `ON`: どのキーでペアを合わせるか。**外部キー = 主キー** の形が標準です。
- `JOIN` だけ書けば INNER JOIN の省略形です。

### 3-2. 三つ以上のテーブルの連結

JOIN は数珠のようにつなげます。注文明細 → 注文 → 顧客、そして注文明細 →
商品。level01 の関係図を横に置いて、**外部キーの矢印に沿って** ON 句を書けば
道に迷いません。

```sql
FROM order_items AS oi
JOIN orders    AS o ON o.order_id    = oi.order_id
JOIN customers AS c ON c.customer_id = o.customer_id
JOIN products  AS p ON p.product_id  = oi.product_id
```

### 3-3. LEFT JOIN — 左側は全員生存

```sql
SELECT c.name, o.order_id
FROM   customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id;
```

注文のない顧客も結果に残り、order_id の欄が NULL になります。ここに
`WHERE o.order_id IS NULL` を付けると「注文のない顧客」だけが残ります —
休眠顧客分析の王道パターンです。(RIGHT JOIN は左右を入れ替えただけなので、
実務ではほとんど LEFT に統一します。)

### 3-4. ファンアウト (fan-out) の落とし穴 — ジョインは行を膨らませる

1:N の関係をジョインすると、**1 側の行が N 個に複製** されます。注文 1 件に商品が
3 種類あれば、orders を order_items につないだ瞬間、その注文は 3 行になります。
ここまでは正常です。事故はその次に起きます。膨らんだ結果に対して
`COUNT(*)` で「注文数」を数えると、1,000 件ではなく 2,000 件ほどに **水増し**
されて出てきます。売上合計に顧客テーブルを間違ってつないでも同じことが起きます。

防御法は二つ:

1. 集計対象の **固有キーで数える**: `COUNT(DISTINCT o.order_id)`。
2. **必要なテーブルだけをジョインする**: その集計に使わないテーブルはつながない。

ジョイン後の集計結果が「体感より大きく」出てきたら、無条件でファンアウトから疑いましょう。

### 3-5. ON と WHERE の役割分担

ON は「ペアを合わせるルール」、WHERE は「つないだ結果から選ぶ条件」です。INNER
JOIN ではどちらに書いても結果は同じですが、LEFT JOIN では右側の
テーブルの条件を WHERE に書いた瞬間、NULL の行が脱落して **事実上 INNER JOIN に
なって** しまいます。LEFT JOIN の右側の条件は ON に書くのが安全です。

## 6. よくある間違い

- **ON の付け忘れ (直積、カルテシアン積)**: ON なしでジョインすると、すべての行×すべての行の
  組み合わせが生まれます。1,000 行×200 行=20 万行。結果が爆発したら、まず ON を確認。
- **間違ったキーでのジョイン**: 名前のように重複し得る列でジョインすると、同姓同名同士が
  絡まります。ジョインキーは主キー↔外部キー。
- **ファンアウトしたまま SUM/COUNT**: 3-4 節を参照。集計の前に「このジョインで行が
  膨らんだか?」と自問しましょう。
- **LEFT JOIN + WHERE に右側の条件**: NULL の行が切り捨てられて INNER になります。
  右側のテーブルの条件は ON へ。
- **別名なしで同じ列名**: 両方のテーブルにある name をそのまま書くと、
  あいまいさのエラーになるか、もっと悪いことに意図と違う側が選ばれます。ジョイン文では
  すべての列に別名を付ける習慣を。
