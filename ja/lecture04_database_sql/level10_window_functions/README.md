# Lecture 04 · Level 10 — ウィンドウ関数と分析クエリ

> 行を折りたたまずに、横へ要約を貼り付けるウィンドウ関数を学びます。ROW_NUMBER・RANK で連番と順位を、SUM OVER で累計売上と移動合計を作りながら、GROUP BY との違いを体に刻みます。

**難易度** ⭐⭐⭐⭐ / **前提** level05, level06 / **目安時間** 55分

## 1. なぜ学ぶのか — ビジネスの視点

レポートを作っていると、GROUP BY ではできない依頼に出会います。「各顧客の
**何回目** の購入かを表示してください」(初回購入の分析)、「部署 **の中での** 売上
順位を付けてください」、「月別売上に **累計** の達成額を添えてください」、「直近
3 か月の **移動合計** でトレンドを見せてください」。共通点は、**行はそのままにして**
連番・順位・累計のような計算結果を横の列に貼る必要がある、ということ。GROUP BY は
行を折りたたんでしまうので不可能です。ウィンドウ関数 (window function) はまさにこの
「折りたたまない集計」で、アナリスト採用の SQL テストの定番であり、Excel で数式の
コピーと並べ替えを繰り返していた月末の作業を一文で終わらせてくれる道具です。

## 2. たとえ話で理解する

GROUP BY は **かごに入れて要約の一行だけを残す** 担当者でした。カード
200 枚が都市のかご 6 行に折りたたまれましたよね。

ウィンドウ関数は違います。担当者はカードを **机の上に全部広げたまま**、カード
一枚一枚の横に付箋を貼ります。付箋に何を書くかは、三つの指示で決まります。

- **どの範囲を見て** (PARTITION BY — 「同じ顧客のカードだけを見て」)
- **どの順序で数えて** (ORDER BY — 「注文日順に」)
- **何を書くか** (ROW_NUMBER — 「何番目か」、SUM — 「ここまでの合計」)

「窓 (window)」という名前は、各カードから見て **自分の周りの一部のカードだけを
眺める窓** が一つずつある、と考えれば腑に落ちます。同じ顧客のカードだけが見える
窓、今月までのカードだけが見える窓。窓の外を要約して自分の付箋に書くこと —
それが `関数() OVER (窓の定義)` です。

## 3. 核心となる考え方

### 3-1. 基本の文法 — OVER が合図

```sql
SELECT name, category, price,
       AVG(price) OVER (PARTITION BY category) AS cat_avg
FROM   products;
```

`OVER` が付いた瞬間、AVG は行を折りたたみません。商品 10 行がそのまま出てきて、
各行の横に「自分のカテゴリの平均価格」が付きます。`price - cat_avg` で
「カテゴリ平均に比べてどれだけ高いか」をすぐに計算できます — GROUP BY の
結果を原本にジョインし直していた作業が、一つの句で終わります。

### 3-2. ROW_NUMBER — 連番を振る

```sql
ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY ordered_at) AS nth
```

顧客ごとに 1 から数え直す購入の連番。`WHERE nth = 1` (サブクエリや CTE で
包んで) で「各顧客の初回注文」だけを取り出すのが実務の最頻出パターンです。
「グループごとに最新/最初/最大の 1 件」= ROW_NUMBER + フィルター、公式として覚えて
おきましょう。

### 3-3. RANK / DENSE_RANK — 順位と同点処理

三つとも順序を付けますが、同点の扱いに違いがあります。

| 値 | ROW_NUMBER | RANK | DENSE_RANK |
|---|---|---|---|
| 100 | 1 | 1 | 1 |
| 90 | 2 | 2 | 2 |
| 90 | 3 | 2 | 2 |
| 80 | 4 | **4** | **3** |

ROW_NUMBER は同点にも一列に番号を振り (順序は任意)、RANK は同着 2 位のあと 4 位へ
飛び、DENSE_RANK は 3 位と続けます。表彰式は RANK、「上位 3 つの
ランク」は DENSE_RANK、「とにかく一行ずつ」は ROW_NUMBER です。

### 3-4. 累計 — ORDER BY 付きの SUM OVER

```sql
SUM(revenue) OVER (ORDER BY month) AS cum_revenue
```

ORDER BY が窓の範囲を「先頭から現在の行まで」にします。月別売上の横に
年初からの累計売上が付きます。PARTITION BY を足せば「部署ごとにそれぞれ
累計」のような、グループ内の累計もできます。

### 3-5. 移動合計/移動平均 — ROWS BETWEEN

```sql
SUM(revenue) OVER (ORDER BY month
                   ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS mov3
```

「直前 2 行 + 現在の行」— 直近 3 か月の移動合計です。月ごとにでこぼこする数字の
トレンドを滑らかに見せるレポートの定番技法で、窓のサイズを直接指定する
文法です。

### 3-6. 実行順序の注意

ウィンドウ関数は WHERE・GROUP BY が終わった **後に** 計算されます。だからウィンドウの
結果 (nth, rank…) を WHERE に直接は書けず、CTE やサブクエリで包んでから
外側でフィルタリングします。main.py の [2] がこのパターンです。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

- **[1] GROUP BY vs ウィンドウ**: 同じ「カテゴリ平均価格」を二つの方式で —
  5→10 行の違い (折りたたみ vs 維持) を並べて確認します。
- **[2] 顧客別の購入連番**: ROW_NUMBER で連番を振り、CTE で包んで
  「各顧客の初回注文」だけを取り出します。
- **[3] 同点処理の三兄弟**: 商品価格 (同点のあるデータ) に
  ROW_NUMBER/RANK/DENSE_RANK を並べて貼り、3-3 節の表を実データで
  再現します。
- **[4] 部署別の売上順位**: 従業員別の担当売上を求めたあと (CTE)、部署の中で
  RANK — 「支店別ランキング」の類のレポートの骨格です。
- **[5] 月別売上 + 累計売上**: SUM OVER (ORDER BY month)。
- **[6] 3 か月移動合計**: ROWS BETWEEN 2 PRECEDING AND CURRENT ROW。

出力ごとに「行が折りたたまれたか、保たれたか」を確認するのが、核心の観戦ポイントです。

## 6. よくある間違い

- **ウィンドウの結果を WHERE に直接書く**: `WHERE ROW_NUMBER() ...` は
  エラーです。CTE で包んで外側でフィルター — いつでもこの二段構造です。
- **PARTITION BY と GROUP BY の混同**: PARTITION BY は折りたたみません。
  「行数が減るなら GROUP BY、保たれるならウィンドウ」で見分けましょう。
- **ORDER BY の抜けた累計**: OVER () に ORDER BY がないと窓が全体に
  なり、すべての行に総合計が付きます。累計がおかしいときは、まず ORDER BY を確認。
- **同点がある ROW_NUMBER の再現性**: 同点のとき誰が 1 番かは実行のたびに
  変わり得ます。ORDER BY に固有キーを足して (`ORDER BY 金額 DESC,
  注文番号`) 順序を釘付けにするのがレポートのマナーです。
- **古い DB バージョン**: ウィンドウ関数は SQLite 3.25 (2018) 以降のサポートです。
  会社のとても古い DB では文法エラーになることがあります。
