# Lecture 04 · Level 05 — 集計関数と GROUP BY

> COUNT・SUM・AVG・MIN・MAX で要約し、GROUP BY で「都市別・カテゴリ別」の小計を出し、HAVING で小計に条件をかけます。Excel のピボットテーブルがやっていた仕事を SQL でこなします。

**難易度** ⭐⭐ / **前提** level04 / **目安時間** 45分

## 1. なぜ学ぶのか — ビジネスの視点

経営陣は行のリストを見ません。**要約された数字** を見ます。「顧客は合計何人か」、
「都市別には何人ずつか」、「カテゴリ別の売上はいくらか」。Excel で
ピボットテーブルを作っていたまさにその仕事が、SQL の集計 (aggregate) と GROUP BY
(グループバイ) です。違いは規模と再現性です。数百万行でも DB の中で要約された
結果だけを受け取るのでファイルが重くなることがなく、クエリを保存しておけば毎週同じ
レポートを数秒で作り直せます。「GROUP BY ができる」ということは、
「レポートのどんな小計でも自分で作れる」という意味です。

## 2. たとえ話で理解する

窓口担当者に今度はこうお願いします。「顧客カードを **都市別にまとめて**、
まとまりごとに **何枚あるか数えて** ください」。

担当者の作業は二段階です。まずカードを都市別の **かごに振り分けて入れ**
(GROUP BY city)、それぞれのかごに対して **要約計算を一つ** します (COUNT)。
結果はカードではなく **かごごとに一行** です — 名古屋 37 枚、大阪 36 枚…

ここで大原則が生まれます。**GROUP BY の結果の一行 = かご一つ。**
だから SELECT に置けるのは (1) かごの名札 (グループの基準の列) と (2) かごの要約値
(集計関数) だけです。かごの中の個別カードの名前などを要求すると、
「どのカードのことですか?」となってしまいます。

HAVING (ハビング) は要約が終わったあとに **かごをふるいにかけるざる** です。「35 枚を
超えるかごだけ報告してください」。WHERE がかごに入れる前のカード一枚一枚を
ふるうのに対し、HAVING は数え終わったあとにかごをふるいます。

## 3. 核心となる考え方

### 3-1. 集計関数の五兄弟

| 関数 | 意味 | 例 |
|---|---|---|
| COUNT(*) | 行数 | 顧客数 |
| SUM(x) | 合計 | 売上の合計 |
| AVG(x) | 平均 | 平均単価 |
| MIN(x) / MAX(x) | 最小/最大 | 最安値/最高値 |

集計関数は複数の行を受け取って **一つの値** に折りたたみます。GROUP BY なしで使うと
テーブル全体がかご一つになり、結果も一行です。

### 3-2. COUNT の三つの顔

- `COUNT(*)` — 行そのものを数えます (NULL を含む)。
- `COUNT(列)` — その列が **NULL でない** 行だけを数えます。
- `COUNT(DISTINCT 列)` — NULL でない **互いに異なる値** の個数。

employees の manager_id で三つの顔を比べると違いがはっきりします。社長
(manager_id が NULL) は `COUNT(manager_id)` から外れます。

### 3-3. GROUP BY — 小計を作る

```sql
SELECT city, COUNT(*) AS customer_cnt
FROM   customers
GROUP BY city
ORDER BY customer_cnt DESC;
```

集計を複数並べることもできます: `COUNT(*), AVG(price), MAX(price)`。
グループの基準を二つ書くと (`GROUP BY city, grade`)、「都市×グレード」の組み合わせ
ごとに一行になります — ピボットテーブルの行/列エリアにフィールドを二つ入れるのと
同じです。

### 3-4. HAVING — 小計にかける条件

```sql
SELECT city, COUNT(*) AS cnt
FROM   customers
GROUP BY city
HAVING COUNT(*) >= 35;
```

WHERE との使い分けが、このレベルの一番の試験ポイントです。

- **WHERE**: まとめる **前**、個別の行の条件。集計関数は使えない。
- **HAVING**: まとめた **後**、かご (グループ) の条件。集計関数を使う場所。

「キャンセル注文は除いて (WHERE)、注文 100 件以上の都市だけ (HAVING)」のように
二つを組み合わせるのが実務の標準形です。

### 3-5. 実行順序のアップデート

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

選び出して → まとめて → かごをふるって → 要約を整えて → 並べて → 切る。
この順序が分かれば、「なぜ WHERE に集計を書けないのか」(まだまとめていないから) が
自然に理解できます。

## 6. よくある間違い

- **グループの基準にない列を SELECT に入れる**: `GROUP BY city` なのに
  `SELECT city, name` — 「かごごとに一行」に個別カードの名前は置けません。
  (SQLite はエラーの代わりに適当な行を一つ選んで返すことがあり、かえって
  危険です。他の DB ではほとんどエラーになります。)
- **WHERE に集計関数**: `WHERE COUNT(*) > 10` はエラー。まとめる前には数えられ
  ません。グループの条件は HAVING で。
- **AVG と NULL**: AVG は NULL を **無視して** 平均を出します。「0 と見なして
  平均」が欲しければ `AVG(COALESCE(x, 0))` のように明示する必要があります。
- **整数の割り算**: SQLite で `SUM(a)/COUNT(*)` は整数同士なので小数点以下が
  切り捨てられます。`1.0 *` を掛けるか AVG を使いましょう。
- **集計結果の検算の省略**: 小計の合計が全体と一致するか (`SUM(小計) = 全体`)
  一度確認する習慣が、レポート事故を防ぎます。
