# Lecture 04 · Level 08 — データの変更とトランザクション

> INSERT・UPDATE・DELETE でデータを変更する方法と、複数の変更を「全部成功か、全部取り消しか」でまとめるトランザクション (BEGIN/COMMIT/ROLLBACK) を学びます。在庫引き落としのシナリオで、成功と失敗→ロールバックの両方を実演します。

**難易度** ⭐⭐⭐ / **前提** level07 / **目安時間** 50分

## 1. なぜ学ぶのか — ビジネスの視点

照会だけしていた人がデータを **変え** 始めた瞬間、責任の重さが
変わります。UPDATE 一行で顧客 20 万人のグレードが変わり得るからです。
だからこのレベルでは文法 (INSERT/UPDATE/DELETE) と一緒に **安全装置** を
学びます。注文処理、在庫の引き落とし、ポイント付与のような実務の作業は、複数の変更が
ひとまとまりです。途中で一つでも失敗したら? 「注文は保存されたのに在庫は
減っていない」データは、会計監査と顧客クレームになって返ってきます。トランザクション
(transaction) はこのまとまりを **全部成功か、全部なかったことか** で保証する
仕組みで、銀行・EC サイト・ERP、あらゆるシステムの心臓部です。

## 2. たとえ話で理解する

**銀行振込** がいちばん良いたとえです。自分の口座から 5 万ウォンを引き (変更 1)、
相手の口座に 5 万ウォンを入れる (変更 2) という二つの動作は、必ず一心同体でなければ
なりません。引くほうだけ成功して入れるほうが失敗したら、5 万ウォンが蒸発します。だから銀行は二つの
動作を一つの封筒に入れ、両方成功したときだけ封筒を封印し (COMMIT)、
一つでも失敗したら封筒ごと破棄します (ROLLBACK)。

もう一つのたとえは **鉛筆で書いて、あとでボールペンで清書** です。
BEGIN (ビギン) 以降の変更は鉛筆のメモです。自分の目には変わったように見えますが、
まだ帳簿の原本ではありません。COMMIT (コミット) はボールペンで確定すること、ROLLBACK
(ロールバック) は消しゴムできれいに消すことです。「UPDATE に WHERE を付け忘れた!」
というヒヤリとする瞬間でも、コミット前なら消しゴムがあります。

## 3. 核心となる考え方

### 3-1. INSERT — 行の追加

```sql
INSERT INTO customers (customer_id, name, city, grade, joined_at)
VALUES (204, '松本ふゆ', '東京', 'BASIC', '2025-12-20');
```

列のリストを明記する習慣をつけましょう。テーブルの構造が変わっても文が
壊れません。主キーが重複していれば、level00 で見たように DB が
拒否します — 安全装置が働いているのです。

### 3-2. UPDATE — 行の修正

```sql
UPDATE customers
SET    grade = 'GOLD'
WHERE  customer_id = 204;
```

**UPDATE の命は WHERE です。** WHERE がなければ全行が変わります。
実務のルール: 同じ WHERE で **先に SELECT を実行** して何行が対象になるかを
確認してから UPDATE で変更します。「照準 → 発射」の順番です。

### 3-3. DELETE — 行の削除

```sql
DELETE FROM customers WHERE customer_id = 204;
```

こちらも WHERE が命です。実務ではそもそも消さずに `status='解約'`
のような印だけを付ける方法 (ソフトデリート) も多く使われます — 履歴を残すべき
データなら、DELETE の前にまずポリシーを確認しましょう。

### 3-4. トランザクション — BEGIN / COMMIT / ROLLBACK

```sql
BEGIN;                       -- 封筒を開く (以降は鉛筆のメモ)
UPDATE inventory SET stock = stock - 2 WHERE product_id = 1;
INSERT INTO orders ...;
COMMIT;                      -- 両方成功 → ボールペンで確定
-- 問題が起きたら: ROLLBACK;  → 封筒ごと破棄、BEGIN 以前に戻る
```

トランザクションが保証する性質を ACID と呼びます。核心の二つだけ覚えれば
十分です。**原子性 (Atomicity)** — 全か無か。**一貫性 (Consistency)**
— ルールに反する中途半端な状態が帳簿に残らない。(残りの分離性・永続性は
「同時に複数人が書いても、停電が起きても大丈夫」という保証です。)

### 3-5. 検証してからコミットするパターン

実務のトランザクションの骨格は次のとおりです。

```
BEGIN
  変更 1, 変更 2, ...
  検証: 在庫がマイナスか? 残高が足りないか?
  問題なし → COMMIT / 問題発見 → ROLLBACK
```

「とりあえず引き落としてみて、マイナスになったら全体取り消し」ができる理由は、コミット前は
鉛筆のメモだからです。このパターンが main.py の [5] にそのまま登場します。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

main.py は products の横に在庫テーブル `inventory` を作ってから始めます。

- **[1] INSERT**: 新規顧客の追加 — 追加前後の行数と新しい行を確認。
- **[2] UPDATE**: 照準 (SELECT で対象を確認) → 発射 (UPDATE) の順番を実演。
- **[3] WHERE を忘れた UPDATE 事故の再現**: トランザクションの中でわざと WHERE のない
  UPDATE を実行して全顧客が VIP になる大惨事を見せ — ROLLBACK で
  原状回復します。消しゴムが働く瞬間です。
- **[4] 在庫引き落としトランザクション (成功)**: 注文作成 + 在庫引き落としを一つの封筒に入れて
  検証を通過 → COMMIT。在庫が実際に減ったことを確認します。
- **[5] 在庫引き落としトランザクション (失敗→ロールバック)**: 在庫より多い数量を注文 →
  引き落とし後の検証でマイナス在庫を発見 → ROLLBACK。**注文も在庫も試行前と
  完全に同じ** であることを確認します。「半分だけ処理された状態」がない、というのが核心の
  出力です。

## 6. よくある間違い

- **WHERE のない UPDATE/DELETE**: 最多の事故パターン。「照準 (SELECT) が先」のルールと、
  トランザクションの中で作業する習慣が二重のシートベルトです。
- **コミットを忘れる**: Python の sqlite3 では変更後に commit() せずに接続を
  閉じると変更が消えます。「私の UPDATE が反映されないんです」の定番の原因。
- **トランザクションを長く開きすぎる**: 封筒を開いている間、他のユーザーの
  作業が待たされることがあります。封筒は短く開けて早く閉じるのがマナーです。
- **エラーが出ても ROLLBACK しない**: 失敗時のロールバックは自動とは限り
  ません。try/except で明示的に rollback() を呼びましょう。
- **本番 DB で練習する**: 練習はいつでもコピーで。この実習 DB のように
  作り直せる環境が練習帳です。
