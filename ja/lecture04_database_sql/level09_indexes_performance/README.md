# Lecture 04 · Level 09 — インデックスとクエリ性能

> インデックスがなぜ検索を速くするのかを索引のたとえで理解し、EXPLAIN QUERY PLAN で DB の作戦を読み、30 万行のテーブルでインデックスの前後の実測時間を比較します。

**難易度** ⭐⭐⭐⭐ / **前提** level08 / **目安時間** 50分

## 1. なぜ学ぶのか — ビジネスの視点

「この画面、なんでこんなに遅いの?」— 社内システムへの不満のかなりの部分は **インデックス
のない検索** が原因です。データが少ないうちはどんなクエリも速いので問題が
隠れていて、データが溜まると突然数十倍遅くなります。インデックス (index) の
原理が分かると二つのことができるようになります。第一に、自分の書いたクエリが遅いときに
漠然と待つ代わりに原因を診断できます。第二に、開発チームと「ここの
customer_id の検索がフルスキャンで回っているようなので、インデックスを確認してもらえますか?」
というレベルの会話ができるようになります。この一言が言える非エンジニアは本当に希少で、
その分だけ大事にされます。

## 2. たとえ話で理解する

**インデックスは本の巻末の索引です。** 600 ページの本で「減価償却」が
出てくる場所を探す二つの方法: (1) 1 ページ目から最後までめくる — フルスキャン (full
scan)。(2) 巻末の索引で「減価償却 → 152、380 ページ」を見てすぐ開く —
インデックス探索。索引は五十音順に並んでいるので、数回の視線の移動だけで目的の
項目が見つかります。データが 10 倍に増えるとフルスキャンは 10 倍遅くなりますが、並んだ
索引から探すコストはほとんど増えません。

タダではありません。索引付きの本に新しい内容を差し込むと、**索引も一緒に
直す** 必要があります。インデックスの多いテーブルほど INSERT/UPDATE が遅くなり、
保存領域も余計に使います。だからインデックスは「よく検索する列にだけ、必要な
分だけ」が原則です。

もう一つ — 索引は **先頭の文字から** 並んでいます。「…償却」のように単語の
途中からは探せませんよね。だから `LIKE '%コーヒー%'` のような中間一致の検索は、
インデックスがあってもフルスキャンになります。

## 3. 核心となる考え方

### 3-1. インデックスの作成

```sql
CREATE INDEX idx_big_customer ON big_orders (customer_id);
```

`テーブル(列)` を指定すると、その列の値を並べ替えた別のデータ構造 (B ツリー) が
作られ、以降その列で検索するクエリで DB が **自動的に** インデックスを
使います。クエリの文は一文字も変える必要がありません — 速くなるのは
実行経路だけです。

### 3-2. EXPLAIN QUERY PLAN — DB の作戦を読む

クエリの前に `EXPLAIN QUERY PLAN` を付けると、実行せずに **作戦だけ** を見せて
くれます。

- `SCAN big_orders` — 全行をなめる (フルスキャン)。大きいテーブルなら警告サイン。
- `SEARCH big_orders USING INDEX idx_... (customer_id=?)` — 索引で
  直接探す。安心。

遅いクエリに出会ったら (1) EXPLAIN で SCAN かどうか確認 → (2) WHERE に使われている
列にインデックスがあるか確認 — この 2 ステップが性能診断の基本です。

### 3-3. 主キーは最初からインデックスである

主キーには自動的にインデックスが張られます。`WHERE order_id = 5` がいつも速い
理由です。問題は外部キーや検索条件としてよく使う普通の列
(customer_id、日付、状態…) で、こうした列がインデックスの候補です。

### 3-4. インデックスが役に立たない場合

- **中間一致の LIKE**: `LIKE '%コーヒー%'` — 索引は先頭の文字からの並びなので不可。
  (`LIKE 'コーヒー%'` なら使えます。)
- **列を加工した条件**: `WHERE price * 1.1 > 1000` — 加工された値は索引に
  ありません。条件式を `price > 1000 / 1.1` に書き換えるとインデックスに乗ります。
- **結果がテーブルの大部分になる条件**: 半分を持ってくるなら、索引を行き来する
  よりそのままなめるほうが速いこともあり、DB が自分でフルスキャンを選ぶことがあります。

### 3-5. 書き込みコスト — インデックスの請求書

インデックスが一つ増えるたびに、INSERT/UPDATE/DELETE はインデックスの更新作業を
追加で行います。照会が圧倒的に多い分析用のテーブルはインデックスを多めに、
書き込みが頻繁な注文受付のテーブルは本当に必要なものだけ — トレードオフです。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

main.py は実習 DB に 30 万行の `big_orders` テーブルを作って実験します
(生成に数秒かかります)。

- **[1] 実験台の準備**: 30 万行を生成 (seed 固定で毎回同じデータ)。
- **[2] インデックスなしで検索**: `WHERE customer_id = ?` を 200 回繰り返し実行して
  合計所要時間を実測します。EXPLAIN の結果は `SCAN` — 毎回 30 万行を
  なめるという意味です。
- **[3] インデックスの作成**: `CREATE INDEX` の一行。作成時間も測定します。
- **[4] インデックス後に同じ検索**: 同じクエリ 200 回を再び実測。EXPLAIN が
  `SEARCH ... USING INDEX` に変わり、時間が数十〜数百倍縮むことを
  数字で確認します。
- **[5] インデックスが役に立たない検索**: `LIKE '%送%'` のような中間一致の条件は、
  インデックスがあっても SCAN であることを EXPLAIN で確認します。
- **[6] 書き込みコスト**: 同じ 1 万行の INSERT をインデックスのないテーブル/あるテーブルに
  それぞれ実行して、書き込み速度の差を測定します。

実行環境によって絶対的な時間は違いますが、**倍率** はいつでも劇的です。
出力の「倍の高速化」の数字を確認してみてください。

## 6. よくある間違い

- **すべての列にインデックスを張る**: 書き込みが遅くなり、領域を浪費します。
  「WHERE/JOIN でよく使う列」だけが候補です。
- **遅い → サーバーのせい**: まず EXPLAIN。フルスキャンの一行が原因の大部分です。
- **小さいテーブルで効果を期待する**: 数百行のテーブルはフルスキャンでも
  一瞬なので差が見えません。インデックスはデータが大きいほど輝きます。
- **関数で包んだ条件**: `WHERE SUBSTR(ordered_at,1,7)='2025-06'` はインデックス
  が効きません。範囲条件 `ordered_at BETWEEN '2025-06-01' AND '2025-06-30'` に
  書き直すとインデックスに乗ります。
- **測定なしの議論**: 「遅い気がする」という感覚ではなく、このレベルのように繰り返しの実測
  の数字で語りましょう。
