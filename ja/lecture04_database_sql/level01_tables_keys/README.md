# Lecture 04 · Level 01 — テーブル・行・列・主キー

> データベースの中身がどうなっているかを学びます。テーブル・行・列の構造、行ごとに付く固有番号 (主キー)、テーブル同士をつなぐ参照番号 (外部キー) を、実習 DB のスキーマを実際に照会しながら確認します。

**難易度** ⭐ / **前提** level00 / **目安時間** 35分

## 1. なぜ学ぶのか — ビジネスの視点

会社のシステム担当者に「注文データをください」と言うと、こんな答えが返ってきます。
「orders テーブルには金額がありません。order_items と products をつなげる必要があります」。
この言葉が理解できないと、データの依頼は延々とキャッチボールになります。DB のデータは
Excel の「一枚の大きな表」ではなく、**複数の小さな表が番号でつながった構造** で
保存されています。この構造図 (スキーマ、schema) が読めれば、どのデータがどこにあり、
何と何をつなげば欲しい表になるのかを自分で判断できます。
SQL の文法より先に学ぶべき、地図の読み方です。

## 2. たとえ話で理解する

町の文房具店の店主の帳簿整理を思い浮かべてください。最初はノート一冊に
「3月2日、佐藤翔太さん (東京在住の常連)、万年筆 2 本、1 本 29,000 ウォン…」と全部
書いていました。ところが佐藤さんが引っ越すと問題が起きます。ノート全体から
佐藤さんが出てくる行を **すべて探して** 住所を直さなければなりません。一行でも
見落とすと帳簿が矛盾します。

賢い店主は帳簿を分けます。**顧客名簿** (顧客ごとに会員番号)、**商品リスト**
(商品ごとに商品番号)、**注文帳簿** (日付と「会員番号 7 番が商品番号 9 番を
2 個」) に分けるのです。これで住所が変わっても顧客名簿のたった一行を直せば済みます。

ここに DB の核心概念が全部登場しました。

- 帳簿一冊 = **テーブル (table)**
- 帳簿の一行 = **行 (row)** — 顧客 1 人、注文 1 件
- 帳簿の項目 (名前、住所…) = **列 (column)**
- 会員番号のように行ごとに付く固有番号 = **主キー (primary key, PK)**
- 注文帳簿に書かれた「会員番号 7 番」= 別の帳簿を指す **外部キー (foreign key, FK)**

## 3. 核心となる考え方

### 3-1. 主キー — 絶対に重複しない名札

名前は主キーになれません。同姓同名がいるからです。そこで、どのテーブルも
行ごとに固有の値 (顧客番号、注文番号、社員番号…) を一つ決めておきます。主キーの
条件は二つ: **重複不可、空 (NULL) 不可。** DB はこのルールに反する保存を
拒否します (level00 ですでに目撃しました)。

### 3-2. 外部キー — 別の帳簿を指す指

orders テーブルの customer_id 列に入っているのは顧客の名前ではなく、
**customers テーブルの主キーの値** です。「この注文の持ち主は顧客名簿の 7 行目」
という参照です。こうすると (1) 顧客情報の修正は一か所で終わり、(2) 存在しない
顧客の注文のような幽霊データを防げます。

### 3-3. 実習 DB の五つのテーブル

この講義全体で使うショップ DB `hjh_shop.db` の構造です。

| テーブル | 内容 | 主キー | 外部キー |
|---|---|---|---|
| customers | 顧客 200 人 (氏名・都市・グレード・入会日) | customer_id | — |
| products | 商品 10 種 (名前・カテゴリ・販売価格・原価) | product_id | — |
| employees | 従業員 20 人 (氏名・部署・給与・上司) | employee_id | manager_id → employees |
| orders | 注文 1,000 件 (誰が・いつ・状態) | order_id | customer_id → customers, employee_id → employees |
| order_items | 注文明細 (どの商品を何個) | (order_id, product_id) | order_id → orders, product_id → products |

テキストで関係図を描くと:

```
customers ──< orders >── employees ┐
                │              └───┘ (manager_id 自己参照)
                └──< order_items >── products
```

`──<` は一対多 (1:N) の関係です。顧客 1 人が注文を何件も持ちます。

### 3-4. なぜ注文帳簿に金額がないのか — 正規化の入り口

orders に商品名と価格まで書き込むと、同じ情報が千回繰り返され、価格が
変わったら千行を直すことになります。**一つの事実は一か所にだけ書く** — この原則を
正規化 (normalization) と呼びます。その代わり照会のときにテーブルをつなぐ必要が
あり、その方法 (JOIN) は level06 で学びます。「保存は分けて、照会はつないで」が
リレーショナル DB の基本のリズムです。

### 3-5. order_items の主キーが二つ?

order_items の主キーは (order_id, product_id) の **組** です。「17 番の注文の
3 番の商品」という組み合わせは一度しか現れない、という意味です。これを複合キー
(composite key) と呼びます。二つの帳簿の間 (注文↔商品) の多対多関係を解きほぐす
橋渡し役のテーブルでよく見かけます。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

main.py は `hjh_shop.db` を作ったあと、DB 自身に「あなたはどんな姿をしているの?」と
尋ねます。SQLite は `sqlite_master` という特別なテーブルにすべてのテーブルの作成
文を保管しているので、SQL でスキーマを照会できます。

- **[1] テーブル一覧**: `SELECT name FROM sqlite_master WHERE type='table'`
- **[2] 各テーブルの構造**: `PRAGMA table_info(テーブル名)` で列名・データ型・
  主キーかどうかを表として出力します。pk 列が 1 以上なら主キーです。
- **[3] 行数を数える**: テーブルごとに `SELECT COUNT(*)` でデータ規模を確認します。
- **[4] 関係図**: 外部キーのつながりをたどってテキストの関係図を出力します。
- **[5] 参照の確認**: orders の customer_id=7 が customers の 7 行目を実際に
  指しているのか、二つのテーブルを並べて照会し、目で確認します。

出力の中で **pk 表示の付いた列** と **`_id` で終わる列** に注目してください。
`_id` 列はほとんどの場合、どこかの主キーを指す外部キーです。初めて見る DB を
把握するときも、このコツ (テーブル一覧 → 各テーブルのキー → 関係図を描く) が
そのまま通用します。

## 6. よくある間違い

- **名前をキーに使うこと**: 同姓同名、改名、誤字の前で崩壊します。キーは
  意味を持たない固有番号がいちばん安全です。
- **すべてを一つのテーブルに入れようとする癖**: Excel 式の発想です。繰り返される
  情報が見えたら、テーブルの分割を思い出してください。
- **外部キー列の数字を「ただの数字」として読むこと**: customer_id=7 は数量や
  金額ではなく、**別のテーブルの 7 行目** という住所です。平均を取ったり
  足したりしてはいけない数字です。
- **スキーマを確認せずにいきなりクエリを書くこと**: 初めて見る DB では必ず
  テーブル一覧とキー構造から確認しましょう。このレベルの [1]〜[4] がその順番です。
