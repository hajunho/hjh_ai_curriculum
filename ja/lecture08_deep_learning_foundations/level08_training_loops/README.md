# Lecture 08 · Level 08 — 学習ループ・バッチ・エポック

> データを皿 (ミニバッチ) に分けて盛りながら学習する実務標準のループを Dataset/DataLoader で実装し、train/valid の loss 曲線を描いて「学習の健康診断表」を読む方法を学びます。

**難易度** ⭐⭐⭐ / **前提** level07 (MLP 分類モデル) / **想定時間** 55分

## 1. なぜ学ぶのか — ビジネスの視点

このレベルで作る学習ループのテンプレートは、これから皆さんが目にする**すべてのディープラーニングコードの骨格**です。コンピュータビジョン (lecture09)、NLP (lecture10)、LLM のファインチューニング (lecture12) — モデルとデータが変わるだけで、ループはそのままです。そして実務でディープラーニング担当者が一日に何度も見る画面が、まさに学習曲線 (learning curve) です。曲線 2 本を読めるようになれば、「いまうまくいっていますか?」「もっと回せば良くなりますか?」「いつ止めますか?」といった質問にデータで答えられます。外注先の週次レポートに載ってくるあのグラフを、このレベルの後には自分で解釈できるようになります。

## 2. たとえ話で理解する

**ビュッフェの皿のたとえ。** 倉庫 (全データ 1,600 件) の料理を一度に全部食べることはできません (メモリの限界)。そこで皿 (バッチ 64 件) に分けて盛り、何度も往復します。

- **バッチ (batch)** = 一度に皿に盛る量。
- **ステップ (step)** = 皿 1 枚を空けること (バッチ 1 個で重みを 1 回更新)。
- **エポック (epoch)** = 倉庫全体を一周食べ切ること (1,600 ÷ 64 = 25 ステップ)。
- **シャッフル (shuffle)** = 毎エポック、皿に盛る順番をランダムに混ぜること。いつも同じ順で食べると、最後の皿の味 (直近バッチの傾向) に舌が慣れてしまいます。

**Dataset = 倉庫の司書、DataLoader = 配膳係。** 司書 (Dataset) は 2 つの質問にだけ答えます — 「全部で何件?」(`__len__`)、「i 番目のものをください」(`__getitem__`)。配膳係 (DataLoader) が司書に番号札を読み上げて皿を仕立て、混ぜ、配ります。役割が分かれているので、データが CSV でも画像フォルダでも、司書だけ差し替えればループはそのままです。

## 3. 核心となる概念

### 3-1. なぜミニバッチなのか

| 方式 | 長所 | 短所 |
|---|---|---|
| full-batch (全部を一度に) | 勾配が正確 | メモリの限界、更新が 1 回/エポックで遅い |
| バッチ 1 件 (オンライン) | 更新が頻繁 | 勾配が跳ね回る、ハードウェア効率が悪い |
| **ミニバッチ (32〜512)** | 両者の折衷 + GPU の並列に最適 | バッチサイズというハイパーパラメータが増える |

ミニバッチの「ほどよく跳ね回る」勾配は、短所だけではありません — 浅いくぼみ (悪い局所解) から抜け出す手助けをするという良い面もあります。

### 3-2. 標準の学習ループテンプレート

```
for epoch in range(n_epochs):
    train を一周: バッチごとに zero_grad → forward → loss → backward → step
    valid を一周: no_grad で採点だけ (backward はなし!)
    2 つの loss を記録
```

実習コードの `run_epoch()` 関数は、opt の有無で学習と評価を兼ねる実務的な書き方です。評価時に `model.eval()` + `torch.no_grad()` をオンにすること、loss をバッチサイズで重み付き平均することがポイントです。

### 3-3. 学習曲線 = 健康診断表

- **train・valid がそろって下降**: 正常。続行。
- **train は下降、valid は上昇 (開いていくハサミ)**: 過学習の始まり。過去問の点数だけが上がっている状態 — 止めるか、level09 の処方を適用します。
- **どちらも高いまま停滞**: 過少適合。モデルの容量・学習率・特徴量を再検討。
- **のこぎりのように乱れる**: 学習率が大きすぎる、またはバッチが小さすぎる。

### 3-4. BCEWithLogitsLoss

今回のモデルは末尾の Sigmoid を外し、ロジット (logit、確率に変える前のスコア) をそのまま出力します。`BCEWithLogitsLoss` が Sigmoid+BCE を内部で数値的に安全にまとめて計算してくれるからです。実務の標準なので、ここからはこの方式を使います。判定も確率 0.5 の代わりにロジット 0 超で同じようにできます。

## 6. よくある間違い

- **valid のループで backward を呼ぶこと。** 検証データで学習してしまう重大事故です。必ず no_grad で、opt なしの採点だけにします。
- **エポックの loss を単純平均すること。** 最後のバッチはサイズが違うことがあるので、`loss.item() * len(xb)` で重み付き平均にしないと正確になりません。
- **毎エポック Dataset を作り直すこと。** 前処理が毎回繰り返されて時間を浪費します。Dataset は一度作って再利用します。
- **まず num_workers を上げること。** 並列ロードは大きな画像データでは有効ですが、小さなデータではプロセス生成のコストのほうが大きく、かえって遅くなります (この実習は既定値の 0)。
- **「エポックを増やせば必ず良くなる」という思い込み。** 今回の実行がその反証です — 40 エポックの valid 性能は 5 エポックより悪いのです。

## 次のレベルの予告

今回の実行で目撃した「ハサミの形」(train↓ valid↑) が、まさに過学習です。level09 ではわざと激しい過学習を作っておいて、ドロップアウト (ランダム欠勤トレーニング)・weight decay (大きな重みへの課税)・早期終了 (成績が悪くなったら下山) という 3 つの処方が、それぞれ valid 性能をどれだけ回復させるかを比較実験します。
