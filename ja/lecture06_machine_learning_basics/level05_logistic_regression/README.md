# Lecture 06 · Level 05 — ロジスティック回帰: 分類の第一歩

> 「解約する/しない」を超えて「解約確率 73%」で答えるモデルを作り、その係数をビジネスの言葉に翻訳します。
**難易度** ⭐⭐⭐ / **前提** level03, level04 / **想定時間** 45分

## 1. なぜ学ぶのか — ビジネスの視点

実務の分類問題の答えは、はい/いいえよりも**確率**の方がはるかに役立ちます。「この顧客は解約します」より「解約確率 73%」が優れている理由: 確率があって初めて**優先順位**を付けられます。フォロー担当の人員が 1 日 50 人分しかないなら、リスク確率の上位 50 人から電話すればよいのです。確率があれば**期待損益の計算**もできます。「解約確率 30% × 顧客生涯価値 40万ウォン = 期待損失 12万ウォン > クーポン費用 1万ウォン → クーポン発送は割に合う商売」。

ロジスティック回帰 (logistic regression) は、確率を出す分類モデルの標準であり、今でも金融機関の信用評価など「説明責任」が重い現場で第一候補として使われるモデルです。係数の一つひとつが解釈できるからです。

## 2. 比喩で理解する

**リスク採点表を使う保険の審査員**を想像してみてください。審査員は項目ごとに点数を付けます。利用日数が少なければ +リスク点、問い合わせ電話が多ければ +リスク点、自動決済を設定していれば −リスク点…… 項目の点数を全部足して総点を出します。ここまでは線形回帰とまったく同じ「加重和」です。

問題は、総点が −5 点にも +12 点にもなり得るのに、私たちの欲しい答えは 0〜100% の確率だということ。そこで、総点を確率に変えてくれる**変換のじょうご**を 1 つ通します。このじょうごがシグモイド (sigmoid) 関数です。総点がとても低ければ 0% 近辺、0 点ならちょうど 50%、とても高ければ 100% 近辺に押し込みます。つまり**ロジスティック回帰 = 線形の採点表 + 確率のじょうご**です。level03 を理解していれば、新しく学ぶのはじょうご 1 つだけです。

## 3. 核心概念

### 3.1 シグモイド: スコア → 確率

```
z = a₁x₁ + a₂x₂ + … + b        (線形スコア、level03 と同じ形)
p = 1 / (1 + e^(−z))            (シグモイド: z を 0〜1 の間に)
```

シグモイドは S 字カーブです。z=0 で p=0.5、z が ±4 くらいになると p はすでに 0.98/0.02 に張り付きます。学習は「訓練データの正解の確率が最大になるように」係数 a たちを探す過程で (最尤法)、線形回帰と違って閉じた公式がないため反復最適化で解きます — sklearn が勝手にやってくれます。

### 3.2 係数の解釈: オッズ比

係数 aᵢ が + ならその特徴量が大きいほど解約確率が上がり、− なら下がります。大きさまで解釈するにはオッズ (odds) の概念が必要です。オッズ = p/(1−p)、「解約 対 継続の賭け率」です。**特徴量 xᵢ が 1 単位増えると、オッズは e^(aᵢ) 倍になります。** 例: 問い合わせ回数の係数が 0.5 なら e^0.5 ≈ 1.65、つまり「問い合わせが 1 回増えるごとに解約オッズ 1.65 倍」。報告書にはこの倍率 (オッズ比、odds ratio) で書くのが慣例です。

注意: 特徴量の単位がバラバラだと (月数 vs ウォン)、係数の大きさを直接比較できません。今日の実習のように標準化 (平均 0、標準偏差 1) した後の係数は「その特徴量が 1 標準偏差動いたとき」の効果なので、互いに比較可能になります。

### 3.3 しきい値: 確率 → 決定

モデルは確率を出し、決定は人がしきい値 (threshold) で下します。デフォルトの 0.5 は何の根拠もない慣例にすぎません。しきい値を下げると (例: 0.3) より多くの顧客をリスクと分類するので、**見逃す解約者は減るが空振りのフォローが増え**、上げると逆になります。しきい値はモデルの問題ではなく、**費用対効果のビジネス判断**です — フォロー 1 件のコストと顧客 1 人を失うコストを知っている人が決めるべきです。

### 3.4 なぜ「回帰」なのに分類なのか

名前の由来は「ログオッズ (log-odds) を線形回帰する」からです。混同しやすい試験の定番ポイント: ロジスティック回帰は**分類モデル**です。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

churn_table (サブスク顧客 2,000 人) で解約確率モデルを作ります。

- **[1]** データを読み込んで特徴量 6 個/正解 1 個に分け、level04 で学んだとおり訓練/テストを分割します。`customer_id` はわざと外します (意味のない列)。
- **[2]** シグモイドのじょうごの形を数字で確認します: z が −4, −2, 0, 2, 4 のとき確率はどうなるか。
- **[3]** 標準化 + ロジスティック回帰を学習し、テスト成績 (正解率・再現率) を出します。
- **[4]** 係数の表を出力し、オッズ比に翻訳します。「問い合わせが 1 標準偏差増 → 解約オッズ N 倍」のような文章が自動生成されます。データジェネレーターに仕込んだ本物のシグナル (利用日数↓、問い合わせ↑、自動決済−) と方向が一致するか確認してください。
- **[5]** 顧客 3 人の予測確率を出し、しきい値を 0.5 → 0.3 に変えたとき再現率と適合率がどうトレードオフされるかを見せます。

コードの心臓部: `Pipeline([("scaler", StandardScaler()), ("clf", LogisticRegression())])`。パイプラインを使うと、スケーラーが訓練セットだけで fit され、level04 のリーク防止ルールが自動的に守られます。係数は `model.named_steps["clf"].coef_` から取り出します。

## 6. よくある間違い

- **確率を捨てて 0/1 だけ報告すること**: ロジスティック回帰の最大の長所を捨てているのと同じです。優先順位も期待損益も確率から生まれます。
- **標準化なしで係数の大きさを比べること**: 「月額料金の係数が一番小さいから重要ではない」 — 単位がウォン (数万単位) だから小さく見えるだけかもしれません。
- **係数を因果として解釈すること**: 「自動決済を設定させれば解約が減る」は因果の主張です。自動決済を設定するタイプの顧客が、もともとロイヤルティが高いだけかもしれません (level03 の相関≠因果の再訪)。
- **しきい値 0.5 を神聖視すること**: 0.5 はデフォルト値にすぎず、コスト構造に応じて調整するのが正常です。
- **正解率 1 つで性能を報告すること**: 解約率 15% のデータでは正解率は錯覚を生みます。まさに次のレベルのテーマです。
