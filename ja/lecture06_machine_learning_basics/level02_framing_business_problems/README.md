# Lecture 06 · Level 02 — ビジネスの質問を ML の問題に変換する

> 「解約を減らしたい」という願いを、機械が解ける定義書 (何を・どの単位で・いつ時点で・どの指標で) に翻訳する技術を学びます。
**難易度** ⭐⭐ / **前提** level01 / **想定時間** 35分

## 1. なぜ学ぶのか — ビジネスの視点

機械学習プロジェクトが失敗する最もありふれた理由は、モデルが悪いからではありません。**そもそも問題定義ができないまま始めたから**です。「解約を減らしたい」は立派な経営目標ですが、そのままでは機械に任せられません。解約とは正確には何でしょうか? 3 か月未ログイン? 解約ボタンのクリック? 誰の単位で予測するのでしょうか — 顧客? アカウント? 家族プラン全体? いつの時点で予測するのでしょうか — 毎月 1 日? その時点で分かっている情報しか使ってはいけない、ということはご存じですか?

この翻訳作業はコーディングではないので、むしろ現場の担当者の方がデータサイエンティストより上手にできる領域です。そしてここでずれてしまうと、その後のどんなモデリングも無意味になります。このレベルはこの講義で唯一「モデルを作らない」レベルですが、実務価値としては最大のレベルかもしれません。

## 2. 比喩で理解する

**ML の問題定義は、外注の発注書を書くことと同じです。** 内装業者に「家をおしゃれにしてください」と頼めば、結果は運任せです。良い発注書は違います。どの部屋を (単位)、いつまでに (時点)、どんなスタイルで (対象)、予算と満足の基準は何か (指標)、そして完成後に何をするのか (アクション) が書かれています。

機械学習モデルも、話の通じない外注業者です。発注書 (問題定義) が曖昧だと、まじめに見当違いのものを作ってきます。特に怖いのは、**モデルは発注書の穴を聞き返してこない**という点です。「予測時点で知り得ない情報を材料として渡してはいけない」という条件を書き忘れると、モデルはその情報をこっそり使い、試験の成績だけが良い偽物の名品を納品してきます (これをリーク (leakage) と呼びます)。

## 3. 核心概念

### 3.1 ML 定義書の 5 要素

ビジネスの質問を ML の問題に変換するとき、必ず答えるべき 5 つの問いです。

1. **予測対象 (target)**: 正確には何を当てるのか? 測定可能な定義で。 — 「解約」→「今月末を基準に、次の 30日以内にサブスクを解約する (1/0)」
2. **予測単位 (unit)**: 1 行 (レコード) が何を表すのか? — 顧客 1 名? アカウント 1 つ? 注文 1 件? 店舗 1 つの 1 日?
3. **予測時点 (timing)**: いつ予測を下すのか、そしてその時点で**実際に知り得る情報だけ**を材料にしているか? — 時点を破るとリークが起きます。
4. **評価指標 (metric)**: うまく当てられたかを何で測るのか? その指標はビジネスの損益とつながっているか? — 解約予測なら正解率より再現率・適合率 (level06)。
5. **アクション (action)**: 予測が出たら何をするのか? — 「リスク上位 10% に電話フォロー」。**アクションのない予測は飾り物です。** アクションが決まって初めて、「上位 10%」のようにモデルの出力形式も決まります。

さらに実務では**ベースライン (baseline)** — 「モデルなしで今のやり方 (勘、ルール) だと成績はいくらか」 — を追加します。ベースラインに勝てないモデルは、導入する理由がありません。

### 3.2 解ける問題 vs 解けない問題

同じ形式で書いてみても、ML で解ける問題とそうでない問題があります。

**解ける問題の条件**: (a) 過去に似たことが繰り返し起きていてデータとして残っている、(b) 入力と結果の間にパターンがありそう、(c) 正解 (ラベル) を確保できる、(d) 多少間違えてもアクションが成立する。

**解けない問題のサイン**: 正解データが数十件しかない (「自社 10 年分の M&A 成功予測」)、ルールがすでに 100% 明確 (消費税の計算 — level00)、予測しても打てるアクションがない、過去のパターンが未来も続く可能性が低い (制度が完全に変わった直後)、人命や法的責任がかかっていて誤差の許容がゼロ。

### 3.3 リーク (leakage) — 未来を盗み見る材料

定義書レビューで最も神経を使う項目です。例: 「解約違約金の請求額」という列は、解約をほぼ完璧に当てます — 解約した人にしか請求されないからです。しかし予測時点 (月初) には存在しない情報です。訓練データにはあるのに予測時点にはない列、あるいは結果が確定した後にはじめて埋まる列は、すべて疑ってください。判定の質問は 1 つです。**「予測ボタンを押すその瞬間、この値を知り得るか?」**

### 3.4 定義書は繰り返し磨く文書である

最初の定義書はたいてい間違っています。「30日以内の解約」と定義したら、決済サイクルが 45 日周期の顧客が全員解約扱いになってしまう、といった問題がデータを見ながら明らかになります。定義書→データ確認→定義書修正の往復が、正常なプロセスです。

## 4. 実習 — main.py

実行:

```bash
python3 main.py
```

このプログラムは**チェックリストエンジン**です。ML 定義書を Python のデータ構造として書くと、5 要素が埋まっているか・リークの危険はないか・ML に適した問題かを自動点検して点数を付けます。

- **[1]** 「解約を減らしたい」を悪い定義書 (空欄だらけ) のまま入れて点検 → 何が空いているのか指摘を受けます。
- **[2]** 同じ願いを良い定義書に仕上げて点検 → 合格していく過程を見ながら 5 要素を身につけます。
- **[3]** リーク危険の検査: 材料リストに「解約違約金の請求額」が混ざった定義書を入れ、エンジンが見抜けるかを確かめます (予測時点より後に生まれる列の検出)。
- **[4]** 候補問題 4 つ (需要予測、消費税計算、M&A 成功予測、不正取引検知) を「解ける問題/解けない問題」の基準で自動分類し、理由を出力します。

コードの心臓部は `MLSpec` データクラスと `validate()` 関数です。点検ルールの一つひとつが 3 章の概念と 1:1 で対応しているので、出力とコードを行き来しながら読んでみてください。このチェックリストは、実際の会議でホワイトボードにそのまま書き写しても使えます。

## 6. よくある間違い

- **目標と予測対象を同一視すること**: 目標は「解約の削減」(ビジネス)、予測対象は「30日以内に解約するか」(ML)。モデルがやるのは後者だけです。解約の削減は、予測 + アクション (面談、特典) が組み合わさって初めて実現します。
- **評価指標に無条件で正解率と書くこと**: 解約率 15% のデータでは、「全員継続」と言い張っても正解率 85% です。指標の選び方は level06 で深く扱います。
- **リーク列を性能向上と勘違いすること**: 試験の成績が急に不自然なほど良くなったら、喜ぶ前にまずリークを疑ってください。
- **一発で完璧な定義書を書こうとすること**: 定義書はデータを見ながら書き直していく、生きた文書です。
