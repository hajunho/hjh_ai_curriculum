# Lecture 07 · Level 05 — スケーリングとパイプライン

> 単位がバラバラの特徴量を同じものさしで測れるようにそろえるスケーリング、そして前処理とモデルをひとかたまりに束ねてリーケージを構造的に防ぐ sklearn の Pipeline を学びます。
**難易度** ⭐⭐⭐ / **前提** level04 / **想定時間** 35分

## 1. なぜ学ぶのか — ビジネスの視点

データの事故の多くは、華やかなアルゴリズムではなく**前処理の順序ミス**から起こります。代表例は 2 つ: ① テストデータまで含めて平均・標準偏差を計算してからスケーリングする (リーケージ)、② 学習時に行った前処理をデプロイコードで入れ忘れる (学習-サービング不一致)。どちらも「検証では良かったのに本番でおかしい」という、原因を突き止めるのが最も難しいタイプの障害を生みます。

sklearn のパイプライン (Pipeline) は、この 2 つの事故を**コード構造のレベルで根絶する**道具です。前処理とモデルを 1 つのオブジェクトに束ねれば、fit は学習データでのみ行われ、transform は常に同じ順序で適用されます。実務で「モデルファイル」をやり取りするとき、実際に行き来しているのはまさにこのパイプラインオブジェクトです。検収する側にとっても、「前処理はパイプラインの中に入っていますか?」という質問ひとつでプロジェクトの品質を推し量ることができます。

## 2. たとえ話で理解する

**スケーリング = 単位の統一**です。ある会議で A チームは「売上 3 (億ウォン)」、B チームは「売上 250,000,000 (ウォン)」と言えば、数字だけ見る人は B チームの案件が 8 千万倍重要だと錯覚します。距離ベースのモデル (KNN など) がまさにこの錯覚をします。月額料金 (9,900〜29,900) と利用日数 (0〜30) を同じものさしで測ると、料金の 1 ウォンの差と利用日数の 1 日の差を同じ大きさとして扱い、料金が距離を独占してしまいます。標準化 (standardization) は、すべての変数を「平均 0、標準偏差 1」という共通単位に換算する作業です。

**パイプライン = 工場のベルトコンベア**です。部品 (データ) がベルトに乗ると、洗浄 (スケーリング)→組み立て (モデル) が常に同じ順序で行われます。ベルトがなければ、作業者が洗浄を忘れたり、出荷検査用の部品 (テストデータ) を洗浄槽の水 (平均・標準偏差の計算) に混ぜてしまう事故が起こります。ベルトがあれば、順序ミスそのものが不可能になります。

## 3. 核心となる概念

### 3.1 StandardScaler — 標準化

各列に対して `(値 − 平均) / 標準偏差` を計算します。結果は「平均から標準偏差いくつ分離れているか」という無単位のスコアです。核心のルール: **平均と標準偏差は学習データからのみ計算 (fit) し、テストにはその値をそのまま適用 (transform) するだけ**。テストまで混ぜて平均を取ると、テストの分布情報が学習に漏れ込みます。

### 3.2 スケーリングが必要なモデル、無関係なモデル

- **敏感**: KNN、SVM、ロジスティック/線形回帰 (正則化付き)、ニューラルネットワーク、K-means — 距離・大きさを直接使うモデル
- **鈍感**: 決定木、ランダムフォレスト、ブースティング — 「いくらより大きいか?」で分割するだけなので単位と無関係

ツリー系しか使わないならスケーリングを省いてもかまいませんが、パイプラインに入れておけばモデルを乗り換えても安全です。

### 3.3 Pipeline がリーケージを防ぐ原理

`make_pipeline(StandardScaler(), KNeighborsClassifier())` で束ねると:

- `pipe.fit(X_train, y_train)` → スケーラーが**学習データのみで**平均・標準偏差を学び、変換されたデータでモデルが学習
- `pipe.predict(X_test)` → 学習時に学んだ平均・標準偏差でテストを変換してから予測

交差検証 (`cross_val_score(pipe, X, y)`) にパイプラインごと渡すと、**フォールドごとに**スケーラーがそのフォールドの学習部分だけで fit し直されます。スケーリングをあらかじめ全データに施してから交差検証を回すと、すべてのフォールドの検証データの情報がスケーラーに既に入り込んだ状態 — これが前処理リーケージの標準的な事例です。スケーリング程度ならリークの影響は小さいのですが、ターゲットエンコーディング・欠損補完・特徴量選択のように正解や分布を濃く使う前処理では、性能が大きく水増しされることがあります。だからルールはひとつに統一します: **前処理はすべてパイプラインの中へ**。

### 3.4 デプロイ観点のボーナス

パイプラインオブジェクトを 1 つ保存するだけで、前処理+モデルが一緒についてきます。デプロイコードでは `pipe.predict(新しいデータ)` の 1 行で済み、「前処理の入れ忘れ」タイプの学習-サービング不一致が消えます。

### 3.5 パイプラインはどこまで育つのか

今日は「スケーラー+モデル」の 2 区画のベルトですが、実務のパイプラインは欠損補完 → エンコーディング (level04) → スケーリング → 特徴量選択 → モデルまで 5 区画以上に育ちます。sklearn の `ColumnTransformer` を使えば、「数値列はスケーリング、文字列はワンホット」のように列ごとに違う処理を 1 本のベルトに束ねられます。構造は今日学んだものと同じなので、必要になったときに名前だけ調べて使えば大丈夫です。

## 6. よくある間違い

- **テストデータに fit_transform を呼ぶ**: テストには `transform` だけ。パイプラインを使えばこのミス自体が不可能になります。
- **スケーリングを交差検証の外で先に済ませる**: フォールドの外の情報が漏れ込みます。`cross_val_score` にはパイプラインごと渡しましょう。
- **ツリーモデルだからとスケーリングを完全に無視する**: 今は正しくても、後でモデルをロジスティック回帰に替えた瞬間、静かに性能が崩れます。パイプラインに入れておけばモデルの交換が安全です。
- **スケーリング後の値の意味を忘れる**: 標準化された係数や値 (-1.2 など) をレポートに元の単位のように書いてはいけません。解釈するときは元の単位に逆換算するか、「標準偏差単位」であることを明記しましょう。
