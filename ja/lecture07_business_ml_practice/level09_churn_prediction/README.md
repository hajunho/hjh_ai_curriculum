# Lecture 07 · Level 09 — 実践 2: 顧客チャーン予測

> EDA→特徴量→交差検証→解釈→アクションリストまで、この講義で学んだ部品をすべて組み立てて解約予測プロジェクトを完結させます。成果物は「リスク顧客トップ 10 + 顧客ごとの推奨アクション」です。
**難易度** ⭐⭐⭐⭐ / **前提** level01〜06 / **想定時間** 60分

## 1. なぜ学ぶのか — ビジネスの視点

新規顧客の獲得コストは既存顧客の維持コストよりはるかに高い、というのはマーケティングの古くからの定説です。だからサブスク・会員制・通信・金融のどこでも、「離れようとしている顧客を先に見つけて引き留める」解約防止は、データチームの定番第一号プロジェクトです。

このレベルの核心は技術ではなく**完結性**です。実務でプロジェクトが「AUC 0.83 達成」で終わると、何も起こりません。マーケティングチームが受け取ってすぐ動ける形 — **誰を (リスト)、なぜ (理由)、どうやって (アクション)** — まで加工して初めてプロジェクトは完成します。main.py の最後の出力が性能指標ではなく「リスク顧客トップ 10 と推奨アクションの表」なのはそのためです。

## 2. たとえ話で理解する

常連の多いジムのベテランマネージャーを思い浮かべてください。彼は会員が辞める 1 か月前から兆候を感じ取ります。「最近、出席がまばらだな」「先週、料金の問い合わせを 2 回していたな」「入会したばかりの方がもう飽き気味だな」。そして兆候が見えたら、相手に合わせて動きます — 出席がまばらな会員には近況確認の連絡と PT 体験券、料金に不満のある会員には料金プランの相談。

解約予測プロジェクトは、このマネージャーの感覚をシステムにする仕事です。① 兆候を探す (EDA)、② 兆候を数値に (特徴量)、③ 兆候を総合してリスクスコアを付ける (モデル)、④ どの兆候のせいかを説明する (解釈)、⑤ 兆候ごとの対応マニュアル (アクションマップ)。マネージャー一人の勘ではなく、顧客 2,000 人全員に対して毎週自動で回る感覚 — それがモデルの付加価値です。

## 3. 核心となる概念

### 3.1 プロジェクト設計書が先

level00 の関門のとおり、コードの前に仕様を書きます。予測対象: 今月の解約の有無。活用: 毎週リスク上位顧客に CRM キャンペーン。目標指標: 再現率 55% 以上のもとで適合率 25% 以上 (キャンペーン予算の制約、無作為送付の的中率 約 15% の 1.7 倍)。ベースライン: 無作為送付。この仕様が、以後のすべての技術選択 (しきい値、評価指標) の基準になります。

### 3.2 リスクスコアは確率で

`predict()` (0/1 判定) ではなく `predict_proba()` (解約確率) を使うのが実務の標準です。確率があって初めて ① リスク順に並べ替え、予算の分だけ上から介入し、② 確率の区間ごとに強度の違うアクション (80% 以上は電話相談、50〜80% はクーポン) を設計できます。0/1 判定は、確率にしきい値を 1 枚かぶせた特殊なケースにすぎません。

### 3.3 解釈: 係数をオッズ比で読む

ロジスティック回帰の標準化係数は、「その特徴量が大きくなると解約リスクが上がるのか下がるのか」の方向と大きさを与えます。`exp(係数)` はオッズ比 (odds ratio) で、「この特徴量が 1 標準偏差大きくなると解約オッズが何倍になるか」と読みます。非専門家向けの報告では「カスタマーセンターへの問い合わせが多いほどリスクが高い (最も強い信号)」くらいの、方向+順位の言葉に翻訳するのが良いでしょう。もうひとつ — **個々の顧客のリスク理由**は、「その顧客の特徴量の値が平均からリスク方向へどれだけ外れているか」(標準化値 × 係数) で近似できます。main.py の「主な原因」列がこの計算です。

### 3.4 アクションマップ — モデルの外側の設計

モデルは「誰が危険か」までしか答えません。「では何をするか」は人間が設計する対応ルールです。例: 主な原因が「利用日数の急減」なら → 再訪を促すコンテンツ/特典、「問い合わせの急増」なら → CS 優先相談、「自動決済の未設定」なら → 自動決済への切り替え特典。原因別のアクションマップはドメイン知識の領域であり、これがあって初めてリストがキャンペーンになります。

### 3.5 成果はどう確認するのか

リストを作ってキャンペーンをしたら、効果の検証は**介入しなかった対照群**との比較で行います (無作為に一部のリスク顧客を除外)。全員に介入すると、「モデルのおかげなのか、そもそも離れない人だったのか」が永遠に分かりません。このテーマは level11 の期待価値計算につながります。

## 4. 実習 — main.py

```bash
python3 main.py
```

`churn_table` の 2,000 人で完結プロジェクトを実行します。

- [1] 問題仕様の出力 (予測対象・活用・目標指標)。
- [2] ミニ EDA: ターゲット比率と、解約/残留グループの差が大きい上位の信号を確認します。
- [3] 特徴量の準備 + 派生特徴量 (`usage_per_tenure` など) を追加。
- [4] 5-fold 交差検証で AUC の平均±標準偏差を報告し、学習/テスト分割で最終モデルを確定します。
- [5] 解釈: 標準化係数を方向 (リスク↑/リスク↓) とともに出力します。
- [6] 成果物: テスト顧客のうち解約確率上位 10 名のリスト — 顧客 ID、解約確率、主な原因、推奨アクション — を表で出力します。

出力のハイライトは [6] です。性能の数字ではなく「マーケティングチームが月曜の朝に受け取ってそのまま実行できる表」が最終成果物である、という感覚を持ち帰ってください。

## 5. やってみよう

1. **(易しい)** トップ 10 をトップ 20 に増やし、確率 50% 未満の顧客がリストに入ってくるか確認してみましょう。入ってくるなら「介入予算をここまで使うのが正しいか?」を level01 の期待利益の観点から検討してみてください。
2. **(中くらい)** [6] の出力ルールを修正し、確率 80% 以上の顧客のアクションの前には `[電話]`、それ未満には `[メッセージ]` タグが付くようにしてみましょう。3.2 の「確率区間ごとの強度調節」をコードに移す練習です。
3. **(挑戦)** ロジスティック回帰を RandomForest に変え、[5] の解釈を `feature_importances_` で置き換えてみましょう。重要度は方向 (リスクを上げるのか下げるのか) を教えてくれないという違いを確認し、2 つのモデルのトップ 10 リストがどれだけ重なるか数えてみてください。

## 6. よくある間違い

- **性能報告でプロジェクトを終える**: 「AUC 0.83」は中間成果物です。リスト+理由+アクションまで行って初めて現場が動きます。
- **customer_id を特徴量として投入する**: ID は一般化の信号を持たない識別子です。偶然のパターンを丸暗記して過学習を招くだけです。
- **全データで学習したモデルで全顧客のリスクスコアを算出し、性能も同じデータで報告する**: 性能は必ず学習に使っていないデータで。運用スコアの算出と性能検証を区別しましょう。
- **アクションのないリストを渡す**: 「リスク顧客 500 名のリストです」とだけ投げられても、現場はどうしていいか分かりません。原因と推奨対応までがデータチームの仕事です。
- **介入効果を対照群なしで主張する**: 「キャンペーン対象の解約率が低かった」のは、モデルが優秀だからではなく、もともと離れない人にクーポンを配ったからかもしれません。
