# Lecture 07 · Level 08 — 実践 1: 売上・需要予測

> カフェチェーンの 1 年分の売上で「来週の日別売上」を予測するフルパイプラインを作ります。曜日・季節・移動平均の特徴量と、時間ベースの分割が主役です。
**難易度** ⭐⭐⭐⭐ / **前提** level03、level06 / **想定時間** 50分

## 1. なぜ学ぶのか — ビジネスの視点

「来週の売上はいくらになるだろう?」は、あらゆる業種に共通する問いです。答えによって発注量、勤務シフト、キャッシュフローの計画が変わります。予測が 10% 外れれば、在庫廃棄や品切れ、人員過剰や行列という形で、そのままコストになります。

需要予測は分類ではなく**回帰 (regression)** であり、データに**時間軸**があるという点で、これまでの問題とは性格が異なります。時間軸があると 2 つのことが変わります。第一に、特徴量の主力が「曜日・季節・直近のトレンド」といった時間派生の特徴量になります。第二に、検証のルールが変わります — 必ず過去で学習し、未来で試験を受けなければなりません (level06 の [4] で見た落とし穴)。このレベルは、この 2 つを備えた**最後まで走り切る最初の実践プロジェクト**です。

## 2. たとえ話で理解する

経験豊富なカフェ店長の頭の中を写し取ってみましょう。店長は来週の発注量を決めるとき、だいたいこう考えます。

1. 「最近、1 日平均どれくらい売れている?」 → **移動平均** (直近のトレンド)
2. 「来週の土曜日は、いつもの土曜日くらい売れるだろう」 → **曜日効果**
3. 「夏が近づいているからドリンクが増えるはず」 → **季節効果**
4. 「昨日急にたくさん売れたなら、明日も少し続くかな?」 → **前日売上 (lag)**

機械学習による需要予測は、この 4 つの直感をそれぞれ数値の列にしてモデルに与えることです。モデルが魔法で未来を見るのではなく、**店長の直感を特徴量に翻訳して、一貫して、大量に、毎日自動で**適用する — それが本質です。だからこのレベルのコードの大部分は、モデルではなく特徴量作りに使われます。

## 3. 核心となる概念

### 3.1 時系列特徴量の御三家

- **カレンダー特徴量**: 曜日 (ワンホットまたは週末フラグ)、月、祝日かどうか。繰り返すパターンを担います。
- **ラグ (lag) 特徴量**: `lag_1` (前日)、`lag_7` (1 週間前の同じ曜日)。「最近どうだったか」を担います。
- **移動平均 (rolling mean)**: 直近 7 日平均、28 日平均。ノイズをこし取ったトレンドを担います。

注意: ラグ・移動平均は、必ず**予測時点より前の値だけ**を使うように `shift(1)` してから計算します。今日の売上予測に今日の売上を含む移動平均を使えば、正解を写すリーケージです。

### 3.2 季節性を数値に — sin/cos 変換

「年間で何日目か (1〜365)」をそのまま入れると、12 月 31 日 (365) と 1 月 1 日 (1) が両極端に離れて見えます。`sin(2π·day/365)`、`cos(2π·day/365)` の 2 列に変えると、年末と年始が自然にお隣どうしになる円形カレンダーになります。曜日も同じ方式が可能ですが、種類が 7 つしかないのでワンホットの方が一般的です。

### 3.3 時間ベースの分割とベースライン

- **分割**: 最後の数週間をテスト (=来たる週の状況を再現)、それより前を学習に。無作為分割は禁止です。評価区間が短すぎると (例: 7 日) 順位が運に左右されるため、実務では複数週にわたるバックテストで評価します。
- **ベースライン (baseline)**: モデルが超えるべき最低ライン。需要予測の慣例的なベースラインは ① 「昨日と同じ」(naive)、② 「先週の同じ曜日と同じ」(seasonal naive) です。この単純ルールに勝てないモデルはデプロイする理由がありません。実務のレポートでも、必ずベースライン比の改善率で語りましょう。

### 3.4 評価指標 — MAE と MAPE

- **MAE** (平均絶対誤差): 「平均して 1 日 N ウォン外れる」。単位がウォンなので直感的です。
- **MAPE** (平均絶対パーセント誤差): 「平均 N% 外れる」。規模の異なる店舗どうしを比較するときに便利ですが、実際の値が 0 に近いと爆発するので注意します。

## 4. 実習 — main.py

```bash
python3 main.py
```

- [1] `sales_table` の 1 年分を整形 (欠損・マイナスを除去) し、日別総売上に集計します。
- [2] 特徴量の生成: 曜日ワンホット、週末フラグ、季節 sin/cos、lag_7 (先週の同じ曜日)、7 日/28 日移動平均 (すべて 7 日前基準 — 予測時点で知り得る値のみ)。
- [3] 時間ベースの分割: 最後の 4 週間 (28 日) を評価区間として封印します。7 日だけでは運が大きく混ざるため、毎週予測を更新する運用を想定した 4 週間バックテストで評価します。
- [4] ベースライン 2 種 (昨日と同じ / 先週の同じ曜日) と RandomForest 回帰の MAE・MAPE を 4 週間バックテストで比較します。
- [5] 「来週」(最後の 7 日) の予測 vs 実際を日別に出力し、直近 8 週間の流れと予測区間を描いた PNG を `outputs/` に保存します。
- [6] 特徴量重要度で「モデルが何を見て予測したのか」を確認します。

観察ポイント: ベースライン (特に seasonal naive) が思ったより強いこと、そしてモデルの改善分がどこから来るのか (曜日+トレンドの組み合わせ) です。PNG では予測線が実際の曜日のリズムに追随しているか確認してみてください。

## 5. やってみよう

1. **(易しい)** 評価区間を変えてみましょう (`BACKTEST_DAYS = 7`、`56`)。7 日評価ではベースラインが勝つこともあります — 評価区間が短いほど順位が運に左右されるという level06 の教訓を再確認してください。
2. **(中くらい)** lag_14 (2 週間前の同じ曜日) と lag_28 を特徴量に追加してみましょう。MAE は改善しますか? 特徴量重要度の順位はどう変わりますか?
3. **(挑戦)** 総売上の代わりに「ドリンクカテゴリだけ」の日別売上で同じパイプラインを回してみましょう。季節 sin/cos の重要度がぐっと上がるはずです — 夏のドリンク繁忙期というドメイン知識と一致するか確認してください。

## 6. よくある間違い

- **無作為分割で検証する**: 時系列の第一の禁忌です。スコアは良さそうに見えても本番で崩れます。分割は常に時間順で。
- **移動平均に今日を含める**: `rolling(7).mean()` を `shift(1)` なしで使うと、今日の値が今日の特徴量に入り込みます。静かなリーケージの定番です。
- **ベースラインなしで「MAE 50 万ウォン」と報告する**: その数字が良いのか悪いのか誰にも分かりません。「昨日と同じ、比 -23%」のように相対改善で報告しましょう。
- **遠い未来を一発で予測する**: ラグ特徴量は 1 日先の予測用です。7 日先を予測するには、予測値を再び入力に使う再帰方式か、7 日前のラグだけを使う直接方式のどちらかを明示的に設計する必要があります (main.py は lag_7・移動平均など「7 日前までの情報だけ」を使う直接方式です)。
- **祝日・プロモーションの無視**: 実データで最も大きな誤差は特殊日に出ます。特殊日カレンダーを特徴量に入れることが、実務の精度の半分です。
