# Lecture 07 · Level 04 — カテゴリ変数のエンコーディング

> 「渋谷店」「コーヒー」「土曜日」のような文字データを、モデルが食べられる数値に変える 3 つの方法と、それぞれの落とし穴を実験で比較します。
**難易度** ⭐⭐⭐ / **前提** level03 / **想定時間** 40分

## 1. なぜ学ぶのか — ビジネスの視点

実務データの半分は数値ではありません。店舗名、商品カテゴリ、加入経路、役職、地域 — すべて**カテゴリ型 (categorical)** 変数です。ところがほとんどのモデルは数値しか受け付けません。文字を数値に変えるエンコーディング (encoding) は、だからこそすべてのテーブルデータプロジェクトの通過儀礼なのです。

問題は、変え方が何通りもあり、**選び方を間違えるとモデルに嘘の情報を注入してしまう**ことです。店舗名を 1, 2, 3 に変えると、モデルは「渋谷店(3) は大阪店(1) の 3 倍」という、ありもしない序列を学習します。逆に方法をうまく選べば、「店舗」という情報ひとつが売上予測の精度を大きく引き上げます。どのエンコーディングがどの状況に合うかを知っていることは、データチームのレポートに対して「なぜこう処理したのですか?」と問える検収能力でもあります。

## 2. たとえ話で理解する

アンケートの「職業欄」をシステムに入力する 3 つの方式を想像してみてください。

- **ワンホットエンコーディング (one-hot)**: 職業ごとにチェックボックスの列を 1 つずつ作ります。「会社員 ☑ / 自営業 ☐ / 学生 ☐」。序列の歪みはまったくありませんが、職業が 500 種類あれば列も 500 個になります。
- **順序エンコーディング (ordinal)**: 職業に番号を振ります。「会社員=1、自営業=2、学生=3」。列は 1 つで済みますが、数字の大小に何の意味もないのにモデルは意味を探そうとします。ただし「一般社員<主任<課長<部長」のように**本当に序列のあるカテゴリ**なら、むしろ正直な方法です。
- **ターゲットエンコーディング (target)**: 職業の代わりに「その職業グループの過去の平均延滞率」のような**正解のグループ平均**を書き込みます。列 1 つに情報を圧縮する強力な方法ですが、正解を材料に使うため、計算を誤ると正解が問題用紙に漏れ込むリーケージ事故が起こります。

## 3. 核心となる概念

### 3.1 3 つのエンコーディングまとめ

| 方法 | 列の数 | 序列の歪み | リークの危険 | 向いている場合 |
|---|---|---|---|---|
| ワンホット | カテゴリ数だけ | なし | なし | カテゴリ数が少ない (数十個以下) ときの既定値 |
| 順序 | 1 | **あり** (無序列カテゴリに使うと) | なし | 本当に順序のあるカテゴリ (等級、役職)、ツリー系モデル |
| ターゲット | 1 | なし | **あり** | 高カーディナリティ (カテゴリ数百〜数万個) |

ツリー系モデル (決定木、ランダムフォレスト) は数値を「分割の基準」としてしか使わないため、順序エンコーディングの歪みには比較的鈍感です。序列の歪みが致命的なのは、数値の大きさをそのまま信じる線形モデルの側です。

### 3.2 ターゲットエンコーディングのリークと防御

ターゲットエンコーディングの値は、必ず**学習データからのみ**計算しなければなりません。テストまで含めてグループ平均を取ると、テストの正解が特徴量に染み込みます。さらに学習データの中でも「自分の行の正解が自分の特徴量に反映される」問題があるため、本番では交差検証方式 (自分のフォールドを除いて計算) やスムージング (サンプルの少ないグループは全体平均の側に引き寄せる) を使います。main.py は最も基本的な防御である「学習データのみで計算 + 未登場カテゴリは全体平均」を実装しています。

### 3.3 高カーディナリティ (high cardinality) 問題

顧客 ID、商品コード、郵便番号のようにカテゴリが数千〜数万個あると、ワンホットは列の爆発 (次元の呪い + メモリ) を引き起こします。このときの選択肢は ① ターゲットエンコーディング、② 頻度エンコーディング (出現回数に置き換え)、③ 上位 N 個だけ残して残りは「その他」にまとめる、④ その列自体を捨てる (顧客 ID のように一般化の信号がないなら捨てるのが正解) です。

### 3.4 未登場カテゴリの処理

デプロイ後には「新規オープン店舗」のように、学習時には存在しなかったカテゴリが入ってきます。ワンホットはすべての列を 0 に、ターゲットエンコーディングは全体平均で代替する、といった**未登場 (unseen) カテゴリのポリシー**をあらかじめ決めておかないと、運用中に障害が起こります。`pd.get_dummies` を学習/テストに別々に適用すると列がずれる事故になるため、実務では sklearn の `OneHotEncoder(handle_unknown="ignore")` をパイプライン (level05) に組み込むのが定石です。

## 4. 実習 — main.py

```bash
python3 main.py
```

`sales_table` の 1 年分から、店舗・カテゴリ・曜日で売上を予測する線形回帰 (Ridge) を、エンコーディングだけ変えて 3 回訓練します。

- [1] データの整形: 欠損・マイナス売上の行を取り除き、カテゴリ型 3 列のカテゴリ数を確認します。
- [2] ワンホット: `OneHotEncoder` で列が何個に増えるかを確認し、性能 (MAE, R²) を測ります。
- [3] 順序: カテゴリを番号に置き換え。列は 3 つだけですが、性能が崩れるのを観察します (序列の歪み)。
- [4] ターゲット: 学習データのグループ平均売上に置き換え。列 3 つでワンホットに迫る性能を確認します。
- [5] まとめ表: 方法別の「列の数 vs 性能」を並べ、高カーディナリティ状況での選択基準を出力します。

注目すべき観察ポイント: 順序の R² がワンホットより明らかに低いこと (線形モデル + 無序列カテゴリの相性問題)、そしてターゲットエンコーディングが列 3 つでその差の大部分を埋めることです。

## 5. やってみよう

1. **(易しい)** [3] でカテゴリに番号を振る順序を変えてみましょう (例: `categories` の順序を逆にする)。性能がまた変わります — 順序エンコーディングの結果が「番号を振る順序」という偶然に左右される証拠です。
2. **(中くらい)** Ridge を `DecisionTreeRegressor(max_depth=8)` に変えて 3 つのエンコーディングを再比較してみましょう。ツリーでは順序エンコーディングの性能低下がずっと小さくなることを確認し、その理由を 3.1 で説明してみてください。
3. **(挑戦)** 「頻度エンコーディング」(各カテゴリを学習データでの出現回数に置き換え) を自分で実装し、4 番目の選手として参戦させてみましょう。ヒント: `value_counts()` を `map` すれば 2 行です。

## 6. よくある間違い

- **無序列カテゴリにうっかり番号を振る**: Excel で「東京=1、大阪=2」とコーディングされたデータをそのままモデルに入れる事故が最も多いパターンです。線形モデルなら必ずワンホットに展開してください。
- **ターゲットエンコーディングを全データで計算する**: 検証性能が急に良くなったら、喜ぶ前にリーケージを疑いましょう。計算は常に学習データのみで。
- **get_dummies を学習/テストに別々に適用する**: 両側の列構成が食い違い、デプロイ時に壊れます。`OneHotEncoder(handle_unknown="ignore")` + パイプラインが定石です。
- **顧客 ID をターゲットエンコーディングして性能が上がったように見える**: 顧客あたりの行数が少ないと、グループ平均は事実上、正解のコピーになります。ID 系の列は原則除外してください。

## 次のレベルの予告

エンコーディングやスケーリングのような前処理は「学習データのみで fit」というルールを守る必要がありますが、手作業で管理すると必ずミスが起きます。level05 では sklearn の Pipeline で前処理とモデルをひとかたまりに束ね、この問題を構造的に解決します。
