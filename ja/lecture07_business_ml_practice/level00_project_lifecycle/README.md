# Lecture 07 · Level 00 — データプロジェクトの全体像

> 問題定義→データ→モデル→デプロイ→モニタリングという 5 段階の地図を頭に入れ、「失敗するプロジェクトの共通点」を先回りして学びます。
**難易度** ⭐ / **前提** lecture06 level00〜02 / **想定時間** 25分

## 1. なぜ学ぶのか — ビジネスの視点

機械学習プロジェクトの失敗原因の第 1 位はモデルではありません。業界で繰り返し観察される失敗談の大半は、「そもそも何を予測すべきか合意ができていなかった」「データがその問いに答えられる状態ではなかった」「作ったのに誰も使わなかった」というものです。つまり失敗はコーディングの段階ではなく、その前後の段階で起こります。

IT 非専門の皆さんがこの地図を知っておくべき理由は明確です。実務での皆さんの役割はモデルのコードを書くことではなく、プロジェクトが 5 段階のうち今どこにいて、どの関門 (ゲート、gate) で止まるべきかを判断することだからです。発注者・現場担当者・検収者のどの役割であっても、この地図が 1 枚あるだけで会議で投げかけるべき質問が変わります。

## 2. たとえ話で理解する

データプロジェクトは**飲食店の開業**と驚くほど似ています。

1. **問題定義 = 立地とメニューの決定**: 「何でもおいしく作ればいい」で始めた店は潰れます。誰に (ターゲット顧客)、何を (メニュー)、いくらで (成功基準) 売るのかを先に決めなければなりません。
2. **データ = 食材の調達**: どんなに優れたシェフでも、傷んだ食材では料理を作れません。食材の検品 (データ品質チェック) を飛ばすと、厨房 (モデル) で事故が起こります。
3. **モデル = 調理**: 全体の仕事の 20% 程度です。開業準備の大半が料理そのものではないように、プロジェクトの時間の大半は前後の段階に使います。
4. **デプロイ = 開店**: 料理が完成しても、お客さまの前に運ぶ動線 (既存の業務システムとの接続) がなければ誰も食べられません。
5. **モニタリング = 常連客の維持**: 開店初日の味が永遠に保たれるわけではありません。食材の相場 (データ分布) が変わればレシピを調整する必要があります。

「モデルさえ良ければいい」という考えは、「料理さえうまければ店は成り立つ」という考えと同じ理由で危険です。

## 3. 核心となる概念

### 3.1 5 つの段階とそれぞれの成果物

| 段階 | 核心となる問い | 代表的な成果物 |
|---|---|---|
| ① 問題定義 | 何を、なぜ、成功基準は? | 問題仕様書 (予測対象・活用方法・目標指標) |
| ② データ | その問いに答えられるデータはあるか? | データ監査レポート (行数・欠損・ターゲット比率) |
| ③ モデル | ベースライン (baseline) より良いか? | 検証済みの性能レポート (交差検証を含む) |
| ④ デプロイ | 現場が実際に使えるか? | 業務プロセスへの接続 (例: 毎週リスク顧客リストを自動送付) |
| ⑤ モニタリング | 性能は維持されているか? | 性能ダッシュボード、再学習の基準 |

重要なのは、各段階の間に**関門**があるという点です。関門を通過できなければ、次の段階へ進まずに立ち止まるか引き返さなければなりません。例: データ監査で解約顧客のサンプルが 50 人しかなければ、モデル段階へ進むのではなく、データをさらに集めるのが正解です。

### 3.2 失敗するプロジェクトの共通点

- **目標指標がない**: 「AI で何かやってみよう」で始めると、何が出てきても成功か失敗かを判定できません。
- **正解ラベルが不十分**: 「解約」の定義が部署ごとに違うと (解約申請? 3 か月未ログイン?)、モデルは互いに別の問題を学習してしまいます。
- **ベースラインなしで始める**: 「先月と同じと予測する」という単純ルールにすら劣るモデルがデプロイされる事態が実際に起こります。
- **デプロイ計画がない**: モデルが出す確率の数字を受け取る人・システム・業務手順が決まらないまま開発から始めてしまいます。
- **モニタリングがない**: コロナ禍のような環境変化でデータ分布が変わっても (分布シフト、data drift)、誰も気づきません。

### 3.3 時間配分の現実

教科書はモデルを長く扱いますが、実務の時間配分はおおよそ「問題定義・データ 60〜70%、モデル 10〜20%、デプロイ・モニタリング 20〜30%」に近いのが実情です。この講義のレベル構成 (部品 8 個 + 実践 4 個) もその現実を反映しています。

## 4. 実習 — main.py

```bash
python3 main.py
```

main.py は架空のプロジェクト「サブスク解約防止」を 5 段階の関門に通すシミュレーションです。

- [1] 問題定義: 仕様書の項目 (予測対象、活用方法、目標指標) が埋まっているかを点検し、関門の判定を出力します。
- [2] データ: `hjh_data.churn_table()` を実際に呼び出して行数・欠損・ターゲット比率を監査し、「少数クラスのサンプルは十分か」という関門を通過させます。
- [3] モデル: まだモデルを学ぶ前なので、「多数決ベースライン」の精度を計算し、この後のモデルが超えるべきラインを確認します。
- [4]〜[5] デプロイ・モニタリング: チェックリストの項目が空欄のままの状態をわざと見せ、関門で「中断」判定が出るのを観察します。

出力の最後にあるサマリー表で、どの段階が PASS でどの段階が STOP かを確認してください。コードの核心部は `gate()` 関数です。段階ごとの点検項目をリストで受け取り、1 つでも空欄なら通しません。とても単純ですが、実務で最も頻繁に省略されるロジックです。

## 5. やってみよう

1. **(易しい)** [4] デプロイ段階のチェックリストで空欄になっている項目 (`""`) を実際の計画の文章で埋め、再実行して PASS に変わるか確認してみましょう。
2. **(中くらい)** `min_minority` の値を 500 に上げてみましょう。データの関門が STOP になります。このとき実務者はどの選択肢 (期間の延長、定義の緩和、プロジェクトの保留) を検討すべきか、README の 3.1 を参考に書き出してみてください。
3. **(挑戦)** 自分の会社 (または架空の会社) の課題を 1 つ選び、[1] 問題定義の辞書を自分で書いてみましょう。「目標指標」を数字で書けるかどうかが鍵です。ヒント: 「解約率を下げる」(×) → 「6 か月以内に月次解約率 18%→15%」(○)。

## 6. よくある間違い

- **モデルを先に決めて問題を後付けする**: 「話題の手法を試してみよう」は、メニューを決める前にオーブンを買うようなものです。
- **精度を無条件に成功基準として採用する**: 解約率 18% のデータでは、「誰も解約しない」と言い続けるだけで精度 82% になります。ベースラインのない精度はただの数字の飾りです。
- **一回きりの分析と運用システムを混同する**: レポートを 1 本書いて終わる分析と、毎週動き続けなければならないシステムでは、要件がまったく異なります。始める前にどちらなのか合意しましょう。
- **関門の判定を感情で下す**: 「ここまで来たのにもったいない」はサンクコスト (埋没費用) の声です。関門はチェックリストで、機械的に。
