# Lecture 07 · Level 03 — 特徴量エンジニアリング

> 同じデータ、同じモデルでも、特徴量をどう仕込むかで性能は変わります。元の特徴量 vs 派生特徴量を同じモデルで対決させ、その威力を証明します。
**難易度** ⭐⭐⭐ / **前提** level02、lecture06 level05 / **想定時間** 40分

## 1. なぜ学ぶのか — ビジネスの視点

Kaggle (コンペ) でも会社でも、予測性能を分けるのはたいていモデルの種類ではなく、**特徴量 (feature、入力変数) の品質**です。そして良い特徴量を作る材料は数学ではなく**ドメイン知識** — その業務を知る人の感覚です。

「深夜に海外で立て続けに使われたカードは怪しい」というのは、カード会社の審査担当なら誰でも知っている常識です。しかしデータには `hour=2`、`is_foreign=1`、`tx_count_1h=9` というバラバラの数字があるだけで、「怪しいパターン」という列はありません。その常識を、モデルが食べられる数値の列に翻訳する仕事が特徴量エンジニアリングであり、これこそ IT 非専門の実務者がデータプロジェクトに貢献できる最大のポイントです。コーディングはデータチームがやるとしても、「どんな特徴量を作るべきか」は現場にしか分かりません。

## 2. たとえ話で理解する

モデルは**与えられた材料しか食べない偏食の審査担当者**です。信用審査の担当者に書類を渡す場面を考えてみてください。

- 元のまま: 「月収 400 万ウォン」「月々のローン返済額 180 万ウォン」 — 2 つの数字を別々に見ても判断が難しい。
- 派生特徴量: 「収入に対する返済比率 45%」 — 割り算を 1 回しただけなのに、ひと目で判断できます。

人間の審査担当者は頭の中でこの割り算を自動的に行いますが、線形モデルは自分で割り算を作り出せません (足し算と定数倍だけが可能)。だから人間があらかじめ比率・差分・グルーピングの列を作り、「消化しやすい形」に整えて出してあげる必要があります。料理でいえば、特徴量エンジニアリングは食材の下ごしらえです。下処理していない丸ごとの魚を渡されたら、どんな腕利きの料理人 (モデル) でも実力を発揮できません。

## 3. 核心となる概念

### 3.1 派生特徴量の代表レシピ

| レシピ | 例 | いつ使うか |
|---|---|---|
| 比率 (ratio) | 収入に対する返済額、利用日数/契約月数 | 2 つの数の相対関係が重要なとき |
| 差分 (diff) | 今月 − 先月の使用量 | 変化・トレンドが信号のとき |
| 対数変換 | log(取引金額) | 金額のように一方へ極端に偏った分布 |
| 区間化・フラグ | 深夜時間帯かどうか (is_night) | 「区間」が意味を持つとき |
| 交互作用 | 海外 × 深夜 | 条件が重なったときだけ危険なパターン |
| 集計 (aggregate) | 顧客ごとの直近 30 日平均決済額 | 取引単位のデータを顧客単位に要約 |

このうち対数変換は、特に金額データの定番です。1 万ウォンと 2 万ウォンの差 (2 倍) と、1 億と 2 億の差 (2 倍) を同じ大きさにしてくれるので、線形モデルが「倍率」の言葉で考えられるようになります。

### 3.2 アイデアはどこから来るか — EDA と現場インタビュー

level02 の二変量分析がそのまま材料リストです。「不正取引は深夜に集中する」を見たなら `is_night` フラグを、「金額の分布がひどく偏っている」を見たなら対数変換を作ります。これに現場インタビュー (「私たちはどこを見て怪しいと感じますか?」) を加えれば、特徴量候補リストの完成です。

### 3.3 データリーケージ (data leakage) — 特徴量エンジニアリング最大の落とし穴

派生特徴量を作っていると、うっかり**未来の情報**や**正解の影**を特徴量に混ぜてしまうことがあります。

- 「返金の有無」で解約を予測: 返金は解約の**後に**起こること — 予測時点では知り得ない値です。
- 全データ (テストを含む) の平均で派生特徴量を計算: テストの情報が学習に漏れ込みます。
- 「調査結果コード」で不正を予測: 調査は不正と**判定された後に**行うもの。

見分ける質問はひとつだけです。**「予測すべきその時点で、この値を知ることができるか?」** 答えが「いいえ」なら、性能がどれだけ良くても捨てなければなりません。リーク特徴量は、検証性能は幻想的に良く、本番ではまったく役に立たない、最も悪質なバグです。

### 3.4 性能比較は公正に

派生特徴量の効果を主張するには、**モデル・データ分割・評価指標を完全に固定**し、特徴量リストだけを変える必要があります。main.py はまさにこの統制実験を行います。

## 4. 実習 — main.py

```bash
python3 main.py
```

`fraud_table` の 5,000 件で不正検知モデルを 2 回訓練します。「元の特徴量」は決済承認の瞬間にそのまま届くフィールド 3 つ (amount, hour, is_foreign) と仮定します。

- [1] データを読み込み、元の特徴量 3 つを確認します。
- [2] ドメイン知識に基づく派生特徴量 3 つを作ります: `log_amount` (対数変換)、`is_night` (深夜フラグ)、`foreign_night` (海外×深夜の交互作用)。
- [3] 同じロジスティック回帰、同じ分割で「元のみ」 vs 「元+派生」を訓練し、AUC と PR-AUC (平均適合率) を比較します。
- [4] 派生特徴量セットの係数を出力し、どの特徴量が働いているかを確認します。
- [5] リーケージのデモ: 正解をこっそり混ぜた偽の特徴量を 1 つ入れると性能が非現実的に跳ね上がることを見せ、警告を出力します。

注目すべき出力は [3] の PR-AUC 比較です。モデルは一文字も変えていないのに性能が跳ね上がる — それが特徴量の威力です。[5] では「良すぎる性能はバグ」という感覚も一緒に持ち帰ってください。

## 5. やってみよう

1. **(易しい)** 派生特徴量を 1 つずつ外して実行し、どの特徴量が性能に最も大きく貢献しているか確認してみましょう。ヒント: `DERIVED` リストから 1 つずつ消してみる。
2. **(中くらい)** 集計特徴量を参戦させてみましょう。テーブルにある `tx_count_1h` (直近 1 時間の決済件数 — 取引履歴を集計して初めて得られる値) と、比率特徴量 `amount_per_tx = amount / (tx_count_1h + 1)` を DERIVED に追加すると、PR-AUC はどこまで上がるでしょうか? 「集計特徴量が定番のエース」である理由を体感してください。
3. **(挑戦)** churn_table で同じ実験を設計してみましょう。候補: `usage_days_30d / tenure_months` (契約期間に対する活動性)、`support_calls_30d - plan_changes` など。どの特徴量がドメインの常識と合う方向の係数を持つか確認してください。

## 6. よくある間違い

- **予測時点の検証を省く**: 特徴量ひとつごとに「予測時点で知り得る値か?」と問わなければ、リーケージは必ず起こります。特徴量リストの横に「生成時点」の列を作って管理しましょう。
- **特徴量を際限なく増やす**: 特徴量は多いほど良いわけではありません。サンプルに対して特徴量が多すぎると過学習 (lecture06 level09) が起こります。作って→検証して→貢献がなければ捨てる。
- **ゼロ除算**: 比率特徴量の定番事故です。分母に +1 する (main.py の方式) か、条件分岐で処理しましょう。
- **テストデータを含めて統計特徴量を計算する**: 「全体平均に対する比率」のような特徴量は、必ず学習データの統計だけで作らなければなりません。level05 のパイプラインがこの問題を構造的に解決します。
