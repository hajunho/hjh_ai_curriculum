# Lecture 02 · Level 11 — 型ヒント・テスト・コード品質

> 型ヒントは関数の入出力の規格を明示した契約書、テストは「このコードはこの場合こう動く」を自動で検証する品質検査チェックリストです。
**難易度** ⭐⭐⭐⭐ / **前提** level10 / **目安時間** 60分

## 1. なぜ学ぶのか — ビジネスの視点

「自分のパソコンで一度動いた」と「信頼して使える」は別の話です。
実務のコードは他人が引き継ぎ、6か月後の自分が直し、データが変わった後も
動き続けなければなりません。そのときに必要なのが、このレベルの3つです。

- **型ヒント (type hint)**: 関数が何を受け取り何を返すのか、規格をコードに明示します。
  コメントと違い、ツール (mypy など) が規格違反を自動で捕まえてくれます。
- **テスト (test)**: 修正するたびに「既存の機能が壊れていないか」を自動で確認します。
  テストがあれば、コードを直すことが怖くなくなります — これが本当の効用です。
- **docstring と規約**: コードが自らを説明するようにする文書化の習慣です。

lecture02 の卒業試験のようなレベルです。この先の AI 実習で作るデータ処理関数に
この習慣が付いているかどうかが、「趣味のコード」と「業務のコード」を分けます。

## 2. たとえ話で理解する

**契約書のたとえ。** 外注業者に仕事を任せるときは、契約書に規格を書きます。
「貴社は取引リスト (各件は金額の整数) を渡し、当社はサマリーレポート (文字列) を納品する。」
型ヒントがまさにこれです。

```python
def summarize(amounts: list[int]) -> str:
```

「amounts は整数のリストで受け取り、文字列を返す」という契約が、関数のシグネチャに刻まれています。
契約書がなければ? 相手が文字列のリストを送ってきても誰も気づかないまま、納品日 (実行時点) に
事故が起きます。契約書があれば、検収担当者 (mypy) が **仕事を始める前に**
「規格の不一致」を指摘してくれます。

**品質検査チェックリストのたとえ。** 工場では製品を出荷する前にチェックリストを回します。
「正常な入力で正常な出力? 空の入力で安全に処理? 境界値 (0ウォン、最大値) で誤動作なし?」
テストコードは、このチェックリストを自動化したものです。人間が毎回目で確認する代わりに、
`python3 main.py` 一発で全項目が検査されます。ラインを少しでも変えたら
チェックリストを回し直すこと — これが回帰テスト (regression test) です。

## 3. 核心となる考え方

### 3.1 型ヒントの文法

```python
def calc_vat(amount: int, rate: float = 0.1) -> int:
    ...

price: int = 4500
stores: list[str] = ["渋谷", "新宿"]
stock: dict[str, int] = {"ボールペン": 37}
memo: str | None = None          # 文字列か None (ないかもしれない値)
```

`引数: 型`、`-> 戻り値の型` がすべてです。コレクションは `list[int]` のように中身の型まで
書き、「ないかもしれない値」は `| None` で表現します。

重要な事実: **Python は実行時に型ヒントを強制しません。** ヒントを破っても
プログラムはいったん動きます。ヒントの効力は3つの経路で現れます —
(1) 読む人への規格の伝達、(2) エディタの自動補完・警告、(3) mypy のような
静的検査器 (static checker) が実行せずにコードだけを走査して規格違反を報告。
mypy は別途インストールするツールなので、この実習では概念だけを扱い、main.py に **超ミニ検査器** を
作って原理 (シグネチャと実際の値の突き合わせ) を体験します。

### 3.2 assert — 1行の自動検査

```python
assert calc_vat(10000) == 1000, "1万ウォンの付加価値税は1000ウォンのはず"
```

`assert 条件, メッセージ` は、条件が真なら静かに通過し、偽ならメッセージとともに
`AssertionError` を出します。「期待値と実際の値の突き合わせ」というテストの核心が、
この1行に詰まっています。実務では pytest のような専門ツールを使いますが、
その根っこはすべて assert です。

### 3.3 良いテストの3点セット

同じ関数でも、3種類の入力を検査して初めて安心できます。

1. **正常ケース**: 代表的な入力 → 期待どおりの出力
2. **境界ケース (edge case)**: 0、空のリスト、最大値、ちょうど基準線の値
3. **エラーケース**: 不正な入力が **意図した例外を出すか** (黙っておかしな値を
   返すのが最悪です)

バグの大部分は2番と3番から生まれます。「空のリストが来たら?」をテストで問いかける
習慣が、深夜の障害電話を減らします。

### 3.4 docstring — 関数の取扱説明書

```python
def net_price(price: int, discount_rate: float) -> int:
    """割引適用価格を計算する。

    Args:
        price: 定価 (ウォン)。0以上。
        discount_rate: 割引率。0.0 〜 1.0。
    Returns:
        割引適用価格 (ウォン、整数切り捨て)。
    Raises:
        ValueError: 割引率が範囲を外れた場合。
    """
```

関数冒頭の三重引用符の文字列が docstring です。`help(net_price)` ですぐに
参照でき、エディタが自動で表示してくれ、型ヒントには収まらない情報 — 単位、範囲、
例外条件 — を収めます。「型ヒント = 規格、docstring = 取扱説明書」と役割が分かれます。

### 3.5 コード品質チェックリスト

- 名前を読むだけで意味が通じるか (level01・05 の原則)
- 関数は一つの仕事だけをしているか、20〜30行を超えていないか
- マジックナンバーの代わりに名前付き定数を使っているか (`0.1` の代わりに `VAT_RATE`)
- 書式を統一しているか — コミュニティ標準のスタイルガイド (PEP 8) と自動フォーマッタがあります
- そして: テストなしにリファクタリングしていないか

## 4. 実習 — main.py

実行方法:

```bash
cd lecture02_python_basics/level11_typing_testing_quality
python3 main.py
```

税金・割引の計算関数 (level05 の題材) に型ヒントと docstring を着せて、
自作テストランナーで検証する総合デモです。

- **[1] 契約書を読む**: 型ヒントの付いた関数たちのシグネチャを出力し、
  `__annotations__` で Python がヒントをどう覚えているかを見ます。
- **[2] ヒントは強制ではない**: 規格を破った呼び出しがそのまま動いてしまう様子を見せ、
  だからこそ検査器が必要だという結論につなぎます。
- **[3] 超ミニ型検査器**: 関数のヒントと実際の引数の型を突き合わせる20行の
  `tiny_type_check` で [2] の違反を捕まえます — mypy がやっていることの原理体験です。
- **[4] ミニテストランナー**: 正常・境界・エラーの3点セットのテスト9個を assert で書き、
  合格/不合格を集計して `9 passed` のレポートを出力します。わざと仕込んだバグ1個
  (境界値の処理) をテストが捕まえ、直した版はすべて合格する流れを見せます。
- **[5] docstring の活用**: `help()` が見せてくれる説明書を出力します。

## 5. やってみよう

1. **ヒントを付ける** — 以前のレベルで作った関数を1つ (例: level08 utils の `format_krw`) 選び、
   型ヒントと docstring を付けてみましょう。(ヒント: `def format_krw(amount: int) -> str:`)
2. **テストの追加** — [4] のテストに「割引率 1.0 (全額割引) なら0ウォン」と
   「マイナスの価格は ValueError」の2ケースを追加しましょう。(ヒント: 例外のテストは try で包み、
   「例外が出たら合格」と反転させて判定します — ランナーに見本があります。)
3. **バグ再現の訓練** — [4] で直したバグをわざと復活させてからテストを回し、
   いくつのテストが不合格に変わるか確認しましょう。(ヒント: テストがあれば、バグを
   「再現 → 修正 → 再検証」するサイクルが1分で済みます。)

## 6. よくある間違い

- **ヒントを付けたから安全だと信じる** — Python は実行時にヒントを強制しません。
  検査器 (mypy) を回すか、重要な値はコードで直接検証 (raise) しましょう。
- **正常ケースだけをテスト** — 合格しても安心できません。境界・エラーケースが本題です。
- **テストが実装を丸写しする** — 関数の中の計算式をコピーして期待値を作ると、
  バグまでコピーされます。期待値は手で、独立に求めましょう。
- **docstring とコードの不一致** — コードを直して説明書を直さなければ、嘘の文書に
  なります。関数を修正したら docstring も一緒に読む習慣を。
- **assert を入力検証に使う** — assert は最適化オプション (-O) で丸ごと無効になることがあります。
  ユーザー入力の検証は raise (level07)、テストは assert — 用途を区別しましょう。
