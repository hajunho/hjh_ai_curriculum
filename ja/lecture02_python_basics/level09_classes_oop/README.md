# Lecture 02 · Level 09 — クラスとオブジェクト指向

> クラスはたい焼きの型 (設計図)、オブジェクトはその型で焼いたたい焼き (実体) です。データ (属性) と手順 (メソッド) を一体に束ね、継承で「ほとんど同じだが少しだけ違う」ルールをすっきり管理します。
**難易度** ⭐⭐⭐ / **前提** level08 / **目安時間** 60分

## 1. なぜ学ぶのか — ビジネスの視点

社員の給与計算プログラムを作るとしましょう。社員ごとに名前・基本給・勤続年数 (データ) があり、
給与計算・年次有給休暇の算定 (手順) があります。これまで学んだやり方なら、データは辞書に、
手順は関数に別々に置きます。社員が5種類 (正社員、マネージャー、契約社員...) に増え、ルールが
少しずつ違ってくると、「この辞書にはどの関数を使うんだっけ?」というペア合わせのミスが始まります。

クラス (class) はデータと手順を1つの単位に束ね、「社員という概念」そのものをコードにします。
そして継承 (inheritance) は「マネージャーは社員のすべてのルールに従うが、給与に役職手当だけ
追加」のように、**共通ルールは1か所に、差分だけを別に** 書けるようにしてくれます。皆さんが毎日使う
pandas の DataFrame も、後で学ぶ torch のモデルも、すべてクラスです。この概念は
AI カリキュラム全体の文法的な土台でもあります。

## 2. たとえ話で理解する

**たい焼きの型のたとえ。** たい焼き屋を始めるには、まず焼き型を作ります。型そのものは食べられません。
型に生地とあんこを入れて焼いて初めて、食べられるたい焼きが出てきます。

- **クラス = たい焼きの型**: 「社員とは名前・基本給・勤続年数を持ち、給与を計算できる」という設計図。
- **オブジェクト (object)/インスタンス (instance) = たい焼き**: その型で焼いた実体。`Employee("田中", ...)`
  するたびに1匹ずつ出てきます。
- **属性 (attribute) = 各たい焼きの中身**: 同じ型から出てきても、あんこのたい焼きとカスタードのたい焼きが
  違うように、オブジェクトごとに自分だけの名前・基本給を持ちます。
- **メソッド (method) = たい焼きができる動作**: 型に刻まれた手順。すべてのたい焼きが同じ
  手順を持ちつつ、**自分の中身で** 動作します。

**継承は改良型を作ること** です。既存のたい焼きの型を溶かして捨てるのではなく、その型をもとに
「しっぽにチーズを追加」した型を作ること。基本の型が改善されれば、改良型も自動的に恩恵を受けます。

## 3. 核心となる考え方

### 3.1 クラス定義と __init__

```python
class Employee:
    def __init__(self, name, base_salary):   # コンストラクタ: たい焼きを焼く瞬間に実行
        self.name = name                      # 属性: このオブジェクトの中身
        self.base_salary = base_salary

    def monthly_pay(self):                    # メソッド: このオブジェクトが行う動作
        return self.base_salary

emp = Employee("田中", 3000000)               # オブジェクト生成 (型から1匹)
emp.monthly_pay()                             # メソッド呼び出し
```

- `__init__` はオブジェクトが作られる瞬間に自動実行される初期化手順 (コンストラクタ) です。
- `self` は「今この動作を実行中のたい焼き自身」です。メソッドの第1引数に必ず書き、
  呼び出すときは Python が自動で埋めてくれます。`emp.monthly_pay()` は実は
  `Employee.monthly_pay(emp)` の省略形です。
- 慣例: クラス名は大文字始まり (`Employee`)、オブジェクトや関数は小文字 (`emp`)。

### 3.2 継承 — 共通は親に、差分だけ子に

```python
class Manager(Employee):                      # Employee を受け継ぐ
    def __init__(self, name, base_salary, team_size):
        super().__init__(name, base_salary)   # 親の初期化を先に実行
        self.team_size = team_size            # マネージャーだけの属性を追加

    def monthly_pay(self):                    # オーバーライド: 同じ名前、違う中身
        return super().monthly_pay() + 500000 + self.team_size * 30000
```

- `class Manager(Employee)` — かっこの中が親クラスです。マネージャーは社員の
  すべての属性・メソッドを自動的に持ちます。
- `super()` は親を指します。「親の手順を先に実行してから自分のものを追加」が基本形です。
- 同じ名前のメソッドを定義し直すと子のものが優先されます — 再定義 (overriding)。

### 3.3 ポリモーフィズム — 同じ指示、各自のやり方

社員とマネージャーが混ざったリストを回しながら `person.monthly_pay()` を呼び出すと、
各オブジェクトが **自分のクラスのやり方で** 計算します。呼び出す側は、相手が社員なのか
マネージャーなのか尋ねる必要がありません。これがポリモーフィズム (polymorphism) です。
「全社員に『今月の給与を計算してください』と通知すれば、各自が自分の規定どおりに
計算して提出する」— if/elif で役職を一つずつ分岐するコードより、拡張がずっと簡単です。

### 3.4 __str__ — オブジェクトの自己紹介

`print(emp)` としたとき `<Employee object at 0x...>` の代わりに人が読める文章が出るように
するには、`__str__` メソッドを定義します。このアンダースコア2つの特殊メソッド (dunder method) は
「Python の文法と自分のクラスをつなぐ接点」で、`__init__` もその一つです。

### 3.5 いつクラスを使うか

すべてのコードをクラスにする必要はありません。基準はこうです。

- データと、そのデータを扱う関数が **いつも一緒に移動する** → クラスの候補
- 同じ構造の実体が **複数** 生まれる (社員100人、商品500個) → クラスの候補
- 「ほとんど同じだが少しだけ違う」変種がある → 継承の候補
- 一度計算して終わりの手順 → 関数で十分

## 6. よくある間違い

- **self の付け忘れ** — メソッド定義で `def monthly_pay():` と書くと、呼び出し時に
  `takes 0 positional arguments but 1 was given` エラーになります。メソッドの第1引数は常に self。
- **クラスとオブジェクトの混同** — `Employee.name` はありません。名前は各たい焼き (オブジェクト) に
  あるので `emp.name`。型を食べようとしないでください。
- **super().__init__ の省略** — 子の `__init__` で親の初期化を呼ばないと、親が
  作ってくれるはずだった属性がなく、後で `AttributeError` になります。
- **何でもかんでもクラスに** — 関数1つで済む仕事をクラスで包むと、かえって読みにくくなります。
  3.5 の基準で判断しましょう。
- **属性をクラス本体に共有で置く** — `class Employee:` のすぐ下に
  `members = []` のように可変の値を置くと、すべてのオブジェクトが1つのリストを共有する罠が生まれます。
  オブジェクトごとのデータは必ず `__init__` の中で `self.` として作りましょう。
