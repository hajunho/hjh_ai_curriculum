# Lecture 02 · Level 07 — 例外処理とデバッグ

> try/except は「問題が起きたらこう対処せよ」という緊急対応マニュアルであり、エラーメッセージはコンピュータが送ってきた正確な事故報告書です。
**難易度** ⭐⭐⭐ / **前提** level06 / **目安時間** 50分

## 1. なぜ学ぶのか — ビジネスの視点

夜通し回るはずの精算バッチが、深夜2時に止まりました。原因は1万件のうちたった1件 —
金額の欄に誰かが「協議中」と書いておいた行でした。例外処理のないプログラムは
この1件でそのまま息絶え、残りの9,999件も処理されません。

実務のデータは必ず壊れています。空欄、タイプミス、形式の違う日付、マイナスの数量。
例外処理 (exception handling) は「不良の1件は記録して飛ばすが、業務全体は
続行する」という防御体系です。そしてデバッグ (debugging) は、エラーが出たときに勘ではなく
証拠 — エラーメッセージと中間値の出力 — で原因を突き止める技術です。この2つが、
「自分のパソコンで一度動いたコード」と「実務に投入できるコード」を分けます。

## 2. たとえ話で理解する

**防災訓練のたとえ。** 建物に消火器と避難マニュアルがあるからといって、火事が起きなくなるわけではありません。
火が出ても **全体が崩れないように** するのです。try/except がまさにその役割です。

> try: 普段の業務を進める (火が出るかもしれない区域)
> except: 火が出たらこのマニュアルどおりに対処する (消火器の位置)
> finally: 火が出ても出なくても、退勤前の戸締まりはする (常に実行)

**事故報告書のたとえ。** Python のエラーメッセージ (traceback) は、脅すために出てくる赤い文字では
なく、5W1H で書かれた事故報告書です。**どのファイルの、何行目の、どのコードで、
どんな種類の事故が、なぜ** 起きたのか、すべて書かれています。読むコツは一つ、
**下から上へ**: 最後の行が事故の種類と原因 (`ValueError: ...`)、そのすぐ上が事故現場です。
報告書を読まずに「コードをあれこれ変えてみる」のは、事故現場を見ずに
適当な壁を塗り直すようなものです。

## 3. 核心となる考え方

### 3.1 よく出会う例外5種

| 例外 | 意味 | よくある原因 |
|---|---|---|
| `ValueError` | 値が形式に合わない | `int("協議中")` |
| `TypeError` | データ型の合わない演算 | `"100" + 5` |
| `KeyError` | 辞書に存在しないキー | `row["金額"]` (列名のタイプミス) |
| `IndexError` | 範囲外のインデックス | 空リストの `items[0]` |
| `ZeroDivisionError` | 0での割り算 | 件数が0なのに平均を計算 |

`FileNotFoundError` (存在しないファイルを開く) まで含めた6つで、初期の実務エラーの大部分をカバーします。
名前そのものが原因の説明なので、名前を正確に読むだけで半分は解決したも同然です。

### 3.2 try / except / else / finally

```python
try:
    amount = int(raw_value)          # 事故が起こりうる区域
except ValueError:
    log_error(raw_value)             # ValueError 発生時の対処
    amount = 0
else:
    process(amount)                  # 事故が「なかったときだけ」実行 (任意)
finally:
    close_connection()               # 事故の有無に関係なく常に実行 (任意)
```

- **例外の種類を明示** してください。`except:` や `except Exception:` で全部飲み込むと、
  本物のバグ (タイプミスによる NameError など) まで隠れてしまいます。
- 複数の種類は `except (ValueError, KeyError):` のようにまとめるか、except 節を複数書きます。
- `except ValueError as e:` として受ければ、`e` に原因の文言が入っているのでログに残せます。
- finally はファイルや接続の後片付けのように「何があってもやるべき後始末」に使います
  (`with` が内部でやってくれているのが、まさにこれです)。

### 3.3 防御範囲は狭く、対処は具体的に

try ブロックにコード100行を全部入れると、どこで事故が起きたのか分からなくなります。
**事故の可能性がある最小の区間** (型変換、ファイルを開く、キーの照会) だけを包むのが原則です。
そして、except の中で何もせず `pass` するのは、火災報知器の電源を切る行為です。
少なくとも「何件が、なぜ失敗したか」の記録 (ログ) を残してこそ、後で「合計がなぜ足りない?」に
答えられます。

### 3.4 raise — 自分で警報を鳴らす

```python
if amount < 0:
    raise ValueError(f"金額は負の値にできません: {amount}")
```

不正な値を黙って通過させるより、早い段階で大きく知らせるほうが安全なとき、
`raise` で自ら例外を発生させます。「この関数はこういう入力を拒否する」という契約の宣言です。

### 3.5 print デバッグ — 最も原始的で、最も確実

エラーは出ないのに結果がおかしいときは、疑わしい区間に print を差し込んで中間値を確認します。

```python
print(f"DEBUG: row={row!r}, amount={amount!r}")
```

コツ: 変数名と一緒に出す、`!r` で引用符や空白まで見えるように出す (`"100 "` のような
隠れた空白が見えます)、原因が分かったらデバッグ用の print は消す。より高度な道具
(デバッガ、logging) は後で学びますが、print デバッグは一生使い続けます。

## 4. 実習 — main.py

実行方法:

```bash

```

わざと汚した月間売上データ10件 — 金額に「協議中」、空の値、隠れた空白、
存在しないキー、0除算の誘発 — を処理します。

- **[1] 例外の観察**: 代表的な例外5種を1つずつわざと起こし、それぞれを except で受けて
  「最後の行の読み方」を見せます。
- **[2] 保護なしの処理**: 例外処理なしで汚れたデータを集計すると、3番目の行で
  即死することを再現します (全体が落ちないように、外側で一度包んであります)。
- **[3] 保護された処理**: try/except で不良行は理由とともに記録して飛ばしながら、
  最後まで集計します。「成功7件、失敗3件 (理由リスト)」の形の運用レポートが出ます。
- **[4] print デバッグ**: エラーなしで合計だけがおかしくなるケース (隠れた空白 " 1000") を
  `!r` のデバッグ出力で捕まえます。
- **[5] raise**: マイナスの金額を拒否する検証関数で、「早く、大きく知らせる」を実演します。

[2] と [3] の対比 — 同じデータで、死ぬコードと生き残るコード — がこのレベルの核心です。

## 6. よくある間違い

- **`except:` で全部飲み込む** — 本物のバグまで隠れます。予想している種類だけを明示しましょう。
- **except の中で黙って pass** — 失敗が存在したという事実そのものが消えます。
  少なくとも件数と理由は記録しましょう。
- **try で丸ごと包む** — 事故現場が分からなくなります。最小の区間だけを。
- **traceback を読まずに修正を始める** — 最後の行を読むだけで原因の半分は分かります。
  エラー文言で検索する習慣も有効です (同じ事故報告書を読んだ人が必ずいます)。
- **デバッグ用 print の放置** — 原因が分かった後に消さないと、運用ログが汚染されます。
  `DEBUG:` の接頭辞を付けておけば、後で見つけて消しやすくなります。
