# Lecture 02 · Level 08 — モジュールとパッケージ

> モジュールは関数や変数を収めた1つの Python ファイルであり、import は他部署の専門家を自分の業務に呼び寄せる内線電話です。Python には標準ライブラリという社内の専門部署が最初から揃っています。
**難易度** ⭐⭐⭐ / **前提** level07 / **目安時間** 50分

## 1. なぜ学ぶのか — ビジネスの視点

コードが300行を超えると、1つのファイルの中で道に迷い始めます。会社が大きくなると
一人で総務・経理・営業を全部こなせなくなり部署を分けるように、プログラムも機能ごとに
ファイルを分けるべきです。その単位がモジュール (module) で、モジュールをフォルダにまとめたものが
パッケージ (package) です。

もう一つの実益は、「すでに出来上がっている専門部署」をそのまま使えることです。日付計算、
数学関数、乱数、集計ツール — こうしたものを自作する必要はありません。Python のインストールに
最初から含まれる標準ライブラリ (standard library) が数百のモジュールを提供しており、
`import` の1行で使えます。「車輪の再発明をするな」という開発の格言は、実務では
「検証済みのライブラリを差し置いて、自作コードでバグを生むな」と翻訳されます。

## 2. たとえ話で理解する

**部署への内線のたとえ。** あなたが企画書を書いていて、法務レビューが必要になったとします。
法律を独学したりせず、法務部を呼びますよね。

> `import legal` → 「法務部につないでください」
> `legal.review(contract)` → 「法務部の review 担当に、この契約書を渡してください」

`モジュール.関数()` という表記は「部署.担当者()」です。所属を明示するので、どの部署の
誰なのか迷いません。よく呼ぶ担当者には直通番号をもらうこともできます:
`from legal import review` → 以後は `review(contract)` と直接呼べます。便利ですが、
複数の部署から同じ名前の担当者を連れてくると (例: 営業部の review と法務部の review)、
誰が誰だか混ざる危険が生まれます。

自分たちで作るモジュールは「うちのチームの業務マニュアルバインダー」です。よく使う手順
(関数) をバインダー (utils.py) に整理しておけば、どの文書 (main.py) からでも取り出して使えます。

## 3. 核心となる考え方

### 3.1 import の3つの形

```python
import math                      # 部署ごと呼ぶ: math.sqrt(2)
from math import sqrt            # 担当者に直通: sqrt(2)
from math import sqrt as rt      # あだ名を付ける: rt(2)
```

基本のおすすめは1つ目の形です。`math.sqrt` のように出どころが見えるので、コードレビューが楽になります。
`from モジュール import *` (全員呼び出し) は名前衝突の温床なので、使わない習慣にしてください。

### 3.2 自分のモジュールを作る — ファイルがそのままモジュール

同じフォルダに `utils.py` を作って関数を定義すれば、`main.py` から
`import utils` で呼び込み、`utils.format_krw(1200000)` のように使えます。ルールは単純です。

- ファイル名がモジュール名です (`utils.py` → `import utils`、`.py` は外します)。
- Python は実行スクリプトのあるフォルダなど、決められたパスのリスト (`sys.path`) からモジュールを探します。
- **import した瞬間、そのファイルのコードが上から下へ1回実行されます。** だからモジュールには
  関数・変数の定義だけを置き、実行コードは `if __name__ == "__main__":` の下に置きます。
  この慣用句の正体がまさにこれです — 「直接実行されたときだけ動き、import されたときは
  定義だけを提供せよ」。これまでのすべての main.py に書いてきた理由が、ここで明らかになります。

### 3.3 パッケージ — モジュールをフォルダにまとめる

モジュールが増えたらフォルダにまとめます。フォルダに `__init__.py` ファイルを置けば Python が
そのフォルダをパッケージとして認識し、`from mypkg import utils` のようにパスで呼び込めます。
pip でインストールする numpy や pandas も、結局は誰かが作って配布したパッケージにすぎません
(インストールと仮想環境は lecture01 level04 で扱いました)。

### 3.4 標準ライブラリツアー — 今日の4部署

| モジュール | 担当業務 | 代表機能 |
|---|---|---|
| `datetime` | 日付・時刻 | 今日の日付、日付の差、締切カウントダウン、書式化 |
| `math` | 数学 | 平方根、切り上げ/切り捨て、対数、円周率 |
| `random` | 乱数 | 抽選、サンプリング、シャッフル (seed で再現性を確保) |
| `collections` | データ構造の拡張 | Counter (頻度集計)、defaultdict (デフォルト値付きの引き出し) |

特に `collections.Counter` は「カテゴリ別の件数数え」を1行で終わらせてくれるので、
実務での登場頻度が非常に高いです。ほかにも `csv` (level06)、`os`、`json`、`statistics` など、
「必要になったらまず標準ライブラリから検索」する習慣が重要です。

## 4. 実習 — main.py

実行方法:

```bash
cd lecture02_python_basics/level08_modules_packages
python3 main.py
```

このレベルのフォルダにはファイルが2つあります。**utils.py** — 通貨の書式化、付加価値税の計算、
営業日計算の関数を収めたチーム共用モジュール — と、それを呼び込んで使う **main.py** です。

- **[1] 自分のモジュールの import**: `import utils` で共用関数を呼び込み、売上サマリーを作ります。
  `utils.py` を import した瞬間にモジュール冒頭の print がちょうど1回だけ実行されること、
  utils を直接実行したときだけ動く自己デモ (`__name__` による区別) も観察します。
- **[2] datetime**: 今日の日付 (固定した基準日を使用)、プロジェクトの締切までのカウントダウン、
  日付の書式化を実演します。
- **[3] math**: 予算配分に切り上げ (`ceil`) がなぜ必要か — 17人を5人乗りの車に分乗させる問題 —
  で見せます。
- **[4] random**: seed を固定してから景品の抽選 (`sample`) と当番のシャッフル (`shuffle`) をします。
- **[5] collections**: `Counter` で注文カテゴリの頻度を1行で集計し、
  `defaultdict` で店舗別の売上を集めます。

まず `python3 utils.py` でモジュールを **直接実行** して自己デモを見て、次に
`python3 main.py` で **import される側** を実行し、2つの場合の違いを比べてみてください。

## 6. よくある間違い

- **標準モジュールと同じファイル名を付ける** — 自分のファイルを `random.py` と名付けると、Python が
  標準ライブラリの代わりに自分のファイルを import してしまい、迷宮入りのエラーになります。標準モジュール名は避けましょう。
- **import があちこちに散らばる** — import はファイルの一番上にまとめて置くのが慣例です。
  コードの途中に散らすと、依存関係の把握が難しくなります。
- **`from ... import *`** — どこから来た名前なのか分からなくなり、衝突も頻発します。
- **モジュールに実行コードを放置** — `if __name__ == "__main__":` なしで実行コードを置くと、
  import しただけでそのコードが走ってしまいます。定義と実行を分離しましょう。
- **random の seed 未固定** — テストやレポートで再現が必要な作業で seed を固定しないと、
  「昨日は動いたのに今日は違う」結果になります。実験の再現性は AI 実習全体の基本です。
