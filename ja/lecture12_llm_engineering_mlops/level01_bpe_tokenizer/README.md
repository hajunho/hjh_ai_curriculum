# Lecture 12 · Level 01 — トークナイザーを作る — BPE を自作する

> 「よく一緒に現れる文字ペアをくっつけ続ける」というたった一つの単純なルールで、LLM の語彙辞書 (BPE) をゼロから作ってみます。

**難易度** ⭐⭐⭐ / **前提** level00 / **想定時間** 50分

## 1. なぜ学ぶのか — ビジネスの視点

LLM の料金表はすべて「トークンあたりいくら」で書かれています。同じ文書でも、トークナイザー (tokenizer) がどう切るかによってトークン数が 2〜3 倍変わり、それがそのまま API コストと応答速度の差になります。とくに日本語は、英語中心のトークナイザーではずっと細かく刻まれる傾向があるため、同じ内容を尋ねても英語より高く課金されることがよくあります。「なぜ当社サービスの LLM コストが想定より高いのですか?」という質問に答えるには、トークンがどう作られるのかを知らなければなりません。

もう一つ、トークナイザーはモデル能力の隠れた決定要因です。後ほど実験しますが、数字をどう切るかによってモデルの計算能力が変わります。「モデルが足し算をできない」という問題の根っこが、学習ではなくデータを切る包丁にあるかもしれない — これがエンジニアリングの感覚です。今日作る BPE (Byte Pair Encoding、バイトペア符号化) は、GPT 系をはじめとする大半の LLM が使っている方式の原型です。

## 2. たとえ話で理解する

社内チャットの単語登録 (ユーザー辞書) を思い出してください。最初は一文字ずつ全部打ちます。ところが「報告書」という 3 文字を 1 日に何十回も打っていることに気づくと、「ほ → 報告書」の短縮を登録しますよね。次によく使う言葉も登録して…… こうして **よく出てくる組み合わせから順に短縮を作っていく** のが BPE のすべてです。

- 出発点: すべての文字がそれぞれ 1 トークン (短縮登録 0 個)
- 第 1 段階: コーパスで最も頻繁に隣り合う 2 トークンを探して 1 つに統合 (最初の短縮を登録)
- 繰り返し: 統合された塊もまた候補になるので、「報+告」→「報告」、「報告+書」→「報告書」のように、だんだん長い語ができていく

短縮をたくさん登録するほど (vocab が大きいほど) タイプ数 (トークン数) は減りますが、辞書が膨大になって管理コストが上がります。このトレードオフは、実際の LLM で vocab サイズを 3 万〜25 万の間で悩む理由とまったく同じです。

## 3. 核心となる概念

### 3-1. BPE の学習アルゴリズム

1. コーパスの単語を文字単位に刻み、単語の末尾に `</w>` の印を付けます。(同じ「学生」でも、語中と語末を区別するためです。)
2. 隣り合うトークンペアの出現頻度を全部数えます。
3. 最も頻繁なペアを 1 つの新しいトークンに統合し、このルールを記録します。
4. 望む統合回数だけ 2〜3 を繰り返します。

学習が終わって残るのは **統合ルールの順序付きリスト** です。新しい文をトークン化するときは、文字に刻んだあとでこのルールを学んだ順に適用し直すだけです。ルールの順序が優先順位なので、同じ vocab でも順序が違えば結果は変わります。

### 3-2. 日本語には「単語の区切り」がない — だからバイト単位 BPE

英語は空白で単語が切れるので、BPE は「単語の中」だけで統合を回せます。ところが日本語は「昨日学生が報告書を作った」のように **空白がまったくありません**。そのため、日本語を扱う本物のトークナイザーは空白に頼らず、テキストをいったん UTF-8 のバイト列に落としてから BPE を回します (バイト単位 BPE / byte-level BPE)。これなら未知の漢字や絵文字が来ても「未知語」にならず、必ず何らかのバイト列として表現できます。

今日の実習コーパス (`common/hjh_data.py` の `tiny_corpus`) は、学習の見通しを良くするために文節の境目にわざと空白を入れてあります。おかげで `word_freqs()` が空白で区切るだけで済み、「学生が」「報告書を」といった文節が統合されていく過程を目で追えます。ただし **実務では空白の助けは借りられない** ことを覚えておいてください。文節の切れ目すら統計で見つけ出すのが、日本語トークナイザーの本当の仕事です。韓国語も似た悩みを持ちますが、韓国語には分かち書き (単語間の空白) があるぶん、日本語よりは楽です。

### 3-3. vocab サイズのトレードオフ

| 統合回数 (=vocab サイズ) | 長所 | 短所 |
|---|---|---|
| 少ない (vocab が小さい) | 埋め込み表が小さい、全トークンが頻出するので学習が進みやすい | 文が長くなり推論コスト・遅延が増える |
| 多い (vocab が大きい) | 文が短くなる → 同じ文脈窓にもっと多くの内容が入る | 希少トークンは学習機会が不足、埋め込みパラメータが急増 |

日本語サービスが日本語コーパスでトークナイザーを作り直すとトークン数が大きく減るのも、この表で説明できます。よく出てくる日本語の組み合わせが vocab に入るからです。

### 3-4. 数字の分割 (digit split)

BPE をそのまま回すと、コーパスに頻出した数字の組み合わせが丸ごとトークンになります。価格データが多ければ「00」「500ウォン」のような塊ができるわけです。問題は **同じ数字でも切られ方がばらばらになる** ことです。987 は「9」+「87」、986 は「986」丸ごと、というふうに切られると、モデルからすれば 2 つの数はまったく別の形の記号なので、桁の概念を学ぶのが難しくなります。そこで最新の LLM は、数字を 1 桁 (または最大 3 桁) 単位で強制的に分割する前処理を入れています。包丁の入れ方ひとつが数学の成績を変えるのです。

## 4. 実習 — main.py

```bash
cd lecture12_llm_engineering_mlops/level01_bpe_tokenizer
python3 main.py
```

`[1]` tiny_corpus (実測 38,834 文字、固有の文字 52 種) を読み込み、`[2]` BPE を 60 回統合しようとして序盤の統合過程をそのまま出力します。実測では最初の 4 回が「が+`</w>`」「を+`</w>`」「た+。」「た。+`</w>`」で、いずれも 2000 回出現。つまり **助詞と文末が最初に塊になる** わけです。その後「し+た。」(1579 回)、「書+を」(819 回)、「生+が」(790 回) と続き、20 回目で「計画+書を」、40 回目でカタカナの「プ+ロ」が統合されます。統合できるペアは 53 回で尽きて早期終了します (要求は 60 回)。

`[3]` では統合 0/10/30/60 回のトークナイザー 4 つで同じ文を切り、トークン数が減っていく様子を見せます。実測:

| 統合回数 | vocab 目安 | トークン数 | 結果 |
|---|---|---|---|
| 0 | 53 | 13 | `昨 / 日 / 学 / 生 / が / 報 / 告 / 書 / を / 作 / っ / た / 。` |
| 10 | 63 | 10 | `昨 / 日 / 学 / 生が / 報 / 告 / 書を / 作 / っ / た。` |
| 30 | 83 | 5 | `昨 / 日 / 学生が / 報告書を / 作った。` |
| 60 | 106 | 4 | `昨日 / 学生が / 報告書を / 作った。` |

13 トークンが 4 トークンまで、つまり 3 分の 1 以下に縮みます。文節 = トークンという形に自然に落ち着くのが見どころです。

`[4]` がハイライトです。金額が多く出てくるコーパスで、数字分割なし/ありの 2 回学習します。実測では分割なしの側に数字混じりの統合が **33 個** でき、`['00', '00ウォン', '500ウォン', '700ウォン', '200ウォン', '100ウォン']` のような塊が生まれます。そのうえで「98700ウォン」を切ると:

- 分割なし: `['9', '8', '700ウォン']` — 前半は 1 桁ずつ、後半は 3 桁 + 通貨が丸ごと 1 トークン
- 分割あり: `['9', '8', '7', '0', '0', 'ウォン']` — 全桁が一貫して 1 桁ずつ

「12500ウォン」も同様に `['1', '2', '500ウォン']` 対 `['1', '2', '5', '0', '0', 'ウォン']` になります。

コードの心臓は 3 つの関数です。`count_pairs()` が隣接ペアの頻度を数え (digit_split フラグが数字の統合を遮断)、`merge_pair()` がすべての単語でそのペアをくっつけ、`train_bpe()` がこの 2 つを繰り返します。実際のライブラリ実装と原理は同じで、規模だけが小さいのです。

## 6. よくある間違い

- **トークン = 単語だと思い込む**: トークンは頻度が作った断片なので、単語とは一致しません。料金見積もりで「単語数 × 1」と計算すると、日本語では大きく外れます。
- **統合ルールの順序を無視する**: vocab のリストだけ保存して順序を失うと、同じ文が違うトークンになります。学習時と推論時には必ず同じルールファイルを使わなければなりません。
- **トークナイザーを変えてモデルはそのままにする**: トークナイザーを交換するとトークン id の意味がすべて変わるので、埋め込みから再学習が必要です。「トークナイザーだけ日本語用に差し替えよう」という提案が簡単でない理由です。
- **前処理 (数字分割など) を些細なことだと考える**: 今日見た通り、前処理の一行がモデルの能力を変えます。データパイプラインのドキュメントに前処理ルールを必ず残しましょう。

## 次のレベルの予告

包丁の使い方 (トークン化) を覚えたので、次は切った材料を倉庫に積む番です。level02 ではトークンを `<s>...</s>` でつないで固定長に切る **パッキング (packing)**、uint16 バイナリシャードへの保存、そして数百 GB のファイルも即座に開く memmap ロードまで — 大規模学習のデータパイプラインをミニチュアで構築します。
