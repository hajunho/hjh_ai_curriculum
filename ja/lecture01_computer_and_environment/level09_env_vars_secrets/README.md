# Lecture 01 · Level 09 — 環境変数とシークレットキーの安全な扱い方

> API キーやパスワードをコードに書くとなぜ事故になるのかを理解し、環境変数と .env パターンで秘密をコードの外で管理する習慣を作ります。

**難易度** ⭐⭐⭐ / **前提** level06 / **想定時間** 40分

## 1. なぜ学ぶのか — ビジネスの視点

実際に繰り返されている事故のパターンがあります。開発者がコードにクラウド接続キーを書いたまま、GitHub の公開リポジトリに push します。インターネットには公開リポジトリを24時間探し回る収集ボットがいて、**数分以内に**そのキーが泥棒の手に渡ります。泥棒はそのキーで高性能サーバーを大量に借りて仮想通貨をマイニングし、翌月、会社には数百万円規模の請求書が届きます。誇張ではなく、業界で実際に繰り返されてきたパターンです。

AI の時代にはリスクがさらに大きくなりました。LLM の API キーひとつで有料呼び出しが無制限にでき、社内データベースのパスワードが漏れれば顧客情報の流出につながります。だから「秘密をコードに入れない」は開発セキュリティの第1の掟であり、セキュリティ監査で真っ先に検査される項目です。幸い、解決策は難しくありません。**秘密は環境変数で注入し、コードは名前だけで参照する** — この一文を体に染み込ませることが、このレベルのすべてです。

## 2. たとえ話で理解する

**コードに書いたパスワードは、玄関のドアに貼っておいた金庫の暗証番号のメモ**です。

コードはあちこちにコピーされ、共有され、リポジトリに永久記録されます(level06 で学んだとおり、Git の履歴は消えません)。そんな文書に金庫の番号を書くのは、引っ越しのたびに一緒に運ばれる玄関のメモ紙に番号を書くのと同じです。

**環境変数(environment variable)は、会社のロッカーの鍵の制度**だと考えるといいでしょう。業務マニュアル(コード)には「金庫の鍵は各自のロッカーにある」とだけ書きます。実際の鍵(秘密の値)は、各社員のロッカー(各コンピュータの環境変数)に入っています。マニュアルが外部に流出しても鍵は安全で、社員(開発用/本番用サーバー)ごとに違う鍵を使えます。

環境変数とは、OS が各プログラムに手渡す「名前=値」のメモ紙の束です。すでに皆さんも使っています — level03 の PATH がまさに環境変数でした。ここに `OPENWEATHER_API_KEY=abc123` のような項目を追加しておけば、コードは `os.environ["OPENWEATHER_API_KEY"]` と**名前だけを呼んで**値を受け取ります。コードのどこにも実際の値はありません。

## 3. 核心となる概念

### 3-1. 環境変数の読み書き

```bash
# シェルで設定 (このターミナルウィンドウが生きている間だけ有効)
export MY_API_KEY="sk-demo-1234"
python3 app.py
```

```python
import os
key = os.environ.get("MY_API_KEY")        # 無ければ None (安全な読み方)
key = os.environ["MY_API_KEY"]            # 無ければエラー (必須値のとき)
```

ターミナルを閉じると消えるので、いつも使う値はシェルの設定ファイル(`~/.zshrc` など)に export を書いておくか、プロジェクトごとには次の .env パターンを使います。

### 3-2. .env ファイルパターン

プロジェクトフォルダに `.env` というファイルを作り、秘密を集めておきます。

```
# .env — このファイルは絶対に Git に上げない!
DB_PASSWORD=s3cret!
LLM_API_KEY=sk-demo-abcd1234
```

そして **`.gitignore` に `.env` を必ず追加**します。この2行セットが核心です。実行時にこのファイルを読んで環境変数に載せてくれる道具(python-dotenv パッケージ)が標準のように使われていますが、ファイル形式が単純なので、このレベルの実習では自分でパーサーを作って原理を確認します。同僚のためには、値を空にした見本 `.env.example`(`DB_PASSWORD=ここに入力`)をリポジトリに上げて、「どんな名前の秘密が必要か」だけを共有します。

### 3-3. 流出を防ぐ三重の防衛線

1. **予防**: 秘密は .env/環境変数だけに。コード・コミットメッセージ・チャットに値そのものを書かない。
2. **検知**: コミット前にハードコーディングされた秘密が無いかスキャン。実務ではコミットフックや CI が自動検査しますが、このレベルの実習ではミニスキャナーを自作して原理を見ます。`sk-` で始まる長い文字列、`password = "..."` のパターンなどが手がかりです。
3. **事後対応**: 流出したら**キーを即座に廃棄・再発行**するのが唯一の解決策です。コミットを消しても、履歴・フォーク・ボットの収集コピーにすでに残っていると想定すべきです。

### 3-4. 出力するときはマスキング

秘密の値はログや画面にも丸ごと出力しません。確認が必要なら `sk-d****1234` のように前後の数文字だけ残して隠す**マスキング(masking)**が慣例です。「値が設定されているか」と「値が何か」を分離して、前者だけを見せるのです。

## 4. 実習 — main.py

```bash
python3 main.py
```

3つの道具を順に実演します。すべての値は実習用の偽物で、インターネットには接続しません。

- **[1] 環境変数の読み取り**: 実習用の変数を設定して `os.environ` で読みます。存在しない変数を `.get()` で安全に読む方法、PATH のような既存の変数の確認も一緒に行います。
- **[2] マスキング出力**: `mask()` 関数で秘密の値を `sk-d****5678` の形に隠し、「設定済みかどうかだけ」を報告するコツを見ます。
- **[3] .env パーサー**: `名前=値` 形式の .env テキストを自分でパースして環境変数に載せるミニ実装で、dotenv という道具の原理を確認します。
- **[4] ハードコーディングスキャナー**: わざと秘密が埋め込まれた悪い例のコードと、環境変数を使う良い例のコードを用意しておき、正規表現のルール(API キーの形、password= のパターンなど)で悪いコードだけを捕まえるスキャナーを回します。
- **[5] 掟のまとめ**: 三重の防衛線をチェックリストとして出力します。

核心となるコードは `scan_for_secrets()` です。「秘密は特定の**形**(パターン)を持つ」という観察を正規表現数行に落とし込んだもので、実際のセキュリティツールの基本原理もこれと同じです。

## 6. よくあるつまずき

- **「非公開リポジトリだから大丈夫」**: リポジトリはいつか公開されたり、転職・外注でアクセスする人が増えたりします。非公開かどうかに関係なく、秘密はコードの外に置くのが原則です。
- **.env を作って .gitignore を忘れる**: いちばんよくある惨事のルートです。`.env` の作成と `.gitignore` への追加は必ずワンセットで。
- **流出後にコミットだけ削除**: 履歴・フォーク・ボットにすでにコピーされています。キーの再発行が唯一の解決策です。
- **エラーメッセージやログに秘密が混ざって出る**: デバッグ出力で `print(config)` のように設定全体を出力すると、秘密も一緒に出ます。マスキングを習慣にしましょう。
- **見本ファイル(.env.example)に本物の値を入れてコミット**: 見本にはプレースホルダーのテキストだけを入れるべきです。
