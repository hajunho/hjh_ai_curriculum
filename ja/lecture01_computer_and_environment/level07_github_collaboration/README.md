# Lecture 01 · Level 07 — GitHub: リモートリポジトリと共同作業

**難易度** ⭐⭐ / **前提** level06 / **想定時間** 45分

## 1. なぜ学ぶのか — ビジネスの視点

level06 で作った決裁書類棚(リポジトリ)は、自分のコンピュータの中にしかありません。ノートパソコンが壊れれば履歴ごと消え、チームのメンバーは私の書類棚を見られません。そこで必要になるのが**リモートリポジトリ(remote repository)** — 全員がアクセスできる中央の書類棚です。そして、その中央書類棚を貸してくれる世界最大のサービスが **GitHub(ギットハブ)** です。

GitHub は開発者の共同作業の場であり、履歴書であり、世界中のオープンソースが集まる広場です。非開発者にとっても意味は大きいです。会社の開発成果物がどこでどのように管理されているのか、「PR レビュー中なのでリリースが遅れます」という開発チームの言葉が何を意味するのか、外部のオープンソースツールを導入するときにそのプロジェクトが健全か(直近のコミット・issue への応答)を見られるようになるからです。このレベルを終えると push/pull/PR といった用語が聞き取れるようになり、リモート共同作業の全体像がつかめます。

## 2. たとえ話で理解する

**リモートリポジトリは本社の中央文書庫、自分のリポジトリは支社の書類棚**です。

- **clone(クローン)**: 新任の支社長が赴任するにあたり、**中央文書庫を丸ごと複写**して支社に備えることです。履歴ごとまるまる複製されるので、以後、支社は独立して仕事ができます。
- **push(プッシュ)**: 支社で決裁した書類(コミット)を**本社の文書庫へ送り上げて**、公式記録にすることです。
- **pull(プル)**: 他の支社が上げた最新の書類を**本社から受け取り**、自分の支社の書類棚を最新に揃えることです。
- **Pull Request(PR)**: 「私の変更案を本編に合流させてください」という**正式な稟議書**です。変更内容を同僚が検討(レビュー)し、承認されれば本編(main)に合流します(merge)。稟議書には議論のコメントが付き、修正依頼が行き交い、この全過程が記録として残ります。

流れを一行で要約すると: **clone で始める → ブランチで作業 → push で上げて → PR でレビューを受けて → main に合流 → 同僚たちは pull で最新化**、です。

もうひとつ面白い事実。本社の文書庫(リモートリポジトリ)には、人が座って働くデスクがありません。作業フォルダを持たず履歴だけ保管するリポジトリを **bare(ベア)リポジトリ**と呼び、GitHub のサーバーは実際にこの形です。今日の実習では自分のコンピュータの中に bare リポジトリを作り、「偽物の GitHub」として使います — インターネットが無くても、push/pull の原理は完全に同じです。

## 3. 核心となる概念

### 3-1. リモート共同作業のコマンド5つ

```bash
git clone <アドレス>      # リモートリポジトリを丸ごと複製して開始
git remote -v             # 自分のリポジトリがつながるリモート(あだ名 origin)の確認
git push origin main      # 自分のコミットをリモートの main へ上げる
git pull origin main      # リモートの新しいコミットを受け取って合流させる
git fetch                 # 受け取るだけで合流はしない(プレビュー)
```

`origin` は、clone してきたリモートリポジトリに自動で付くあだ名です。「本社」と読み替えれば OK です。

### 3-2. GitHub が提供するもの

Git はツール(プログラム)で、GitHub はそのツール用の中央リポジトリを貸してくれる**サービス**です(似たサービスに GitLab、Bitbucket など)。GitHub はリポジトリのホスティングの上に共同作業機能を載せています: PR レビュー、issue(イシュー、タスク・バグの掲示板)、Wiki、そしてコミットや PR に反応して自動でテストを回す自動化(CI)などです。会社では通常**非公開(private)リポジトリ**を使い、オープンソースは**公開(public)**リポジトリで世界とコードを分かち合います。

### 3-3. コンフリクト(conflict) — 共同作業の通過儀礼

2つの支社が**同じファイルの同じ部分**をそれぞれ違うふうに直して上げると、Git はどちらが正しいか判断せず、人間に尋ねます。これがコンフリクト(衝突)です。ファイルの中に `<<<<<<<`、`=======`、`>>>>>>>` の印で両方の内容が並べて置かれ、人間が望む方(あるいは第3の折衷案)に直して再びコミットすれば解決します。見た目は怖いですが、「2つの修正案を並べてお見せしますので、決めてください」という丁寧な質問にすぎません。コンフリクトを減らすコツは、**こまめに pull して、小さくこまめに push** することです。

### 3-4. 共同作業のマナー

- main ブランチに直接 push せず、ブランチ + PR でレビューを経るのが標準です。
- PR は小さく分けます。500行の稟議書は誰もまともにレビューできません。
- pull が先、push は後: 上げる前に最新を受け取り、自分の側で合流を試す習慣がコンフリクトを減らします。

## 4. 実習 — main.py

```bash
python3 main.py
```

git がインストールされていれば、一時フォルダの中に**本社(bare リモート)1つと2つの支社(開発者 A・B)のリポジトリ**を作り、共同作業のシナリオを自動実行します。(git が無ければ概念シミュレーションで代替します。)

- **[1] 本社の設立**: `git init --bare` で作業デスクの無い中央文書庫を作ります。
- **[2] 支社の開設**: 開発者 A と B がそれぞれ `clone` で支社を構えます。
- **[3] A の push**: A がメニューファイルを作ってコミットし、本社へ push します。
- **[4] B の pull**: B が pull すると A のファイルが B の支社に現れます — リモート共同作業の核心の瞬間です。
- **[5] やり取り**: B が内容を追加して push し、A が pull で受け取って、両者が同じ最新状態になることを確認します。
- **[6] PR の流れの解説**: 実際の GitHub なら、この push が PR・レビュー・merge へつながる過程をフロー図として出力します。

肝心なのは、**リモートだからといって特別なものは何も無い**という点です。リモートのアドレスがインターネットの URL でも自分のコンピュータのフォルダパスでも、push/pull の動作は完全に同じです。コードの `run()` 関数が各支社フォルダで git コマンドを実行する様子から、「誰が(cwd)どのリモートと(origin)何をやり取りするのか」の構造を目で確認してください。

## 5. やってみよう

1. **(易しい)** 出力の [4] で、B が pull する前と後で B の支社フォルダのファイル一覧がどう変わったか探してみましょう。*(ヒント: pull の前は空でした。)*
2. **(普通)** シナリオに「A が再度 pull」の段階を追加する前と後を比べながら、pull せずに A が push だけを続けるとどんな問題が起きるか考えてみましょう。*(ヒント: B のコミットを知らないまま上げるとリモートが拒否します — だから pull が先なのです。)*
3. **(挑戦)** GitHub のアカウントを作り(無料)、Web 画面で新しいリポジトリを作って README ファイルを Web 上で直接編集・コミットしてみましょう。その後 `git clone` で自分のコンピュータに受け取ってみてください。*(ヒント: リポジトリページの緑色の Code ボタンに clone のアドレスがあります。)*

## 6. よくあるつまずき

- **pull せずに push**: リモートに他人が上げた新しいコミットがあると push は拒否されます。エラーではなく「まず受け取って合流させてください」という案内です。`git pull` してから再び push すれば OK です。
- **シークレットキーを push**: 一度 push されたシークレットキーは履歴に永遠に残ります。公開リポジトリなら数分以内に泥棒ボットが収集していきます。level09 で予防法を学びます。
- **clone とダウンロード(zip)の混同**: zip ダウンロードは履歴の無いファイルコピーにすぎません。共同作業するなら必ず clone でないと push/pull ができません。
- **リモートとローカルを同一視**: コミットだけして push を忘れると、同僚には何も見えません。「コミット=支社の決裁、push=本社への送付」は別々の段階です。
