# Lecture 01 · Level 10 — Docker: 環境を丸ごと再現する

> 「自分のパソコンでは動くんですけど」の最終解決策であるコンテナの概念を、規格貨物のたとえで理解し、Dockerfile の基本文法を読み書きできるようになります。

**難易度** ⭐⭐⭐⭐ / **前提** level04 / **想定時間** 45分

## 1. なぜ学ぶのか — ビジネスの視点

level04 の仮想環境は Python のパッケージまでは統一してくれますが、その下には手が届きません。OS が違い、システムにインストールされたプログラムが違い、設定が違えば、依然として「自分のパソコンでは動くんですけど」が発生します。開発者の Mac で完成した AI サービスが、Linux サーバーで動かない、という具合です。

**Docker(ドッカー)**はこの問題を終わらせます。プログラムだけでなく、**プログラムが動く環境全体(OS のライブラリ、Python、パッケージ、設定、コード)をひとつの箱に詰めて**、どんなコンピュータでも同じように実行します。今日、Web サービスや AI モデルのデプロイの事実上の標準なので、開発チームの会話(「イメージをビルドして上げますね」「コンテナを再起動しました」)やクラウドの料金体系(コンテナ単位の課金)を理解するには、概念を知っておく必要があります。非エンジニアの皆さんが Docker を自分で運用することは少なくても、**読めること**の価値は大きい — 求人票、外注の見積書、障害報告書、どこにでも Docker が登場するからです。

## 2. たとえ話で理解する

**コンテナは海運業の規格貨物コンテナ**です。このたとえは飾りではなく、実際の語源です。

コンテナ発明前の港を想像してください。米俵、家具、機械部品を、ばらばらの形のまま船に積んでいました。船ごとに積み方が違い、港ごとに降ろし方が違い、時間がかかり破損も頻繁でした。そこに**規格コンテナ**が登場します。中身が何であれ同じサイズの鋼鉄の箱に詰めさえすれば、世界のどの港のどのクレーンでも同じように扱えるようになりました。物流コストは劇的に下がりました。

ソフトウェアの Docker コンテナ(container)がまさにこれです。中身(どの言語、どのプログラムでも)に関係なく規格の箱に詰めれば、Docker がインストールされたどんなコンピュータ(港)でも同じように実行できます。

用語3つを物流に対応させると:

- **Dockerfile** = **梱包指示書**。「何をどの順序で箱に詰めるか」を書いた文書です。
- **イメージ(image)** = 指示書どおり**梱包済みの標準貨物**。複製・輸送が可能な原本です。
- **コンテナ** = その貨物を**開封して実際に稼働中の状態**。イメージひとつからコンテナを複数同時に立ち上げられます(同じ設計の店舗を複数出店するように)。

仮想環境(venv)との違いも、このたとえで鮮明になります。venv は「道具箱だけ統一」、Docker は「作業室の建物ごと丸ごと梱包」です。

## 3. 核心となる概念

### 3-1. Dockerfile の文法 — 6つの命令で読める

```dockerfile
FROM python:3.12-slim            # ベースの貨物: Python 入りのミニ Linux から始める
WORKDIR /app                     # 箱の中の作業位置を指定
COPY requirements.txt .          # 自分のファイルを箱の中へコピー
RUN pip install -r requirements.txt   # 梱包中に実行するコマンド(道具の設置)
COPY . .                         # 残りのコードを全部コピー
CMD ["python", "main.py"]        # 開封(実行)時に自動で回すコマンド
```

| 命令 | 意味 | たとえ |
|---|---|---|
| FROM | どの既製イメージから始めるか | 半組み立て状態のベース貨物の選択 |
| WORKDIR | コンテナの中の作業フォルダ | 箱の中の作業台の位置 |
| COPY | 自分のコンピュータ → 箱の中へファイルコピー | 荷物の積み込み |
| RUN | 梱包(ビルド)中に実行するコマンド | 梱包段階の組み立て作業 |
| ENV | 環境変数の設定 (level09!) | 箱の中のロッカーのメモ |
| CMD | コンテナ起動時に実行するコマンド | 開封と同時に入れるスイッチ |

`requirements.txt` を先に COPY してコードを後で COPY する順序には理由があります。Docker は各行の結果を**層(layer)としてキャッシュ**し、変わっていない層は再梱包を飛ばします。頻繁に変わるコードを後ろに置けば、パッケージのインストールを毎回やり直さずに済み、ビルドが速くなります。

### 3-2. コマンドは2つだけ覚える

```bash
docker build -t myapp .     # 梱包指示書(Dockerfile)どおりイメージを作る
docker run myapp            # イメージをコンテナとして稼働させる
```

作ったイメージは**レジストリ(registry)**という貨物ターミナル(Docker Hub など)に上げて共有します。サーバーはそのイメージをダウンロードして `run` するだけで終わり — サーバーに Python をインストールする必要すらありません。

### 3-3. 仮想マシンとの違い (面接の定番知識)

仮想マシン(VM)は、建物の中に**もうひとつの建物**を丸ごと建てる方式なので重いです(OS 全体を含み、ギガバイト級、起動に数十秒)。コンテナは建物(ホスト OS)の骨組みは共有して**部屋だけを規格化**する方式なので軽い(メガバイト級、1秒未満で起動)。軽いから1台のサーバーにコンテナを数十個立ち上げられ、これがクラウドの経済性の土台です。

### 3-4. AI の実務と Docker

AI モデルのデプロイの標準的な流れが「モデル+コード+依存関係をイメージに梱包 → クラウドでコンテナとして稼働」です。GPU を使う学習環境も CUDA ドライバの組み合わせが厄介なので、あらかじめ組み合わされた公式イメージから始めるのが慣例です。「環境が再現できず実験結果が変わる」という AI 研究の持病への処方箋でもあります。

## 4. 実習 — main.py

```bash
python3 main.py
```

Docker が無くても動く実習です。2つの部分で構成されます。

- **[1] Docker インストール診断**: `shutil.which` で docker コマンドの存在を確認し、インストールされていれば `docker --version` を実行してみて、無ければインストール案内(Docker Desktop)を出力します。どちらでも次の段階へ進めます。
- **[2] Dockerfile 生成器**: プロジェクトの仕様(Python のバージョン、必要なパッケージ、実行ファイル)を辞書で受け取り、**Dockerfile のテキストを自動生成**して、1行ずつ解説を付けて出力します。データ分析用と Web API 用の2つの仕様で生成して違いを比較します。
- **[3] ファイルへ保存**: 生成した Dockerfile を `outputs/` フォルダに保存し、後で Docker をインストールしたときに `docker build` で実際に梱包を試せるようにします。
- **[4] ビルドの流れの解説**: 実際にビルドが起きたら層(layer)がどう積み上がるかをフロー図で見せます。

核心となるコードは `generate_dockerfile()` 関数です。Dockerfile とは結局ルールのあるテキストにすぎず、Python の文字列組み立てで作れるということ — 「梱包指示書を読み書きできること」がこのレベルの目標であることを、コードで示しています。

## 5. やってみよう

1. **(易しい)** [2] のプロジェクト仕様で Python のバージョンを 3.11 に変えて、生成される Dockerfile の FROM の行がどう変わるか確認してみましょう。*(ヒント: `SPECS` 辞書の `python_version`。)*
2. **(普通)** 仕様に `env` 項目(例: `{"APP_MODE": "production"}`)を追加して、生成器が ENV の行を作り出すように `generate_dockerfile()` を修正してみましょう。*(ヒント: COPY と CMD の間に ENV の行を差し込めば OK です。シークレットキーは ENV で焼き込まない、というのも忘れずに!)*
3. **(挑戦)** Docker Desktop をインストールして、outputs/ の Dockerfile と簡単な `main.py` ひとつで `docker build -t hello .` → `docker run hello` を実際にやってみましょう。*(ヒント: 会社のコンピュータならインストールポリシーを先に確認してください。)*

## 6. よくあるつまずき

- **イメージとコンテナの混同**: イメージは梱包された原本(静的)、コンテナは稼働中の実体(動的)です。「イメージを再起動する」という言い方は成立しません。
- **コンテナの中にデータを保管**: コンテナはいつでも廃棄・再生成される消耗品です。残すべきデータは外の保管場所(ボリューム、データベース)に置く必要があります。
- **シークレットキーをイメージに焼き込む**: COPY や ENV で .env やキーをイメージに入れると、イメージを受け取る全員に秘密が配達されます。秘密は実行時点で注入します(level09 の原則の延長)。
- **巨大なベースイメージの選択**: FROM にフルサイズのイメージを使うと数 GB の貨物になります。slim 系から始めるのが慣例です。
