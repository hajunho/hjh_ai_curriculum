# Lecture 01 · Level 04 — 仮想環境とパッケージ管理

> プロジェクトごとに独立した Python の作業室(venv)を作り、pip で必要な道具(パッケージ)を調達する方法を学びます。

**難易度** ⭐⭐ / **前提** level03 / **想定時間** 40分

## 1. なぜ学ぶのか — ビジネスの視点

ソフトウェア業界には昔からのお決まりのセリフがあります。「自分のパソコンでは動くんですけど?」— 開発者 A のコードが開発者 B のコンピュータで動かない状況です。原因のほとんどは、2人がインストールした**パッケージ(package)の構成やバージョンが違うから**です。A はあるライブラリの 2.0 を、B は 1.5 を使っていた、というわけです。

この問題は個人にもやってきます。プロジェクト X には旧バージョンのライブラリが、新しいプロジェクト Y には新バージョンが必要なとき、コンピュータ全体にひとつしかインストールできないなら、どちらかは壊れます。解決策が**仮想環境(virtual environment)** — プロジェクトごとに独立した Python のインストール空間をひとつずつ作ることです。実務の Python プロジェクトは例外なく仮想環境から始まり、このカリキュラムのリポジトリにも `.venv` という仮想環境があります。このレベルを終えれば、「いま自分はどの環境で、どの道具を持って仕事しているのか」に常に答えられるようになります。

## 2. たとえ話で理解する

**パッケージは専門道具、仮想環境はプロジェクト専用の道具箱**です。

Python をインストールすると、基本の工具(標準ライブラリ)は付いてきます。ハンマーやドライバーレベルの必需品です。ところがデータ分析には電動ドリル(pandas)、グラフ描画には塗装設備(matplotlib)のような専門道具が必要です。こうした道具を世界共用の倉庫(PyPI、Python Package Index)から取り寄せてくれる調達担当者が **pip** です。

問題は、道具をすべて**会社共用の工具箱ひとつ**に入れるときに起こります。リフォームチームには旧型ドリルの規格が、新築チームには新型が必要なのに、工具箱には1種類しか置けないとしたら? 一方のチームが道具を交換した瞬間、もう一方の作業が止まります。

だから賢い会社は、**プロジェクトごとに専用の道具箱**を用意します。これが仮想環境です。プロジェクトフォルダの中に `.venv` という箱を作り、そのプロジェクト用の Python とパッケージだけを入れます。箱同士は完全に独立していて互いを壊せず、プロジェクトが終われば箱ごと捨てれば済みます。「activate(有効化)」は、作業を始める前に**そのプロジェクトの道具箱を腰に着ける行為**です。

## 3. 核心となる概念

### 3-1. 仮想環境のライフサイクル4段階

```bash
# 1) 作る — プロジェクトフォルダで一度だけ
python3 -m venv .venv

# 2) 有効化 — 作業を始めるたびに
source .venv/bin/activate        # Mac/Linux
# .venv\Scripts\activate         # Windows (PowerShell)

# 3) 道具の設置 — 有効化された状態で
pip install requests

# 4) 無効化 — 作業が終わったら
deactivate
```

有効化されるとプロンプトの先頭に `(.venv)` が付きます。この表示が「いまどの道具箱を着けているか」の視覚的な合図です。有効化された状態では、`python` と `pip` が両方ともその箱の中のものに切り替わります。

### 3-2. pip の必須コマンド

| コマンド | やること |
|---|---|
| `pip install 名前` | 共用倉庫(PyPI)からパッケージをインストール |
| `pip install 名前==2.1.0` | 特定バージョンを指定してインストール |
| `pip list` | この環境にインストールされたパッケージの一覧 |
| `pip uninstall 名前` | 削除 |
| `pip freeze > requirements.txt` | 現在の道具リストをファイルに記録 |
| `pip install -r requirements.txt` | そのリストどおり一度に再構成 |

`requirements.txt` は**道具箱の物品リスト**です。このファイルさえ渡せば、同僚は自分のコンピュータに同じ構成の箱をそのまま再現できます。「自分のパソコンでは動くんですけど」の第一のワクチンがこのファイルです(第二のワクチンは level10 の Docker です)。

### 3-3. 自分がどの環境にいるかを知る方法

Python のコードの中から確認する確実な方法があります。

- `sys.prefix` — いまの Python が道具を探すインストール空間の場所
- `sys.base_prefix` — 元の(システム)Python の場所
- この2つが**違えば仮想環境の中**、同じならシステムの Python をそのまま使っている最中です。

たとえるなら `sys.base_prefix` は本社の工具倉庫の住所、`sys.prefix` はいま腰に着けている箱の住所です。住所が違えば、専用の箱を着けているということです。

### 3-4. 守るべき慣例

- 仮想環境フォルダの名前は慣例として `.venv` にし、プロジェクトフォルダの直下に置きます。
- `.venv` フォルダは Git に上げません(容量が大きく、コンピュータごとに異なるため)。代わりに `requirements.txt` を上げます。
- システムの Python に `pip install` を乱発しないこと。最近の OS はそもそも禁止していることもあります(externally-managed エラー)。仮想環境の中でだけインストールする習慣をつけましょう。

## 4. 実習 — main.py

```bash
python3 main.py
```

このスクリプトは、**いま実行中の環境の診断書**を出力します。リポジトリの `.venv` の Python で実行すると(`../../.venv/bin/python main.py`、または有効化してから `python main.py`)「仮想環境の中」、システムの `python3` で実行すると「システム Python」と判定が変わるのを、実際に比べてみてください。

- **[1] どの道具箱か**: `sys.prefix` と `sys.base_prefix` を並べて出力し、2つの値を比較して仮想環境かどうかを判定します。
- **[2] 道具箱の中身**: `importlib.metadata` でインストール済みパッケージの一覧とバージョンを並べます。`pip list` が見せてくれるのと同じ情報をコードで得るということです。
- **[3] 標準ライブラリの確認**: インストールなしで使える基本の工具(json、csv、datetime など)がすでにあることを確認します。
- **[4] requirements.txt のプレビュー**: 現在の環境のパッケージ一覧を `名前==バージョン` の形式で出力し、`pip freeze` が作る物品リストの正体を見せます。

核心となるコードは `sys.prefix != sys.base_prefix` という比較の1行と、`importlib.metadata.distributions()` のループです。Python は自分の環境を自分のコードでのぞき込める — これが、環境の問題を怖がらなくていい理由です。

## 5. やってみよう

1. **(易しい)** 同じ main.py を (a) システムの `python3` で、(b) リポジトリの `.venv` の Python で、それぞれ実行して [1] の判定と [2] のパッケージ数がどう違うか比べてみましょう。*(ヒント: `.venv/bin/python main.py` のように、実行する Python を直接指定できます。)*
2. **(普通)** 適当な練習用フォルダで `python3 -m venv test_env` として新しい仮想環境を作って有効化し、`pip list` でほとんど空の箱であることを確認してから、`deactivate` してフォルダごと消してみましょう。*(ヒント: 箱は作るのも捨てるのも気軽にできてこそ正常です。)*
3. **(挑戦)** [2] の出力で、パッケージを名前順ではなく「名前の長さ順」に並べ替えてみましょう。*(ヒント: `sorted(..., key=...)` の key 関数を変えれば OK です。)*

## 6. よくあるつまずき

- **有効化を忘れてインストール**: `(.venv)` の表示なしに `pip install` すると、見当違いの場所(システム)にインストールされます。インストール前にプロンプトを確認しましょう。
- **仮想環境を作ったのに IDE は別の Python を使っている**: エディタ(VS Code など)にはインタプリタを別途指定する必要があります(次のレベルで扱います)。「インストールしたのに import できません」の常連の原因です。
- **`.venv` フォルダを丸ごとコピー・移動**: 仮想環境は作った場所に紐付いていて、動かすと壊れやすいです。移すときは `requirements.txt` から作り直すのが定石です。
- **requirements.txt の更新を忘れる**: パッケージを追加したら `pip freeze` でリストを作り直さないと、同僚の環境が付いてこられません。
