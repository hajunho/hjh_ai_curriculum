# Lecture 03 · Level 00 — データとは何か — 表の構造

> データ分析の出発点である「表」を解剖します。行は事例、列は属性という原理さえつかめば、Excel も Python も同じ言語に見えてきます。

**難易度** ⭐ / **前提** なし (lecture02 の Python 基礎を終えていれば十分です) / **目安時間** 40分

## 1. なぜ学ぶのか — ビジネスの視点

会社で行き交う情報の大部分は、結局は表に整理されます。売上レポート、顧客名簿、在庫状況、勤怠記録 — 形式は違っても、すべて「複数の事例を同じ項目で記録したもの」です。データ分析の道具が Excel でも、Python でも、SQL でも、BI ダッシュボードでも、すべてこの表構造の上で動きます。

だからこそ、表の構造を正確に理解することは、特定の道具を学ぶことより先に来ます。「この表の1行は何を意味するのか?」という質問に答えられれば、どの道具を使うにしても半分は始まったも同然です。逆にこの質問に答えられないまま関数から暗記すると、数字は出てくるのに、その数字が何を数えたのか分からない状態になります。実務での誤った報告の多くが、ここから生まれます。

このレベルでは、まだ Pandas (パンダス) も NumPy (ナンパイ) も使いません。Python の基本の材料である辞書 (dictionary) とリスト (list) だけで表を直接さわりながら、道具が隠してしまいがちな表の本質を手で確かめます。

## 2. たとえ話で理解する

表は **マンションの集合郵便受け** に似ています。郵便受けの一つひとつ (値) は「何号棟の何号室」という2つの座標で正確に指定できます。表も同じように「何行目の、どの列」という2つの座標さえあれば、どんな値でも取り出せます。

もう少し仕事に近いたとえは、**社員の人事記録カードのファイル** です。

- カード1枚 = **行 (row)**。社員1人という「事例」を丸ごと収めます。
- カードに印刷された記入欄 (氏名、部署、入社日...) = **列 (column)**。すべてのカードが同じ記入欄を持ちます。
- 記入欄の見出しの一覧 = **スキーマ (schema)**。「うちのカードにはどの項目がどんな形式で書かれるか」という約束です。

重要なのはカードファイルのルールです。あるカードには「入社日」欄があり、別のカードにはないとしたら、ファイル全体を入社日順に並べ替えることはできません。表の力は、**すべての行が同じ列構造を共有する** という約束から生まれます。この約束のあるデータを構造化データと呼び、約束のない自由な記録 (例: 顧客が残したレビューの文章) を非構造化データと呼びます。

## 3. 核心となる考え方

### 3-1. 行 = 事例、列 = 属性

- **行 (row, record)**: 観察した事例1つ。「2025年1月3日、渋谷店、コーヒーカテゴリの1日の売上」のように、世の中で起きた出来事1件です。
- **列 (column, attribute/変数)**: すべての事例に共通して記録する項目。日付、店舗、カテゴリ、売上額のようなものです。統計では変数 (variable) とも呼びます。

表を受け取ったら、真っ先に問うべき質問があります。**「この表の1行は、何の1件なのか?」** 同じ売上データでも、行が「取引1件」の表と「店舗・カテゴリ別の1日の合計」の表では、扱い方がまったく違います。この単位をグレイン (grain、穀粒) と呼ぶこともあります。

### 3-2. スキーマ — 列の名前と型の約束

スキーマは2つのことを決めます。

1. 列の **名前**: `date`、`store`、`revenue` のように、どんな項目があるか。
2. 列の **型 (type)**: 各項目が文字列なのか、整数なのか、日付なのか。

型が重要な理由は、演算が型によって変わるからです。`"100" + "200"` は文字列の連結なので `"100200"` になり、`100 + 200` は `300` になります。実務事故の定番の原因です。

### 3-3. 構造化 vs 非構造化

| 区分 | 構造化データ | 非構造化データ |
|---|---|---|
| 形 | 行と列が固定された表 | 自由テキスト、画像、音声 |
| 例 | 売上台帳、会員名簿 | 顧客レビュー、相談の録音、写真 |
| 集計 | `SUM`、平均がすぐ可能 | 先に構造を抽出しないと不可能 |

非構造化が劣っているわけではありません。情報量はむしろ多いのです。ただ、**集計するには先に表へ変換する作業** (例: レビュー → ポジティブ/ネガティブの列) が必要なだけです。後の講義 (自然言語処理) で、その変換を扱います。

### 3-4. Python で表を表現する最も素朴な方法

辞書のリスト (list of dicts) です。

```python
table = [
    {"store": "渋谷店", "revenue": 500000},
    {"store": "新宿店", "revenue": 420000},
]
```

- リストの要素1つ = 行1つ
- 辞書のキー (key) = 列の名前

Pandas の DataFrame も、結局はこの構造をはるかに速く便利にしたものです。原型を手でさわっておけば、level03 から学ぶ Pandas が「魔法」ではなく「便利機能」に見えてきます。

### 3-5. 欠損 — 欄が空いているという事実も情報である

現実のデータには、値が記録されなかった欄が必ずあります。Python では `None` で表現します。「0」と「空である」はまったく別物です。売上0ウォンは「売れなかった」という事実であり、`None` は「いくら売れたのか分からない」という状態です。この区別は level06 で本格的に扱いますが、表を初めて見るときから、いくつの欄が空いているかを数える習慣をつけるのが良いです。

## 4. 実習 — main.py

実行方法:

```bash
cd lecture03_data_handling/level00_what_is_data

```

このスクリプトは、架空のカフェチェーンの30日分の売上表 (750行) を作り、次を実行します。

- **[1] 表の大きさ**: 行数 (事例数) と列の名前 (スキーマ) を出力します。`rows[0].keys()` がそのまま列の一覧です。
- **[2] プレビュー**: `hjh_data.head` で表の先頭を見ます。表を受け取ったら、何はともあれまず目で見る習慣です。
- **[3] 行1つの解剖**: 先頭の行を取り出し、「この表の1行 = 特定の日付・店舗・カテゴリの1日の売上」であることを確認します。
- **[4] 列の抽出**: リスト内包表記で `revenue` 列だけを抜き出し、列が「同じ属性の値の集まり」であることを見ます。
- **[5] 条件で行を探す**: 渋谷店のコーヒーの行だけを選んで数えます。フィルタの原型です。
- **[6] ミニスキーマ要約**: 列ごとに登場した型と欠損 (`None`) の数を自分で数えて出力します。Pandas の `info()` がやってくれる仕事を手作りするわけです。
- **[7] 構造化 vs 非構造化**: 同じ情報を自由な文章 (非構造化) で書いた例と比較しながら、文章には `SUM` をかけられないことを確認します。

出力では特に、`revenue` 列に `None` が何件あるか、そしてマイナスの売上が何件混ざっているかに注目してください。わざと汚しておいた値であり、この先のレベルで何度も出会うことになります。

## 6. よくある間違い

- **行の意味を確認せずに合計から求める**: この表での `sum(revenue)` は「カテゴリ別の日次売上の総和」です。行を取引件数だと勘違いすると、「取引750件」という誤った報告になります。
- **`None` と 0 を混ぜる**: `None` の混ざったリストにそのまま `sum()` をかけると `TypeError` になります。エラーが出てくれてありがたいケースです。こっそり0に変えると、平均が歪みます。
- **列名のタイプミス**: `rows[0]["revenu"]` のようにキーを書き間違えると `KeyError` になります。列名は常に `keys()` で先に確認しましょう。
- **型を目で判断する**: 画面で `123` に見えても、実際は文字列の `"123"` かもしれません。`type()` で確認する習慣が必要です。
