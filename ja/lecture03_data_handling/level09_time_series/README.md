# Lecture 03 · Level 09 — 時系列データの扱い方

> 売上を「時間軸の上に載せて」トレンド・季節性・成長率を読み取る方法を学びます。

**難易度** ⭐⭐⭐⭐ / **前提** level07 (グループ化・集計) / **目安時間** 60分

## 1. なぜ学ぶのか — ビジネスの視点

経営陣が投げてくる質問の半分は時間に関するものです。「先週よりどれだけ増えた?」「今月はトレンドが折れたのか、それとももともとこういう季節なのか?」「週末効果を除いて見たら、本当に成長しているのか?」といった質問ですね。これらの質問はすべて、データを日付順に並べてはじめて答えられます。

このように時間の順序が意味を持つデータを時系列 (time series) と呼びます。売上、来店客数、在庫、株価、サーバーのトラフィック — 実務データのほとんどは、実は時系列です。ところが時系列は扱い方が少し特別です。行の順序をむやみに混ぜてはいけないし、「日別 → 週別」のように時間の単位を変える演算が必要で、「前週比」のように過去の自分自身と比べる計算が肝心だからです。Pandas はこうした作業のための専用の道具として `to_datetime`、`resample`、`rolling`、`shift` を用意しています。この4つを身につけるだけで、週報の肝心な数字はすべてコードで出せるようになります。

## 2. たとえ話で理解する

**時系列分析は体重記録の管理と同じです。** 毎朝体重を記録しているとしましょう。

- 一日一日の数字はばらつきます。前日に飲み会があれば今日は1kg増えて見えますよね。だから私たちは「直近7日の平均」を見ます。これがまさに移動平均 (rolling mean) です。1日限りのノイズを消して本当のトレンドだけを残す虫めがねです。
- 「毎日の記録は多すぎるから週単位でまとめて見よう」と言うなら、日記を週次サマリーに変えるのと同じです。これがリサンプリング (resample) です。
- 「先週の平均より今週は何%変わった?」と比べるのが `shift` (1つずらす) と `pct_change` (増減率) です。先週の自分と今週の自分を並べて比べるわけです。

もう一つ。体重手帳の日付が「2月31日」と書かれていたらどうでしょう? 人は笑って済ませますが、コンピュータは止まります。現実のデータには、こうした誤った日付文字列が本当に混ざり込んできます。時系列分析の最初のボタンは、いつも「日付が本物の日付かどうか」を確かめることです。

## 3. 核心となる考え方

### 3.1 文字列は日付ではない — to_datetime

CSV から読み込んだ `"2025-03-15"` はただの文字です。文字のまま並べ替えると辞書順に混ざり、引き算もできません。`pd.to_datetime()` で日付型 (datetime64) に変換してはじめて、「何日差か」「何曜日か」といった計算が可能になります。

このとき `errors` オプションが重要です。

| オプション | 動作 | いつ使うか |
|---|---|---|
| `errors="raise"` (既定) | 誤った日付に出会ったら即エラー | 汚染がないと確信できるとき |
| `errors="coerce"` | 誤った日付を NaT (Not a Time、日付の欠損値) に変える | 現実のデータのほとんど |

`coerce` で変換したあと `isna().sum()` で NaT の数を数えれば、「日付の汚染が何件あるか」の診断が終わります。level06 で欠損値を診断していた習慣を、日付にもそのまま当てはめるわけです。

### 3.2 DatetimeIndex と dt アクセサ

日付の列をインデックスに上げると (DatetimeIndex)、`resample` のような時系列専用の機能が開きます。インデックスに上げていない日付の列からは `dt` アクセサで部品を取り出します。`df["date"].dt.month` は月、`.dt.dayofweek` は曜日の番号を返します。

### 3.3 resample — 時間の単位を変える

`daily.resample("W").sum()` は日別データを週 (week) 単位の箱に振り分け、箱ごとに合計を求めます。`"W"` は週、`"ME"` は月末 (month end) 基準の月単位です。groupby の時間版だと考えれば正確です。実際、内部の動作も「時間の区間でグループを分ける → 各グループに集計関数を適用」で、level07 の分割-適用-結合と同じです。

### 3.4 rolling — 移動平均でノイズを消す

`daily.rolling(7).mean()` は「今日を含む直近7日の平均」を毎日計算します。窓 (window) を1日ずつずらしながら平均を取るので移動平均と呼びます。私たちのカフェのデータのように週末ごとに売上が跳ねる場合、7日の窓を使うと曜日効果がちょうど1周期ずつ含まれるので、揺れが消えて季節のトレンドだけが残ります。最初の6日は7個を埋められずに NaN になるのが正常です。

### 3.5 shift と pct_change — 過去の自分と比べる

`weekly.shift(1)` は Series を1つ下にずらして「先週の値」を今週の行の隣に持ってきます。そうすれば成長率は `(今週 - 先週) / 先週` で計算できますね。この計算を一行でやってくれるのが `weekly.pct_change()` です。最初の行は比べる過去がないので NaN になります。

### 3.6 時系列の2つの落とし穴

1つ目は、並べ替えられていない日付です。複数のファイルをつなぎ合わせたデータは日付がばらばらな場合が多いのですが、その状態で `shift` を使うと「先週」ではなく「ただ上の行」と比べることになります。`sort_index()` が先です。2つ目は、抜けている日付です。休業日が行そのものとして存在しないと、移動平均の窓が実際には7日より長い期間を覆ってしまいます。`resample("D")` で空の日付を埋めて確認する習慣が必要です。

## 4. 実習 — main.py

実行方法:

```bash
cd lecture03_data_handling/level09_time_series
python3 main.py
```

出力の流れは次のとおりです。

- **[1] 日付の汚染の診断** — `sales_table` の `date` 列を `to_datetime(errors="coerce")` で変換してみます。このデータの日付は「31日ずつ12か月」という誤った規則で振られているので、`2025-02-31` のようなカレンダーに存在しない日付が混ざっています。coerce がこうした値を NaT に変えた件数 (171件) を数えて汚染の規模を確認したあと、信頼できる `day_index` (開店後の経過日数) に `pd.to_timedelta` を足して正しい日付を作り直します。「原本のどの列を信じるか」を判断する過程そのものが実務です。
- **[2] 日別の時系列を作る** — 全店舗・全カテゴリの売上を日付ごとに合計して DatetimeIndex を持つ日別の Series にし、`dt` アクセサで月を取り出してみます。
- **[3] resample** — 週間の合計 (53週分) と月間の合計を求めます。最初の週と最後の週は7日を埋めきれていない「部分的な週」なので値が小さく出ることも確認します。
- **[4] rolling(7)** — 日別売上の上に7日移動平均を重ね、週末の揺れが消えて季節のトレンドが現れるのを見ます。標準偏差が 1.4 → 0.7 百万ウォンに縮むのが、その効果の数値的な証拠です。
- **[5] 前週比の成長率** — 週間売上に `pct_change` を適用して成長率の上位3週と下位3週を取り出します。`shift` で同じ計算を自分で再現し、2つの方法が一致することを検証します。
- **[6] グラフの保存** — 日別売上 (薄い線) と7日移動平均 (太い線) を `outputs/daily_trend.png` に保存します。移動平均がなぜ「トレンドを読む眼鏡」なのか、目で確かめてみてください。グラフの中の文字は、日本語フォントがない環境でも崩れないように英語にしてあります。

## 6. よくある間違い

- **文字列のまま並べ替え・比較する** — `"2025-9-2"` は文字列の並べ替えでは `"2025-10-1"` より後ろに行きます。時系列の作業の前に `to_datetime` の変換をするのが、無条件に第一歩です。
- **coerce の結果を確認しない** — `errors="coerce"` は便利ですが、静かにデータを NaT に消します。変換した直後に NaT の数を数えないと、データが消えたことにも気づけません。
- **resample の前にインデックスを作らない** — `resample` には DatetimeIndex (または `on=` の指定) が必要です。「Only valid with DatetimeIndex」というエラーが出たら、まずインデックスを確認しましょう。
- **pct_change の最初の NaN をバグと勘違いする** — 比べる過去がない区間の NaN は正常です。無理に0で埋めると「成長率0%」という嘘の情報になります。
- **部分的な週・部分的な月をそのまま報告する** — 期間の両端の箱は、日数を埋めきれていないことがあります。レポートに入れる前に切り落とすか、注記を付けましょう。
