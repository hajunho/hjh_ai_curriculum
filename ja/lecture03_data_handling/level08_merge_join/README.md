## 1. なぜ学ぶのか — ビジネスの視点

表1枚で終わる分析は、ほとんどありません。売上は POS システムに、店舗情報 (地域・開店年・担当者) は総務部の名簿に、今年の目標は企画部の資料にあります。「店舗別の目標達成率を地域別に見せてください」というありふれた依頼ひとつで、もう表が3つ必要です。

Excel ではこの仕事を VLOOKUP でやります。ところが VLOOKUP は列を1つずつしか引っ張ってこられず、キーが重複していると最初の1件だけを黙って取ってきて、見つからなかった値は #N/A となって散らばります。Pandas の `merge` は表全体を一度につなぎ、見つからなかったキーや重複キーを **検証する道具** まで用意しています。データベースの JOIN と同じ概念なので、ここで身につけた感覚は lecture04 の SQL にそのままつながります。

結合は強力なだけに、事故が最も多い工程でもあります。行が音もなく増えたり消えたりしているレポートは、結合のミスから生まれます。このレベルの半分は、その落とし穴を避ける方法です。

## 2. たとえ話で理解する

同窓会の名簿づくりを考えてみてください。手元には2枚の名簿があります。**A: 卒業アルバムの名簿** (名前、クラス)、**B: 連絡先の名簿** (名前、電話番号)。名前をキー (key) にして2枚を合わせる方法は4つあります。

- **inner (積集合)** — 両方にいる人だけ。「連絡が取れる確実な同窓生」だけが残ります。
- **left (左を基準)** — 卒業アルバムの全員を保ち、連絡先がない人は空欄。「全員名簿 + 分かっている連絡先」です。
- **right (右を基準)** — 連絡先名簿の全員が基準。left の左右を入れ替えたものです。
- **outer (和集合)** — どちらか一方にでもいれば全部。「卒業アルバムにはいないのに連絡先にはいる人」(転校生?) まで浮かび上がるので、**データの不一致を探す用途** に向いています。

そして落とし穴を一つ。連絡先名簿に「田中太郎」が **2行** あったら? 合わせた名簿に田中太郎が2行できます。アルバムにも2行、連絡先にも2行なら 2×2=4行になります。これが結合の最大の事故、**キー重複の爆発** です。

`concat` はまったく別の作業です。1組の名簿の下に2組の名簿を **縦につなぎ足すこと**、つまり横につなぐ (merge) のではなく下に積むことです。

## 3. 核心となる考え方

### 3.1 merge の基本形

```python
pd.merge(left_df, right_df, on="store", how="left")
```

- `on` : 両方の表で名前が同じキー列。名前が違う場合は `left_on="store"`、`right_on="店舗名"` のように別々に指定します。
- `how` : 結合の方式。`inner` (既定値)、`left`、`right`、`outer`。

### 3.2 how 4種の選び方ガイド

| how | 残る行 | 代表的な状況 |
|---|---|---|
| inner | 両方にあるキー | 確実なデータだけで計算するとき |
| left | 左の表のすべて | **基準となる表が決まっているとき (実務の既定値)** |
| right | 右の表のすべて | left と対称 (表の順序を入れ替えて left で書くのが普通) |
| outer | どちらかにあるキー | 2つの表の不一致を点検するとき |

実務の感覚: 「売上表に店舗情報を **貼り付ける**」のように基準が明確なら left、「2つの名簿が互いに合っているか **監査する**」なら outer です。

### 3.3 indicator=True — 結合を検証する習慣

`pd.merge(..., how="outer", indicator=True)` を使うと `_merge` 列ができて、各行が `both` / `left_only` / `right_only` のどこから来たのかが表示されます。`value_counts()` 一行で「相手のいないキーが何件あるか」を即座に監査できます。結合のあとにこの検証を習慣にすれば、事故の大部分を予防できます。

### 3.4 キー重複の落とし穴 — 行数の爆発

右の表に同じキーが k 回出てくると、左の該当行は k 倍に増えます (デカルト積、Cartesian product)。目標表に渋谷店がうっかり2行入っていたら、結合後に渋谷店の売上が **二重に集計** され、総額が水増しされます。予防策は2つです。

1. 結合の前に `right_df["store"].duplicated().sum()` で重複を確認し、必要なら `drop_duplicates()`。
2. 結合の前後で `len()` を比較 — 行数が想定と違ったら、すぐ手を止めて原因を調べる。

### 3.5 concat — 積むこと

```python
pd.concat([first_half, second_half], ignore_index=True)
```

同じ構造の表を縦につなぎます (月別ファイル12個をまとめる、など)。`ignore_index=True` がないと元のインデックスがそのまま残り、0,1,2,...,0,1,2,... のように重複します。なお DataFrame には `join` メソッドもありますが、インデックスをキーに使う merge の短縮形なので、概念は同じです。

## 6. よくある間違い

- **how を省略して既定値 (inner) だと気づかない** — 相手のいない行が音もなく消えます。結合の前後で必ず行数を比較しましょう。
- **キー列の表記の不一致** — 「渋谷店」vs「渋谷 店」(空白)、「SHIBUYA」vs「shibuya」(大文字小文字) は別のキーです。結合の前に `str.strip()` などで正規化しましょう。
- **重複キーの放置** — 行数の爆発と二重集計の原因1位です。`duplicated()` の確認、または `validate=` 引数を使いましょう。
- **merge すべきところを concat で (または逆)** — 列を横に付けるのが merge、行を下に積むのが concat です。concat で横に付けると、インデックスを基準に見当違いに並んでしまうことがあります。
- **suffixes の放置** — 両方の表にキー以外で同じ名前の列があると `_x`、`_y` が付きます。どちらがどの表かを `suffixes=("_実績", "_目標")` のように明示すれば事故が減ります。
