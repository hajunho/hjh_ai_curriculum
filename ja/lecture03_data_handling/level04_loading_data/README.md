## 1. なぜ学ぶのか — ビジネスの視点

分析業務の最初の関門は、いつも「ファイルを開くこと」です。情報システム部門が出してくれた CSV、取引先が送ってきた Excel、システムが吐き出した JSON — 形式もエンコーディングもバラバラなファイルを DataFrame へ無事に持ち込むことが、すべての分析の第0段階です。そしてこの段階で、驚くほど多くの時間が消えていきます。日本語が `æ±äº¬` のように化け、「1,234」という数字が文字として読まれ、欠損が「-」と書かれているせいで平均の計算が丸ごと狂います。

`read_csv` のオプションをいくつか知っていれば、この問題の90%はオプション1行で解決します。逆に知らなければ、ファイルを Excel で開いて手で直す手作業に戻ることになり、その瞬間に再現性 (reproducibility) が消えます。「ファイルには手を触れず、コードで解決する」が、このレベルの鉄則です。

## 2. たとえ話で理解する

CSV ファイルを読む仕事は、**海外からの小包を通関させる仕事** に似ています。小包 (ファイル) は発送国のルールどおりに梱包されています。言語 (エンコーディング) が違い、品目リストの区切り方 (区切り文字) が違い、「なし」を表記する慣習 (欠損の表記) が違います。通関申告書 (read_csv のオプション) に「この小包は cp932 という言語で書かれ、項目はセミコロンで区切られ、『-』は空欄という意味です」と正確に書いてあげれば、小包は問題なく通過します。申告書を適当に書くと? 税関 (Pandas) が中身を見当違いに解釈するか、そのまま返送 (エラー) します。

エンコーディングは特に **錠前と鍵** のたとえが正確です。cp932 で施錠したファイルは cp932 の鍵でしか開きません。utf-8 の鍵を差し込むと、錠前が壊れるのではなく「この鍵じゃありません」というエラー (UnicodeDecodeError) が出ます。鍵を差し替えれば済む話です。

## 3. 核心となる考え方

### 3.1 read_csv 必須オプションの地図

```python
pd.read_csv(
    "sales.csv",
    sep=",",              # 区切り文字。セミコロンのファイルなら ";"
    encoding="utf-8",     # 日本語が化けたら "cp932" を試す
    na_values=["-", ""],  # これらの表記を欠損 (NaN) として認識
    thousands=",",        # "1,234" を数値 1234 に
    parse_dates=["date"], # 日付の列を本物の日付型に
    usecols=["date", "revenue"],  # 必要な列だけ
    nrows=1000,           # 先頭1000行だけ (大容量のプレビュー)
    dtype={"zipcode": str},       # 郵便番号のように0で始まる値の保護
)
```

すべて暗記する必要はありません。「こういう問題はオプションで解ける」という地図さえ頭にあれば、必要なときに調べて使えば十分です。

### 3.2 日本語実務の最大の伏兵 — エンコーディング

エンコーディング (encoding) は、文字をコンピュータの数字に変えるルールです。国際標準は utf-8 ですが、日本の古いシステムや Excel の既定の CSV 保存は cp932 (Shift_JIS 系) を使います。症状と処方は2つだけです。

| 症状 | 処方 |
|---|---|
| `UnicodeDecodeError` が発生 | `encoding="cp932"` で読み直す |
| エラーはないのに日本語が宇宙語 | 逆のエンコーディングで読み直す |

自分が保存するときは常に `encoding="utf-8"` (Excel で開くファイルは `utf-8-sig`) で保存する習慣をつければ、未来の同僚を救えます。

### 3.3 数字が文字として読まれる事故

システムが「1,234,000」のようにカンマ入りの数字を出力すると、Pandas はこれを文字 (object) として読みます。その瞬間、`sum()` は文字列の連結になるかエラーを出します。`thousands=","` のオプションで1行解決です。同様に、欠損を「-」「なし」「N/A」などと書いてあるファイルは、`na_values` オプションで欠損表記のリストを教えてあげれば済みます。

### 3.4 JSON — システム間の宅配ボックス

JSON はウェブシステム同士がデータをやり取りする標準形式です。表データなら、たいてい **records 形式** (行1つ = 辞書1つのリスト) で届きます。

```json
[{"store": "渋谷店", "revenue": 512000},
 {"store": "新宿店", "revenue": 430000}]
```

この形式は `pd.read_json(path)`、または `json.load()` の後 `pd.DataFrame()` で、すぐに表になります。逆にネスト (nested) された JSON は `pd.json_normalize()` で平らに伸ばす必要があります。

### 3.5 Excel ファイルは概念だけ

`pd.read_excel("report.xlsx", sheet_name="1月")` で Excel も読めます (openpyxl パッケージが必要)。ただし Excel ファイルはシート・書式・結合セルのせいで事故が多く、実務では **できれば CSV でもらえ** が定石です。結合セルのあるレポート用 Excel は、`header=2` や `skiprows` のようなオプションで表の部分だけを切り出す必要があります。

### 3.6 保存 — to_csv / to_json

```python
df.to_csv("out.csv", index=False, encoding="utf-8-sig")
df.to_json("out.json", orient="records", force_ascii=False)
```

`index=False` を忘れると、名前のない番号列がファイルに紛れ込み、次の人が読むときに `Unnamed: 0` 列が生まれます。`force_ascii=False` は JSON 内の日本語を人が読める形のまま保ちます。

## 6. よくある間違い

- **化けた日本語を手で直す** — ファイルを Excel で開いて保存すると、その瞬間に原本が変形します。原本には絶対に触れず、読む側のオプションで解決しましょう。
- **`index=False` の付け忘れ** — to_csv のデフォルトは index をファイルに書くことなので、読み直すと `Unnamed: 0` 列が生まれます。
- **dtype 確認の省略** — 読んだ途端に計算から始めると、文字として読まれた数字のせいで結果が静かに狂います。読んだ直後の `df.dtypes` の確認は、通関後の検品と同じです。
- **郵便番号・社員番号を数値として読む** — 「01234」が 1234 になり、先頭の0が消えます。`dtype={"zipcode": str}` で保護しましょう。
- **Excel の CSV を utf-8 と思い込む** — 日本語版 Excel が保存した CSV はたいてい cp932 です。「CSV なんだから utf-8 だろう」と仮定しないでください。
