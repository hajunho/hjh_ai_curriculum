# Lecture 12 · Level 10 — 모델 서빙과 배포

> 학습이 끝난 모델 파일이 실제 서비스가 되기까지 — 추론 API 서버를 직접 띄우고 지연시간과 처리량을 측정합니다.

**난이도** ⭐⭐⭐⭐ / **선행** level09_quantization / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

지금까지 만든 모델은 디스크에 놓인 파일일 뿐입니다. 고객은 파일을 쓸 수 없습니다. 고객이 쓰는 것은 "질문을 보내면 답이 돌아오는 무언가", 즉 API입니다. 모델 파일과 API 사이를 잇는 작업이 서빙(serving)이고, 그것을 실제 서버에 올려 운영을 시작하는 일이 배포(deployment)입니다.

이 단계가 중요한 이유는 돈과 경험이 여기서 결정되기 때문입니다. 아무리 똑똑한 모델도 응답에 20초가 걸리면 고객은 떠납니다. 반대로 서빙을 잘하면 같은 GPU로 10배 많은 요청을 처리해 원가를 10분의 1로 만들 수 있습니다. vLLM 같은 서빙 전용 소프트웨어가 별도의 산업이 된 이유입니다. 회사에서 "챗봇 도입" 프로젝트가 시작되면 회의의 절반은 모델 품질이 아니라 "응답 속도는? 동시 사용자 몇 명까지? 서버 비용은?" 같은 서빙 질문입니다. 이 레벨을 마치면 그 회의에서 오가는 숫자들의 의미를 정확히 알게 됩니다.

## 2. 비유로 이해하기

훌륭한 요리사(모델)를 스카우트했다고 식당이 열리는 게 아닙니다. 주문을 받는 카운터(API 엔드포인트), 주문서 양식(요청 형식), 홀과 주방 사이의 동선(서버 구조), 그리고 "주문 후 몇 분 안에 나오는가"(지연시간)와 "한 시간에 몇 그릇 파는가"(처리량)를 설계해야 합니다.

지연시간과 처리량은 다른 개념입니다. 요리사가 한 그릇을 10분에 끓여내면 지연시간은 10분입니다. 그런데 화구가 8개라 8그릇을 동시에 끓이면, 각 손님의 대기 시간은 그대로 10분이어도 시간당 판매량(처리량)은 8배가 됩니다. LLM 서빙의 배칭(batching)이 정확히 이 원리입니다.

KV 캐시는 요리사의 "미리 손질해 둔 재료"입니다. 대화가 길어질 때 매번 대화 전체를 처음부터 다시 계산하는 대신, 앞부분 계산 결과를 냉장고에 보관해 두고 새 문장만 계산하는 것입니다. 손님이 추가 주문을 할 때마다 육수를 처음부터 다시 우리지 않는 것과 같습니다.

## 3. 핵심 개념

### 3.1 모델 파일에서 서비스까지의 여정

1. **모델 파일** — level09에서 양자화까지 마친 가중치 (예: GGUF 파일)
2. **추론 엔진** — 가중치를 메모리에 올리고 토큰을 생성하는 프로그램
3. **API 서버** — HTTP 요청을 받아 엔진에 전달하고 JSON으로 응답
4. **배포 인프라** — 서버 여러 대, 로드밸런서, 헬스체크, 모니터링

실습에서는 2~3번을 파이썬 표준 라이브러리만으로 미니어처로 만듭니다. 실무에서 자주 듣는 이름들은 이렇게 대응됩니다. Ollama는 1~3번을 개인 PC용으로 묶은 도구("모델 이름만 대면 받아서 띄워줌"), Hugging Face는 모델 파일을 올리고 내려받는 창고이자 호스팅 서비스, vLLM은 대규모 서비스용 고성능 추론 엔진입니다. 개념만 알아두고, 코드는 전부 직접 짭니다.

### 3.2 지연시간 — 평균이 아니라 p95를 본다

지연시간(latency)은 요청을 보내고 응답을 받기까지의 시간입니다. 100번 호출한 뒤 빠른 순서로 줄 세웠을 때 50번째 값이 p50(중앙값), 95번째 값이 p95입니다. 평균은 착시를 만듭니다. 99번이 0.1초여도 1번이 30초면 그 한 명은 화가 난 고객입니다. 서비스 수준 목표(SLO)는 보통 "p95 < 1초"처럼 백분위수로 정합니다.

LLM에는 지연시간이 둘로 나뉩니다. 첫 토큰까지의 시간(TTFT)과 토큰당 생성 시간입니다. 챗봇이 "생각 중..." 후 첫 글자를 빨리 내보내면 체감 속도가 크게 좋아지는 이유입니다.

### 3.3 처리량과 동시성

처리량(throughput)은 단위 시간당 처리하는 요청(또는 토큰) 수입니다. GPU 추론 중에 CPU는 대부분 결과를 기다리며 놀고 있으므로, 그 사이에 다른 요청을 받으면 처리량이 올라갑니다. 실습의 스레드 서버가 이것을 보여줍니다. 실전 엔진은 여기에 더해 여러 요청의 토큰 생성을 한 GPU 연산으로 묶는 연속 배칭(continuous batching)으로 처리량을 다시 수십 배 끌어올립니다.

### 3.4 KV 캐시

트랜스포머는 새 토큰 하나를 만들 때 이전 모든 토큰의 어텐션 키(K)·값(V)이 필요합니다. 이를 매번 재계산하면 n번째 토큰 생성 비용이 n에 비례해 폭증합니다. 한 번 계산한 K·V를 메모리에 쌓아 두면(KV 캐시) 매 토큰 생성이 "새 토큰 1개 계산 + 캐시 조회"로 줄어듭니다. 대신 GPU 메모리를 대화 길이에 비례해 잡아먹기 때문에, "동시 사용자 수 × 문맥 길이"가 서버 메모리 용량의 핵심 변수가 됩니다.

## 4. 실습 — main.py

실행 방법:

```bash
cd lecture12_llm_engineering_mlops/level10_serving_deployment
python3 main.py
```

인터넷 접속은 없습니다. 서버와 클라이언트 모두 내 컴퓨터 안(127.0.0.1)에서만 통신합니다.

출력 단계별 안내:

- **[1]** tiny_corpus로 문자 3-gram 마르코프 모델을 만듭니다. 진짜 트랜스포머 대신 즉시 응답하는 초소형 모델을 "추론 엔진" 자리에 놓는 것입니다.
- **[2]** `ThreadingHTTPServer`를 `port=0`으로 띄웁니다. 0을 주면 운영체제가 비어 있는 포트를 자동으로 골라 주어 포트 충돌이 없습니다. `/health` 엔드포인트로 생존 확인을 합니다. 실제 로드밸런서가 서버를 살았는지 두드려 보는 것과 같은 관행입니다.
- **[3]** `POST /generate`로 프롬프트를 보내 생성 결과와 왕복 지연을 확인합니다. 서버 핸들러에는 요청당 5ms의 `sleep`이 들어 있는데, 이는 실제 GPU 계산 시간(CPU가 기다리는 시간)을 흉내 낸 것입니다.
- **[4]** 순차로 40회 호출해 p50/p95/최대 지연과 순차 처리량을 계산합니다.
- **[5]** 클라이언트 스레드 8개로 같은 40회를 동시에 호출합니다. 처리량이 순차 대비 몇 배로 뛰는지 확인하세요. 개별 지연은 비슷한데 처리량만 오르는 것이 동시성의 핵심입니다.
- **[6]** `server.shutdown()`으로 우아한 종료를 합니다. 처리 중인 요청을 끝내고 내려가는 것이 배포 교체의 기본 예절입니다.

코드에서 눈여겨볼 부분은 `InferenceHandler`입니다. `do_POST`가 JSON을 읽고 → 모델을 호출하고 → JSON으로 응답하는 30줄이, OpenAI API 같은 상용 서비스 구조의 최소 골격 그대로입니다.

## 5. 직접 해보기

1. **(기본)** `n_chars`를 60에서 300으로 늘려 긴 생성을 요청해 보세요. 지연시간이 어떻게 변하나요? 힌트: 클라이언트 `call()`의 요청 본문을 수정하면 됩니다. 생성 길이와 지연의 비례 관계가 LLM 요금이 토큰당인 이유와 이어집니다.
2. **(중급)** [5]의 클라이언트 스레드 수를 1, 2, 4, 8, 16으로 바꿔 처리량 곡선을 만들어 보세요. 어느 지점부터 더 늘려도 처리량이 안 오르나요? 힌트: 서버 쪽 처리 능력이 포화되는 지점이 있습니다.
3. **(도전)** `/generate`에 잘못된 JSON을 보내면 지금은 서버가 예외를 일으킵니다. try/except로 400 응답을 돌려주도록 고쳐 보세요. 힌트: `json.loads`를 감싸고 `self._send(400, {"error": ...})`를 쓰면 됩니다. 입력 검증은 서빙 코드의 절반입니다.

## 6. 자주 하는 실수

- **평균 지연만 보고하기.** 데모에서는 평균이 예뻐 보여도 실사용자 불만은 꼬리(p95, p99)에서 나옵니다. 처음부터 백분위수로 측정하는 습관을 들이세요.
- **포트를 고정 숫자로 하드코딩하기.** 8000번을 박아 두면 다른 프로그램과 충돌해 "가끔만 실패하는" 골치 아픈 버그가 됩니다. 테스트·데모에서는 `port=0` 자동 할당이 안전합니다.
- **지연시간과 처리량을 같은 것으로 착각하기.** 처리량을 올리는 배칭이 개별 지연은 오히려 약간 늘릴 수 있습니다. 서비스 목표에 따라 균형점이 다릅니다.
- **종료를 강제 종료로 하기.** 처리 중인 요청을 끊고 프로세스를 죽이면 고객 화면에는 오류가 뜹니다. shutdown → 마무리 → 교체 순서를 지키세요.
- **모델 로딩을 요청마다 하기.** 가중치는 서버 시작 때 한 번만 메모리에 올려야 합니다. 요청 핸들러 안에서 로딩하면 지연시간이 수십 배가 됩니다.
