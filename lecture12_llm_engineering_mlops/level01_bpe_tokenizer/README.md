# Lecture 12 · Level 01 — 토크나이저 만들기 — BPE 직접 구현

> "자주 붙어 다니는 글자쌍을 계속 합친다"는 단순한 규칙 하나로 LLM의 어휘 사전(BPE)을 밑바닥부터 만들어 봅니다.

**난이도** ⭐⭐⭐ / **선행** level00 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

LLM 요금표는 전부 "토큰당 얼마"로 적혀 있습니다. 같은 문서라도 토크나이저(tokenizer)가 어떻게 자르느냐에 따라 토큰 수가 두세 배 차이 나고, 그것이 곧 API 비용과 응답 속도의 차이가 됩니다. 특히 한국어는 영어 중심 토크나이저에서 훨씬 잘게 쪼개지는 경향이 있어서, 같은 내용을 물어도 영어보다 비싸게 과금되는 일이 흔합니다. "왜 우리 서비스의 LLM 비용이 예상보다 높죠?"라는 질문에 답하려면 토큰이 어떻게 만들어지는지 알아야 합니다.

또 하나, 토크나이저는 모델 능력의 숨은 결정 요인입니다. 뒤에서 실험하겠지만, 숫자를 어떻게 쪼개는지에 따라 모델의 계산 능력이 달라집니다. "모델이 덧셈을 못 한다"는 문제의 뿌리가 학습이 아니라 데이터를 써는 칼에 있을 수 있다는 것, 이것이 엔지니어링 감각입니다. 오늘 만드는 BPE(Byte Pair Encoding, 바이트 쌍 부호화)는 GPT 계열을 비롯한 대부분의 LLM이 쓰는 방식의 원형입니다.

## 2. 비유로 이해하기

회사 메신저의 자동완성 단축어를 떠올려 보세요. 처음에는 한 글자씩 다 칩니다. 그런데 "보고서"라는 세 글자를 하루에 수십 번 친다는 걸 알게 되면, "ㅂㄱㅅ → 보고서" 단축어를 등록하죠. 그다음 자주 쓰는 말을 또 등록하고… 이렇게 **자주 나오는 조합부터 차례로 단축어를 만드는 것**이 BPE의 전부입니다.

- 출발점: 모든 글자가 각각 하나의 토큰 (단축어 0개)
- 1단계: 코퍼스에서 가장 자주 붙어 나오는 두 토큰을 찾아 하나로 병합 (첫 단축어 등록)
- 반복: 병합된 덩어리도 후보가 되므로, "보+고" → "보고", "보고+서" → "보고서"처럼 점점 긴 단어가 만들어짐

단축어를 많이 등록할수록(vocab이 클수록) 타자 수(토큰 수)는 줄지만, 단축어 목록이 방대해져 관리 비용이 커집니다. 이 트레이드오프가 실제 LLM에서 vocab 크기를 3만~25만 사이에서 고민하는 이유와 정확히 같습니다.

## 3. 핵심 개념

### 3-1. BPE 학습 알고리즘

1. 코퍼스의 단어를 글자 단위로 쪼개고 단어 끝에 `</w>` 표시를 붙입니다. (같은 "학생"이라도 단어 중간과 단어 끝을 구분하기 위해서입니다.)
2. 이웃한 토큰 쌍의 등장 빈도를 전부 셉니다.
3. 가장 잦은 쌍을 하나의 새 토큰으로 병합하고, 이 규칙을 기록합니다.
4. 원하는 병합 횟수만큼 2~3을 반복합니다.

학습이 끝나면 남는 것은 **병합 규칙의 순서 목록**입니다. 새 문장을 토큰화할 때는 글자로 쪼갠 뒤 이 규칙을 배운 순서대로 다시 적용하면 됩니다. 규칙 순서가 우선순위이기 때문에, 같은 vocab이라도 순서가 다르면 결과가 달라집니다.

### 3-2. vocab 크기 트레이드오프

| 병합 횟수(=vocab 크기) | 장점 | 단점 |
|---|---|---|
| 적음 (vocab 작음) | 임베딩 표가 작음, 모든 토큰이 자주 등장해 학습이 잘 됨 | 문장이 길어져 추론 비용·지연 증가 |
| 많음 (vocab 큼) | 문장이 짧아짐 → 같은 문맥 창에 더 많은 내용 | 희귀 토큰은 학습 기회 부족, 임베딩 파라미터 급증 |

한국어 서비스가 한국어 코퍼스로 토크나이저를 다시 만들면 토큰 수가 크게 줄어드는 것도 이 표로 설명됩니다. 자주 나오는 한국어 조합이 vocab에 들어가기 때문입니다.

### 3-3. 숫자 분리(digit split)

BPE를 그냥 돌리면 코퍼스에 자주 나온 숫자 조합이 통째로 토큰이 됩니다. 가격 데이터가 많으면 "00", "500원" 같은 덩어리가 생기죠. 문제는 **같은 숫자라도 쪼개지는 방식이 들쭉날쭉해진다**는 점입니다. 987은 "9"+"87"로, 986은 "986" 통째로 잘리는 식이면, 모델 입장에서 두 수는 전혀 다른 모양의 기호라 자릿수 개념을 배우기 어렵습니다. 그래서 최신 LLM들은 숫자를 한 자리(또는 최대 세 자리) 단위로 강제 분리하는 전처리를 넣습니다. 칼질 규칙 하나가 수학 성적을 바꾸는 것입니다.

## 4. 실습 — main.py

```bash
cd lecture12_llm_engineering_mlops/level01_bpe_tokenizer
python3 main.py
```

`[1]` tiny_corpus(약 3.9만 자)를 불러오고, `[2]` BPE를 60회 병합하며 초반 병합 과정을 그대로 출력합니다. "들+었 → 들었", "보고+서를 → 보고서를"처럼 조사·어미가 어떻게 덩어리지는지 지켜보세요. `[3]`에서는 병합 0/10/30/60회짜리 토크나이저 네 개로 같은 문장을 잘라 토큰 수가 14 → 4로 줄어드는 것을 보여 줍니다. `[4]`는 하이라이트입니다. 금액이 많이 나오는 코퍼스로 숫자 분리 없이/있이 두 번 학습한 뒤 "98700원"을 잘라 보면, 분리 없는 쪽은 `['9','8','700원']`처럼 들쭉날쭉하게, 분리한 쪽은 한 자리씩 일관되게 쪼개집니다.

코드의 심장은 세 함수입니다. `count_pairs()`가 이웃 쌍 빈도를 세고(digit_split 플래그가 숫자 병합을 차단), `merge_pair()`가 모든 단어에서 해당 쌍을 붙이며, `train_bpe()`가 이 둘을 반복합니다. 실제 라이브러리 구현과 원리가 같고 규모만 작습니다.

## 6. 자주 하는 실수

- **토큰 = 단어라고 생각하기**: 토큰은 빈도가 만든 조각이라 단어와 일치하지 않습니다. 요금 견적 때 "단어 수 × 1"로 계산하면 한국어는 크게 어긋납니다.
- **병합 규칙의 순서를 무시**: vocab 목록만 저장하고 순서를 잃으면 같은 문장이 다르게 토큰화됩니다. 학습 때와 추론 때 반드시 같은 규칙 파일을 써야 합니다.
- **토크나이저를 바꾸고 모델은 그대로 두기**: 토크나이저를 교체하면 토큰 id의 의미가 전부 달라지므로 임베딩부터 다시 학습해야 합니다. "토크나이저만 한국어용으로 갈아 끼우자"는 제안이 간단하지 않은 이유입니다.
- **전처리(숫자 분리 등)를 사소하게 여기기**: 오늘 본 것처럼 전처리 한 줄이 모델 능력을 바꿉니다. 데이터 파이프라인 문서에 전처리 규칙을 반드시 남기세요.
