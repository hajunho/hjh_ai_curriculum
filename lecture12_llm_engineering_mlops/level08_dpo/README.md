# Lecture 12 · Level 08 — 선호도 정렬(DPO)

> 두 답안 중 "사람이 고른 쪽"의 확률을 높이는 DPO 손실을 수식 그대로 구현해, 모델의 취향이 바뀌는 것을 로그확률로 지켜봅니다.

**난이도** ⭐⭐⭐⭐⭐ / **선행** level07 / **예상 시간** 70분

## 1. 왜 배우나 — 비즈니스 관점

SFT까지 마친 모델은 형식을 갖춰 답합니다. 그런데 "답할 수 있는" 것과 "좋게 답하는" 것은 다릅니다. 고객 불만에 "그건 택배 회사 문제입니다"라고 답하는 것도, "불편을 드려 죄송합니다"라고 답하는 것도 문법적으로는 똑같이 멀쩡한 답입니다. 어느 쪽이 좋은지는 정답이 아니라 **선호**의 문제이고, 이것을 가르치는 공정이 선호도 정렬(preference alignment)입니다.

ChatGPT를 유명하게 만든 RLHF(인간 피드백 강화학습)가 이 단계였습니다. 하지만 RLHF는 보상 모델을 따로 학습하고 PPO라는 강화학습을 돌려야 해서, 모델 4개를 동시에 띄우는 무겁고 불안정한 공정이었습니다. 2023년 등장한 DPO(Direct Preference Optimization)는 같은 목표를 **분류 손실 하나**로 달성해 정렬의 진입 장벽을 극적으로 낮췄고, 현재 오픈소스 모델 정렬의 사실상 표준이 되었습니다. "우리 챗봇이 자꾸 퉁명스럽게 답해요"라는 품질 문제의 해법이 바로 이 단계이며, 필요한 데이터가 (질문, 좋은 답, 나쁜 답) 세 쌍이라는 것을 알면 데이터 수집 기획을 직접 설계할 수 있습니다.

## 2. 비유로 이해하기

신입사원(SFT를 마친 모델)이 응대 답변을 두 가지 초안으로 써 옵니다. 선배가 빨간펜으로 "이쪽이 낫다"라고만 표시해 줍니다. 점수도, 채점 기준표도 없습니다. 그저 **둘 중 낫다** 뿐입니다.

- **RLHF 방식** = 먼저 선배의 취향을 학습한 "채점 로봇"(보상 모델)을 만들고, 신입이 답안을 쓸 때마다 채점 로봇에게 점수를 받아 강화학습으로 교정합니다. 채점 로봇이 이상하면 신입이 채점 로봇의 허점을 파고드는(보상 해킹) 부작용도 생깁니다.
- **DPO 방식** = 채점 로봇 없이, "선배가 고른 답안은 더 자주 쓰고, 탈락한 답안은 덜 쓰도록" 습관을 직접 조정합니다. 단, 한 가지 안전장치가 있습니다: **원래의 나(참조 모델)에서 너무 멀어지지 말 것**. 칭찬받으려고 말투를 통째로 바꿔 버리면 멀쩡하던 다른 능력까지 무너지기 때문입니다.

## 3. 핵심 개념

### 3-1. 선호 데이터: (x, y_w, y_l)

DPO 데이터 한 건은 프롬프트 x, 선택된 응답 y_w(chosen/winner), 탈락한 응답 y_l(rejected/loser)의 세 쌍입니다. 실무에서는 모델이 생성한 두 응답을 사람(또는 더 강한 모델)이 비교 평가해 만듭니다. 절대 점수보다 상대 비교가 사람에게 훨씬 쉽고 일관적이라는 것이 이 데이터 형식의 출발점입니다.

### 3-2. DPO 손실 — 수식 한 줄

```
L = -log σ( β·[ (log π(y_w|x) − log π_ref(y_w|x)) − (log π(y_l|x) − log π_ref(y_l|x)) ] )
```

- log π(y|x): 현재 정책(policy) 모델이 프롬프트 뒤에 그 응답을 생성할 로그확률(응답 토큰 logp 의 합).
- log π_ref: 학습 전 자신을 복사해 동결한 참조(reference) 모델의 같은 값. 각 응답의 확률을 "출발점 대비 얼마나 올렸/내렸나"로 상대화합니다.
- 괄호 안(margin)은 "chosen 을 올린 정도 − rejected 를 올린 정도". 시그모이드 σ에 넣어 -log 를 취하면, margin 이 클수록 손실이 0에 가까워지는 **이진 분류 손실**이 됩니다. 학습 시작 시점엔 policy=ref 이므로 margin=0, 손실은 정확히 -log 0.5 = 0.693 입니다. 실습 출력에서 이 값을 직접 확인할 수 있습니다.
- **β (베타)**: 참조 모델에서 벗어나는 것에 대한 민감도. 보통 0.1~0.5. β가 작을수록 조심스럽게, 클수록 과감하게 움직입니다.

이 수식은 RLHF의 "보상 최대화 + KL 제약" 문제를 수학적으로 풀면 보상 모델이 소거되고 이 형태만 남는다는 유도에서 나왔습니다. 즉 DPO는 RLHF의 지름길이지 다른 목표가 아닙니다. 그래서 β(log π − log π_ref)를 **암묵적 보상(implicit reward)**이라고 부릅니다.

### 3-3. 참조 모델은 왜 필요한가

참조항 없이 "chosen 확률 ↑, rejected 확률 ↓"만 하면, 모델은 rejected 를 낮추는 가장 쉬운 길 — 예컨대 아예 말이 안 되는 출력 분포로 도망가는 — 을 택할 수 있습니다. 참조 모델과의 차이로 상대화하면 "원래 잘하던 것은 유지하면서 선호 방향만 기울이는" 학습이 됩니다. 그래도 데이터가 적거나 오래 학습하면 chosen 확률까지 함께 떨어지는 과최적화가 일어납니다(6절 참고).

### 3-4. RLHF vs DPO 한눈에

| | RLHF(PPO) | DPO |
|---|---|---|
| 필요한 모델 | policy·ref·보상모델·가치모델 4개 | policy·ref 2개 |
| 학습 방식 | 강화학습(불안정, 튜닝 어려움) | 지도학습식 분류 손실(안정적) |
| 보상 | 명시적 보상 모델 | 손실에 내장된 암묵적 보상 |
| 비용 | 크다 | 상대적으로 작다 |

## 4. 실습 — main.py

실행:

```bash
cd lecture12_llm_engineering_mlops/level08_dpo
python3 main.py
```

- **[1]** 고객 응대 선호 쌍 6개(질문 / 공손한 chosen / 책임 회피형 rejected)를 인코딩합니다.
- **[2]** 준비 SFT: chosen 과 rejected 를 **같은 비중으로** 학습해 둘 다 그럴듯한 상태를 만듭니다. 실제 파이프라인에서도 DPO는 SFT를 마친 모델에서 출발합니다.
- **[3]** policy 를 deepcopy 해 참조 모델로 동결합니다. DPO 학습 전 표를 보세요 — margin 이 전부 정확히 0.00이고(policy=ref), 이 시드에서는 오히려 rejected 쪽 로그확률이 높아 chosen 승률이 0/6입니다. 실제로 greedy 생성도 "그건 택배 회사에 물어보세요."라는 무례한 답을 냅니다.
- **[4]** DPO 학습 30에폭. `-F.logsigmoid(BETA * ((pw - rw) - (pl - rl)))` — 손실이 수식 그대로 한 줄입니다. 첫 에폭 손실이 이론값 0.6931임을 확인하세요. 참조 모델의 로그확률은 변하지 않으므로 루프 밖에서 한 번만 계산하는 것도 눈여겨보세요.
- **[5]** 학습 후 표: chosen 로그확률은 거의 유지되고 rejected 는 -20~-35 수준으로 추락해 margin 이 13~31로 벌어지고, 승률이 6/6이 됩니다. greedy 응답도 "불편을 드려 죄송합니다..."로 바뀝니다. **정답을 새로 가르친 것이 아니라, 이미 알던 두 답 사이의 선호를 기울인 것**입니다.

## 5. 직접 해보기

1. **β 실험**: BETA 를 0.5와 0.02로 바꿔 보세요. margin 이 벌어지는 속도와 최종 chosen 로그확률이 어떻게 달라지나요? (힌트: β가 클수록 빨리 정렬되지만 참조에서 과감하게 벗어납니다.)
2. **과최적화 관찰**: DPO 에폭을 30에서 200으로, lr 을 5e-4로 늘려 보세요. rejected 는 계속 추락하지만 chosen 로그확률도 함께 떨어지고, greedy 생성이 깨지기 시작하는 지점을 찾아보세요. (힌트: DPO 논문 이후 알려진 유명한 현상으로, "margin 은 커지는데 둘 다 나빠지는" 구간입니다.)
3. **선호 뒤집기**: PAIRS 에서 chosen 과 rejected 를 서로 바꿔 학습해 보세요. 모델이 정말 "무례한 챗봇"으로 정렬되나요? 정렬 기술 자체는 방향에 중립적이며, 어느 쪽으로 정렬할지는 사람이 정한다는 것 — 이것이 거버넌스(level11)가 필요한 이유입니다.

## 6. 자주 하는 실수

- **참조 모델도 같이 학습**: ref 를 동결하지 않거나 deepcopy 대신 참조 복사(=)를 쓰면 policy 와 ref 가 같이 움직여 margin 이 늘 0 근처가 되고 학습이 되지 않습니다.
- **로그확률을 평균으로 계산**: DPO 표준 수식은 응답 토큰 logp 의 **합**입니다. 평균을 쓰는 변형도 있지만, 섞어 쓰면 β의 의미가 달라집니다.
- **SFT 없이 바로 DPO**: 두 응답 모두 확률이 사실상 0인 상태에서 선호만 기울이면 학습이 불안정합니다. "일단 둘 다 쓸 줄 알게 한 뒤 취향을 기울인다"가 올바른 순서입니다.
- **margin 만 보고 성공 판단**: margin 은 상대값입니다. chosen 의 절대 로그확률과 실제 생성 품질을 함께 확인해야 과최적화를 놓치지 않습니다.
