# Lecture 12 · Level 02 — 학습 데이터 파이프라인과 패킹

> 문서들을 `<s>...</s>`로 이어붙여 고정 길이로 자르고, uint16 바이너리 샤드와 memmap으로 "수조 토큰을 흘려보내는 컨베이어 벨트"를 미니어처로 만듭니다.

**난이도** ⭐⭐⭐ / **선행** level01 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

LLM 사전학습에서 GPU는 시간당 수천 원~수만 원짜리 계량기를 달고 돕니다. 이 비싼 기계가 데이터를 기다리며 노는 순간이 곧 돈 낭비입니다. 그래서 대형 학습의 실력 차이는 모델 코드보다 **데이터를 끊김 없이, 낭비 없이 공급하는 파이프라인**에서 갈리는 경우가 많습니다.

비즈니스 관점에서 이 레벨이 답하는 질문은 세 가지입니다. 첫째, "왜 학습 데이터는 텍스트 파일이 아니라 이상한 바이너리로 저장하나요?" — 매번 토큰화를 다시 하면 CPU가 병목이 되기 때문에, 한 번 토큰화한 결과를 기계가 바로 먹을 수 있는 형태로 저장해 둡니다. 둘째, "수백 GB 데이터를 어떻게 메모리에 올리나요?" — 올리지 않습니다. memmap이라는 기법으로 필요한 조각만 그때그때 읽습니다. 셋째, "문서 길이가 제각각인데 GPU는 왜 항상 꽉 차 있나요?" — 패킹 덕분입니다. 이 세 가지는 AI 인프라 견적서와 병목 논의에 그대로 등장하는 실무 개념입니다.

## 2. 비유로 이해하기

김밥 공장을 상상해 보세요. 주문(문서)은 길이가 제각각입니다. 어떤 손님은 꼬마김밥 두 알, 어떤 손님은 열 줄을 시킵니다.

**나쁜 방식**: 주문마다 도시락 상자(고정 길이 배치) 하나씩 배정하고, 빈 공간은 스티로폼(`<pad>` 토큰)으로 채웁니다. 꼬마김밥 두 알에 대형 상자를 쓰면 상자 대부분이 스티로폼 — GPU 연산의 대부분이 의미 없는 패딩 계산에 낭비됩니다.

**패킹 방식**: 모든 주문을 김발 위에 끝없이 이어 말아 하나의 초장대 김밥(토큰 스트림)을 만듭니다. 주문과 주문 사이에는 칸막이 단무지(`<s>`, `</s>` 토큰)를 끼워 경계를 표시합니다. 그리고 상자 크기(block_size)만큼 툭툭 잘라 담습니다. 어떤 상자는 두 주문에 걸치지만, 칸막이가 있으니 먹는 사람(모델)이 "여기부터 새 주문이구나"를 알 수 있습니다. 상자에 빈 공간은 없습니다.

저장은 대형 김치통(바이너리 샤드) 방식입니다. 낱개 포장(문서별 파일 수백만 개) 대신 큰 통 몇천 개에 나눠 담으면, 냉장고 문을 여닫는 횟수(파일 열기 비용)가 줄어 물류가 빨라집니다.

## 3. 핵심 개념

### 3-1. 패킹(packing): `<s> 문서1 </s> <s> 문서2 </s> ...`

모든 문서를 토큰화해 특수 토큰으로 감싼 뒤 하나의 긴 스트림으로 잇고, block_size(실습에서는 64, 실제로는 4096~128k)씩 잘라 학습 샘플로 씁니다. 장점은 두 가지입니다. (1) 패딩이 0이라 GPU 연산이 전부 진짜 학습에 쓰입니다. (2) 샘플 길이가 균일해 배치 구성이 단순해집니다. 대신 한 샘플 안에 서로 다른 문서의 꼬리와 머리가 섞이는데, `<s>` 토큰이 "새 문서 시작" 신호가 되어 모델이 문맥을 끊어 읽는 법을 함께 배웁니다.

### 3-2. uint16 샤드(shard)

토큰 id는 정수입니다. vocab이 65,536보다 작으면 id 하나를 2바이트(uint16)로 저장할 수 있습니다. 토큰당 2바이트 고정이므로 파일 크기 계산이 즉시 되고(1억 토큰 = 200MB), 파싱 없이 통째로 숫자 배열로 읽힙니다. 전체 데이터를 수백~수천 개의 샤드 파일로 나누면 여러 GPU가 서로 다른 샤드를 병렬로 읽을 수 있고, 손상 시 해당 샤드만 다시 만들면 됩니다.

### 3-3. memmap — 열지 않고 여는 기술

`np.memmap`은 파일을 RAM으로 복사하지 않고 "이 파일이 메모리에 있는 셈 치자"고 운영체제에 등록만 합니다. 실제 읽기는 배열의 특정 구간을 건드리는 순간 그 부분만 디스크에서 올라옵니다. 그래서 200GB 샤드도 여는 데 0초에 가깝고, 배치를 뽑을 때 필요한 몇 KB만 I/O가 발생합니다. lecture03에서 배운 numpy 배열 슬라이싱 문법이 그대로 통한다는 점도 매력입니다.

### 3-4. 배치 (x, y) — 정답지는 한 칸 밀기

언어 모델의 정답은 "다음 토큰"이므로, 입력 x가 스트림의 `[i : i+64]`라면 정답 y는 `[i+1 : i+65]`입니다. 별도의 라벨 파일이 필요 없습니다. 데이터 자체가 문제지이자 정답지인 것 — 이것이 사전학습 데이터가 "그냥 텍스트"면 되는 이유입니다.

## 4. 실습 — main.py

```bash
cd lecture12_llm_engineering_mlops/level02_data_pipeline_packing
python3 main.py
```

파이프라인 7단계가 차례로 실행됩니다. `[1]` tiny_corpus를 5문장씩 묶어 200개 문서로 만들고, `[2]` 특수 토큰 4개(`<s>`, `</s>`, `<pad>`, `<unk>`) + 글자들로 vocab을 만듭니다(글자 단위 — level01의 BPE로 바꾸면 스트림이 더 짧아집니다). `[3]` `tokenize_and_pack()`이 모든 문서를 `<s>...</s>`로 감싸 약 2만 토큰짜리 스트림 하나로 잇고, `[4]` `stream.tofile()`로 `outputs/shard_000.bin`에 저장합니다. 토큰당 2바이트라 원문 UTF-8보다 오히려 작아진 크기를 확인하세요. `[5]` `np.memmap`으로 즉시 로딩, `[6]` `get_batch()`가 무작위 시작점 8곳에서 길이 64짜리 (x, y) 쌍을 잘라 옵니다. y가 x를 정확히 한 칸 민 것임을 출력으로 확인하세요. `[7]`에서 배치 한 줄을 글자로 복원해 보면 문장 중간에서 시작하고 `</s><s>` 경계가 섞여 있는데, 이것이 바로 패킹된 학습 데이터의 실제 모습입니다.

## 5. 직접 해보기

1. **(쉬움)** `block_size`를 64에서 256으로 바꿔 실행해 보세요. 배치 모양과 한 배치가 소비하는 토큰 수가 어떻게 변하나요? (힌트: 배치당 토큰 = block_size × batch_size. 실제 학습에서 이 값이 "스텝당 처리량"의 기본 단위입니다.)
2. **(보통)** `[7]`을 참고해, 배치 8줄 전체에서 `<s>` 토큰 개수를 세는 코드를 추가해 보세요. block_size가 커질수록 경계 포함 확률이 어떻게 변하는지 확인해 보세요. (힌트: `(x == stoi[BOS]).sum()` 한 줄이면 됩니다.)
3. **(도전)** 문서를 2,000자짜리 샤드 두 개(`shard_000.bin`, `shard_001.bin`)로 나눠 저장하고, 배치를 뽑을 때 샤드를 무작위로 고르도록 고쳐 보세요. (힌트: 스트림 배열을 반으로 잘라 각각 `tofile` 하고, `get_batch` 앞에서 `rng.integers(0, 2)`로 샤드를 고릅니다. 이것이 멀티 GPU 데이터 로더의 뼈대입니다.)

## 6. 자주 하는 실수

- **`<s>` 없이 패킹하기**: 경계 표시가 없으면 앞 문서의 끝이 뒷 문서의 시작을 예측하는 "가짜 신호"가 되어 모델이 혼란을 학습합니다. 칸막이 단무지를 빼먹지 마세요.
- **uint16 범위 초과**: vocab이 65,536을 넘는데 uint16으로 저장하면 토큰 id가 조용히 잘려 엉뚱한 데이터가 됩니다. 저장 전 `vocab_size < 65536` 검증을 습관화하세요. (실제 대형 모델 vocab은 10만이 넘어 uint32를 쓰기도 합니다.)
- **memmap을 통째로 복사**: `np.array(mm)`처럼 전체를 변환하면 memmap의 이점이 사라지고 RAM이 터집니다. 항상 슬라이스로 필요한 구간만 꺼내세요.
- **토크나이저 버전 불일치**: 샤드를 만든 토크나이저와 다른 버전으로 디코딩하면 데이터가 통째로 오염됩니다. 샤드 옆에 vocab 파일과 버전 정보를 반드시 같이 저장하세요.
