# Lecture 01 · Level 07 — GitHub: 원격 저장소와 협업

> 원격 저장소(clone/push/pull)와 Pull Request 협업 흐름을 이해하고, 인터넷 없이 로컬 bare 저장소를 "가짜 GitHub" 삼아 push/pull 을 실습합니다.

**난이도** ⭐⭐ / **선행** level06 / **예상 시간** 45분

## 1. 왜 배우나 — 비즈니스 관점

level06 에서 만든 결재 서류함(저장소)은 내 컴퓨터 안에만 있습니다. 노트북이 고장 나면 이력째 사라지고, 팀원은 내 서류함을 볼 수 없습니다. 그래서 필요한 것이 **원격 저장소(remote repository)** — 모두가 접근할 수 있는 중앙 서류함입니다. 그리고 그 중앙 서류함을 빌려주는 세계 최대 서비스가 **GitHub(깃허브)** 입니다.

GitHub 는 개발자의 협업 장소이자 이력서이며, 전 세계 오픈소스가 모이는 광장입니다. 비개발자에게도 의미가 큽니다. 회사의 개발 산출물이 어디서 어떻게 관리되는지, "PR 리뷰 중이라 배포가 늦어진다"는 개발팀의 말이 무슨 뜻인지, 외부 오픈소스 도구를 도입할 때 그 프로젝트가 건강한지(최근 커밋·이슈 응답)를 볼 수 있게 되기 때문입니다. 이 레벨을 마치면 push/pull/PR 같은 용어가 들리기 시작하고, 원격 협업의 전체 그림이 잡힙니다.

## 2. 비유로 이해하기

**원격 저장소는 본사 중앙 문서고, 내 저장소는 지사 서류함**입니다.

- **clone(클론)**: 신입 지사장이 부임하며 **중앙 문서고 전체를 복사**해 지사에 갖추는 일입니다. 이력까지 통째로 복제되므로, 이후 지사는 독립적으로 일할 수 있습니다.
- **push(푸시)**: 지사에서 결재한 서류(커밋)들을 **본사 문서고로 올려보내** 공식 기록으로 만드는 일입니다.
- **pull(풀)**: 다른 지사들이 올린 최신 서류를 **본사에서 받아와** 내 지사 서류함을 최신으로 맞추는 일입니다.
- **Pull Request(PR)**: "제 변경안을 본편에 합쳐 주십시오"라는 **정식 품의서**입니다. 변경 내용을 동료가 검토(리뷰)하고, 승인되면 본편(main)에 합쳐집니다(merge). 품의서에는 토론 댓글이 달리고, 수정 요구가 오가며, 이 모든 과정이 기록으로 남습니다.

흐름을 한 줄로 요약하면: **clone 으로 시작 → 브랜치에서 작업 → push 로 올리고 → PR 로 검토받아 → main 에 합류 → 동료들은 pull 로 최신화**입니다.

한 가지 재미있는 사실: 본사 문서고(원격 저장소)에는 사람이 앉아 일하는 책상이 없습니다. 작업 폴더 없이 이력만 보관하는 저장소를 **bare(베어) 저장소**라고 하며, GitHub 서버가 실제로 이 형태입니다. 오늘 실습에서는 내 컴퓨터 안에 bare 저장소를 만들어 "가짜 GitHub" 로 씁니다 — 인터넷 없이도 push/pull 의 원리는 완전히 동일합니다.

## 3. 핵심 개념

### 3-1. 원격 협업 명령 5가지

```bash
git clone <주소>          # 원격 저장소를 통째로 복제해 시작
git remote -v             # 내 저장소가 연결된 원격(별명 origin) 확인
git push origin main      # 내 커밋을 원격의 main 으로 올림
git pull origin main      # 원격의 새 커밋을 받아와 합침
git fetch                 # 받아오기만 하고 합치지는 않음(미리 보기)
```

`origin` 은 clone 해 온 원격 저장소에 자동으로 붙는 별명입니다. "본사"라고 읽으면 됩니다.

### 3-2. GitHub 가 제공하는 것

Git 은 도구(프로그램)이고, GitHub 는 그 도구용 중앙 저장소를 빌려주는 **서비스**입니다(비슷한 서비스로 GitLab, Bitbucket 등). GitHub 는 저장소 호스팅 위에 협업 기능을 얹습니다: PR 리뷰, 이슈(issue, 할 일·버그 게시판), 위키, 그리고 커밋·PR 에 반응해 자동으로 테스트를 돌리는 자동화(CI) 등입니다. 회사에서는 보통 **비공개(private) 저장소**를 쓰고, 오픈소스는 **공개(public)** 저장소로 세상과 코드를 나눕니다.

### 3-3. 충돌(conflict) — 협업의 통과의례

두 지사가 **같은 파일의 같은 부분**을 서로 다르게 고쳐 올리면, Git 은 어느 쪽이 옳은지 판단하지 않고 사람에게 묻습니다. 이것이 충돌입니다. 파일 안에 `<<<<<<<`, `=======`, `>>>>>>>` 표시로 양쪽 내용이 나란히 놓이며, 사람이 원하는 쪽(또는 제3의 절충안)으로 고쳐 다시 커밋하면 해결됩니다. 무섭게 생겼지만 "두 수정안을 나란히 보여줄 테니 결정해 주세요"라는 정중한 질문일 뿐입니다. 충돌을 줄이는 요령은 **자주 pull 하고, 작게 자주 push** 하는 것입니다.

### 3-4. 협업 예절

- main 브랜치에 직접 push 하지 않고, 브랜치 + PR 로 검토를 거치는 것이 표준입니다.
- PR 은 작게 쪼갭니다. 500줄짜리 품의서는 아무도 제대로 검토하지 못합니다.
- pull 을 먼저, push 는 나중에: 올리기 전에 최신을 받아와 내 쪽에서 합쳐 보는 습관이 충돌을 줄입니다.

## 4. 실습 — main.py

```bash
python3 main.py
```

git 이 설치되어 있으면, 임시 폴더 안에 **본사(bare 원격) 1개와 두 지사(개발자 A·B) 저장소**를 만들어 협업 시나리오를 자동 실행합니다. (git 이 없으면 개념 시뮬레이션으로 대체합니다.)

- **[1] 본사 설립**: `git init --bare` 로 작업 책상 없는 중앙 문서고를 만듭니다.
- **[2] 지사 개설**: 개발자 A 와 B 가 각각 `clone` 으로 지사를 차립니다.
- **[3] A 의 push**: A 가 메뉴 파일을 만들어 커밋하고 본사로 push 합니다.
- **[4] B 의 pull**: B 가 pull 하자 A 의 파일이 B 지사에 나타납니다 — 원격 협업의 핵심 순간입니다.
- **[5] 주고받기**: B 가 내용을 추가해 push 하고, A 가 pull 로 받아 양쪽이 같은 최신 상태가 됨을 확인합니다.
- **[6] PR 흐름 해설**: 실제 GitHub 라면 이 push 가 PR·리뷰·merge 로 이어지는 과정을 순서도로 출력합니다.

핵심은 **원격이라고 특별한 것이 없다**는 점입니다. 원격 주소가 인터넷 URL 이든 내 컴퓨터의 폴더 경로든, push/pull 의 동작은 완전히 같습니다. 코드의 `run()` 함수가 각 지사 폴더에서 git 명령을 실행하는 모습에서, "누가(cwd) 어느 원격과(origin) 무엇을 주고받는가"의 구조를 눈으로 확인하세요.

## 5. 직접 해보기

1. **(쉬움)** 출력 [4]에서 B 가 pull 하기 전과 후, B 지사 폴더의 파일 목록이 어떻게 달라졌는지 찾아보세요. *(힌트: pull 전에는 비어 있었습니다.)*
2. **(보통)** 시나리오에 "A 가 다시 pull" 단계를 추가하기 전과 후를 비교하며, pull 없이 A 가 계속 push 만 하면 어떤 문제가 생길지 생각해 보세요. *(힌트: B 의 커밋을 모르는 채 올리면 원격이 거부합니다 — 그래서 pull 먼저입니다.)*
3. **(도전)** GitHub 계정을 만들고(무료), 웹 화면에서 새 저장소를 만들어 README 파일을 웹에서 직접 편집·커밋해 보세요. 그 다음 `git clone` 으로 내 컴퓨터에 받아 보세요. *(힌트: 저장소 페이지의 초록색 Code 버튼에 clone 주소가 있습니다.)*

## 6. 자주 하는 실수

- **pull 없이 push**: 원격에 남이 올린 새 커밋이 있으면 push 가 거부됩니다. 에러가 아니라 "먼저 받아서 합치세요"라는 안내입니다. `git pull` 후 다시 push 하면 됩니다.
- **비밀키를 push**: 한 번 push 된 비밀키는 이력에 영원히 남습니다. 공개 저장소라면 몇 분 안에 도둑 봇이 수집해 갑니다. level09 에서 예방법을 배웁니다.
- **clone 과 다운로드(zip) 혼동**: zip 다운로드는 이력 없는 파일 복사일 뿐입니다. 협업하려면 반드시 clone 이어야 push/pull 이 됩니다.
- **원격과 로컬을 동일시**: 커밋만 하고 push 를 잊으면 동료에게는 아무것도 보이지 않습니다. "커밋=지사 결재, push=본사 송부"는 별개의 단계입니다.
