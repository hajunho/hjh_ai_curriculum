# Lecture 01 · Level 09 — 환경변수와 비밀키 안전하게 다루기

> API 키·비밀번호를 코드에 적으면 왜 사고가 나는지 이해하고, 환경변수와 .env 패턴으로 비밀을 코드 밖에서 관리하는 습관을 만듭니다.

**난이도** ⭐⭐⭐ / **선행** level06 / **예상 시간** 40분

## 1. 왜 배우나 — 비즈니스 관점

실제로 반복되는 사고 유형이 있습니다. 개발자가 코드에 클라우드 접속 키를 적은 채 GitHub 공개 저장소에 push 합니다. 인터넷에는 공개 저장소를 24시간 뒤지는 수집 봇이 있어서, **몇 분 안에** 그 키가 도둑의 손에 들어갑니다. 도둑은 그 키로 고성능 서버를 잔뜩 빌려 가상화폐를 채굴하고, 다음 달 회사에는 수천만 원의 청구서가 날아옵니다. 과장이 아니라 업계에서 실제로 반복되어 온 패턴입니다.

AI 시대에는 위험이 더 커졌습니다. LLM API 키 하나로 유료 호출이 무한정 가능하고, 사내 데이터베이스 비밀번호가 새면 고객 정보 유출로 이어집니다. 그래서 "비밀을 코드에 넣지 않는다"는 개발 보안의 1번 수칙이고, 보안 감사에서 가장 먼저 검사하는 항목입니다. 다행히 해법은 어렵지 않습니다. **비밀은 환경변수로 주입하고, 코드는 이름으로만 참조한다** — 이 한 문장을 몸에 익히는 것이 이 레벨의 전부입니다.

## 2. 비유로 이해하기

**코드에 적은 비밀번호는 현관문에 붙여 둔 금고 비밀번호 메모**입니다.

코드는 여기저기 복사되고, 공유되고, 저장소에 영구 기록됩니다(level06 에서 배웠듯 Git 이력은 지워지지 않습니다). 그런 문서에 금고 번호를 적는 것은, 이사 다닐 때마다 같이 옮겨지는 현관문 메모지에 번호를 적는 것과 같습니다.

**환경변수(environment variable)는 회사의 사물함 열쇠 제도**라고 생각하면 좋습니다. 업무 매뉴얼(코드)에는 "금고 열쇠는 각자의 사물함에 있음"이라고만 적습니다. 실제 열쇠(비밀값)는 각 직원의 사물함(각 컴퓨터의 환경변수)에 들어 있습니다. 매뉴얼이 외부에 유출되어도 열쇠는 안전하고, 직원(개발용/운영용 서버)마다 다른 열쇠를 쓸 수 있습니다.

환경변수란 운영체제가 각 프로그램에게 건네주는 "이름=값" 메모지 묶음입니다. 이미 여러분도 쓰고 있습니다 — level03 의 PATH 가 바로 환경변수였습니다. 여기에 `OPENWEATHER_API_KEY=abc123` 같은 항목을 추가해 두면, 코드는 `os.environ["OPENWEATHER_API_KEY"]` 라고 **이름만 불러** 값을 받아옵니다. 코드 어디에도 실제 값은 없습니다.

## 3. 핵심 개념

### 3-1. 환경변수 읽고 쓰기

```bash
# 셸에서 설정 (이 터미널 창이 살아 있는 동안만 유효)
export MY_API_KEY="sk-demo-1234"
python3 app.py
```

```python
import os
key = os.environ.get("MY_API_KEY")        # 없으면 None (안전한 읽기)
key = os.environ["MY_API_KEY"]            # 없으면 에러 (필수값일 때)
```

터미널을 닫으면 사라지므로, 늘 쓰는 값은 셸 설정 파일(`~/.zshrc` 등)에 export 를 적어 두거나, 프로젝트별로는 다음의 .env 패턴을 씁니다.

### 3-2. .env 파일 패턴

프로젝트 폴더에 `.env` 라는 파일을 만들어 비밀을 모아 둡니다.

```
# .env — 이 파일은 절대 Git 에 올리지 않는다!
DB_PASSWORD=s3cret!
LLM_API_KEY=sk-demo-abcd1234
```

그리고 **`.gitignore` 에 `.env` 를 반드시 추가**합니다. 이 두 줄 세트가 핵심입니다. 실행 시 이 파일을 읽어 환경변수로 올려 주는 도구(python-dotenv 패키지)가 표준처럼 쓰이지만, 파일 형식이 단순해서 이 레벨 실습에서는 직접 파서를 만들어 원리를 확인합니다. 동료를 위해서는 값을 비운 견본 `.env.example` (`DB_PASSWORD=여기에_입력`)을 저장소에 올려 "어떤 이름의 비밀이 필요한지"만 공유합니다.

### 3-3. 유출을 막는 3중 방어선

1. **예방**: 비밀은 .env/환경변수로만. 코드·커밋 메시지·채팅에 값 자체를 적지 않기.
2. **탐지**: 커밋 전에 하드코딩된 비밀이 없는지 스캔. 실무에서는 커밋 훅이나 CI 가 자동 검사하며, 이 레벨 실습에서 미니 스캐너를 직접 만들어 원리를 봅니다. `sk-` 로 시작하는 긴 문자열, `password = "..."` 패턴 등이 단서입니다.
3. **사후 대응**: 유출됐다면 **키를 즉시 폐기·재발급**하는 것이 유일한 해법입니다. 커밋을 지워도 이력·포크·봇 수집본에 이미 남았다고 가정해야 합니다.

### 3-4. 출력할 때는 마스킹

비밀값은 로그·화면에도 통째로 찍지 않습니다. 확인이 필요하면 `sk-d****1234` 처럼 앞뒤 몇 글자만 남기고 가리는 **마스킹(masking)** 이 관례입니다. "값이 설정되어 있는가"와 "값이 무엇인가"를 분리해서, 전자만 보여주는 것입니다.

## 4. 실습 — main.py

```bash
python3 main.py
```

세 가지 도구를 차례로 시연합니다. 모든 값은 실습용 가짜이며 인터넷에 연결하지 않습니다.

- **[1] 환경변수 읽기**: 실습용 변수를 설정하고 `os.environ` 으로 읽습니다. 없는 변수를 `.get()` 으로 안전하게 읽는 법, PATH 같은 기존 변수 확인도 함께합니다.
- **[2] 마스킹 출력**: `mask()` 함수로 비밀값을 `sk-d****5678` 형태로 가려 "설정됨 여부만" 보고하는 요령을 봅니다.
- **[3] .env 파서**: `이름=값` 형식의 .env 텍스트를 직접 파싱해 환경변수로 올리는 미니 구현으로, dotenv 도구의 원리를 확인합니다.
- **[4] 하드코딩 스캐너**: 일부러 비밀이 박힌 나쁜 예제 코드와 환경변수를 쓰는 좋은 예제 코드를 준비해 두고, 정규표현식 규칙(API 키 모양, password= 패턴 등)으로 나쁜 코드만 잡아내는 스캐너를 돌립니다.
- **[5] 수칙 요약**: 3중 방어선을 체크리스트로 출력합니다.

핵심 코드는 `scan_for_secrets()` 입니다. "비밀은 특정한 **모양**(패턴)을 가진다"는 관찰을 정규표현식 몇 줄로 옮긴 것인데, 실제 보안 도구들의 기본 원리가 이와 같습니다.

3. **(도전)** `mask()` 함수를 수정해 8자 미만의 짧은 비밀은 전부 `****` 로만 표시되게 만들어 보세요. 짧은 값은 앞뒤 글자만으로도 추측될 수 있기 때문입니다. *(힌트: `len(value)` 로 분기하세요.)*

## 6. 자주 하는 실수

- **"비공개 저장소니까 괜찮다"**: 저장소는 언젠가 공개되거나, 이직·외주로 접근자가 늘어납니다. 비공개 여부와 무관하게 비밀은 코드 밖에 두는 것이 원칙입니다.
- **.env 를 만들고 .gitignore 를 잊음**: 가장 흔한 참사 경로입니다. `.env` 생성과 `.gitignore` 추가는 반드시 한 세트로 하세요.
- **유출 후 커밋만 삭제**: 이력·포크·봇에 이미 복사되었습니다. 키 재발급이 유일한 해법입니다.
- **에러 메시지·로그에 비밀이 섞여 나감**: 디버깅 출력에 `print(config)` 처럼 설정 전체를 찍으면 비밀도 함께 찍힙니다. 마스킹을 습관화하세요.
- **견본 파일(.env.example)에 진짜 값을 채워 커밋**: 견본에는 자리표시 텍스트만 넣어야 합니다.
