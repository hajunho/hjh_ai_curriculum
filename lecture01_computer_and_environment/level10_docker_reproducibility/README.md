# Lecture 01 · Level 10 — 도커: 환경을 통째로 재현하기

> "내 컴퓨터에선 되는데요"의 최종 해법인 컨테이너 개념을 규격 화물 비유로 이해하고, Dockerfile 의 기본 문법을 읽고 쓸 수 있게 됩니다.

**난이도** ⭐⭐⭐⭐ / **선행** level04 / **예상 시간** 45분

## 1. 왜 배우나 — 비즈니스 관점

level04 의 가상환경은 파이썬 패키지까지는 통일해 주지만, 그 아래는 못 건드립니다. 운영체제가 다르고, 시스템에 설치된 프로그램이 다르고, 설정이 다르면 여전히 "내 컴퓨터에선 되는데요"가 발생합니다. 개발자의 맥에서 완성한 AI 서비스가 리눅스 서버에서 안 돌아가는 식입니다.

**도커(Docker)**는 이 문제를 끝냅니다. 프로그램만이 아니라 **프로그램이 도는 환경 전체(운영체제 라이브러리, 파이썬, 패키지, 설정, 코드)를 하나의 상자에 담아**, 어떤 컴퓨터에서든 똑같이 실행합니다. 오늘날 웹 서비스·AI 모델 배포의 사실상 표준이라, 개발팀 대화("이미지 빌드해서 올릴게요", "컨테이너 재시작했어요")와 클라우드 요금 체계(컨테이너 단위 과금)를 이해하려면 개념을 알아야 합니다. 비전공자인 여러분이 도커를 직접 운영할 일은 드물어도, **읽을 줄 아는 것**의 가치는 큽니다 — 채용 공고, 외주 견적서, 장애 보고서 어디에나 도커가 등장하기 때문입니다.

## 2. 비유로 이해하기

**컨테이너는 해운업의 규격 화물 컨테이너**입니다. 이 비유는 장식이 아니라 실제 어원입니다.

컨테이너 발명 전의 항구를 상상해 보세요. 쌀가마니, 가구, 기계 부품을 제각각의 모양대로 배에 실었습니다. 배마다 싣는 법이 다르고, 항구마다 내리는 법이 달라, 시간이 오래 걸리고 파손도 잦았습니다. 그러다 **규격 컨테이너**가 등장합니다. 내용물이 무엇이든 같은 크기의 강철 상자에 담기만 하면, 세계 어느 항구의 어느 크레인이든 똑같이 다룰 수 있게 되었죠. 물류 비용이 극적으로 떨어졌습니다.

소프트웨어의 도커 컨테이너(container)가 정확히 이것입니다. 내용물(어떤 언어, 어떤 프로그램이든)과 무관하게 규격 상자에 담으면, 도커가 설치된 어떤 컴퓨터(항구)든 똑같이 실행합니다.

용어 셋을 물류에 대응시키면:

- **Dockerfile** = **포장 지시서**. "무엇을 어떤 순서로 상자에 담을지" 적은 문서입니다.
- **이미지(image)** = 지시서대로 **포장 완료된 표준 화물**. 복제·운송이 가능한 원본입니다.
- **컨테이너** = 그 화물을 **개봉해 실제로 가동 중인 상태**. 이미지 하나로 컨테이너 여러 개를 동시에 띄울 수 있습니다(같은 설계의 매장을 여러 지점 여는 것처럼).

가상환경(venv)과의 차이도 이 비유로 선명해집니다. venv 는 "도구상자만 통일", 도커는 "작업실 건물째 통째로 포장"입니다.

## 3. 핵심 개념

### 3-1. Dockerfile 문법 — 6개 명령이면 읽는다

```dockerfile
FROM python:3.12-slim            # 바탕 화물: 파이썬 깔린 미니 리눅스에서 시작
WORKDIR /app                     # 상자 안 작업 위치 지정
COPY requirements.txt .          # 내 파일을 상자 안으로 복사
RUN pip install -r requirements.txt   # 포장 중 실행할 명령(도구 설치)
COPY . .                         # 나머지 코드 전부 복사
CMD ["python", "main.py"]        # 개봉(실행) 시 자동으로 돌릴 명령
```

| 명령 | 뜻 | 비유 |
|---|---|---|
| FROM | 어떤 기성 이미지에서 시작할지 | 반조립 상태의 바탕 화물 선택 |
| WORKDIR | 컨테이너 안의 작업 폴더 | 상자 안 작업대 위치 |
| COPY | 내 컴퓨터 → 상자 안으로 파일 복사 | 물건 싣기 |
| RUN | 포장(빌드) 중 실행할 명령 | 포장 단계의 조립 작업 |
| ENV | 환경변수 설정 (level09!) | 상자 안 사물함 메모 |
| CMD | 컨테이너 시작 시 실행할 명령 | 개봉 즉시 가동할 스위치 |

`requirements.txt` 를 먼저 COPY 하고 코드를 나중에 COPY 하는 순서에는 이유가 있습니다. 도커는 각 줄의 결과를 **층(layer)으로 캐시**해서, 바뀌지 않은 층은 재포장을 건너뜁니다. 자주 바뀌는 코드를 뒤에 두면 패키지 설치를 매번 다시 하지 않아 빌드가 빨라집니다.

### 3-2. 명령 두 개만 기억하기

```bash
docker build -t myapp .     # 포장 지시서(Dockerfile)대로 이미지 만들기
docker run myapp            # 이미지를 컨테이너로 가동
```

만든 이미지는 **레지스트리(registry)**라는 화물 터미널(Docker Hub 등)에 올려 공유합니다. 서버는 그 이미지를 내려받아 `run` 만 하면 끝 — 서버에 파이썬을 설치할 필요조차 없습니다.

### 3-3. 가상머신과의 차이 (면접 단골 상식)

가상머신(VM)은 건물 안에 **또 하나의 건물**을 통째로 짓는 방식이라 무겁습니다(운영체제 전체 포함, 기가바이트급, 부팅 수십 초). 컨테이너는 건물(호스트 운영체제)의 뼈대는 공유하고 **방만 규격화**하는 방식이라 가볍습니다(메가바이트급, 1초 미만 시작). 가벼워서 하나의 서버에 컨테이너 수십 개를 띄울 수 있고, 이것이 클라우드 경제성의 바탕입니다.

### 3-4. AI 실무와 도커

AI 모델 배포의 표준 흐름이 "모델+코드+의존성을 이미지로 포장 → 클라우드에서 컨테이너로 가동"입니다. GPU 를 쓰는 학습 환경도 CUDA 드라이버 조합이 까다로워, 미리 조합된 공식 이미지에서 시작하는 것이 관례입니다. "환경 재현이 안 돼 실험 결과가 달라진다"는 AI 연구의 고질병에 대한 처방이기도 합니다.

## 4. 실습 — main.py

```bash
python3 main.py
```

도커가 없어도 동작하는 실습입니다. 두 부분으로 구성됩니다.

- **[1] 도커 설치 진단**: `shutil.which` 로 docker 명령의 존재를 확인하고, 설치되어 있으면 `docker --version` 을 실행해 보고, 없으면 설치 안내(Docker Desktop)를 출력합니다. 어느 쪽이든 다음 단계로 진행됩니다.
- **[2] Dockerfile 생성기**: 프로젝트 사양(파이썬 버전, 필요한 패키지, 실행 파일)을 딕셔너리로 받아 **Dockerfile 텍스트를 자동 생성**하고, 한 줄 한 줄 해설을 붙여 출력합니다. 데이터 분석용과 웹 API 용 두 가지 사양으로 생성해 차이를 비교합니다.
- **[3] 파일로 저장**: 생성한 Dockerfile 을 `outputs/` 폴더에 저장해, 나중에 도커를 설치했을 때 `docker build` 로 실제 포장해 볼 수 있게 합니다.
- **[4] 빌드 흐름 해설**: 실제 빌드가 일어난다면 층(layer)이 어떻게 쌓이는지 순서도로 보여줍니다.

핵심 코드는 `generate_dockerfile()` 함수입니다. Dockerfile 이란 결국 규칙 있는 텍스트일 뿐이어서, 파이썬 문자열 조립으로 만들 수 있다는 것 — "포장 지시서를 읽고 쓸 줄 아는 것"이 이 레벨의 목표임을 코드로 보여줍니다.

## 5. 직접 해보기

2. **(보통)** 사양에 `env` 항목(예: `{"APP_MODE": "production"}`)을 추가하고, 생성기가 ENV 줄을 만들어 내도록 `generate_dockerfile()` 을 수정해 보세요. *(힌트: COPY 와 CMD 사이에 ENV 줄들을 끼워 넣으면 됩니다. 비밀키는 ENV 로 굽지 않는다는 것도 기억!)*
3. **(도전)** Docker Desktop 을 설치하고, outputs/ 의 Dockerfile 과 간단한 `main.py` 하나로 `docker build -t hello .` → `docker run hello` 를 실제로 해 보세요. *(힌트: 회사 컴퓨터는 설치 정책을 먼저 확인하세요.)*

## 6. 자주 하는 실수

- **이미지와 컨테이너 혼동**: 이미지는 포장된 원본(정적), 컨테이너는 가동 중인 실체(동적)입니다. "이미지를 재시작한다"는 말은 성립하지 않습니다.
- **컨테이너 안에 데이터 보관**: 컨테이너는 언제든 폐기·재생성되는 소모품입니다. 남겨야 할 데이터는 바깥 저장소(볼륨, 데이터베이스)에 두어야 합니다.
- **비밀키를 이미지에 굽기**: COPY 나 ENV 로 .env·키를 이미지에 넣으면, 이미지를 받는 모든 사람에게 비밀이 배달됩니다. 비밀은 실행 시점에 주입합니다(level09 원칙의 연장).
- **거대한 바탕 이미지 선택**: FROM 에 풀사이즈 이미지를 쓰면 수 GB 짜리 화물이 됩니다. slim 계열로 시작하는 것이 관례입니다.
