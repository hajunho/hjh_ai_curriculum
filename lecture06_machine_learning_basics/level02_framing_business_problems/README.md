# Lecture 06 · Level 02 — 비즈니스 질문을 ML 문제로 바꾸기

> "이탈을 줄이고 싶다"라는 소망을, 기계가 풀 수 있는 명세서(무엇을·누구 단위로·언제 기준으로·어떤 지표로)로 번역하는 기술을 배웁니다.
**난이도** ⭐⭐ / **선행** level01 / **예상 시간** 35분

## 1. 왜 배우나 — 비즈니스 관점

머신러닝 프로젝트가 실패하는 가장 흔한 이유는 모델이 나빠서가 아닙니다. **애초에 문제 정의가 안 된 채 시작했기 때문**입니다. "이탈을 줄이고 싶다"는 훌륭한 경영 목표지만, 그대로는 기계에게 시킬 수 없습니다. 이탈이 정확히 뭔가요? 3개월 미접속? 해지 버튼 클릭? 누구 단위로 예측하나요 — 고객? 계정? 가족 요금제 전체? 언제 시점에 예측하나요 — 매월 1일? 그때 우리가 아는 정보만 써야 하는 건 아시나요?

이 번역 작업은 코딩이 아니라서 오히려 현업 담당자가 데이터 과학자보다 잘할 수 있는 영역입니다. 그리고 여기서 어긋나면 이후 어떤 모델링도 소용없습니다. 이 레벨은 이 강의에서 유일하게 "모델을 안 만드는" 레벨이지만, 실무 가치로는 가장 큰 레벨일 수 있습니다.

## 2. 비유로 이해하기

**ML 문제 정의는 외주 발주서 쓰기와 같습니다.** 인테리어 업자에게 "집을 예쁘게 해 주세요"라고 하면 결과는 복불복입니다. 좋은 발주서는 다릅니다. 어느 방을(단위), 언제까지(시점), 어떤 스타일로(대상), 예산과 만족 기준은 무엇인지(지표), 그리고 완성 후 무엇을 할 것인지(액션)가 적혀 있습니다.

머신러닝 모델도 말이 안 통하는 외주 업체입니다. 발주서(문제 명세)가 모호하면, 성실하게 엉뚱한 것을 만들어 옵니다. 특히 무서운 것은 **모델은 발주서의 허점을 되묻지 않는다**는 점입니다. "예측 시점에 알 수 없는 정보를 재료로 주면 안 된다"는 조건을 빠뜨리면, 모델은 그 정보를 몰래 써서 시험 성적만 좋은 가짜 명품을 납품합니다(이를 누설(leakage)이라 부릅니다).

## 3. 핵심 개념

### 3.1 ML 명세서의 5요소

비즈니스 질문을 ML 문제로 바꿀 때 반드시 답해야 할 다섯 가지입니다.

1. **예측 대상(target)**: 정확히 무엇을 맞히나? 측정 가능한 정의로. — "이탈" → "이번 달 말 기준, 다음 30일 안에 구독을 해지함(1/0)"
2. **예측 단위(unit)**: 한 줄(행)이 무엇인가? — 고객 1명? 계정 1개? 주문 1건? 매장 1곳의 하루?
3. **예측 시점(timing)**: 언제 예측을 내리는가, 그리고 그 시점에 **실제로 알 수 있는 정보만** 재료로 쓰는가? — 시점을 어기면 누설이 일어납니다.
4. **평가지표(metric)**: 잘 맞혔는지 무엇으로 재나? 그 지표가 비즈니스 손익과 연결되나? — 이탈 예측이면 정확도보다 재현율·정밀도(level06).
5. **액션(action)**: 예측이 나오면 무엇을 하나? — "위험 상위 10%에게 상담 전화". **액션이 없으면 예측은 장식품입니다.** 액션이 정해져야 "상위 10%"처럼 모델 출력 형태도 정해집니다.

여기에 실무에서는 **기준선(baseline)** — "모델 없이 지금 방식(감, 규칙)으로 하면 성적이 얼마인가" — 을 추가합니다. 기준선을 못 이기는 모델은 도입할 이유가 없습니다.

### 3.2 될 문제 vs 안 될 문제

같은 형식으로 적어 봐도, ML로 풀릴 문제와 아닌 문제가 있습니다.

**될 문제의 조건**: (a) 과거에 비슷한 일이 반복적으로 일어났고 데이터로 남아 있다, (b) 입력과 결과 사이에 패턴이 존재할 법하다, (c) 정답(레이블)을 확보할 수 있다, (d) 어느 정도 틀려도 액션이 성립한다.

**안 될 문제의 신호**: 정답 데이터가 수십 건뿐이다("우리 회사 10년치 M&A 성공 예측"), 규칙이 이미 100% 명확하다(부가세 계산 — level00), 예측해도 할 수 있는 액션이 없다, 과거 패턴이 미래에 유지될 가능성이 낮다(제도가 완전히 바뀐 직후), 사람 목숨·법적 책임이 걸려 오차 허용이 0이다.

### 3.3 누설(leakage) — 미래를 훔쳐보는 재료

명세서 검토에서 가장 신경 쓸 항목입니다. 예: "해지 위약금 청구액" 열은 이탈을 거의 완벽히 맞힙니다 — 해지한 사람에게만 청구되니까요. 하지만 예측 시점(월초)에는 존재하지 않는 정보입니다. 훈련 데이터에는 있는데 예측 시점에는 없는 열, 또는 결과가 정해진 뒤에야 채워지는 열은 전부 의심하세요. 판별 질문은 하나입니다. **"예측 버튼을 누르는 그 순간, 이 값을 알 수 있는가?"**

### 3.4 명세는 반복해서 다듬는 문서다

첫 명세서는 보통 틀립니다. "30일 내 해지"로 정의했더니 정기결제일이 45일 주기인 고객이 전부 이탈로 잡힌다든가 하는 문제가 데이터를 보면서 드러납니다. 명세서→데이터 확인→명세서 수정의 왕복이 정상적인 과정입니다.

## 4. 실습 — main.py

실행:

```bash
python3 main.py
```

이 프로그램은 **체크리스트 엔진**입니다. ML 명세서를 파이썬 자료구조로 적으면, 5요소가 채워졌는지·누설 위험은 없는지·ML에 적합한 문제인지 자동 점검해 점수를 매깁니다.

- **[1]** "이탈을 줄이고 싶다"를 나쁜 명세서(빈칸투성이)로 넣고 점검 → 무엇이 비었는지 지적을 받습니다.
- **[2]** 같은 소망을 좋은 명세서로 완성해 점검 → 통과 과정을 보며 5요소를 익힙니다.
- **[3]** 누설 위험 검사: 재료 목록에 "해지 위약금 청구액"이 섞인 명세서를 넣어 엔진이 잡아내는지 봅니다(예측 시점 이후에 생기는 열 탐지).
- **[4]** 후보 문제 4개(수요 예측, 부가세 계산, M&A 성공 예측, 이상거래 탐지)를 "될 문제/안 될 문제" 기준으로 자동 분류하고 이유를 출력합니다.

코드 핵심부는 `MLSpec` 데이터클래스와 `validate()` 함수입니다. 점검 규칙 하나하나가 3장의 개념과 1:1로 대응하므로, 출력과 코드를 오가며 읽어 보세요. 이 체크리스트는 실제 회의에서 화이트보드에 그대로 옮겨 써도 됩니다.

## 6. 자주 하는 실수

- **목표와 예측 대상을 동일시**: 목표는 "이탈 감소"(비즈니스), 예측 대상은 "30일 내 해지 여부"(ML). 모델은 후자만 합니다. 이탈 감소는 예측+액션(상담, 혜택)이 함께 만들어 냅니다.
- **정확도를 무조건 지표로 적기**: 이탈률 15% 데이터에서는 "전원 유지"라고 우겨도 정확도 85%입니다. 지표 선택은 level06에서 깊게 다룹니다.
- **누설 열을 성능 향상으로 착각**: 시험 성적이 갑자기 이상하게 좋아졌다면 기뻐하기 전에 누설부터 의심하세요.
- **한 번에 완벽한 명세를 쓰려는 것**: 명세는 데이터를 보며 고쳐 쓰는 살아 있는 문서입니다.
