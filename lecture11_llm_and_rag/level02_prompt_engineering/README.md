# Lecture 11 · Level 02 — 프롬프트 엔지니어링: 지시서 잘 쓰는 법

> 같은 모델이라도 지시서(프롬프트)를 어떻게 쓰느냐로 결과가 하늘과 땅 차이 — 역할·맥락·형식·예시 4대 요소를 실습으로 익힙니다.
**난이도** ⭐⭐ / **선행** level01 / **예상 시간** 40분

## 1. 왜 배우나 — 비즈니스 관점

LLM 도입 프로젝트에서 가장 투자 대비 효과가 큰 기술은 모델 교체도, 서버 증설도 아니고 **프롬프트를 고쳐 쓰는 것**입니다. 비용은 0원인데 품질이 눈에 띄게 달라집니다. "AI가 이상한 답을 해요"라는 불만의 절반 이상은 사실 "지시가 모호했어요"입니다.

프롬프트 엔지니어링(prompt engineering)은 별도의 프로그래밍 언어가 아닙니다. **업무 지시를 명확하게 쓰는 기술** — 즉, 좋은 관리자의 소통 기술과 같습니다. 그래서 코딩 경험이 없는 직장인이 개발자보다 잘하는 경우도 많습니다. 여러분이 팀원에게 일을 잘 시켜 본 경험이 그대로 자산이 됩니다.

## 2. 비유로 이해하기

신입사원에게 일을 시키는 두 팀장을 비교해 보세요.

**A팀장**: "이거 요약해 줘." — 신입은 당황합니다. 몇 줄로? 누가 읽는데? 뭐가 중요한데? 결과물은 복불복입니다.

**B팀장**: "자네가 임원 보고 담당 비서라고 생각하고(역할), 바쁜 상무님이 30초 안에 읽으실 거니까(맥락), 결정사항 위주로 3줄 개조식으로(형식), 지난번 보고서처럼(예시) 정리해 줘." — 신입이 처음이어도 결과물이 안정적으로 나옵니다.

LLM은 매번 기억이 리셋되는, 그러나 매우 유능한 신입사원입니다. **B팀장의 지시서를 매번 새로 줘야** 일정한 품질이 나옵니다. 프롬프트 엔지니어링은 결국 "B팀장의 지시서 양식 만들기"입니다.

## 3. 핵심 개념

### 3.1 프롬프트 4대 요소

| 요소 | 하는 일 | 예시 문구 |
|---|---|---|
| 역할(Role) | 말투·전문성 수준 설정 | "당신은 임원 보고용 비서입니다" |
| 맥락(Context) | 취사선택 기준 제공 | "바쁜 임원이 30초 안에 읽습니다" |
| 형식(Format) | 출력 모양 고정 | "3줄 개조식으로", "JSON으로" |
| 예시(Example) | 스타일을 샘플로 전달 | "예시: 입력→출력" |

네 가지를 모두 채울 필요는 없지만, 결과가 마음에 안 들 때 **무엇을 추가할지 점검하는 체크리스트**로 쓰면 됩니다.

### 3.2 few-shot — 예시의 힘

예시 없이 지시만 하는 것을 zero-shot, 입출력 예시를 1개 이상 보여주는 것을 few-shot(퓨샷)이라고 합니다. 예시는 두 가지를 동시에 해결합니다. (1) 말로 설명하기 어려운 스타일 전달, (2) **출력 형식 고정** — 특히 분류·추출처럼 결과를 다음 프로그램이 받아 처리하는 업무에서는 형식이 흔들리면 전체 자동화가 깨지므로, few-shot이 사실상 필수입니다.

### 3.3 시스템 프롬프트 vs 사용자 프롬프트

실제 API에서는 지시서가 두 층으로 나뉩니다. 시스템 프롬프트(system prompt)에는 역할·규칙처럼 매번 같은 내용을, 사용자 메시지에는 이번 작업의 재료를 넣습니다. 회사로 치면 시스템 프롬프트가 "직무기술서", 사용자 메시지가 "오늘의 업무 요청"입니다. main.py 하단 주석의 Claude API 예시에서 `system=` 파라미터가 그것입니다.

### 3.4 반복 개선 루프

프롬프트는 한 번에 완성되지 않습니다. 실무 순서는: 초안 작성 → 대표 입력 5~10개로 테스트 → 실패 사례를 보고 요소 보강 → 다시 테스트. 이 "테스트 입력 모음"이 나중에 평가셋(level11)으로 발전합니다.

### 3.5 프롬프트는 자산이다 — 템플릿화와 버전 관리

잘 다듬은 프롬프트는 개인 노하우로 흩어지기 쉽습니다. 팀 차원에서는 (1) 잘 되는 프롬프트를 빈칸 있는 템플릿으로 만들어 공유하고, (2) 수정할 때마다 날짜와 변경 이유를 기록하고(버전 관리), (3) 어떤 입력에서 실패했는지 사례를 모아 두는 것이 좋습니다. "프롬프트 v3에서 v4로 바꿨더니 분류 정확도가 떨어졌다"를 알아채려면 기록이 있어야 합니다. 이 관리 체계는 level11의 평가셋과 만나 완성됩니다 — 프롬프트를 바꿀 때마다 같은 평가셋으로 채점해 개선 여부를 숫자로 확인하는 것입니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level02_prompt_engineering
python3 main.py
```

출력 해설:

- **[1]** 4대 요소 요약.
- **[2] 사례 A(회의록 요약)**: 나쁜 프롬프트("요약해줘")는 문장 1개를 아무렇게나 돌려주지만, 역할+맥락+형식을 채운 프롬프트는 결정사항 위주의 개조식 3줄을 돌려줍니다. 각 프롬프트 위에 `포함 요소 N/4` 채점이 함께 출력됩니다.
- **[3] 사례 B(민원 분류)**: 나쁜 프롬프트는 "음, 이건 환불/결제 관련인 것 같습니다"처럼 사람이 읽기엔 괜찮지만 프로그램이 처리할 수 없는 문장을 냅니다. few-shot 프롬프트는 `분류: ...` / `근거 키워드: ...`의 고정 형식을 돌려줍니다.
- **[4]** 요소별 효과 정리.

코드 핵심부: `audit_prompt()`는 프롬프트에 4대 요소가 있는지 키워드로 채점하는 간단한 점검기입니다. `MockLLM.complete()`는 역할·형식·예시가 감지되면 구조화된 응답을, 없으면 두루뭉술한 응답을 내도록 설계되어 실제 LLM에서 관찰되는 경향을 재현합니다. 실제 모델은 이렇게 기계적이지는 않지만, "명확한 지시 → 안정된 출력"이라는 방향성은 같습니다.

## 5. 직접 해보기

1. **(쉬움)** 사례 A의 좋은 프롬프트에서 "개조식 형식으로" 문구를 지우고 실행해 보세요. 출력이 어떻게 퇴화하나요? (힌트: `audit_prompt` 점수와 응답 구조가 함께 변합니다.)
2. **(중간)** "번역" 업무용 좋은 프롬프트를 직접 작성해 `llm.complete()`에 넣어 보세요. 4대 요소를 모두 채워 `4/4`를 만들어 보세요. (힌트: "예시:"라는 단어가 들어가야 예시 요소로 인정됩니다.)
3. **(도전)** 여러분이 실제로 자주 하는 업무 1개(주간보고 작성 등)의 프롬프트 템플릿을 만들어 보세요. 변하는 부분은 `{이번 주 실적}`처럼 빈칸으로 두고, 대표 입력 3개로 테스트하는 코드를 추가해 보세요.

## 6. 자주 하는 실수

- **한 문장 지시로 복잡한 결과를 기대** — "잘 요약해줘"의 "잘"은 모델에게 아무 정보도 주지 않습니다. 기준을 문장으로 쓰세요.
- **금지 사항만 잔뜩 나열** — "~하지 마"보다 "~해라"가 잘 듣습니다. 원하는 모습을 예시로 보여주는 것이 최선입니다.
- **형식을 지정하지 않고 자동화에 연결** — 사람이 읽을 때는 자유 형식도 괜찮지만, 프로그램이 받는 출력은 형식(가능하면 JSON, level03)을 강제해야 합니다.
- **한 번 테스트하고 완성 선언** — 입력이 조금만 달라져도 무너지는 프롬프트가 많습니다. 최소 5개의 다양한 입력으로 테스트하세요.

## 다음 레벨 예고

좋은 프롬프트로도 출력이 "대체로" 형식을 지킬 뿐, 100%는 아닙니다. 프로그램에 연결하려면 JSON으로 받고, 스키마를 검증하고, 실패하면 재요청하는 안전장치가 필요합니다. Level 03에서 그 패턴을 구현합니다.
