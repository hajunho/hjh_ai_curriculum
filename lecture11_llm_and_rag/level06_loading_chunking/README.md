# Lecture 11 · Level 06 — 문서 로딩과 청킹

> 문서를 "어떻게 자르느냐"가 검색 품질의 절반을 결정합니다 — 3가지 청킹 전략을 같은 평가셋으로 비교 실험합니다.
**난이도** ⭐⭐⭐ / **선행** level05 / **예상 시간** 45분

## 1. 왜 배우나 — 비즈니스 관점

"규정집을 통째로 AI에 넣으면 되지 않나요?" — RAG 프로젝트에서 가장 먼저 나오는 질문입니다. 안 되는 이유가 두 가지 있습니다. 첫째, LLM이 한 번에 읽을 수 있는 분량(문맥창, context window)에는 한계가 있고, 넣는 만큼 토큰 요금이 나갑니다. 둘째, 더 중요한 이유 — **통째로 넣으면 검색이 흐려집니다.** 100페이지 문서 전체의 임베딩은 "이 문서는 대충 인사 규정"이라는 뭉툭한 좌표가 될 뿐, "연차 신청은 3영업일 전"이라는 구체 정보를 찾는 데는 쓸모가 없습니다.

그래서 문서를 적당한 조각(청크, chunk)으로 잘라 조각 단위로 임베딩·검색합니다. 이 "적당한"을 정하는 것이 청킹 설계이며, 실제 RAG 시스템의 품질 문제 중 모델 교체 없이 청킹 수정만으로 해결되는 비율이 놀랄 만큼 높습니다.

## 2. 비유로 이해하기

**서류 창고의 파일링**을 생각해 보세요. 10년치 서류를 상자 하나에 다 넣으면(통문서) 무엇이든 찾으려면 상자를 통째로 뒤져야 합니다. 반대로 종이를 한 장 한 장 반으로 찢어 보관하면(너무 작은 청크) "계약 금액" 앞부분과 "1억 2천만원" 뒷부분이 다른 봉투에 들어가 정보가 못 쓰게 됩니다.

좋은 파일링은 **의미 단위**로 묶습니다: 계약서 1건, 규정 1개 조항. 그리고 경계가 애매한 서류는 **양쪽 폴더에 복사본**을 넣어 둡니다 — 이것이 오버랩(overlap)입니다. 청킹 설계는 결국 "찾기 좋게 서류를 나누는 파일링 기술"입니다.

## 3. 핵심 개념

### 3.1 왜 자르나 — 세 가지 이유

1. **문맥창 한계**: 모델이 한 번에 읽는 분량은 유한하고, 요금은 넣은 만큼 나갑니다.
2. **검색 정밀도**: 조각이 한 가지 주제만 담아야 임베딩 좌표가 또렷해집니다.
3. **근거 인용**: 답변에 "출처: 휴가규정 제1조"처럼 조각 단위 근거를 붙일 수 있습니다(level08, 11).

### 3.2 세 가지 전략

| 전략 | 방법 | 장점 | 약점 |
|---|---|---|---|
| A. 고정 길이 | 글자 수로 뚝뚝 | 구현 1분 | 단어·문장이 경계에서 잘림 |
| B. 고정 + 오버랩 | A에 겹침 구간 추가 | 경계 손실 보완 | 저장량 증가, 여전히 잘림 |
| C. 문장/문단 경계 | 의미 단위로 묶음 | 조각이 온전한 뜻 유지 | 구현 손이 더 감, 길이 들쭉날쭉 |

실무 기본값은 "C를 기본으로 하되 상한 길이를 두고, 10~20% 오버랩"입니다. 마크다운 제목·조항 번호 같은 구조가 있으면 그 경계를 최우선으로 존중합니다.

### 3.3 크기의 트레이드오프

- **너무 작으면**: "국내 출장 일비는"과 "3만원"이 다른 조각으로 갈라져, 어느 조각도 완결된 답을 담지 못합니다.
- **너무 크면**: 휴가·경비·재택 규정이 한 조각에 섞여, "재택" 질문에도 "휴가" 문장 덩어리가 통째로 딸려 옵니다. 검색은 흐려지고 프롬프트 토큰만 늘어납니다.

정답 크기는 문서마다 다르므로, 오늘 실습처럼 **평가셋으로 명중률을 재서** 정합니다. 또 하나의 실무 요령은 각 조각에 문서 제목·조항 번호를 접두어로 붙여 저장하는 것입니다("[휴가규정 제1조] 연차휴가는..."). 조각만 떼어 놓아도 어느 문서의 무슨 조항인지 문맥이 유지되어 검색과 인용이 모두 좋아집니다.

### 3.4 로딩(loading)에 대하여

실무에서는 자르기 전에 PDF·워드·웹페이지에서 텍스트를 꺼내는 로딩 단계가 있습니다(표·머리글·꼬리말 처리 등이 은근히 어렵습니다). 오늘은 `SAMPLE_DOCS`가 이미 텍스트라 이 단계를 생략하지만, "로딩 품질 → 청킹 품질 → 검색 품질"로 이어지는 파이프라인임을 기억해 두세요.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level06_loading_chunking
python3 main.py
```

출력 해설:

- **[1]** 문서 5건(657자)을 로딩하고, 자르는 세 가지 이유를 요약합니다.
- **[2]** 전략별 조각 수·평균 길이: A는 15개, B는 22개(오버랩만큼 증가), C는 10개.
- **[3]** 전략 A의 조각을 눈으로 확인합니다 — "2년마다"가 "2년마"와 "다"로 쪼개지는 경계 손상을 직접 봅니다.
- **[4]** 같은 질문 5개로 명중률 비교: A는 4/5, 오버랩을 더한 B와 문장 단위 C는 5/5. 오버랩과 경계 존중이 실제로 점수를 올리는 것을 확인합니다.
- **[5]** 최고 전략의 질문별 상세(몇 위 조각에서 정답을 찾았는지)를 출력합니다.

코드 핵심부: `chunk_fixed()`(글자 수 + 오버랩), `chunk_by_sentence()`(문장 경계를 지키며 상한까지 묶기), 그리고 `evaluate()` — 조각을 임베딩해 검색기를 만들고 "상위 2조각 안에 정답 구절 포함" 여부로 채점합니다. 이 평가 방식(검색 명중률, retrieval hit rate)은 level11 평가기의 원형입니다.

## 6. 자주 하는 실수

- **청크를 한 번도 눈으로 안 봄** — 검색이 이상하면 십중팔구 조각이 이상합니다. `print(chunks[:5])`가 최고의 디버거입니다.
- **글자 수 = 토큰 수로 혼동** — 한국어는 대략 1~2자당 1토큰입니다. 문맥창 계산 시 여유를 두세요.
- **모든 문서에 같은 청크 크기 적용** — 규정(조항 단위)과 매뉴얼(절차 단위)과 회의록(안건 단위)은 자연 경계가 다릅니다.
- **오버랩을 0 아니면 50%로 극단 설정** — 0은 경계 손실, 과도한 오버랩은 저장·검색 중복. 10~20%부터 시작하세요.
- **청킹 바꾸고 재임베딩 안 함** — 조각이 바뀌면 벡터도 전부 다시 만들어야 합니다. (다음 레벨의 벡터 저장소가 이를 관리합니다.)
