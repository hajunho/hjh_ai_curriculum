# Lecture 11 · Level 01 — LLM 업무 활용 지도

> 요약·초안·분류·추출·번역·코드 — 회사에서 LLM을 어디에 쓰면 되는지 지도를 그리고, 3가지 업무를 모의 LLM으로 자동화해 봅니다.
**난이도** ⭐ / **선행** level00 / **예상 시간** 35분

## 1. 왜 배우나 — 비즈니스 관점

"우리 회사도 AI 도입합시다"라는 지시가 내려오면 대부분 이렇게 됩니다: 몇 달간 챗봇을 만들다가, 챗봇이 이상한 소리를 해서 프로젝트가 중단됩니다. 실패 원인은 기술이 아니라 **과제 선정**입니다. LLM에게 가장 위험한 일(고객 앞에서 사실을 말하기)을 처음부터 시켰기 때문입니다.

성공하는 조직은 반대로 갑니다. 틀려도 손해가 작은 업무 — 초안 작성, 요약, 분류 — 부터 시작해서 신뢰와 노하우를 쌓고, 검증 장치(이 강의 후반의 RAG·가드레일)를 갖춘 뒤에 고객 접점으로 확장합니다. 이 레벨은 그 "어디부터 시작할지"의 지도를 제공합니다.

## 2. 비유로 이해하기

LLM 도입은 **말솜씨 좋은 신입사원 채용**과 같습니다. 이 신입은 글을 놀랍게 잘 쓰고, 지치지 않고, 월급이 쌉니다. 그런데 회사 사정을 전혀 모르고, 모르는 것도 아는 척하는 버릇이 있습니다.

이 신입에게 일을 시키는 순서를 생각해 보세요.

- **첫 주**: 회의록 정리, 이메일 초안 — 틀려도 선배가 고치면 그만입니다.
- **첫 달**: 접수된 문의를 부서별로 분류 — 가끔 틀리면 재분류하면 됩니다.
- **믿음이 쌓인 뒤**: 자료(문서)를 쥐여주고 고객 응대 보조 — 단, 근거 없이 말하지 말라는 규칙과 함께.

절대 시키면 안 되는 일도 명확합니다: 검토 없이 회사 도장이 찍혀 나가는 일, 회사 기밀을 외부에 노출하는 일. LLM 활용 지도는 결국 "신입에게 일 맡기는 순서표"입니다.

## 3. 핵심 개념

### 3.1 6대 업무 유형

| 유형 | 예시 | LLM이 잘하는 이유 | 리스크 |
|---|---|---|---|
| 요약 | 회의록→3줄 | 원문이 눈앞에 있음(환각 여지 적음) | 낮음 |
| 초안 | 이메일·공지 | 사람이 최종 수정 전제 | 낮음 |
| 분류 | 민원 라우팅 | 선택지가 정해져 있음 | 중간 |
| 추출 | 계약서에서 금액·날짜 | 형식화 가능(level03) | 중간 |
| 번역 | 거래처 메일 | 언어 패턴의 정수 | 중간 |
| 코드 | 엑셀 수식·SQL | 실행해 보면 검증됨 | 중간 |

공통 원리: **원문이 주어지고, 사람이 검토하거나, 기계적으로 검증 가능한 업무**일수록 안전합니다. 반대로 "모델의 기억에 의존해 사실을 말하는" 업무(자유 상담)는 위험합니다.

### 3.2 리스크 체크리스트 — 도입 전 6문항

main.py의 [5]에 출력되는 체크리스트가 핵심입니다. 특히 3번(개인정보·기밀을 외부 API로 전송해도 되는가)은 IT부서·법무팀과 반드시 사전 협의해야 하는 항목입니다. 많은 회사가 이 항목 때문에 사내 전용(온프레미스) 모델이나 기업용 계약을 선택합니다.

### 3.3 자동화 수준의 3단계

1. **보조(Copilot)**: LLM이 초안, 사람이 완성 — 시작점으로 최적.
2. **반자동**: LLM이 처리, 사람이 표본 검수 — 분류·추출 업무.
3. **완전 자동**: 사람 개입 없음 — 근거 인용·가드레일(level11)이 갖춰진 뒤에만.

### 3.4 비용 감각 — 사람 시급과 비교하기

도입 결정에는 대략의 비용 감각이 필요합니다. LLM API는 토큰(token, 단어 조각) 단위 종량제로, 한국어는 대략 1~2자가 1토큰입니다. 이메일 초안 하나(입력+출력 합쳐 2천 토큰 안팎)는 모델에 따라 수 원에서 수십 원 수준 — 사람의 10분(시급 환산 수천 원)과 비교하면 자릿수가 다릅니다. 다만 호출량이 하루 수만 건이 되면 이야기가 달라지므로, "건당 비용 × 예상 호출량"을 월 단위로 계산해 보는 습관이 필요합니다. 계산 방법과 비용 추적 코드는 level04에서 직접 구현합니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level01_llm_business_map
python3 main.py
```

출력 해설:

- **[1]** 업무 활용 지도를 표로 출력합니다. 팀 회의에서 그대로 써도 되는 요약본입니다.
- **[2]** 받는 사람·목적·기한 3가지 정보만 주면 MockLLM이 격식 있는 이메일 초안을 만듭니다. 핵심은 "사람은 검토와 서명만"이라는 협업 구도입니다.
- **[3]** 5문장 회의록에서 핵심 3줄을 뽑습니다. "점심 메뉴" 문장이 요약에서 빠졌는지 확인해 보세요 — 요약 품질 검수의 미니 체험입니다.
- **[4]** 민원 4건을 배송/환불·결제/품질·고장/응대·서비스로 분류하고 근거 키워드를 함께 출력합니다. 근거를 함께 내놓게 하는 것이 오분류를 잡는 실무 요령입니다.
- **[5]** 리스크 체크리스트 6문항.

코드 핵심부: 이 레벨의 MockLLM은 `mock_llm.py`의 규칙 기반 구현입니다. `complete()`가 프롬프트에서 "분류/요약/이메일" 같은 지시어를 찾아 작업을 라우팅합니다. 실제 LLM도 내부 원리는 다르지만 **"지시문을 읽고 작업 모드를 결정한다"**는 사용자 관점 동작은 같습니다. 파일 하단 주석에 실제 Claude API 호출 코드가 있으니, 키가 생기면 `llm.complete(prompt)` 자리만 바꾸면 됩니다.

## 5. 직접 해보기

1. **(쉬움)** `COMPLAINTS`에 새 민원을 추가해 보세요: "앱에서 로그인이 안 돼요". 어떻게 분류되나요? (힌트: 사전에 없는 유형은 "기타"가 됩니다 — 분류 체계에 없는 입력을 어떻게 처리할지가 실무 설계 포인트입니다.)
2. **(중간)** `mock_llm.py`의 `_CATEGORY_LEXICON`에 "계정/앱" 카테고리를 추가하고(키워드: 로그인, 비밀번호, 앱, 오류) 1번 민원이 제대로 분류되게 만들어 보세요.
3. **(도전)** 여러분 회사(또는 가상의 회사)의 업무 10개를 적고, 3.1의 기준(원문 제공? 사람 검토? 기계 검증?)으로 안전/위험을 나눠 보세요. 그중 "이번 달에 시작할 1개"를 골라 [5] 체크리스트 6문항에 답해 보세요.

## 6. 자주 하는 실수

- **가장 어려운 업무(자유 상담 챗봇)부터 시작** — 실패 확률이 가장 높은 출발점입니다. 초안·요약·분류부터.
- **검토 단계 없는 자동화** — "LLM이 쓴 메일이 그대로 발송"은 사고의 지름길입니다. 보조(Copilot) 단계부터.
- **근거 없이 분류 결과만 받기** — 근거 키워드를 함께 출력하게 하면 오분류를 사람이 10배 빨리 찾습니다.
- **보안 검토 생략** — 고객 개인정보가 포함된 텍스트를 외부 API에 보내는 것은 대부분 회사에서 규정 위반입니다. 마스킹(level11)을 먼저 배우세요.
