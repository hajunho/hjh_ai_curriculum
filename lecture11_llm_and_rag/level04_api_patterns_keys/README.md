# Lecture 11 · Level 04 — API 호출 패턴과 키 관리

> LLM은 네트워크 너머의 유료 API — 키 보안, 토큰 과금, 재시도·백오프·타임아웃까지 운영에 필요한 호출 기술을 가짜 서버로 연습합니다.
**난이도** ⭐⭐⭐ / **선행** level03 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

LLM을 업무 시스템에 붙이는 순간, 여러분은 세 가지 현실을 마주합니다. 첫째, **호출할 때마다 돈이 나갑니다** — 토큰(token) 단위 종량제입니다. 둘째, **가끔 실패합니다** — 사용량 한도 초과(429), 서버 오류(500), 응답 지연은 정상 운영의 일부입니다. 셋째, **API 키가 유출되면 남이 여러분 회사 카드로 결제합니다** — 실제로 깃허브에 키를 올렸다가 하룻밤에 수백만 원이 청구된 사고가 반복해서 일어납니다.

데모와 운영의 차이가 여기서 갈립니다. 성공 경로만 있는 코드는 데모이고, 실패 경로(재시도·타임아웃·비용 상한·키 보안)까지 있는 코드가 운영입니다. 이 레벨은 그 차이를 만드는 4가지 기본기를 다룹니다.

## 2. 비유로 이해하기

LLM API는 **전화로 일을 맡기는 외부 전문 번역 사무소**와 같습니다.

- **API 키 = 법인카드 번호**: 전화로 카드 번호를 불러야 일을 받아 줍니다. 카드 번호를 포스트잇에 적어 모니터에 붙여 두면(코드에 하드코딩) 언젠가 사진 찍혀 유출됩니다. 금고(환경변수·비밀 관리자)에 보관하세요.
- **토큰 과금 = 통·번역 분량 요금**: 원문이 길수록(입력 토큰), 번역문이 길수록(출력 토큰) 요금이 올라갑니다. 견적 없이 일을 계속 맡기면 월말 청구서에 놀라게 됩니다.
- **429 오류 = "지금 주문이 밀려 있어요"**: 사무소가 바쁘면 "잠시 후 다시 걸어 주세요"라고 합니다. 이때 1초마다 계속 전화하면(무지성 재시도) 더 밀립니다. 1분, 2분, 4분… 점점 간격을 늘려 다시 거는 것이 지수 백오프(exponential backoff)입니다.
- **타임아웃 = "30분 안에 회신 없으면 없던 일로"**: 하염없이 기다리면 우리 업무 전체가 멈춥니다. 기다림의 상한을 정해 두고, 넘으면 끊고 다시 시도합니다.

## 3. 핵심 개념

### 3.1 요청/응답 구조

요청에는 모델명과 대화 메시지 목록이, 응답에는 생성 텍스트와 **usage(토큰 사용량)**가 들어 있습니다. usage를 매 호출 기록하는 것이 비용 관리의 시작입니다. 한국어는 대략 글자 1~2자가 토큰 1개입니다(모델마다 다름).

### 3.2 오류의 두 부류 — 재시도할 것과 말 것

| 부류 | 예 | 대응 |
|---|---|---|
| 일시적(재시도 가치 있음) | 429 한도 초과, 500 서버 오류, 타임아웃 | 백오프 후 재시도 |
| 설정 문제(재시도 무의미) | 401 키 오류, 400 요청 형식 오류 | 즉시 중단, 코드/설정 수정 |

401을 백오프로 재시도하는 것은 틀린 카드 번호로 계속 전화 거는 것과 같습니다 — 구분이 중요합니다.

### 3.3 지수 백오프 + 지터

재시도 간격을 1초 → 2초 → 4초 → 8초로 늘리고(지수), 무작위 시간을 살짝 더합니다(지터, jitter). 지터가 없으면 동시에 실패한 수백 개의 클라이언트가 동시에 재시도해 서버를 다시 무너뜨립니다. 상한(예: 최대 4회)을 반드시 두고, 초과하면 큐에 쌓거나 사람에게 알립니다.

### 3.4 키 관리 3원칙

1. 코드·저장소에 키를 넣지 않는다 — `os.environ.get("ANTHROPIC_API_KEY")`로 읽는다.
2. 화면·로그에 전체 키를 찍지 않는다 — 앞 몇 자만 남기고 마스킹.
3. 유출이 의심되면 즉시 폐기·재발급한다 — 키는 언제든 갈아 끼울 수 있게 설계.

### 3.5 대량 처리는 배치로

실시간 응답이 필요 없는 작업(밤사이 문서 1만 건 분류 등)은 한 건씩 호출하지 말고 배치(batch) 처리를 검토하세요. 주요 API들은 배치 전용 창구를 제공하며 보통 절반 가격입니다. 배치가 아니더라도, 대량 호출 시에는 호출 사이에 간격을 두어 분당 한도(rate limit)를 애초에 넘지 않게 설계하는 것이 재시도로 버티는 것보다 낫습니다. "미리 속도를 조절하는 것"과 "초과 후 백오프로 물러나는 것"은 보완 관계이며, 둘 다 갖춘 클라이언트가 운영급입니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level04_api_patterns_keys
python3 main.py
```

출력 해설:

- **[1]** 키를 환경변수에서 읽고 마스킹해 표시합니다. `export MOCK_LLM_API_KEY=...`를 설정하면 "환경변수"로 출처가 바뀝니다.
- **[2]** 요청/응답 JSON 구조를 관찰합니다. `usage`의 입력/출력 토큰이 과금의 근거입니다.
- **[3]** 잘못된 키로 호출하면 401 — 재시도 없이 즉시 중단하는 분기를 확인합니다.
- **[4]** 5건을 처리하며 429(백오프 재시도), 500(재시도 후 성공), 45초 지연(타임아웃 처리), 재시도 한도 초과(실패 처리·사람 알림)의 4가지 실패 경로가 모두 등장합니다. 대기 시간은 데모용으로 1/100로 축소되어 실제로는 즉시 끝납니다.
- **[5]** 누적 토큰과 요금(가상 단가)을 리포트합니다.

코드 핵심부: `fake_llm_api()`는 시드 고정 난수로 실제 API의 성공/429/500/지연을 재현하는 가짜 서버입니다. `RobustClient.chat()`이 이 레벨의 핵심으로, "호출 → 상태 분기(성공/영구 오류/일시 오류) → 백오프 대기 → 재시도 → 상한 초과 시 포기"의 운영 패턴을 담고 있습니다. 하단 주석처럼 실제 Claude SDK는 재시도·타임아웃을 옵션(`timeout=`, `max_retries=`)으로 내장하고 있지만, 원리를 알아야 옵션을 제대로 설정할 수 있습니다.

## 6. 자주 하는 실수

- **키 하드코딩** — `api_key = "sk-..."`가 코드에 있으면 깃에 올리는 순간 사고입니다. 커밋 이력에 남은 키는 삭제해도 복구 가능하므로 즉시 재발급해야 합니다.
- **모든 오류를 같은 방식으로 재시도** — 401/400은 몇 번을 다시 보내도 실패합니다. 오류 코드로 분기하세요.
- **백오프 없는 재시도** — 실패 즉시 재호출하는 루프는 한도 초과를 더 악화시키고 비용만 태웁니다.
- **타임아웃 미설정** — 기본값이 매우 긴 경우, 지연 응답 하나가 배치 전체를 몇 분씩 세워 둡니다.
- **비용 로그 없음** — usage를 버리면 월말 청구서가 첫 비용 보고서가 됩니다. 호출 단위로 기록해 두세요.
