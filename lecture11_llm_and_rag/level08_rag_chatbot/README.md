# Lecture 11 · Level 08 — RAG 챗봇: 검색·증강·생성의 완결 조립

> 임베딩·청킹·벡터 저장소를 조립해, 사내 규정 질문에 출처를 인용하며 답하고 모르면 모른다고 말하는 챗봇을 완성합니다.
**난이도** ⭐⭐⭐⭐ / **선행** level05~07 / **예상 시간** 60분

## 1. 왜 배우나 — 비즈니스 관점

LLM의 두 가지 태생적 한계를 level00에서 봤습니다: 우리 회사 일은 모르고(지식 시점), 모르는 것도 아는 척합니다(환각). 이 두 문제를 한 번에 완화하는 표준 설계가 RAG(Retrieval-Augmented Generation, 검색 증강 생성)입니다. 사내 규정 챗봇, 고객센터 자동 응답, 계약서 Q&A, 기술 문서 도우미 — 기업 LLM 도입 사례의 대부분이 사실상 RAG입니다.

RAG의 사업적 매력은 세 가지입니다. (1) **모델을 재학습하지 않습니다** — 문서만 바꾸면 지식이 갱신됩니다. (2) **출처를 인용합니다** — "휴가규정 제1조에 따르면"이라고 답하니 검증과 책임 추적이 가능합니다. (3) **모른다고 말하게 설계할 수 있습니다** — 근거가 없으면 답변을 거부시켜 환각을 구조적으로 줄입니다.

## 2. 비유로 이해하기

**오픈북 시험**을 떠올려 보세요. 암기 시험(순수 LLM)에서는 가물가물한 기억으로 그럴듯하게 쓴 오답이 나옵니다. 오픈북 시험(RAG)에서는 다릅니다.

1. 문제를 읽고 **교과서에서 관련 페이지를 찾습니다** — 검색(Retrieval).
2. 찾은 페이지를 **답안지 옆에 펼쳐 놓습니다** — 증강(Augmentation).
3. 펼쳐 놓은 내용에 **근거해서만 답을 쓰고, 몇 페이지인지 각주를 답니다** — 생성(Generation).

그리고 시험의 철칙: **책에 없는 문제는 백지로 내는 것이 지어내는 것보다 낫습니다.** 사내 챗봇이 최저임금을 지어내서 답하면 그것은 기능이 아니라 사고입니다. "문서에서 확인되지 않습니다. 담당 부서에 문의하세요"가 정답입니다.

## 3. 핵심 개념

### 3.1 파이프라인 전체 그림

```
[색인 시점(미리)]  문서 → 청킹(06) → 임베딩(05) → 벡터 저장소(07)
[질문 시점(실시간)] 질문 → ①검색: top-k 조각 → ②증강: 프롬프트에 삽입
                        → ③생성: LLM 이 근거 안에서만 답변 + 출처 인용
```

새로 배우는 것은 ②와 ③의 연결부이며, ①은 이미 만든 부품의 재사용입니다.

### 3.2 증강 프롬프트의 구조

실습에서 실제로 출력되는 프롬프트가 표준형입니다: (a) 역할 지정, (b) **"근거 문서에 있는 내용만으로 답하라"**는 제약, (c) 근거가 없으면 없다고 말하라는 지시, (d) 검색된 조각들(출처 표기), (e) 질문. (b)와 (c)가 환각 억제의 핵심 문구로, 이것이 없으면 LLM은 근거와 자기 기억을 섞어 버립니다.

### 3.3 "모른다" 임계값

검색 1위의 유사도가 기준(오늘은 0.15) 미만이면 생성 단계로 가지 않고 정중한 거절 + 담당자 안내로 응답합니다. 임계값이 너무 높으면 답할 수 있는 질문도 거절하고(불편), 너무 낮으면 엉뚱한 근거로 답합니다(위험). 실무에서는 평가셋(level11)으로 이 값을 조정합니다.

### 3.4 top-k와 문맥 예산

몇 조각을 프롬프트에 넣을지(top-k)는 비용·품질 트레이드오프입니다. 많이 넣으면 놓침이 줄지만 토큰 비용이 늘고, 무관한 조각이 섞여 답이 흐려집니다. 3~8개가 흔한 출발점이고, 무관 조각 문제는 level09의 리랭킹·MMR로 개선합니다.

### 3.5 자주 나오는 운영 질문 두 가지

**"대화가 이어지면요?"** 후속 질문("그럼 이월은요?")은 그 자체로 검색하면 실패합니다. 실무에서는 직전 대화를 참고해 질문을 독립형으로 고쳐 쓴 뒤("연차 이월 규정은?") 검색합니다 — 이 재작성도 LLM에게 시키는 것이 일반적입니다. **"문서끼리 충돌하면요?"** 구 규정과 신 규정이 함께 검색되는 문제는 메타데이터(개정일)로 최신본을 우선하거나 폐기 문서를 색인에서 제외해 해결합니다. 둘 다 "생성"이 아니라 "검색 앞뒤 단계"의 설계 문제라는 점이 RAG 운영의 특징입니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level08_rag_chatbot
python3 main.py
```

출력 해설:

- **[1]** 문서 5건 → 18조각 색인. "모른다 기준 유사도 0.15"가 함께 표시됩니다.
- **[2]** 첫 질문(연차 신청 기한)은 검색 과정(채택/탈락과 유사도), **실제 LLM에 보낼 증강 프롬프트 전문**, 그리고 출처가 인용된 답변까지 전 과정을 공개합니다.
- **[3]~[5]** 경비·재택·보증 질문들이 각자 올바른 문서를 근거로 답합니다. [4]에서는 유사도 0.148짜리 무관 조각(보증 문서)이 임계값에 걸려 "탈락"하는 것도 보입니다.
- **[6]** 핵심 장면: "내년도 최저임금은?"이라는 문서 밖 질문에 최고 유사도가 0.115에 그쳐, 챗봇이 지어내지 않고 **모른다고 답합니다.**

코드 핵심부: `RAGChatbot` 클래스의 3개 메서드가 파이프라인 그 자체입니다 — `retrieve()`(행렬곱 검색), `build_prompt()`(증강 프롬프트 조립), `answer()`(임계값 판정 후 생성 또는 거절). 생성은 `MockLLM.answer_with_context()`가 근거 문장을 재조립하는 방식으로 흉내 내며, 하단 주석처럼 실제 API를 쓸 때도 검색·증강 코드는 그대로 두고 생성 호출만 바꾸면 됩니다.

3. **(도전)** 답변 마지막에 "이 답변은 문서 N건을 근거로 했으며, 최신 규정은 담당 부서에서 확인하세요"라는 자동 꼬리말을 붙이고, 근거 조각의 유사도 평균이 0.3 미만이면 "확신도 낮음" 경고를 추가해 보세요.

## 6. 자주 하는 실수

- **"근거 안에서만 답하라"는 지시 누락** — 검색만 붙이면 RAG가 되는 게 아닙니다. 이 지시가 없으면 모델이 근거와 상상을 섞습니다.
- **모른다 경로 없이 무조건 답변** — 검색은 항상 '무언가'를 1위로 돌려줍니다. 유사도가 낮아도 그럴듯하게 답해 버리는 것이 RAG 환각의 주범입니다.
- **출처 표기 생략** — 출처 없는 답은 검증할 수 없습니다. 인용은 사용자 신뢰 문제이자 운영팀의 디버깅 도구입니다.
- **색인 갱신 계획 없음** — 규정이 개정됐는데 챗봇이 옛 규정을 답하면 더 위험합니다. 문서 변경 → 재청킹 → 재임베딩의 갱신 절차를 함께 설계하세요.
- **검색 품질 문제를 모델 탓으로 진단** — 답이 이상하면 먼저 검색된 조각을 보세요. 십중팔구 엉뚱한 조각이 들어갔거나 좋은 조각이 못 들어간 것입니다.
