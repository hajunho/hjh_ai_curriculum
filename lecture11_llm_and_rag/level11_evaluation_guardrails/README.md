# Lecture 11 · Level 11 — 평가·가드레일·환각 억제

> "믿고 내놓아도 되는가?"에 숫자로 답합니다 — 근거 일치율 자동 채점기와 개인정보 마스킹·금칙어 가드레일을 구현합니다.
**난이도** ⭐⭐⭐⭐⭐ / **선행** level08 (level03·09 권장) / **예상 시간** 60분

## 1. 왜 배우나 — 비즈니스 관점

데모는 잘 돌아갑니다. 문제는 그 다음입니다. "이 챗봇, 고객에게 열어도 됩니까?"라는 질문에 "몇 번 써 봤는데 괜찮던데요"라고 답하면 안 됩니다. 금융·인사·고객 응대에서 LLM의 오답 하나는 민원, 언론 보도, 법적 분쟁이 될 수 있습니다.

필요한 것은 두 가지입니다. **평가(evaluation)** — 품질을 숫자로 재는 체계. "프롬프트를 바꿨더니 정답률이 80%→92%가 됐다"고 말할 수 있어야 개선도, 배포 결정도 가능합니다. **가드레일(guardrail)** — 모델이 아무리 좋아도 실수는 나므로, 입력과 출력에 안전 관문을 세우는 것. 개인정보가 외부 API로 나가는 것을 막고, 근거 없는 주장과 과잉 약속이 고객에게 발송되는 것을 막습니다. 이 레벨은 lecture11 전체의 마무리이자, LLM을 "장난감"에서 "업무 시스템"으로 바꾸는 마지막 관문입니다.

## 2. 비유로 이해하기

식품 공장을 생각해 보세요. 요리사(LLM)가 아무리 훌륭해도 공장은 요리사 솜씨만 믿지 않습니다.

- **품질 검사표(평가셋)**: 출하 전 표본을 정해진 검사 항목으로 채점합니다. 검사 항목 없이 "맛있어 보이네"로 출하하는 공장은 없습니다.
- **원재료 검수(입력 가드레일)**: 오염된 재료(개인정보가 든 입력)는 조리실에 들어가기 전에 걸러냅니다.
- **금속 탐지기(출력 가드레일)**: 포장 직전 마지막 관문에서 이물질(근거 없는 주장, 금지 표현)을 잡습니다. 요리사를 의심해서가 아니라, **사람이든 AI든 실수는 통계적으로 반드시 나기 때문**입니다.
- **리콜 대장(실패 사례 축적)**: 문제가 된 제품은 기록해 다음 검사 항목에 추가합니다. 평가셋은 이렇게 자랍니다.

## 3. 핵심 개념

### 3.1 평가셋 만들기

평가셋은 (질문, 기대 결과)의 목록입니다. 기대 결과는 "정답 키워드"(예: "3영업일")와 "기대 출처"로 적고, **일부러 문서 밖 질문도 넣어** 거절을 잘하는지 봅니다(거절해야 만점). 처음엔 10~20문항이면 충분하고, 운영 중 실패 사례를 계속 추가하는 것이 핵심입니다. 자주 쓰는 지표:

| 지표 | 뜻 |
|---|---|
| 정답률 | 기대 키워드가 답변에 포함된 비율 |
| 근거 일치율 | 답변의 주장 중 검색된 근거 원문에 실제로 있는 비율 |
| 거절 정확도 | 답 없는 질문을 제대로 거절한 비율 |

### 3.2 근거 일치율(groundedness) — 환각의 자동 검출

답변을 주장 문장 단위로 쪼개고, 각 문장이 검색된 근거 원문에 존재하는지 대조합니다. 근거에 없는 문장의 비율이 높으면 환각 신호이며, 기준 미달 답변은 발송 대신 사람 검토로 보냅니다. 중요한 교훈: **모델은 출처 표기까지 그럴듯하게 지어낼 수 있으므로**, "(출처: ...)"가 붙어 있다는 사실이 아니라 원문 대조가 근거 검증입니다. (실무에서는 완전 일치 대신 문장 유사도나 LLM 채점자를 쓰기도 하지만 원리는 같습니다.)

### 3.3 입력 가드레일 — 개인정보 마스킹

전화번호·주민등록번호·이메일은 정규표현식으로 패턴이 명확해, 외부 API로 보내기 전에 `[전화번호]` 같은 토큰으로 치환할 수 있습니다. 마스킹은 (1) 외부 전송 전, (2) 로그 저장 전 두 곳 모두에 적용해야 합니다. 로그에 남은 개인정보도 유출 사고입니다.

### 3.4 출력 가드레일 — 금칙어·과잉 약속 필터

발송 직전 최종 관문에서 금칙어(경쟁사 비방, 비속어)와 과잉 약속("무조건", "100% 보장" — 법적 책임을 만드는 표현)을 검사합니다. 걸리면 발송하지 않고 안전한 기본 문구로 대체하거나 사람에게 넘깁니다. 단순한 문자열 검사가 촌스러워 보여도, **결정적(deterministic)이라 100% 재현되는 마지막 방어선**이라는 점이 가치입니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level11_evaluation_guardrails
python3 main.py
```

출력 해설:

- **[1]** 평가셋 5문항(정상 4 + 문서 밖 1)을 미니 RAG에 돌려 자동 채점합니다. 문항별 정답 O/X와 근거 일치율, 마지막에 총점(5/5, 평균 100%)이 나옵니다. 이 총점이 "배포 전후 비교의 기준선"입니다.
- **[2]** 정상 답변에 "미사용 연차는 30일까지 이월 가능"이라는 **지어낸 문장**(그럴듯한 출처 표기 포함)을 섞으면, 채점기가 근거 일치율 67%로 떨어뜨리고 해당 문장을 정확히 지목합니다.
- **[3]** 전화번호·이메일·주민번호가 든 고객 문의가 마스킹되어 LLM에는 가려진 버전만 전달됩니다.
- **[4]** 정상 안내문은 통과, "무조건 가능·100% 보장" 응답은 금칙어 필터에 차단됩니다.
- **[5]** 배포 전/입력/출력/배포 후로 이어지는 운영 품질 체계를 한 장으로 정리합니다.

코드 핵심부: `groundedness()`(답변에서 주장 문장을 추출해 근거 원문과 대조), `grade()`(키워드+출처+거절 판정), `mask_pii()`(정규식 3종 치환), `check_banned()`(금칙어 검사). 모두 합쳐 60줄이 안 되는 코드가 "감"을 "숫자와 관문"으로 바꿉니다.

## 5. 직접 해보기

1. **(쉬움)** `EVAL_SET`에 "경비 영수증 제출 기한"(기대: "7일") 문항을 추가하고 총점 변화를 확인해 보세요.
2. **(중간)** `PII_PATTERNS`에 계좌번호 비슷한 패턴(예: 3-2-6자리 `\d{3}-\d{2}-\d{6}`)을 추가하고, [3]의 입력에 계좌번호를 넣어 마스킹되는지 확인해 보세요. 과잉 마스킹(날짜를 계좌로 오인 등) 위험도 함께 생각해 보세요.
3. **(도전)** `groundedness()`를 "완전 일치" 대신 유연한 대조로 바꿔 보세요: 주장 문장과 근거 문장들의 임베딩 코사인 유사도가 0.8 이상이면 지지된 것으로 판정합니다(`MockEmbedding` 재사용). 완전 일치 방식과 어떤 차이가 생기나요?

## 6. 자주 하는 실수

- **평가셋 없이 "체감"으로 개선** — 프롬프트를 고치면 어떤 질문은 좋아지고 어떤 질문은 나빠집니다. 총점 없이는 개선인지 개악인지 알 수 없습니다.
- **행복한 경로만 평가** — 답 없는 질문, 공격적 질문, 애매한 질문을 평가셋에 넣지 않으면 운영에서 처음 마주하게 됩니다.
- **출처 표기를 근거 검증으로 착각** — 환각은 출처까지 지어냅니다. 원문 대조만이 검증입니다.
- **마스킹을 출력에만 적용** — 입력(외부 전송 전)과 로그가 더 흔한 유출 경로입니다.
- **가드레일로 품질 문제를 덮으려는 시도** — 필터는 마지막 방어선이지 품질 개선책이 아닙니다. 차단이 잦다면 검색·프롬프트(level06~09)로 돌아가세요.
- **평가를 일회성 행사로 취급** — 모델·문서·프롬프트가 바뀔 때마다 다시 채점해야 합니다. 자동화된 스크립트로 만들어 두세요(오늘 코드가 그 원형입니다).
