# Lecture 11 · Level 07 — 벡터 데이터베이스

> "의미로 찾는 도서관"을 NumPy로 직접 구현합니다 — add/search/save/load, 메타데이터 필터, 그리고 근사 검색(ANN) 개념까지.
**난이도** ⭐⭐⭐⭐ / **선행** level05, level06 / **예상 시간** 50분

## 1. 왜 배우나 — 비즈니스 관점

level05~06에서 문서 조각을 임베딩해 검색하는 데 성공했습니다. 그런데 실무에는 세 가지 문제가 더 있습니다. 첫째, **임베딩은 비쌉니다** — 문서 10만 조각을 API로 임베딩하면 시간과 돈이 들기 때문에, 한 번 만든 벡터는 저장해 두고 재사용해야 합니다. 둘째, **조건 검색이 필요합니다** — "인사 규정에서만", "2025년 이후 문서에서만" 같은 필터 없이는 업무 시스템이 될 수 없습니다. 셋째, **규모가 커지면 속도**가 문제됩니다.

이 세 가지(영속화·필터·규모)를 해결하는 전용 저장소가 벡터 데이터베이스(vector database)입니다. Chroma, FAISS, pgvector 같은 이름을 도입 검토 회의에서 듣게 될 텐데, 오늘 그 내부 원리를 직접 만들어 보면 "무엇을 사는 것인지" 정확히 알고 선택할 수 있게 됩니다.

## 2. 비유로 이해하기

일반 데이터베이스가 **제목·저자 순 서가의 도서관**이라면(정확한 제목을 알아야 찾음), 벡터 DB는 **주제가 비슷한 책끼리 이웃에 꽂아 둔 도서관**입니다. "이 책이랑 비슷한 책 주세요"라고 하면 사서가 그 책이 꽂힌 자리 주변을 보여줍니다.

- **색인(add)** = 새 책이 오면 내용을 읽고(임베딩) 알맞은 자리에 꽂기.
- **검색(search)** = 질문의 좌표에서 가까운 책 꺼내기.
- **필터(where)** = "단, 사내규정 서가에서만" — 라벨(메타데이터)로 범위 제한.
- **영속화(save/load)** = 도서관 배치도를 저장해 두어, 내일 다시 와도 재정리 없이 바로 찾기.
- **근사 검색(ANN)** = 장서가 수천만 권이면 전 서가를 다 볼 수 없으니, 구역을 나눠 **유망한 구역만** 뒤지기 — 아주 가끔 최적의 책을 놓치지만 수백 배 빠릅니다.

## 3. 핵심 개념

### 3.1 벡터 DB의 실체 = 행렬 + 원문 + 메타데이터

오늘 구현이 보여주듯, 본질은 세 덩어리입니다: (1) 임베딩 벡터 행렬(N×512 NumPy 배열), (2) 각 행에 대응하는 원문 텍스트, (3) 출처·분류·날짜 같은 메타데이터. 검색은 `vectors @ query_vector` 행렬곱 한 번 + 정렬입니다.

### 3.2 메타데이터 필터

유사도 계산 전에(또는 후에) 조건에 안 맞는 후보를 제외합니다. 오늘 코드는 조건 밖 후보의 점수를 `-inf`로 만들어 배제합니다. 실무에서는 "권한 필터"로도 씁니다 — 질문자가 볼 수 없는 문서는 검색 자체에서 제외해야 정보 유출을 막습니다.

### 3.3 영속화 — 한 번 색인, 계속 재사용

임베딩 계산이 전체 비용의 대부분이므로, 벡터는 디스크에 저장합니다(오늘은 `.npz`+`.json`). 문서가 바뀌면 바뀐 조각만 다시 임베딩하는 증분 색인이 실무 패턴입니다. 주의: **임베딩 모델을 바꾸면 전체 재색인**입니다(좌표계가 달라지므로).

### 3.4 전수 검색 vs 근사 검색(ANN)

전수(brute-force) 비교도 NumPy로 20만 벡터에 수십 ms면 됩니다 — 중소규모 사내 문서라면 오늘 구현으로 충분하다는 뜻입니다. 수천만 벡터 규모에서 근사 최근접 탐색(ANN, Approximate Nearest Neighbor)이 필요해집니다. 벡터 공간을 구역으로 나누거나(IVF), 이웃 그래프를 만들어(HNSW) 유망한 곳만 탐색합니다. Chroma/FAISS는 이런 인덱스를 내장한 라이브러리이며, 사용 API는 오늘 만든 `add/search`와 놀랄 만큼 닮았습니다.

### 3.5 도입 선택지 한눈에

실무 검토 시 선택지는 대략 세 층입니다. (1) **직접 구현/경량**: 오늘의 NumPy 방식 — 수만 조각 이하, 단일 서버, 의존성 최소. (2) **라이브러리 내장형**: Chroma(간편), FAISS(대규모·고성능 인덱스) — 애플리케이션 안에 심어 쓰는 방식. (3) **기존 DB 확장/관리형 서비스**: pgvector(이미 쓰는 PostgreSQL에 벡터 컬럼 추가), 클라우드 관리형 벡터 DB — 운영·백업·권한을 기존 체계와 통합하고 싶을 때. 선택 기준은 유행이 아니라 **조각 수, 갱신 빈도, 권한 요구, 운영 인력**입니다. 작은 규모에 무거운 선택지를 고르는 것이 가장 흔한 낭비입니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level07_vector_databases
python3 main.py
```

출력 해설:

- **[1]~[2]** 사내 문서 18조각을 메타데이터(출처/분류/번호)와 함께 색인합니다. 저장소의 실체가 `(18, 512)` 행렬임을 확인하세요.
- **[3]** "수리를 받으려면?" 질문이 제품매뉴얼의 보증 조항(유사도 0.65)을 1위로 찾습니다.
- **[4]** 같은 질문에 `where={"category": "규정"}` 필터를 걸면 매뉴얼이 제외되고 규정 문서만 후보로 남습니다.
- **[5]** `save()` 후 `load()`로 복원한 저장소가 같은 검색 결과를 내는지 검증합니다(`True`). 생성물은 `outputs/mini_store.npz`, `outputs/mini_store.json`.
- **[6]** 가짜 벡터 1천/2만/20만 개로 전수 검색 시간을 실측하고, 그 너머의 세계(ANN)를 소개합니다.

코드 핵심부: `MiniVectorStore` 클래스 하나가 전부입니다. `search()`의 필터 구현(`np.where(mask, sims, -inf)`)과 `save/load`의 이원 저장(벡터는 npz, 텍스트·메타는 json)을 눈여겨보세요. 실전 벡터 DB를 쓰게 되더라도 이 구조를 알면 문서의 어떤 설정이 무엇을 의미하는지 바로 읽힙니다.

3. **(도전)** 간단한 ANN을 흉내 내 보세요: 색인 시 벡터를 k-means(2~4개 군집, `sklearn.cluster.KMeans` 사용 가능)로 나눠 두고, 검색 시 질문과 가장 가까운 군집 안에서만 전수 비교합니다. 20만 벡터 실험에서 속도와 정확도(전수 결과와 1위 일치율)를 비교해 보세요.

## 6. 자주 하는 실수

- **매 실행마다 재임베딩** — 서버를 재시작할 때마다 전체 문서를 다시 임베딩하는 코드는 비용 낭비의 대표 사례입니다. save/load를 처음부터 설계하세요.
- **원문을 안 저장하고 벡터만 저장** — 검색 결과로 사람에게 보여줄 것은 벡터가 아니라 원문입니다. 벡터·원문·메타는 항상 한 몸으로 관리하세요.
- **임베딩 모델 교체 후 기존 벡터 재사용** — 서로 다른 모델의 벡터를 섞으면 유사도가 무의미해집니다. 모델 버전을 메타데이터에 기록해 두세요.
- **소규모인데 무거운 인프라 도입** — 문서 수만 조각이면 오늘의 NumPy 저장소나 SQLite+pgvector급으로 충분합니다. 규모 실측([6]) 후 결정하세요.
- **권한 필터 없는 전사 검색** — 연봉 테이블이 검색되는 챗봇은 출시 첫날 사고가 납니다. 필터는 편의 기능이 아니라 보안 기능입니다.
