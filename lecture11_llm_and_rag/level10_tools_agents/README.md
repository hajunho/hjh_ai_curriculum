# Lecture 11 · Level 10 — 도구 호출과 에이전트

> LLM에게 계산기와 문서검색을 쥐여주고, 생각→행동→관찰을 반복하는 ReAct 루프로 "일하는 AI"의 뼈대를 만듭니다.
**난이도** ⭐⭐⭐⭐⭐ / **선행** level08 / **예상 시간** 60분

## 1. 왜 배우나 — 비즈니스 관점

지금까지의 LLM은 "말"만 했습니다. 그런데 실제 업무는 말로 끝나지 않습니다 — 계산하고, DB를 조회하고, 메일을 보내고, 티켓을 만들어야 합니다. LLM에게 이런 **도구(tool)**를 연결하고, 어떤 도구를 언제 쓸지 스스로 판단하게 만든 것이 에이전트(agent)입니다.

에이전트가 중요한 사업적 이유는 역할 분담에 있습니다. LLM은 산수를 자주 틀리고 사내 데이터를 모르지만, **판단(어떤 도구가 필요한가)**은 잘합니다. 계산기·검색·DB는 판단은 못 하지만 실행은 정확합니다. 이 둘을 붙이면 "정확하게 실행하는 유연한 시스템"이 됩니다. 요즘 쏟아지는 "AI 에이전트" 제품들의 내부가 정확히 오늘 만드는 루프입니다 — 원리를 알면 제품 데모에 현혹되지 않고 한계와 위험(무한 루프, 잘못된 도구 호출)까지 평가할 수 있습니다.

## 2. 비유로 이해하기

**유능한 신입 비서에게 사무기기를 쥐여주는 것**과 같습니다. 비서(LLM)는 판단력이 좋지만 암산이 약하고 회사 규정을 다 외우지 못합니다. 그래서 책상에 계산기와 규정집 검색 단말기를 놓아 줍니다.

"해외 출장 4일 가면 일비가 총 얼마죠?"라는 질문을 받은 비서의 머릿속:

1. **생각(Thought)**: "일비 기준을 모르네. 규정집부터 찾자."
2. **행동(Action)**: 검색 단말기에 "출장 일비" 입력.
3. **관찰(Observation)**: "해외 출장 일비는 8만원." — 메모.
4. **생각**: "이제 계산이 필요해. 암산 말고 계산기로."
5. **행동**: 계산기에 80000×4. **관찰**: 320000.
6. **생각**: "다 모였다." → **답변**: "규정상 일비 8만원, 4일이면 총 32만원입니다."

이 "생각→행동→관찰"의 반복이 ReAct(Reason + Act) 루프입니다. 그리고 좋은 상사가 비서에게 "30분 넘게 헤매면 나에게 물어봐"라고 하듯, 에이전트에도 최대 반복 횟수라는 안전장치를 답니다.

## 3. 핵심 개념

### 3.1 도구 호출(tool use)의 구조

LLM에 도구 목록(이름·설명·입력 형식)을 프롬프트로 알려주면, 모델은 답변 대신 **"calculator를 '80000*4'로 호출해 달라"는 구조화된 요청**을 출력합니다. 프로그램(우리 코드)이 실제로 도구를 실행하고, 결과를 다시 프롬프트에 붙여 보냅니다. 중요한 사실: **도구를 실행하는 것은 항상 우리 코드**이고, LLM은 실행을 요청할 뿐입니다. 그래서 위험한 도구(메일 발송, 결제)는 실행 전에 사람 승인 단계를 끼워 넣을 수 있습니다.

### 3.2 ReAct 루프

```
반복 (최대 N회):
  결정 = LLM(질문, 지금까지의 관찰 기록)
  결정이 "최종 답변"이면 → 종료
  아니면 → 도구 실행 → 결과를 관찰 기록에 추가
```

관찰 기록(스크래치패드)이 누적되며 다음 판단의 입력이 되는 것이 핵심입니다. 매 단계 로그가 남으므로 "왜 이런 답을 했는지" 추적이 가능합니다 — 감사(audit)가 필요한 업무에서 큰 장점입니다.

### 3.3 왜 계산기가 필요한가

LLM은 다음 토큰 예측기(level00)라서 "127×34" 같은 계산을 그럴듯한 숫자로 지어낼 수 있습니다. 계산·날짜·DB 조회처럼 **정답이 하나뿐인 작업은 도구로 강제**하는 것이 에이전트 설계의 제1원칙입니다.

### 3.4 안전장치 3종

1. **최대 단계 수**: 무한 루프 = API 비용 폭주. 반드시 상한.
2. **도구 입력 검증**: 오늘의 계산기도 숫자·연산자만 허용하는 화이트리스트 검증을 합니다. LLM이 만든 입력은 외부 입력처럼 취급하세요.
3. **못 하는 일 선언**: 도구로 답할 수 없는 질문(점심 메뉴)은 시도하지 않고 한계를 밝히는 것이 정답입니다.

### 3.5 관측성 — 에이전트는 로그가 생명이다

에이전트는 여러 단계를 스스로 결정하므로, 잘못됐을 때 "어디서부터 틀렸는지"를 볼 수 있어야 합니다. 최소한 단계별 Thought/Action/Observation 전체, 각 도구의 입력·출력·소요 시간, 총 호출 횟수와 토큰 비용을 기록하세요. 오늘 실습이 모든 단계를 화면에 출력하는 것은 데모를 위해서이기도 하지만, 운영에서도 같은 내용을 로그로 남긴다는 뜻입니다. 이 기록은 장애 분석뿐 아니라 "에이전트가 실제로 밥값을 하는가"(성공률·건당 비용)를 보고하는 근거가 됩니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level10_tools_agents
python3 main.py
```

출력 해설:

- **[2]** 순수 계산 질문: Thought(계산기를 쓰자) → calculator('127 * 34') → 4318 → 답변. 도구 1개로 끝나는 최단 루프입니다.
- **[3]** "연차가 며칠 남았나(6일 사용)": 문서 검색으로 "15일 부여" 규정을 찾고 → 계산기로 15−6=9 → 근거와 계산을 함께 인용해 답합니다. **두 도구의 순차 조합**이 이 레벨의 하이라이트입니다.
- **[4]** "해외 출장 4일 일비 총액": 문서에서 단가(8만원)를, 질문에서 일수(4)를 얻어 320,000원을 계산합니다.
- **[5]** 점심 메뉴 질문: 도구로 해결 불가 → 시도하지 않고 한계를 답합니다.

코드 핵심부: `run_agent()`가 ReAct 루프 그 자체입니다(결정→실행→관찰 기록→반복, 최대 4단계). `MockAgentLLM.decide()`는 실제 LLM이 프롬프트로 수행할 "다음 행동 판단"을 규칙으로 흉내 낸 것으로, 어떤 검색어를 만들지(`search_query`)조차 판단의 일부임을 보여줍니다. 하단 주석에 실제 Claude API의 도구 선언(`tools=[{name, description, input_schema}]`)과 `stop_reason == "tool_use"` 루프가 오늘 구조와 1:1로 대응함을 적어 두었습니다.

## 6. 자주 하는 실수

- **LLM에게 직접 계산·조회를 시킴** — "아까는 맞았는데"가 가장 위험합니다. 정답이 하나뿐인 작업은 반드시 도구로.
- **반복 상한 없는 루프** — 에이전트가 같은 검색을 무한 반복하면 요금이 실시간으로 불어납니다. 상한 + 중단 로그는 필수입니다.
- **도구 입력을 검증 없이 실행** — LLM이 만든 SQL·수식·명령은 신뢰할 수 없는 입력입니다. 화이트리스트 검증, 읽기 전용 권한, 승인 단계로 방어하세요.
- **도구 설명을 대충 씀** — 실제 API에서 모델은 도구의 `description`을 읽고 사용 여부를 판단합니다. 도구 설명서가 부실하면 잘못된 도구를 잡습니다.
- **모든 것을 에이전트로 해결하려는 시도** — 순서가 정해진 업무는 일반 코드(파이프라인)가 더 싸고 안정적입니다. 판단 분기가 진짜 필요한 곳에만 에이전트를 쓰세요.
