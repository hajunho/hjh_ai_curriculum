# Lecture 11 · Level 03 — 구조화된 출력과 파싱: JSON으로 받기

> LLM의 답을 사람이 아니라 프로그램이 받아 쓰려면 — JSON 출력, 스키마 검증, 실패 시 재요청 패턴을 구현합니다.
**난이도** ⭐⭐⭐ / **선행** level02 / **예상 시간** 45분

## 1. 왜 배우나 — 비즈니스 관점

챗봇 화면에서 LLM의 답을 사람이 읽을 때는 형식이 조금 흐트러져도 괜찮습니다. 그러나 진짜 업무 자동화 — 계약서에서 금액을 뽑아 ERP에 넣고, 민원 분류 결과로 티켓을 배정하고, 이력서에서 경력을 뽑아 DB에 쌓는 일 — 에서는 LLM의 출력이 **다음 프로그램의 입력**이 됩니다.

프로그램은 "계약 금액은 1억 2천만원쯤 되어 보입니다^^"를 이해하지 못합니다. `{"amount_krw": 120000000}`이어야 합니다. LLM 자동화 프로젝트가 데모까지는 잘 되다가 운영에서 무너지는 가장 흔한 지점이 바로 이 "출력 형식이 가끔 어긋나는" 문제이며, 오늘 배우는 요청-검증-재시도 패턴이 그 표준 해법입니다.

## 2. 비유로 이해하기

경비 정산을 생각해 보세요. 직원이 영수증 내역을 **자유 서식 이메일**로 보내면 경리팀은 매번 사람이 읽고 옮겨 적어야 하고, "점심값 대충 3만원쯤"같은 항목에서 사고가 납니다. 그래서 회사는 **정해진 양식(폼)**을 씁니다: 날짜 칸, 금액 칸(숫자만), 항목 칸(선택지 중 택1).

LLM에게 JSON으로 답하게 하는 것이 바로 "양식 지급"입니다. 그리고 경리팀이 양식을 받아도 검산하듯(금액 칸에 한글이 있으면 반려), 프로그램도 받은 JSON을 검증하고 문제가 있으면 **반려 사유를 적어 재제출**을 요구합니다. 세 번 반려되면? 사람이 직접 처리합니다. 오늘 구현하는 루프가 정확히 이 프로세스입니다.

## 3. 핵심 개념

### 3.1 JSON — 프로그램 간 공용 양식

JSON(JavaScript Object Notation)은 `{"필드": 값}` 형태의 표준 데이터 형식입니다. 파이썬의 딕셔너리와 거의 같아서 `json.loads()` 한 줄로 딕셔너리가 됩니다. LLM에게 "JSON만 출력하세요. 필드는 party_a(문자열), amount_krw(숫자)..."라고 지시하는 것이 출발점입니다.

### 3.2 실전에서 겪는 3대 실패 유형

1. **잡담 섞임**: "네! 추출해 드릴게요: {...} 도움이 되셨길!" — JSON 앞뒤에 인사말.
2. **마크다운 펜스**: ` ```json ... ``` `으로 감싸서 반환.
3. **타입·필드 오류**: 금액이 `"1억 2천만원"`(문자열)이거나 필드가 누락됨.

1·2번은 **방어적 파싱**(정규식으로 JSON 부분만 잘라내기)으로, 3번은 **스키마 검증 + 재요청**으로 해결합니다.

### 3.3 요청-검증-재시도 루프

```
프롬프트(스키마 명시) → 응답 → JSON 잘라내기 → 파싱
  → 검증 통과? → 사용
  → 실패? → "이전 응답의 문제: 금액은 숫자여야 함" 을 덧붙여 재요청 (최대 N회)
  → N회 초과? → 사람 검토 대기열로 (폴백)
```

핵심은 재요청 프롬프트에 **실패 사유를 그대로 실어 보내는 것**입니다. LLM은 자기 출력의 무엇이 틀렸는지 알려주면 대부분 1~2회 안에 고칩니다. 그리고 무한 재시도 대신 상한을 두고, 초과하면 조용히 버리지 말고 반드시 사람에게 넘깁니다.

### 3.4 스키마 검증 — 최소한 세 가지

- **필드 존재**: 필요한 키가 다 있는가.
- **타입**: 숫자 칸에 숫자가 있는가 (`isinstance` 확인).
- **형식/범위**: 날짜가 `YYYY-MM-DD`인가, 비율이 0~100 사이인가.

참고로 최신 API에는 스키마를 서버 차원에서 강제하는 구조화 출력 기능이 있어(하단 주석 예시) 재시도가 거의 필요 없어지지만, 검증 습관은 여전히 필수입니다 — 값의 **내용**(예: 계약서에 없는 금액을 지어냄)까지 보장해 주지는 않기 때문입니다.

### 3.5 실무 적용 범위 — 어디까지 맡길까

같은 패턴이 그대로 통하는 업무: 이력서에서 경력·학력 추출, 영수증에서 금액·일자·항목 추출, 상담 기록에서 불만 유형·요청 사항 추출, 회의록에서 결정사항·담당자·기한 추출. 공통점은 "원문이 주어지고, 출력 형식이 정해져 있다"는 것입니다. 반대로 원문에 없는 값을 추론해야 하는 항목(예: "이 계약의 위험도")은 추출이 아니라 판단 문제이므로, 별도 검증 체계 없이 자동화하면 안 됩니다. 실무 배치에서는 추출 결과에 신뢰도 표시(검증 통과/재시도 횟수)를 함께 저장해 두면, 나중에 표본 검수 대상을 고르기 쉬워집니다.

## 4. 실습 — main.py

실행:

```bash
cd lecture11_llm_and_rag/level03_structured_output
python3 main.py
```

출력 해설:

- **[1]** 과제 정의: 208자 계약서 원문과 기대 스키마 6개 필드(당사자·금액·기간·위약금율)를 보여줍니다.
- **[2] 시도 1**: 모의 LLM이 잡담+펜스+`"1억 2천만원"`(문자열 금액)+필드 누락이 섞인, 실전에서 흔한 응답을 냅니다. 방어적 파싱은 통과하지만 검증에서 2건의 오류가 잡힙니다.
- **[2] 시도 2**: 오류 내용이 프롬프트에 추가되자 올바른 JSON이 돌아오고 검증을 통과합니다.
- **[3]** 확정된 데이터로 "지연 1일당 위약금 12만원"을 즉시 계산합니다 — 타입이 보장된 데이터의 힘입니다.

코드 핵심부: `extract_json_block()`(펜스/잡담 제거), `validate()`(누락·타입·날짜 형식을 한꺼번에 수집), `extract_with_retry()`(실패 사유를 `feedback`으로 누적해 재요청). `MockExtractorLLM`은 프롬프트에 오류 피드백이 있는지를 보고 1차 실패/2차 성공을 재현합니다 — 실제 LLM의 자기 수정 경향을 단순화한 것입니다.

## 5. 직접 해보기

1. **(쉬움)** `SCHEMA`에 `"vat_included": (bool, "부가세 포함 여부")`를 추가해 보세요. 시도 2 응답에는 이 필드가 없으니 어떤 일이 벌어지나요? (힌트: 3회 모두 실패 → 사람 검토 폴백 경로가 처음으로 실행됩니다.)
2. **(중간)** `validate()`에 범위 검증을 추가해 보세요: `amount_krw`는 0보다 커야 하고, `end_date`는 `start_date`보다 뒤여야 합니다. (힌트: 문자열 `YYYY-MM-DD`는 사전순 비교가 날짜 비교와 같습니다.)
3. **(도전)** `MockExtractorLLM`의 1차 응답을 "중괄호가 하나 빠진 깨진 JSON"으로 바꿔 `json.JSONDecodeError` 경로도 실행되게 만들어 보세요. 파싱 실패와 검증 실패의 피드백 문구가 어떻게 다른지 확인해 보세요.

## 6. 자주 하는 실수

- **`json.loads()`를 try 없이 호출** — LLM 출력은 언제든 깨질 수 있는 외부 입력입니다. 예외 처리는 선택이 아니라 기본값입니다.
- **첫 응답이 잘 되니 검증 생략** — 100번 중 97번 잘 되는 것이 LLM입니다. 나머지 3번이 운영 장애가 됩니다.
- **재요청 시 같은 프롬프트를 그대로 반복** — 실패 사유를 알려주지 않으면 같은 실패가 반복됩니다. 오류 메시지를 프롬프트에 넣으세요.
- **무한 재시도** — 상한 없는 루프는 비용 폭탄이자 장애 지점입니다. 3회 안팎 + 사람 폴백이 표준입니다.
- **검증 통과 = 내용 정확으로 착각** — 스키마 검증은 "모양"만 봅니다. 금액이 계약서와 일치하는지는 표본 검수·평가(level11)로 확인해야 합니다.
